## What

Every phase of the pipeline returns a tree whose text, parsed again with the tree's own parse options, is that tree (FMT-PIPE-021), and keeps every annotation of its input on the nodes and tokens of the code it keeps (FMT-PIPE-022). *(amended 2026-10-31)* Today two phases break this:

- The structural-transform phase returns text that is another program. `int Get() => 42;` becomes `int Get(){return42;}`, where `return42` is one identifier, and `Foo(); // trailing` in an unbraced `if` body becomes `{Foo(); // trailing}`, where the inserted `}` is part of the comment. Later phases repair both by accident: the spacing phase writes a space after `return` because `return` is one of its keywords (FMT-SPACE-012), and the line-break phase puts `}` on its own line (FMT-BREAK-002).
- The indentation phase moves a misaligned multi-line raw string literal by parsing a new literal from text. Every token of the literal is new, so the annotations of the old ones are gone. `FormatNodeInDocumentWithContextAsync` finds its target through such an annotation (FMT-PIPE-018); with a target inside a literal that moves, it finds none and returns the document unchanged. Once the annotation survives, the entry point formats such a target, and the result falls into the gap FMT-PIPE-017 records, as a third case: the phases move the line the target starts on, the text in front of the target on that line is written back as in the document, and the target's other lines take the phases' columns. For the invocation `Call(1, 2)` in `$"""` / `            a {Call(1,` / `            2)} b` / `            """`, with the local declaration as context, `1` stays in column 20 and `2` is written in column 25, where the phases place it under `1` in the moved literal. Closing the gap stays with thoenissen/Reihitsu#1501. *(amended 2026-10-31)*
- *(amended 2026-10-31)* The trailing-comma removal of the structural-transform phase appends the removed comma's comments behind the line break that already ends the last element's line. The text then gives the comment to the closing brace, and the formatter is not idempotent: `B // about B` followed by `    , // comma` in an enum, or `2 /* two */` followed by `// before comma` and `, };` in an array initializer, leaves the comment in column 1 after one pass and puts a blank line in front of it and indents it in the next. Such a comment now leads the closing brace in the transform's own tree (FMT-STRUCT-027), so one pass gives what two passes give today.

The structural transforms write the separators their text needs and no other layout (FMT-STRUCT-026): one space after a created keyword that would otherwise fuse with the next token, a line break after a single-line comment that a created token follows, and a line break after a created token that a comment leading the next token or a directive follows — behind an inserted `{` as well as behind an inserted `}`. *(amended 2026-10-31)* They write no other line break after an inserted `{` or `}`. The comments they carry over keep the whitespace and line breaks the author wrote in front of and between them: the transforms write none there and drop none (*amended 2026-10-31*). The braced statement keeps its own trailing line break, and the created `}` of a converted expression body takes the trailing trivia of the replaced `;`, line break included (*amended 2026-10-31*). The field split keeps its own layout until the RH7101 fix stops running it alone (thoenissen/Reihitsu#1502). The accessor and get-only-member transforms keep writing one space on each side of the `=>` they create, because no spacing rule covers that gap and the final output stays `get => _value;`; a spacing rule for it is an approved follow-up. The tokens the structural transforms create carry no elastic trivia, so their tree and its text are spaced alike. *(amended 2026-10-31, implementer stage)*

The line-break phase leaves the whitespace in front of a line break it inserts to the cleanup phase (FMT-BREAK-029): where it writes a line break in front of a moved token and keeps the trailing trivia of the token before, it no longer removes the whitespace that ends that trivia, and FMT-CLEAN-001 removes it. Only the phase's own output changes. *(amended 2026-10-31)* The requirement reaches only a line break written into the moved token's leading trivia; where the phase rewrites the previous token's trailing trivia, as its shared gap normalizer and the initializer rewriter do, it may still remove the whitespace with it. *(amended 2026-10-31, implementer stage)* One path of the line-break phase places the braces of a member body; the final output does not change. *(amended 2026-10-31)*

The formatter's final output is unchanged by these requirements except for the inputs below. *(amended 2026-10-31)* Toward FMT-PIPE-013, which these outputs violate today, because the brace transform no longer rebuilds the trivia of the comments it carries:

- `if (a)` followed by `/* x */ /* y */ Foo();` keeps the two comments in front of `Foo();` on one line; today each comment and `Foo();` get a line of their own.
- A blank line between two comments that lead an unbraced `if` body is kept; today it is dropped.
- *(amended 2026-10-31)* `Foo(); /* a */ // b` as an unbraced `if` body keeps the space between the two comments; today it becomes `Foo(); /* a */// b`.

*(amended 2026-10-31)* Because the transforms keep the author's whitespace in front of the comments they carry:

- `Foo();    // x` as an unbraced `if` body keeps its four spaces, and `Foo();// y` keeps its zero gap, as the same statements do in a block; today both become `Foo(); // x` and `Foo(); // y`. Every trailing comment of a braced body whose gap is not one space keeps that gap.
- An expression body whose expression starts its own line with a block comment in front of it, `int Get() =>` followed by `/* c */ 42;` at the start of the line, becomes `return/* c */ 42;`, because no whitespace stood in front of the comment; today it becomes `return /* c */ 42;`. Indented, as code usually is, the indentation collapses to one space and the output stays `return /* c */ 42;`.

*(amended 2026-10-31)* The trailing-comma inputs above get in one pass the output that two passes give today (FMT-STRUCT-027).

## Why

A phase receives a tree, but the documentation phase reads its text, the trace prints the text and parses it again between passes, and the next formatter run parses it as well. When text and tree are two programs, each of them is formatted correctly only as long as some later phase happens to repair the difference. The repair is not guaranteed: for a token pair that no spacing rule covers, FMT-SPACE-002 forbids inserting a gap, so a transform that fused such a pair would ship it. A test that parses the phase's output passes on an error-recovered tree, which is how `ControlFlowBraceTransformTests.TrailingCommentOnIfBodyIsPreserved` passes today.

Layout that a structural transform writes beyond its separators is decided again by the phase that owns it — line breaks by FMT-BREAK, spaces by FMT-SPACE, columns by FMT-INDENT. Writing it twice is the pattern FMT-PIPE-001 forbids for columns: one decision in two places, which can disagree.

Annotations are how a caller finds its nodes again. An element that a phase rebuilds instead of editing loses them, and the context entry point is the first caller that depends on them.

## Decisions

### "The same tree" holds tokens, structure, and the owner of every comment

FMT-PIPE-021 compares the reparsed tree with the phase's tree by its nodes and their structure, its tokens with their kinds, texts, and places, the absence of any added or skipped token, and, for each comment, documentation comment, directive, and disabled-text span, the token that holds it and on which side. Whitespace and line breaks need only stand at the same places; the token that holds them may differ, and two runs of whitespace may join.

The owner of a comment decides what the phases do with it: a comment that trails a token stays at the end of that token's line (FMT-BREAK-001), a comment that leads one starts its own line. A tree that puts `// leading` behind an inserted `{` on its line, as leading trivia of the next statement, reads back with the comment trailing the brace, and the two are formatted differently. The owner of a line break decides nothing a phase relies on, and the line-break phase writes every line break it inserts in front of the token it moves, where the parser gives it to the token before (FMT-BREAK-001).

The text is parsed with the parse options of the tree the formatter was given, preprocessor symbols included, not with the language version FMT-PIPE-008 resolves: without the symbols, code under `#if DEBUG` reads back as disabled text, and a `Preview` tree clamped to C# 14 reads back with version errors. *(amended 2026-10-31)*

The comparison covers the tree that `FormatDocumentAsync` and `FormatSyntaxTree` pass through the phases. The node-level entry points pass a node, whose text is not a compilation unit; FMT-PIPE-022 covers what they need, the annotation on their target.

### Phases keep the annotations they do not own

A phase returns every annotation of its input on each node and token of the code it keeps, also where it changes that token's text or trivia or the node's children or moves it into a node it creates. A node or token the phase removes takes its annotations along, one it creates carries none of the input's — also where it replaces a removed token of the same kind, such as the `;` of a converted expression body — and a phase's own annotations are its own business. A node or token written more than once, such as the modifiers each split field repeats, is left out: which copy keeps the annotation is not decided. *(amended 2026-10-31)* Trivia and the nodes and tokens inside documentation comments and directives are outside the requirement: no entry point takes them as a target, and covering them would change every phase that writes whitespace, the documentation phase, tab replacement, and region formatting for no caller.

The raw-string move therefore edits the literal's tokens — the text tokens of its content and closing lines, and the nodes and tokens of its holes — instead of parsing a new literal. *(amended 2026-10-31)* It no longer needs parse options, so the question which language version a reparse would use disappears with it.

### The structural transforms write separators only

FMT-STRUCT-026 names the separators the transforms write and forbids every other space, line break, and indentation next to a token a transform creates or in the trivia it carries over. The decided separators follow from FMT-PIPE-021: a space where two tokens would read as one, a line break behind a single-line comment, and a line break in front of a comment that has to stay leading trivia of the next token — behind an inserted `{` or an inserted `}` *(amended 2026-10-31)* — or in front of a directive, which has to start its line. This applies to every structural transform: besides the brace and expression-body transforms the issue names, the accessor and get-only-member transforms are covered. *(amended 2026-10-31, implementer stage)* They keep one piece of layout: one space on each side of the `=>` they create. No spacing rule covers the gap between an accessor keyword, a member name, or an indexer's `]` and that `=>`, so the spacing phase keeps it as it finds it (FMT-SPACE-002); without the transforms' spaces, 31 final outputs of the test suite would change to `get=> …`. The maintainer chose to name the spaces in FMT-STRUCT-026 rather than add a spacing rule in this run; the rule is an approved follow-up, after which the spaces go.

The tokens the structural transforms create carry no elastic trivia. *(amended 2026-10-31, implementer stage)* `SyntaxFactory` gives a token built without explicit trivia zero-width elastic markers, which the spacing phase treats as whitespace although the text holds none, so the phase's tree and its text are spaced differently — a difference FMT-PIPE-021's structural comparison does not see but its Why rules out. The rule is stated for the structural transforms only; whether any phase may write elastic trivia is a follow-up candidate.

The comments a transform carries over keep the whitespace the author wrote in front of and between them, and the comments that lead a braced statement keep their line breaks too. *(amended 2026-10-31)* That is the phase-level form of FMT-PIPE-013, which the final output already has to meet, and it makes a braced body format like the same code in a block. The spacing phase keeps a gap in front of a comment as it finds it, so the one space the transforms write today in front of a trailing comment is the only thing that produces today's output; the inputs whose output changes are listed under What.

The trailing trivia of a braced statement stays on it, so a line break ends its line in front of the inserted `}` exactly where the author wrote one; the created `}` of a converted expression body takes the trailing trivia of the replaced `;`. Phase-level tests need one answer, and both keep what the author wrote. *(amended 2026-10-31)*

A removed trailing comma's comment that stands below the line the last element ends on leads the closing brace (FMT-STRUCT-027): that is the only owner the text gives it, and joining it to the last element's line would move it between lines. *(amended 2026-10-31)*

The field split keeps its line breaks and indentation, recorded as an exception in FMT-STRUCT-026: the RH7101 fix runs it without the phases after it, and the exception goes when that fix formats through a named entry point (thoenissen/Reihitsu#1502).

### The line-break phase leaves whitespace before its line breaks to the cleanup phase

FMT-BREAK-029 makes the cleanup phase the only owner of the whitespace that ends a line in front of a line break the line-break phase inserts. *(amended 2026-10-31)* The phase trims that whitespace today only where the token in front of the line break lies inside the node it rewrites, so its output depends on where a node starts; the cleanup phase removes it everywhere. Where the phase writes a line break in front of a moved token and keeps the trailing trivia of the token before, it no longer trims. A line break the phase moves out of the previous token's trailing trivia, as when it rewraps a list, is outside the requirement: there the trivia is rebuilt anyway.

One path places the braces of a member body: today `LineBreakBlockRewriter` places them as for every block and `DeclarationBraceLineBreakRewriter` places them again. Which path stays is not specified behavior; the brace requirements of FMT-BREAK keep deciding the output, which does not change. *(amended 2026-10-31)*

FMT-BREAK-029 reaches only a line break the phase writes into the moved token's leading trivia while it leaves the previous token's trailing trivia in place. The shared gap normalizer and the initializer rewriter, which rewrite that trailing trivia, still remove whitespace with it; changing them is outside this run, and the final output is the same either way. *(amended 2026-10-31, implementer stage)*

### A target inside a moving literal is the third case of FMT-PIPE-017's gap

The context entry point keeps writing back only the target (FMT-PIPE-010, FMT-PIPE-018). For a target whose line the phases move, its first token keeps the document column and its other lines take the phases' columns, the same misalignment the two recorded cases of the gap produce. FMT-PIPE-017 lists the case and its example; laying out the target from its column in the document is the restructuring of thoenissen/Reihitsu#1501 (`squad/decisions/2026-10-31-phase-tree-round-trip-target-in-moving-literal.md`).

## Alternatives considered

- **Require only the final output to be correct, and state in FMT-PIPE that later phases repair a structural transform's separators** — rejected: it writes the accidental repair into the spec, makes every later phase a co-owner of the separators, and still lets a fused pair that no spacing rule covers ship (FMT-SPACE-002).
- **Full structural equality, the owner of every whitespace and line break included** — rejected: the line-break phase writes the line breaks it inserts into the moved token's leading trivia (FMT-BREAK-001), which the parser gives to the token before. The requirement would force every line-break rewriter to be rebuilt for a difference no phase relies on.
- **Equal token sequences and equal trivia kinds, without the owner of a comment** — rejected: it accepts a comment behind an inserted `{` that reads back as trailing trivia of the brace, which the phases format differently from the tree they were given.
- **Keep the line break the brace transform writes after an inserted `}`, as the line ending the statement's line moved there** — rejected: the line break phase places `}` and the token after it on their lines (FMT-BREAK); a line break the transform writes there is a second owner of that decision. A line break stays only where a directive or a comment that leads the next token follows, because the text needs it. *(amended 2026-10-31)*
- **Place `2` under `1` in its document column (20) for a target inside a moving literal** — rejected for this change: the entry point would have to lay out the target from its document column against the raw-string move, the restructuring left to thoenissen/Reihitsu#1501.
- **Write back the moved literal lines outside the target** — rejected: FMT-PIPE-010 lets the entry point rewrite only its target.
- **Keep returning the document unchanged for such a target** — rejected: the entry point would refuse a target it can find once annotations survive.
- *(amended 2026-10-31)* **Keep today's one space in front of a carried trailing comment and on both sides of a comment moved behind `return` as separators** — rejected by the maintainer: the transforms would write a space no parse needs, making the spacing decision two-owned, and a braced body would keep formatting this gap differently from the same code in a block.
- *(amended 2026-10-31)* **Drop the whitespace in front of carried comments** — rejected: `Foo(); // trailing` would become `Foo();// trailing`, against FMT-STRUCT-026's own unchanged example.
- *(amended 2026-10-31)* **Keep annotations on trivia, or inside documentation comments and directives, as well** — rejected by the maintainer: no caller targets them, and every phase that writes whitespace would change.
- *(amended 2026-10-31)* **Keep the line-break phase's trim and state the residue as a permission only** — rejected by the maintainer: whitespace at the end of a line would keep two owners.
- *(amended 2026-10-31)* **Exempt the trailing-comma removal from FMT-PIPE-021 and follow it up separately** — rejected by the maintainer: it is a structural transform whose text is another tree, and the formatter is not idempotent on it.
- *(amended 2026-10-31, implementer stage)* **Accept `get=> …` as the new final output of converted accessors and get-only members** — rejected by the maintainer: 31 outputs would change for a gap no rule owns.
- *(amended 2026-10-31, implementer stage)* **Add a spacing rule for the arrow of an expression-bodied accessor or member in this run** — deferred by the maintainer to an approved follow-up: it is new spacing behavior beyond this change.
- *(amended 2026-10-31, implementer stage)* **Require that no phase output carries elastic trivia, and fix every phase now** — rejected by the maintainer for this run: the structural transforms are the case that reaches the run; the pipeline-wide rule is a follow-up candidate.
- *(amended 2026-10-31, implementer stage)* **Extend FMT-BREAK-029 to the shared gap normalizer and the initializer rewriter** — rejected by the maintainer for this run: the normalizer has about 25 call sites, and the final output does not change.
