## 2. #1795 (maintainer-filed, no `agent-filed`: goals binding)

- **What it is.** Not long inputs: whole code bases of ordinary files (450–926 files, 0.12–0.34 s per file, 1–3 min per `--check`). Goal: noticeably faster on several hundred files; output, exit codes and summary unchanged.
- **Premise on main.** Valid: `FormatCommandHandler.ProcessFilesAsync` (`src/Reihitsu.Cli/FormatCommandHandler.cs:254-291`) is a sequential `foreach`, and `ProcessFileAsync` writes its console lines per file, so parallel processing needs results buffered and written in file order. The formatter keeps no mutable static state that would block parallel calls (checked: no static caches/collections in `src/Reihitsu.Formatter`).
- **Relation to #1802/#1803.** Not duplicates. #1802/#1803 are single-file super-linear costs on rare long inputs; #1795 is the per-file constant on ordinary files plus single-core use. #1795's "profile the per-file pipeline" bullet overlaps #1803 only if the profile finds the same helper; a phase hotspot the #1795 run finds is a follow-up that joins #1803, not part of the run.
- **Lane.** bug-fix by the lane check (shipped `src/Reihitsu.Cli` only, no change doc) as long as no option is added and no CLI requirement changes; a degree-of-parallelism option would be a new CLI option = behavior change with an output question. Recommendation to the run: no option (bounded by `Environment.ProcessorCount`), output in file order.
- **Placement.** batch 2, `/squad #1795`. Files: `FormatCommandHandler.cs`, its unit/integration tests, possibly `sdd/specs/cli/reihitsu-format.md`. No batch 2 run touches them (#1724 is `Diagnostics/PipelineTraceCommand.cs` and its own test class). Constraint for the run: no edit to `ReihitsuFormatter.cs` (run 2.1) and no phase change; if the speed-up needs one, it becomes a follow-up.
