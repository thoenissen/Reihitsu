## #2000 — code fixes: sequential Fix All across documents has one owner instead of two

- **Source:** PR #1997 (#1990), *Follow-up work*.
- **Premise (read):** overstated. The issue says both providers "decide the same thing: apply the fixes of a scope one document after another on an evolving solution and re-analyze a document an earlier fix changed". On main they do not:
  - `DocumentOrderFixAllProvider` solution-scoped mode (`src/Reihitsu.Analyzer.CodeFixes/Core/DocumentOrderFixAllProvider.cs:324-358`): iterates documents, **re-runs the analyzer** on a document an earlier fix changed (`:345-349`, `GetDiagnosticsAsync` `:295`), and re-registers each fix on the current code in document order (`ApplyPassAsync`, `:89`).
  - `CasingCodeFixProviderBase<T>.CasingFixAllProvider` (`src/Reihitsu.Analyzer.CodeFixes/Base/CasingCodeFixProviderBase{T}.cs:807-834` → `ApplyFixAllAsync` `:637-688`): collects candidates **once** from the starting diagnostics, annotates the declarations (`AnnotateFixAllCandidatesAsync` `:202`), computes duplicate-target conflict groups up front (`GetDuplicateTargetCandidatesAsync` `:235`, SHARED-CASING-010), then re-resolves each declaration by annotation and renames it. It never re-analyzes and never iterates by document.
  - The difference is spec-relevant: #1997's own review notes record that the solution-scoped mode fixes every diagnostic found on a re-analyzed document, which deviates from SHARED-FIX-002 ("only those offered on the starting code") for interacting fixes in two parts of a partial type, left unguarded as rare. The casing provider keeps to the starting diagnostics. Routing casing through the shared mode would either import that deviation into every casing fix and drop the up-front SHARED-CASING-010 conflict grouping, or move casing-specific machinery (annotations, duplicate targets) into the shared provider. Neither is "one rule stated once"; the *Done when* ("tests pass unchanged") is likely unreachable without one of those.
- **Reachability:** both providers are reached (Fix All of RH2001, of every casing rule). No user-visible defect is claimed.
- **Group:** Maintenance (refactor, no behavior change intended). **Labels:** none to add.
- **Placement:** recommend closing as not planned with the reasoning above (two algorithms, not one rule in two places). If the maintainer keeps it: 1.8.0, *Core and code-fix cleanups* `#1032 #1475 #1582 #1583 #1740 #1789` (T14 shared helpers); shares `CasingCodeFixProviderBase{T}.cs` with any casing work and `DocumentOrderFixAllProvider.cs` with every layout fix that uses it — sequential with #1774's run in 1.8.0. Not needed by 1.6.0's features.
