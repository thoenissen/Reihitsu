# Phase 5 — When a formatter-delegating fix is offered (inventory against the maintainer's 2026-11-06 clarification)

Base: `origin/main` at `0fa1778`. Read-only inventory; nothing posted to GitHub.

## The maintainer's clarification (2026-11-06, translated)

> The statement "where an analyzer reports, a fix is offered" meant: when an analyzer reports a location, the formatter must not suppress the formatting inside a quick fix. That is about reasons that do not prevent correct formatting — e.g. auto-generated code: the formatter could format those sources, we only decided against it (for whole files) because it is not useful. Other reasons, such as syntax errors that may make formatting impossible, are valid reasons. [...] Generally a code fix should also not be offered through the formatter when no change happens. Then it should rather be investigated whether the formatter has a bug or the diagnostic is wrong.

Three parts:

- **(a)** The node-level entry points must not refuse inside a fix for a reason that does not prevent correct formatting (generated code).
- **(b)** A syntax error that may make formatting impossible is a valid reason not to format, and so not to offer the fix.
- **(c)** A fix whose formatter call changes nothing is not offered; such a case is a defect to investigate (formatter bug, or a diagnostic that should not be reported — SHARED-DIAG-010 / SHARED-FIX-005).

## 2. Comparison with the three parts

### (a) No refusal for reasons that do not prevent formatting — **stated clearly for generated code; the general principle is missing, and its only statement is overbroad**

- Clear: FMT-PIPE-006 (`pipeline.md:111`, `:113`) — node-level entry points "MUST NOT check the marker", with the right reason ("A second check in the entry points would refuse the fix's formatting where the analyzer reported").
- Missing: no living spec states the general rule behind it — that a node-level entry point refuses a fix's input only for a reason that prevents correct or safe formatting. Generated code is the one named instance.
- Overbroad/contradicted: the only place that states the principle is the change doc, as "where an analyzer reports, a (code) fix is offered" (`rh7101-...md:19`, `:29`, `:663`, `:691`). Read literally, it contradicts `AGENTS.md:46` ("A reported diagnostic with no available fix is a supported end state") and SHARED-FIX-003/-005 themselves, and it was used as the reason to reject a fix-side guard (`:691`). The maintainer's clarification narrows it to "the formatter must not suppress formatting inside a fix for a reason that does not prevent correct formatting". Issue #1588 quotes the overbroad form in its `Principle:` line. Change docs are history (`sdd/README.md:109`), so the correction has to land in a living spec.

### (b) A syntax error is a valid reason not to format, and not to offer the fix — **formatter side stated clearly; fix side missing; scope ambiguous**

- Clear (formatter side): FMT-PIPE-005 (`pipeline.md:97`, `:99`).
- Missing (fix side): no shared requirement says what a formatter-delegating fix does in a file with a syntax error. `code-fixes.md` has no sentence on it. The only resolution on record is per rule and on the reporting side: SHARED-JOIN-002 (`line-join-rules.md:64`) for RH5105, RH5106, RH7101 (RH7101-001, `RH7101.md:25`, `:27`). For every other delegating fix the result follows only by combining SHARED-FIX-005 (a pure delegator returns the input → not offered) and SHARED-FIX-007 (an edit-first fix would leave its edit unformatted → cannot meet it), and nobody wrote that combination down.
- Ambiguous (which side): RH7101 took "do not report" because of the overbroad principle (`rh7101-...md:29`), whereas the clarification calls a syntax error a valid reason, which fits "report, withhold the fix" (`code-fixes.md:162`: "withholding a fix never removes a report"). The specs do not say which is the default for a rule that has no line-join reason.
- Ambiguous (scope): FMT-PIPE-005 refuses for "any error-level diagnostic" anywhere in the tree, while `FormatNode` (FMT-PIPE-012) and `OrganizeUsingDirectivesInDocumentAsync` (FMT-PIPE-030) check none. The clarification says "syntax errors that *may* make formatting impossible". The specs do not say whether an error outside the target counts, and the two node-level families treat it in opposite ways.

### (c) A fix whose formatter call changes nothing is not offered, and is a defect to investigate — **first half stated clearly; second half stated only for layout rules; the fix-side mechanism is ambiguous**

- Clear: SHARED-FIX-005 (`code-fixes.md:643`), with FC-009 (`failure-classes.md:48`) as the failure class.
- Partly stated: the "investigate: formatter bug or wrong diagnostic" half exists only for layout rules, through SHARED-DIAG-010 (`diagnostics.md:532`, `:536`): a layout rule must not report a shape the formatter keeps. For order/content/syntax-form rules (`:534`), and for formatter refusals that are deliberate safety guards (FMT-STRUCT-003, FMT-STRUCT-023), no text says that a no-op formatter result means a defect, or that the withholding guard must name the formatter requirement that refuses (as RH7101-005 does via FMT-PIPE-031).
- Ambiguous: the change doc rejects a fix-side guard that "copies the entry point's checks" (`rh7101-...md:691`), while #1150's *Done when* asks for "a shared check [that] covers all delegating providers". Neither the specs nor AGENTS say whether a generic "format, compare, withhold if unchanged" guard is acceptable. Under (c) it would hide the defects the maintainer wants investigated. FMT-PIPE-031's pattern, where the fix asks the formatter a named question, is the documented alternative.

### (ii) One follow-up issue — rewording the offering rules

Variant: **Clarification**, with a scope note. The node-level, generated-code, and FMT-PIPE-005 parts write down behavior that already exists. The new SHARED-FIX requirement follows from SHARED-FIX-005 + SHARED-FIX-007 (a fix that cannot be formatted has no compliant result other than being withheld), so bringing the code in line is a bug fix (#1150/#1588) and needs **no change doc** (`sdd/README.md:86–94`: "a clarification — the spec gains a requirement that writes down behavior that already exists" / "a bug fix — the code is brought back to the spec").
**A change doc is needed only if** the maintainer picks the reporting-side answer for every rule (no diagnostic in a file with a syntax error, extending SHARED-JOIN-002), because that changes what ~40 rules report (`sdd/README.md:88`, "a requirement is added with new behavior").
The issue therefore carries one open question for that choice, in the form `sdd/README.md` *Open questions* asks for.

> **Title:** SHARED-FIX: state when a fix that formats through the formatter is offered
>
> Lane: docs
> Principle: SHARED-FIX-005 — `sdd/specs/shared/code-fixes.md`; FMT-PIPE-005/-006 — `sdd/specs/formatter/pipeline.md`
>
> ## Spec
>
> `sdd/specs/shared/code-fixes.md`, `sdd/specs/formatter/pipeline.md`, `sdd/specs/shared/line-join-rules.md`, `sdd/specs/analyzer/RH7101.md`
>
> ## Behavior to write down
>
> A formatter node-level entry point declines a code fix's input only for a reason that prevents correct or safe formatting, such as a syntax error, never because the file is generated. A fix that formats through it is not offered where that formatting would leave the fix's result unchanged or unformatted, and such a case is a defect of the formatter or of the diagnostic unless a named formatter requirement declines the input.
>
> ### Sentences to change
>
> 1. **New requirement, `code-fixes.md`, after SHARED-FIX-005** (`SHARED-FIX-009 — A fix that formats through the formatter is offered only where the formatter formats`):
>    "A code fix whose result a formatter entry point lays out MUST NOT be offered where that entry point returns its input unchanged (FMT-PIPE-005), and the diagnostic is still reported (SHARED-FIX-003). A fix whose formatting the formatter declines for any other reason MUST NOT be offered either, and its rule's spec MUST name the formatter requirement that declines, such as FMT-STRUCT-003 or FMT-STRUCT-023, and ask the formatter instead of copying its condition (FMT-PIPE-031). Where neither holds and the formatter still changes nothing, the formatter or the diagnostic is wrong (SHARED-DIAG-010): the case is a defect, not an input to withhold."
>    Why: "A syntax error may make correct formatting impossible, so the formatter declines and the fix has no result it may offer: a fix that only formats would change nothing (SHARED-FIX-005), and one that edits first would leave its edit unformatted (SHARED-FIX-007). Any other no-op is a disagreement between a rule and the formatter that a guard in the fix would hide."

> ### Open question for the maintainer
>
> **Context.** In a file with a syntax error anywhere, `FormatNodeInDocumentAsync` returns the document unchanged (FMT-PIPE-005). About 38 fixes are then offered as a no-op or apply an unformatted edit. RH5105, RH5106, and RH7101 avoid this by not reporting (SHARED-JOIN-002).
>
> ```csharp
> class C { void M(int a) { a=1; } void N( }   // RH6023 on `=`; fix offered, changes nothing
> ```
>
> **Question.** In such a file, does a rule other than the line-join rules keep its diagnostic without a fix, or report nothing?
>
> - **A** — Keep the diagnostic and withhold the fix (SHARED-FIX-009 as drafted). RH6023 is reported and no fix is offered until the error is gone. This needs no change doc and no change to what the rules report. Each delegating provider gets a syntax-error check before it registers.
> - **B** — The analyzer reports nothing (extend SHARED-JOIN-002 to every rule whose fix formats). RH6023 is not reported until the error is gone. This needs a change doc, because ~40 rules change what they report, and a user typing in a file loses those diagnostics for the duration.
> - **C** — Narrow FMT-PIPE-005 for node-level entry points to an error inside the target (or context), and keep A for that case. RH6023 is fixed despite the unrelated `void N(` error. This needs a change doc (a formatter behavior change), and errors outside the target must be shown not to affect the target's layout.
>
> **Recommendation: A.** It matches the clarification (a syntax error is a valid reason to withhold the fix), keeps SHARED-FIX-003's "withholding a fix never removes a report", and needs no change doc. C is the better long-term result if FMT-PIPE-005's whole-file scope turns out broader than "may make formatting impossible", but that should be its own change.
