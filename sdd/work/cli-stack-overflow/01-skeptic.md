## Premise

The issue is real, and the CLI reaches it. The path is `FormatCommandHandler.ProcessFileAsync` → `DefaultSourceFormatter.FormatSyntaxTree` → `ReihitsuFormatter.FormatSyntaxTree` → `FormattingPipeline.ExecutePhases`, running on a thread-pool thread (`Task.Run` in `FormatCommandHandler.ProcessFilesAsync`). The issue exists only in some builds and on some threads (see the second list below).

Fixtures were generated in a scratch directory outside the repository with the Python generator quoted under *Breaking inputs*, and deleted afterwards. The CLI was the Release build from `scripts/build.sh`, run directly:

```shell
dotnet src/Reihitsu.Cli/bin/Release/net11.0/Reihitsu.Cli.dll --check --verbose --max-parallelism 1 <dir>
```

What I observed:

- **Directory with `A.cs`, `Deep.cs` and `Z.cs`.** `A.cs` and `Z.cs` each hold `internal int  M()`. `Deep.cs` holds the issue's 6400-link chain.
  - Output: `Not formatted:` lines for `A.cs` and `Z.cs`, then `Stack overflow.` and `Repeated 7926 times: at Reihitsu.Formatter.Pipeline.Indentation.Utilities.LayoutComputer.ComputeBlockIndentation`.
  - Exit code 134. No summary is printed.
- **The same files with the default parallelism (4 cores) and eight more small files.** Exit code 134. Only 6 of the 11 files are reported, and there is no summary.
- **Deeper inputs.** A 16000-link chain and a 32000-term concatenation are reported as CLI-016 requires:
  - `Error processing <path>: Insufficient stack to continue executing the program safely. This can happen from having too many functions on the call stack or function on the stack using too much stack space.`
  - `0 of 1 file(s) need formatting.`
  - `1 file(s) encountered errors.`
  - Exit code 2.

  So the CLI's `catch (Exception ex)` (`src/Reihitsu.Cli/FormatCommandHandler.cs:532`) already meets CLI-016 for a *catchable* `InsufficientExecutionStackException`. Only the uncatchable overflow escapes it.
- **Search for a stack check.** `rg EnsureSufficientExecutionStack src` finds none. This confirms the issue's statement.

Whether the input fails depends on the build and the thread:

- With `scripts/format.sh` (a Debug build via `dotnet run`), the same 6400-link directory does not overflow. It prints `3 of 3 file(s) need formatting.` and exits with code 1.
- `scripts/apply-fix.sh RH3202 <dir>` runs over an expression-bodied method `=> items` followed by the same 6400 `.Where(...)` links. It reports `fixed` under LF and CRLF, with no overflow.

So the depth that kills the process is not a property of the input. It depends on the thread's stack size and on the build configuration (FC-033).

Things that narrow the issue's severity argument:

- Generated code that carries a generated-file header never reaches the formatter. The same `Deep.cs` with `// <auto-generated/>` as its first line prints `Skipped (generated)` and exits with code 0. A file whose name marks it as generated (`.g.cs`, `.Designer.cs`) is skipped by name.
- The reachable inputs are therefore unmarked generated files and hand-written files with thousands of directly nested links. That is rare, but the CLI reaches them. The maintainer's triage already classes this as a critical bug against CLI-016, and I do not contest that.

## Mechanism and candidates

**Mechanism.** Recursion written in Reihitsu's own code whose depth grows with the input's syntax nesting has no execution-stack check. On a deep enough input it exhausts the thread's stack, and the runtime terminates the process with an uncatchable stack overflow. Roslyn's guarded walkers and rewriters (`CSharpSyntaxRewriter.Visit`, the parser's guarded paths) would instead throw the catchable `InsufficientExecutionStackException`, which the CLI's per-file catch reports as CLI-016 requires.

**Membership.** For any construct, a frame belongs to the class when the method calls itself, or calls back into itself, once per nesting level of a syntax node, and the call does not go through a Roslyn `Visit`. A guarded outer recursion does not protect an unguarded inner one. In the else-if member below, the rewriter's guarded `VisitIfStatement` recursion uses up part of the stack, and the unguarded `GetTokenBehindIfStatement` then recurses 3118 levels between two guard checks.

**Dispatch.** The candidate set comes from the code: every self-recursive method in `src/Reihitsu.Formatter`, `src/Reihitsu.Core` and `src/Reihitsu.Cli`. I found them with a scan for methods whose body calls their own name, which misses mutual recursion through lambdas. Overloads that only delegate are excluded. These candidates recurse once per nesting level:

Each one goes in a run together with another file, and the test checks that the other file is still processed and that the summary and exit code 2 follow.

Two facts constrain how such a test can be red:

- A stack overflow cannot be caught. A failing reproduction run on `main` terminates the test host, and that ends the whole test run.
- The depth that fails depends on the thread's stack size and on Release versus Debug (see *Premise*). A test that depends on the default thread-pool stack can pass or fail depending on the configuration and the platform. `scripts/test.sh` builds Release by default.

## Refuse option

- **Leave the construct as written.** The formatter would return a deep input unchanged instead of failing. That is visible output different from the maintainer's option A: the CLI would print `Unchanged`/exit 0 or would not report the file as failed. It contradicts the triage answer, so it is not available.
- **Declare a shape unsupported.** The shape would be expression or statement nesting deeper than a fixed N, refused by the precheck. This does not meet the contract in `AGENTS.md`, *Special cases do not grow the source*:
  - The depth that kills the process is not a property of the input. A 6400-link chain formats in Debug and on a larger stack and dies in Release on a thread-pool thread. Any fixed N either refuses files that format today (a visible output change for common-enough code, such as an `else if` ladder of a few thousand branches) or misses files that still overflow.
  - It would delete no special case: no phase has a depth guard today, and a shape that deletes nothing is not declared.
  - I name it only because the role requires me to. It should not be escalated as a viable option.
- **No change (option B).** The maintainer rejected it.
- **Narrower change.** This would close only the reported member, `LayoutComputer.ComputeBlockIndentation`. It is cheaper, but it leaves the `elseif` (6400) and `memberaccess` (16000) cells aborting the CLI, so CLI-016 is still violated for the issue's own class (FC-016). Not recommended.
- **Rarity.** The input class is rare: thousands of directly nested links, and generated files with a header are skipped. Rarity argues against machinery built for these inputs. It does not argue against meeting CLI-016, which the maintainer has decided.

## Output questions

_None._ CLI-016 and CLI-017, together with the maintainer's triage answer (option A), decide the visible output: `Error processing <path>: <message>`, the other files processed, the summary, and exit code 2. The message is the runtime's message for the exception, as the CLI already prints it for the 16000-link chain. One condition applies: no input that formats today may start failing. An approach that refuses at a fixed depth would put that in question (see *Refuse option*).

## Internal choices

1. **Scope of the class.**
   - **(a)** Close every Reihitsu member that fails in the matrix: `ComputeBlockIndentation`, `GetTokenBehindIfStatement`, `FluentChain.Collect*`. The masked and unexercised candidates are checked by running the matrix again once the first member is closed.
   - **(b)** Close only `ComputeBlockIndentation`.

   **Recommendation: (a).** Both choices give the same visible output for every cell they close, and (b) leaves two observed cells against CLI-016.
2. **Roslyn parser and lexer members** (`generic` at 16000, `interp` at 16000). They overflow in Roslyn's own recursion inside `ParseText`, before any Reihitsu code runs. No change inside the formatter or `Reihitsu.Core` can reach them. Only changing the stack the CLI parses and formats on, or isolating each file in its own process, affects them, and a larger stack only moves the depth at which they fail. The inputs are far rarer than the issue's: 16000-deep nested generic type arguments or interpolated strings.
   - **(a)** Leave them outside this run and record them as a follow-up candidate.
   - **(b)** Handle them in this run.

   **Recommendation: (a).** Under *Special cases do not grow the source*, machinery for that class is not justified. No visible output is in question, because these files abort today and keep aborting.

## Issue goals

- **Motivation and *Affected Surface* name only `LayoutComputer.ComputeBlockIndentation` and "CLI error handling".**
  - Change: the class also covers the structural-transform phase (`ControlFlowBraceTransform.GetTokenBehindIfStatement`) and `Reihitsu.Core` `FluentChain` (line-break phase).
  - Drop: "CLI error handling". The CLI's handler already meets CLI-016 for a catchable exception.
  - No visible output change follows from either.
- **"Every file after `Deep.cs` is left unprocessed."** This is accurate only for `--max-parallelism 1`. With parallelism, files that run at the same time may be processed but never reported. The goal (option A) is unaffected.
- **"A fluent chain of 6400 links or a concatenation of 16000 terms triggers it."** True for a Release build on a thread-pool thread. Not true in a Debug build or on a thread with a larger stack. The issue's numbers must not be taken as fixed thresholds for a test.
- **The 32000-term concatenation is reported per file with exit code 2.** Confirmed.
- **"Desired output: the file stays unchanged and is reported."** I keep this goal, and it is consistent with CLI-016.

## Architecture findings

_None._ The class spans three components: the indentation phase, the structural-transform phase, and `Reihitsu.Core`. Each owns its own recursion, though, and no decision is shared, predicted, or stated twice, so it is not an architecture finding as `README.md` defines one. It is an FC-016 sibling set.
