### Architecture findings

Two components own the decision "is a fix offered for this diagnostic in this document" (SHARED-FIX-012, and SHARED-FIX-011 where it applies):
- `ReihitsuCodeFixProviderBase.RegisterCodeFixesAsync` decides it for every registration.
- A Fix All provider that does not re-enter registration decides applicability with its own predicate: `RH3002…ApplyFixAllAsync` with `TryGetFixableExpression`, and `RH7101…ApplyFixAllAsync` with `TryGetFixableFieldDeclaration`.

The input that shows them disagreeing is the project-scope Fix All of finding #1. `CasingFixAllProvider` also bypasses registration, but it restates the decision in `RenameWithoutConflictAsync`, which is why it holds. The base is the one owner the change doc names ("one check … before any fix registers"). Every Fix All path that bypasses registration is a second owner, now or later.

### Hints

- `DocumentOrderFixAllProvider`: the starting-code filter applies to the first pass only. After a pass that loses a diagnostic, `GetDiagnosticsAsync` re-analyzes the document, and the next pass also attempts a diagnostic whose fix was withheld on the starting code and which no earlier fix rewrote. In a document that both loses a nested diagnostic and holds such a released guard, Fix All would apply a fix that SHARED-FIX-002 says nobody was offered. I did not construct an input that reaches both conditions with one rule, so this is not a finding.
- `FormatsThroughFormatter` restates, per provider, a fact that the provider's calls already show. All 29 overrides match the callers today. No architecture test ties a provider that reaches `FormatNodeInDocumentAsync` or `FormatNodeInDocumentWithContextAsync` to the override, so a new formatting fix can omit it and be offered as a no-op in a file with a syntax error.
- `DocumentOrderFixAllProvider.cs:19-21` and `:231-236`: the edited XML summaries keep the old line breaks (one line runs to 143 characters, another ends after "The"). Cosmetic.
