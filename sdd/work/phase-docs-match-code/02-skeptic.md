## Breaking inputs

Failure classes that reach this run:

- **FC-002 and FC-003, qualifier and both sides.** The new FMT-SWITCH-003 qualifier is "measured on the code as the line-break phase leaves it". It has three sides, and the spec text names only two of them. Observed with `scripts/format.sh`:

  | FMT-BREAK effect on a single non-terminal statement | Input | Section multi-line? | Observed |
  |---|---|---|---|
  | joins (FMT-BREAK-015) | `A(out⏎var v);` | no | no section braced |
  | joins (FMT-BREAK-015, named argument) | `Foo(message:⏎"x");` | no | no section braced |
  | joins (FMT-BREAK-015, tuple element) | `var t = (a:⏎1, 2);` | no | no section braced |
  | joins (FMT-BREAK-014, indexer) | `var y = a[1,⏎2];` | no | no section braced |
  | joins (FMT-BREAK-014, type arguments) | `Foo<int,⏎string>();` | no | no section braced |
  | joins (FMT-BREAK-016, assignment) | `var y =⏎1;` | no | no section braced |
  | keeps (FMT-BREAK-012) | `A(1,⏎2);` | yes | braced (existing test) |
  | keeps (chain) | `a.B()⏎.C();` | yes | braced |
  | keeps and re-lays (conditional) | `var y = x > 0 ? 1 :⏎2;` | yes | braced |
  | **adds** (lambda block body) | `Run(() => { X(); Y(); });` written on one line | yes | braced |
  | **adds** (object initializer) | `var y = new D { A = 1, B = 2 };` written on one line | yes | braced |
  | splits statements ("later line" part) | `A(); return 1;` on one line | yes | braced; `return 1;` lands on its own line |
  | splits statements, comment between | `A(); /* c */ return 1;` on one line | yes | braced; comment stays behind `A();` |

  Every member holds. The requirement's general sentence covers the **adds** rows. Its explanatory clause ("a wrap that FMT-BREAK joins … does not …, and a wrap that FMT-BREAK keeps does") names only joins and keeps, and a reader could take that list as exhaustive. This is a precision point for the spec author, not a defect: adding "or adds" closes it. The test implementer should cover at least one join, one keep, and one add.

  **Nested switches.** The phase measures after it has already rewritten the inner switches (`base.VisitSwitchStatement` runs first). That is not strictly "as the line-break phase leaves it". The difference cannot be observed: FMT-BREAK puts the braces of every switch statement on their own lines, so a nested switch statement is multi-line whatever the inner rewrite does.

- **FC-028, detached vs document-scoped.** Both differences between `FormatNode` and the node-in-document entry points are intended by spec: the guards (FMT-PIPE-012) and the version source (FMT-PIPE-008). Tests should pin each family separately and not assert that the families agree.

- **FC-033, harness normalizes away.** For an `AdhocWorkspace` document, the tree's parse options are the project's parse options, so no test can tell "tree" from "project" for `FormatDocumentAsync`. That is acceptable, as the spec author notes; the test sets the project's language version.

  The detached-node sentence of FMT-PIPE-008 ("a detached node belongs to a tree with the default parse options") is a claim about Roslyn: a parentless node's lazily created tree uses `CSharpParseOptions.Default`. I did not run this. The existing test `FormatNodeFormatsDetachedNodeForTheNewestSupportedVersion` uses `SyntaxFactory.ParseCompilationUnit(text)` with no options. Candidate input that would break the sentence if Roslyn kept the options: `SyntaxFactory.ParseCompilationUnit("class Empty\n{\n}", options: CSharpParseOptions.Default.WithLanguageVersion(LanguageVersion.CSharp11))` passed to `FormatNode`. The spec predicts `class Empty;`.

- **FC-017, weak assertion.** Run the switch and version tests under LF and CRLF, as the existing `ReihitsuFormatterLanguageVersionTests` helpers do. For the node-in-document guards, assert the same document instance or identical text.

Candidate inputs for FMT-PIPE-005 / FMT-PIPE-006 on the node-in-document entry points. The spec phrase "whichever node of it is the target or the context" is the claim to falsify:

1. Syntax error inside the target: `class C{void M(){int x=1}}`, target `M`. This is the spec example.
2. Syntax error outside the target: `class C{void M(){int x=1;} void N(){int y=2}}`, target `M`. The document must still come back unchanged, because the guard checks the whole tree.
3. `FormatNodeInDocumentWithContextAsync` with target ≠ context (`M` in `C`) and with target == context, which takes the delegation path.
4. Generated header `// <auto-generated />` on the first line, with a target that is not the first member, so the marker is not in the target's own trivia.
5. Holding side: a marker in the leading trivia of the target class when the class is not the file's first token, for example after a `using` directive. It must not disable formatting (FMT-PIPE-006, second sentence).

Existing behavior that belongs to "any error-level diagnostic" and is already tested for the tree entry point: an unmatched `#region`/`#endregion` (`FormatSyntaxTreeWithUnmatchedRegionReturnsOriginalTree`). A `#error` directive, which also raises an error-level diagnostic, has no test that I found.
