## Refuse option

Refusing is option B: leave the construct as written and state in FMT-BLANK-019 that the positional clause is not covered. The maintainer's answer rejected it, and it would keep the positional `)` the one FMT-BREAK-022 closing delimiter with its own blank-line rule.

The requested change is cheap: one more condition in one existing predicate, with no new type and no new mechanism. The input class is not rare. A positional pattern written across lines is ordinary code, and a stray blank line in front of the closing delimiter is as common as for a list pattern.

Declaring a shape unsupported is not an option. No shape here forces a special case into any phase, and the class is ordinary code.

No simpler option exists than the one-predicate change.

## Internal choices

1. **FMT-BLANK-019's pointer for other closing parentheses.** The new sentence says the blank lines before "a closing parenthesis owned by any other node … are decided as FMT-BLANK-018 states for any other token". FMT-BLANK-018 is about glued comments and itself defers to FMT-BLANK-014 for those tokens. Recommendation: point at FMT-BLANK-014 directly. No visible output changes.
2. **The empty clause `P(⏎⏎)`.** "A blank line behind the opening … is kept" and "removed directly before the closing" name the same blank line here. The ambiguity already exists for an empty list pattern or collection expression, and `main` resolves it by removing the line (`[⏎⏎]` becomes `[⏎]`). The answer "like the list pattern's `]`" decides the positional case the same way. Recommendation: one sentence in FMT-BLANK-019 stating that in a construct with no element the blank line is removed, and a test for `P(⏎⏎)`. This matches `main`'s list output, so nothing new is in question.
3. **"whether the pattern stands behind `is`, in a switch expression arm, or in a `case` label"** can read as an exhaustive list. The positional `)` is also named behind `not`/`and`/`or`, nested inside another subpattern, or followed by a property clause or designation. Recommendation: phrase it as examples ("wherever the pattern stands, for example …"), since the owning node alone decides. No visible output changes.
4. FMT-BLANK-009/018/020 each restate the token list instead of referring to FMT-BLANK-019. The diff updates all four consistently, so nothing drifts in this run. Recommendation: leave as is in this run.

## Architecture findings

**One set stated in two components (FC-015).** These two components each list the closing delimiters whose construct is laid out one element per line (FMT-BREAK-022, FMT-INDENT-025):

- `BraceBlankLinePolicy.IsClosingTokenOfPatternOrCollectionExpression` (`src/Reihitsu.Formatter/Pipeline/BlankLines/Utilities/BraceBlankLinePolicy.cs:131-139`);
- `CommentIndentationContributor.AlignCommentsBeforeToken` (`src/Reihitsu.Formatter/Pipeline/Indentation/Contributors/CommentIndentationContributor.cs:67-69`).

The input that shows them disagreeing is member 11 above. Today the indentation phase indents `// last` into the subpatterns as a closing-delimiter comment (FMT-INDENT-006), while the blank-line phase treats the `)` as "any other token". This drift is the cause of the issue.

After the planned change, the two sets are equal: braces, collection and list-pattern `]`, and positional and parenthesized `)`. The narrow fix adds no new copy, but it keeps two statements that the next construct added to FMT-BREAK-022 must again update in both places. The indentation phase is not a component the run otherwise changes.

The specs state the same set separately as well: FMT-INDENT-006 against FMT-BLANK-019, the latter restated in FMT-BLANK-009/018/020.

`CommentPositionUtilities.IsOwningConstruct` (analyzer) and `ListElementInteriorUtilities.IsOwningConstruct` (formatter) are a different decision ("owns the line"). They already say they must stay in step, and they are not affected here.
