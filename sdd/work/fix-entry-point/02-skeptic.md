## Premise

The issue is real for RH7101. The RH7101 fix is the caller, and every case below is a code-fix input.

- `RH7101DoNotCombineFieldsCodeFixProvider.ApplyCodeFixAsync` runs `new FieldDeclarationSplitTransform(...).Visit(typeDeclaration)` on the whole type, nested types included. Measured: `private int _a, _b; private int _c, _d;` gets one fix, and that fix splits both declarations. Today's fix therefore violates the unchanged SHARED-FIX-006, independent of the issue's architectural motivation (change doc case 8).
- The field split's code-fix-only layout exists: `GetMemberIndentationTrivia`, the line break after each field, and the line break after a moved comment. Today's fix output is not stable under the formatter (SHARED-FIX-007). I re-measured the change doc's cases 1, 2, 3, and 5 with `scripts/format.sh`, and the "after" blocks in the change doc match document-level output exactly.
- For RH7201–RH7207 the issue's motivation is stale. FMT-USING's scope sentence already names the dependency (`using-directives.md` line 10). FMT-USING-003 and SHARED-USING-010 specify the scope indentation. FMT-USING-010's Why already records that formatting a using fix's result may add a blank line. I agree with dropping the using goals.
- The issue's target behavior, "the fixes' output stays as it is today", contradicts SHARED-FIX-006 (case 8) and SHARED-FIX-007 (cases 1–7), and both are unchanged. It cannot be kept.

## Mechanism and candidates

Mechanism of today's defects: the RH7101 fix runs one structural transform over the whole type, with that transform's own layout, instead of formatting the reported declaration through the phases. As a result it splits every combined declaration the visitor reaches, and it lays the fields out in a way the later phases redo differently.

Dispatch: the analyzer reports every `SyntaxKind.FieldDeclaration` with more than one declarator. The fix requires `fieldDeclaration.Parent is TypeDeclarationSyntax`. The split visits `ClassDeclarationSyntax`, `StructDeclarationSyntax`, `RecordDeclarationSyntax` (class and struct records), and `InterfaceDeclarationSyntax`. Candidates, by `TypeDeclarationSyntax` subtype:

- Class, struct, record, record struct, interface: split. These are the candidates the tests must cover (`CombinedFieldDeclarationsOfEveryTypeKindAreReported` already enumerates them for reporting).
- `ExtensionBlockDeclarationSyntax`: not visited. A field inside `extension(int i) { private static int _x, _y; }` parses without a syntax error. It is reported, and the fix is offered and changes nothing (measured: `no-progress`). This is a pre-existing FC-009 defect. The change keeps it unless the guard covers it (see *Breaking inputs*, class 1).

### Fact for the test implementer

Code reading only, not run: the split copies the target's first token (`private`, or `[` of the first attribute list) into every field it creates. `FindCorrespondingNode` (`ReihitsuFormatter.cs`) returns `null` when the annotated token occurs more than once, and the entry point then returns the document unchanged. A FMT-PIPE-029 test written before the implementation exists is expected to fail with "document unchanged", not with a layout difference.

**2 · RH7101 · Do not combine fields — initializers and attributes of the split declaration**

                                return;
                            }

## Architecture findings

- **Components:** the registration guard in `RH7101DoNotCombineFieldsCodeFixProvider.RegisterCodeFixesAsync`, and `ReihitsuFormatter.FormatNodeInDocumentWithContextAsync` (`HasSyntaxErrors`, `IsAutoGeneratedSource`, the structural phase's type-kind dispatch, and `CarriesDirective`).
- **Decision they share:** whether formatting the reported declaration changes the document. After the change, the fix's whole edit is that formatting call, so the guard has to predict every refusal of the entry point.
- **Input showing them disagree under the spec diff:** a header-marked file analyzed under `generated_code = false` (class 1). The guard the spec diff states covers syntax errors only.
- **Places that state the rule:** FMT-PIPE-005, FMT-PIPE-006, FMT-STRUCT-023, RH7101-005, RH7101-006. Today `CarriesDirective` is shared, not copied. A syntax-error or generated-code check written inside the fix would be a second copy of the entry point's checks. The same decision recurs in the spec author's RH5111/RH5417 follow-up candidate.
