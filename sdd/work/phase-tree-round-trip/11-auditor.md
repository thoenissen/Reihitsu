## Architecture findings

**A1 — two owners of "do two tokens written tight read as one".**
- **Components.** `Reihitsu.Formatter/Pipeline/Core/Utilities/TokenGapUtilities.WouldMergeWhenTight` and `Reihitsu.Analyzer.CodeFixes/Rules/Clarity/RH3002StatementMustNotUseUnnecessaryParenthesesCodeFixProvider.WouldMergeIntoOneToken`.
  - The formatter's owner is a character heuristic. This run moved it into a shared formatter helper and made the new `return` separator depend on it.
  - The code fix's private copy asks the lexer, so it is exact.
- **Disagreement.** `return` + `a`: the formatter answers "no merge", while the lexer reads one identifier. `return` + `@a`: the formatter answers "merge", while the lexer reads two tokens.
- **Defect.** Finding #3. The run depends on it for a MUST of FMT-STRUCT-026 and FMT-PIPE-021.

**A2 — `LineBreakBlockRewriter` predicts `DeclarationBraceLineBreakRewriter`.**
- **Components.**
  - `LineBreakBlockRewriter.VisitBlock`/`VisitAccessorList` skip the braces of a member body or an event accessor list, on the prediction that `DeclarationBraceLineBreakRewriter` places them.
  - The prediction reads `Parent`, which can lie outside the formatting root, while `DeclarationBraceLineBreakRewriter` only reaches declarations inside the root.
- **Shared decision.** Who places these braces for a given formatting root.
- **Input.** `FormatNodeInDocumentAsync` with the body block of `void M()` / `    { Foo(); }` as target. Neither rewriter places the braces.
- **Defect.** Finding #4.
