# Analyzer — RH2005 Fields must be private

| | |
|---|---|
| ID prefix | RH2005 |
| Status | Active |
| Category | Design |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH2005FieldsMustBePrivateAnalyzer`, `RH2005FieldsMustBePrivateCodeFixProvider`, `DeclarationModifierUtilities` |
| Uses | SHARED-FIX-003 |

RH2005 reports a `public` field of a class or record class that can be reassigned, and offers a code fix that makes it `private`.

## Non-goals

- Fields with any accessibility other than `public` — `protected`, `internal`, `protected internal`, `private protected`, and implicit private fields are not reported.
- Fields of structs, record structs, and interfaces.
- The name of the field after the fix — RH4106 reports it once the field is private.
- Replacing the field with a property. The user documentation recommends it where the value belongs to the public surface; the fix does not do it.

## Requirements

### RH2005-001 — Writable public fields of reference types are reported

The analyzer MUST report a field declaration that carries the `public` modifier and is declared directly in a class or a record class, including nested classes. `const` fields and fields that are both `static` and `readonly` MUST NOT be reported. Instance `readonly`, `static`, and `volatile` fields are reported.

Why: A public field hands every caller a slot of the object's state; it cannot be validated or reimplemented later without breaking callers. A constant or a static readonly field cannot be reassigned, so exposing it hands out no writable slot; an instance readonly field is still part of the object's layout and is reported.

Example:

```csharp
public class C
{
    public string {|RH2005:publicField|};

    protected int protectedField;

    internal bool internalField;

    protected internal int protectedInternalField;

    private protected int privateProtectedField;

    private string privateField;

    string implicitPrivateField;

    public static readonly string Shared = string.Empty;

    public const int Constant = 1;
}

public struct S
{
    public int PublicField;
}

public record R
{
    public int {|RH2005:recordField|};
}

public record struct RS
{
    public int PublicField;
}
```

### RH2005-002 — One diagnostic per declaration, on the first name

The analyzer MUST report one diagnostic per field declaration, located on the identifier of its first declarator.

Why: The accessibility belongs to the declaration, not to a single declarator; the fix changes it for all of them at once.

Example:

```csharp
public class C
{
    public readonly int {|RH2005:A|}, B;
    public volatile int {|RH2005:Flag|};
}
```

```csharp
public class C
{
    private readonly int A, B;
    private volatile int Flag;
}
```

### RH2005-003 — The fix replaces `public` with `private`

The code fix MUST remove the declaration's accessibility modifiers and put `private` first in the modifier list, keeping the other modifiers in their order and keeping the declaration's attributes, documentation comment, and name. `private` MUST stand where the first token behind the declaration's attribute lists stood: on that token's line and in its column, behind every comment and directive line that stood in front of that token. When a removed accessibility modifier is not the first modifier and starts its own line, the line it started MUST keep its place: the token that followed the modifier stands on that line and in the modifier's column. This holds also when the modifier ends that line. When a removed accessibility modifier is not the first modifier, does not start its own line, and ends it, the line break that ended it MUST keep its place: the modifier in front of it ends that line, and the token that followed it keeps its line and its column. A comment or directive behind such a modifier withholds the fix (RH2005-005).

Why: The fix makes exactly the change the diagnostic asks for. The name stays, so references inside the type keep working; renaming to `_camelCase` is RH4106's separate step. Every line the fix does not have to change keeps its place, so the fix changes no more of the layout than the removed keyword occupied.

Example:

```csharp
public class C
{
    /// <summary>Doc</summary>
    [System.Obsolete]
    public static int {|RH2005:Counter|};
}
```

```csharp
public class C
{
    /// <summary>Doc</summary>
    [System.Obsolete]
    private static int Counter;
}
```

Example — `public` that is not the first modifier: `private` takes its place in front of the other modifiers, on the field's line and in its column:

```csharp
public class C
{
    static public int {|RH2005:Counter|};
}
```

```csharp
public class C
{
    private static int Counter;
}
```

Example — an attribute list on its own line in front of `static public`: `private` stands on the field's line and in its column, not behind the attribute list:

```csharp
using System;

public class C
{
    [Obsolete]
    static public int {|RH2005:Counter|};
}
```

```csharp
using System;

public class C
{
    [Obsolete]
    private static int Counter;
}
```

Example — a comment line and a directive line between the attribute list and the field stay in front of it:

```csharp
using System;

public class C
{
    [Obsolete]
    // note
#pragma warning disable CS0414
    static public int {|RH2005:Counter|} = 1;
}
```

```csharp
using System;

public class C
{
    [Obsolete]
    // note
#pragma warning disable CS0414
    private static int Counter = 1;
}
```

Example — `public` behind another modifier, on a line of its own: `private` takes the place of `static`, and `int` takes the place of `public`, on its line and in its column:

```csharp
public class C
{
    static
        public int {|RH2005:Counter|};
}
```

```csharp
public class C
{
    private static
        int Counter;
}
```

Example — `public` behind another modifier, on a line of its own that it also ends: the line of `public` keeps its place, and `int` stands on it, in the column of `public`:

```csharp
public class C
{
    static
        public
        int {|RH2005:Counter|};
}
```

```csharp
public class C
{
    private static
        int Counter;
}
```

Example — `public` behind another modifier ends its line: `private` takes the place of `static`, `static` ends the line, and `int` keeps its line and column:

```csharp
public class C
{
    static public
        int {|RH2005:Counter|};
}
```

```csharp
public class C
{
    private static
        int Counter;
}
```

### RH2005-004 — The fix is withheld for a field used outside its type

The code fix MUST NOT be offered when any field the declaration declares is referenced anywhere in the solution from code outside its containing type: code that lies in the body of no declaration of that type, where the types nested in the containing type belong to its body. Every such reference counts, also one that would still compile once the field is `private`, such as `nameof` in an attribute of the containing type itself or a `cref` in the documentation comment of another type. The diagnostic is still reported.

A reference from another part of a `partial` containing type, or from a type nested in the containing type, is inside it: the field stays accessible there once it is `private`, and the fix is offered. A reference from a derived type is outside it.

This requirement decides references in the active code of the solution; a reference in code that an `#if` branch excludes is decided by SHARED-FIX-003.

Why: Once the field is `private`, a reference from outside its containing type no longer compiles in most positions (CS0122), so the fix would hand the user a broken build (SHARED-FIX-003). A reference outside the type also shows that other code relies on the field, so whether it should stay part of what the type offers is the author's decision; one rule for every reference outside the type keeps that decision with the author instead of telling apart the positions where a `private` field still compiles. Code outside the solution cannot be seen; the fix makes the change the diagnostic asks for wherever the solution itself shows no use of the field outside its type.

Example:

```csharp
public class C
{
    public int {|RH2005:Value|};
}

public class User
{
    public int Read(C c) => c.Value;
}
```

is reported, and no code fix is offered. The same holds when the reference stands in a type derived from `C`:

```csharp
public class C
{
    public int {|RH2005:Value|};
}

public class D : C
{
    public int Read() => Value;
}
```

Example — references inside the containing type, from another part and from a nested type:

```csharp
public partial class C
{
    public int {|RH2005:Value|};

    private class Nested
    {
        public int Read(C c) => c.Value;
    }
}

public partial class C
{
    public int Twice() => Value * 2;
}
```

```csharp
public partial class C
{
    private int Value;

    private class Nested
    {
        public int Read(C c) => c.Value;
    }
}

public partial class C
{
    public int Twice() => Value * 2;
}
```

Example — one declaration with two fields, of which only `B` is referenced outside the type:

```csharp
public class C
{
    public int {|RH2005:A|}, B;
}

public class User
{
    public int Read(C c) => c.B;
}
```

is reported, and no code fix is offered: the fix makes both fields `private`.

Example — references outside the bodies of the type's declarations that would still compile, in an attribute of the type and in a `cref`:

```csharp
using System.Diagnostics;

[DebuggerDisplay(nameof(C.Value))]
public class C
{
    public int {|RH2005:Value|};
}

/// <summary>See <see cref="C.Value"/>.</summary>
public class User
{
}
```

is reported, and no code fix is offered.

### RH2005-005 — The fix is withheld for a comment or directive next to a later accessibility modifier

The code fix MUST NOT be offered when a comment or a directive stands next to an accessibility modifier that is not the declaration's first modifier, in either of these places:

- in front of the modifier, on a line below the line of the modifier in front of it;
- behind the modifier and in front of the token that follows it, on the modifier's line, such as `static public // note` or `static public /* note */ int`, or on a line below it.

This includes an `#if` block whose excluded code stands in one of these places. The diagnostic is still reported.

A comment or directive line in front of the declaration's first modifier does not withhold the fix; it stays in front of `private` (RH2005-003). A comment behind the modifier in front, on that modifier's line, such as `static /* note */ public`, is not covered by this requirement. A line break alone in either place does not withhold the fix; RH2005-003 decides the layout.

Why: The comment or directive stood with the accessibility modifier the fix removes. Whether it then belongs with the next modifier or the type, or should go, is the author's decision; dropping or moving it is what SHARED-FIX-003 forbids. One rule for every comment and directive in these places keeps the fix simple.

Example — a comment line in front of `public`:

```csharp
public class C
{
    static
        // note
        public int {|RH2005:Counter|};
}
```

is reported, and no code fix is offered.

Example — a directive line, and an `#if` block that excludes a modifier, in front of `public`:

```csharp
public class C
{
    static
#pragma warning disable CS0649
        public int {|RH2005:Counter|};

    static
#if NEVER
        readonly
#endif
        public int {|RH2005:Total|};
}
```

Both are reported, and no code fix is offered.

Example — a comment behind `public` on its line, at its end and in front of the type, and a comment line between `public` and the type:

```csharp
public class C
{
    static public // note
        int {|RH2005:Counter|};

    static public /* note */ int {|RH2005:Count|};

    static public
        // note
        int {|RH2005:Total|};
}
```

All three are reported, and no code fix is offered.

Example — a directive line, and an `#if` block that excludes a modifier, between `public` and the type:

```csharp
public class C
{
    static public
#pragma warning disable CS0649
        int {|RH2005:Counter|};

    static public
#if NEVER
        readonly
#endif
        int {|RH2005:Total|};
}
```

Both are reported, and no code fix is offered.
