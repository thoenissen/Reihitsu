# Analyzer — RH8107 Void return value must not be documented

| | |
|---|---|
| ID prefix | RH8107 |
| Status | Active |
| Category | Documentation |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH8107VoidReturnValueMustNotBeDocumentedAnalyzer`, `RH8107VoidReturnValueMustNotBeDocumentedCodeFixProvider` |
| Uses | SHARED-DOC-008, SHARED-DOC-017, SHARED-DOC-018 |

RH8107 reports a `<returns>` element in the documentation comment of a member that returns `void`, and offers a code fix that removes the element.

## Non-goals

- A missing `<returns>` element on a member that returns a value — RH8105 — and an empty one — RH8106.
- The content, order, and layout of the remaining documentation — RH8301–RH8309.
- Members that cannot return a value at all, such as constructors and properties.

## Requirements

### RH8107-001 — A `<returns>` element on a `void` member is reported

The analyzer MUST report a `<returns>` element in the documentation comment of a method, delegate, operator, or conversion operator whose return type is the `void` keyword. The tag name MUST be matched case-insensitively, and an empty element (`<returns/>`) or an element without an end tag counts. Both `///` and `/** */` documentation comments are checked. The documentation comment is the first one in the member's leading trivia.

Why: A `void` member has no return value; a `<returns>` element describes something that does not exist and misleads the reader of the generated documentation.

Example:

```csharp
public class C
{
    /// <summary>
    /// Runs
    /// </summary>
    /// {|RH8107:<returns>Nothing</returns>|}
    public void Run()
    {
    }

    /// <summary>
    /// Adds
    /// </summary>
    /// {|RH8107:<returns/>|}
    public void operator +=(int value)
    {
    }
}

/// <summary>
/// Handler
/// </summary>
/// {|RH8107:<Returns>Nothing</Returns>|}
public delegate void Handler();
```

### RH8107-002 — Only `void` itself counts

The analyzer MUST NOT report a member whose return type is anything other than the `void` keyword, including `Task`, `ValueTask`, and `async` members.

Why: A `Task` is a value the caller receives and awaits; documenting it is correct even when it produces no result.

Example:

```csharp
using System.Threading.Tasks;

public class C
{
    /// <summary>
    /// Runs
    /// </summary>
    /// <returns>A task</returns>
    public Task RunAsync()
    {
        return Task.CompletedTask;
    }
}
```

is not reported.

### RH8107-003 — A nested `<returns>` counts, a sample does not

When the documentation comment has no top-level `<returns>` element, the analyzer MUST report the first `<returns>` element nested inside another element, unless it lies inside a `<code>` or `<example>` element (matched case-insensitively). When a top-level `<returns>` element exists, only that one is considered.

Why: A `<returns>` element nested in `<remarks>` still documents a return value. Inside a code sample it is sample text — for example the documentation of another member shown as an example — and says nothing about this member.

Example:

```csharp
public class C
{
    /// <summary>
    /// Runs
    /// </summary>
    /// <remarks>{|RH8107:<returns>Nested</returns>|}</remarks>
    public void Run()
    {
    }

    /// <summary>
    /// Runs
    /// </summary>
    /// <example><code><returns>Sample</returns></code></example>
    public void Run2()
    {
    }
}
```

```csharp
public class C
{
    /// <summary>
    /// Runs
    /// </summary>
    /// <remarks></remarks>
    public void Run()
    {
    }

    /// <summary>
    /// Runs
    /// </summary>
    /// <example><code><returns>Sample</returns></code></example>
    public void Run2()
    {
    }
}
```

### RH8107-004 — Nothing is reported when documentation is not parsed

The analyzer MUST NOT report anything when the syntax tree's documentation mode is `None`, as SHARED-DOC-008 specifies.

Why: Without documentation parsing, the comment is plain trivia and its elements cannot be identified. RH0002 reports that mode.

### RH8107-005 — The diagnostic covers the element

The analyzer MUST report one diagnostic per member, on the span of the reported `<returns>` element — from its start tag to its end tag, or to the end of its content when the end tag is missing.

Why: The element is exactly what the fix removes, so the squiggle shows the text that will disappear.

Example: see RH8107-001.

### RH8107-006 — The fix removes the element and only the lines it owns

The code fix MUST remove the reported `<returns>` element as SHARED-DOC-018 specifies.

Why: A `void` member has no return value, so nothing of the element is worth keeping, while the rest of the documentation stays as written.

Example: see SHARED-DOC-018, whose example is the RH8107 fix.

### RH8107-007 — The fix is withheld for an element without an end tag of its own

The code fix MUST NOT be offered when the reported `<returns>` element has no end tag of its own, as SHARED-DOC-017 defines it. The diagnostic is still reported.

Why: Without an end tag, the parser extends the element to the end of the comment, so removing it would also remove whatever documentation follows it; an end tag of another name belongs to the element around it.

Example:

```csharp
public class C
{
    /// <summary>
    /// Runs
    /// </summary>
    /// <returns>Nothing
    public void Run()
    {
    }
}
```

is reported from `<returns>` through the line break at the end of its line, and no code fix is offered.
