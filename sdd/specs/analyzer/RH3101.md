# Analyzer — RH3101 Do not prefix calls with base unless local implementation exists

| | |
|---|---|
| ID prefix | RH3101 |
| Status | Active |
| Category | Clarity |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH3101DoNotPrefixCallsWithBaseUnlessLocalImplementationExistsAnalyzer`, `RH3101DoNotPrefixCallsWithBaseUnlessLocalImplementationExistsCodeFixProvider` |
| Uses | SHARED-FIX-003 |

RH3101 reports a `base.` member access or a `base[…]` element access that binds to the same member without `base`, and offers a code fix that removes the `base` qualifier.

## Non-goals

- The `this.` qualifier — RH3105.
- A constructor initializer `: base(…)`, which is not a member access.

## Requirements

### RH3101-001 — A `base` access that binds the same without `base` is reported

The analyzer MUST report a member access `base.X` and an element access `base[…]` when the same code without the qualifier — `X`, or `this[…]` for an element access — binds to the same symbol, unless RH3101-002 applies.

Why: `base.` suggests that the type has its own implementation of the member that the call deliberately bypasses. When the type has none, the qualifier misleads the reader and adds nothing.

Example:

```csharp
class B
{
    public virtual int M() => 1;
    public int P { get; set; }
    public int this[int i] => i;
    protected int F;
}

class D : B
{
    int Run()
    {
        return {|RH3101:base|}.M() + {|RH3101:base|}.P + {|RH3101:base|}[0] + {|RH3101:base|}.F;
    }
}
```

### RH3101-002 — A `base` access the type needs is not reported

The analyzer MUST NOT report a `base` access whose member binds differently without the qualifier, such as a member the type overrides or hides, nor a `base` access inside the override of the very member it accesses.

Why: In these places the qualifier selects the base implementation on purpose; without it the call would reach the type's own member, or call itself.

Example:

```csharp
class B
{
    public virtual int M() => 1;
    public virtual int N() => 1;
    public int Q() => 1;
}

class D : B
{
    public override int M() => base.M();

    public override int N() => 2;

    public new int Q() => 2;

    int Run()
    {
        return base.N() + base.Q();
    }
}
```

is not reported.

### RH3101-003 — The diagnostic is on `base`

The analyzer MUST report one diagnostic per access, on the `base` keyword.

Why: The qualifier is what the fix removes; the member and its arguments stay.

Example: see RH3101-001.

### RH3101-004 — The fix removes the qualifier

The code fix MUST replace `base[…]` with `this[…]`, and `base.X` with `X` where the largest expression that contains the access does not hold both a `<` operator and a `>` operator, unless RH3101-005, RH3101-006, or RH3101-007 withholds the fix.

Why: An element access needs a receiver, and `this` is the one that binds to the same indexer; a member access needs none.

Example:

```csharp
class B
{
    public int M() => 1;
    public int P { get; set; }
    public int this[int i] => i;
    protected int F;
}

class D : B
{
    int Run()
    {
        return {|RH3101:base|}.M() + {|RH3101:base|}.P + {|RH3101:base|}[0] + {|RH3101:base|}.F;
    }
}
```

```csharp
class B
{
    public int M() => 1;
    public int P { get; set; }
    public int this[int i] => i;
    protected int F;
}

class D : B
{
    int Run()
    {
        return M() + P + this[0] + F;
    }
}
```

### RH3101-005 — A fix that would parse as a generic name or a cast is withheld

The code fix MUST NOT be offered when the code it writes would parse as a generic name or as a cast: when, without the `base.` qualifier, a `<` in front of the member name and a later `>` would read as a type argument list, as they do when the `>` is followed by `(`; or when the member name, alone in parentheses, would read as the type of a cast, as `(A)` does when `(`, `!`, or `with` follows it. The diagnostic is still reported. Where the code the fix writes parses with the same operators and operands as the code it replaces, this requirement does not withhold the fix.

Why: `A < base.B` is a comparison only because `base.B` is not a simple name; `A < B, D > (7)` reads as the call of a generic method `A<B, D>`. Likewise `(base.A)(5)` invokes a delegate, while `(A)(5)` reads as a cast of `5` to a type `A`. Neither compiles (SHARED-FIX-003).

Example:

```csharp
class P
{
    protected int B;
}

class C : P
{
    int A;
    int D;

    void M(bool x, bool y)
    {
    }

    void Run()
    {
        M(A < {|RH3101:base|}.B, D > (7));
    }
}
```

is reported, and no code fix is offered. Neither is one offered where the member name in parentheses would read as a cast:

```csharp
using System;

class P
{
    protected Action<int> A;
}

class C : P
{
    void Run()
    {
        ({|RH3101:base|}.A)(5);
    }
}
```

is reported, and no code fix is offered.

### RH3101-006 — A comment between `base` and the member name withholds the fix

The code fix MUST NOT be offered when a comment or a preprocessor directive stands between `base` and the member name of a member access. The diagnostic is still reported. A comment in an element access, behind `base` and in front of `[`, MUST NOT withhold the fix and stays behind the `this` the fix writes.

Why: The fix keeps only the member name of a member access; a comment around the `.` it removes would be deleted (SHARED-FIX-003). In an element access, the fix replaces only the keyword, and the comment behind it stays where it is.

Example:

```csharp
class B
{
    public int M() => 1;
}

class D : B
{
    int Run()
    {
        return {|RH3101:base|} /* a */ . /* b */ M();
    }
}
```

is reported, and no code fix is offered. In an element access, the comment stays:

```csharp
class B
{
    public int this[int i] => i;
}

class D : B
{
    int Run()
    {
        return {|RH3101:base|} /* a */ [0];
    }
}
```

```csharp
class B
{
    public int this[int i] => i;
}

class D : B
{
    int Run()
    {
        return this /* a */ [0];
    }
}
```

### RH3101-007 — A virtual member in a type that is not sealed withholds the fix

The code fix MUST NOT be offered when the member the access binds to is virtual — declared `virtual`, or an `override` that is not `sealed` — and the type that contains the access is not sealed. The diagnostic is still reported. In a sealed type, and for a member that is not virtual or is a `sealed override`, this requirement does not withhold the fix.

Why: `base.M()` calls the base implementation without virtual dispatch; `M()` calls whichever override the runtime type of `this` has, and a type derived from one that is not sealed can override `M`. The fix would change what runs (SHARED-FIX-003). In a sealed type, no type can derive from it, and the type itself does not override the member (RH3101-002), so both calls reach the same implementation.

Example:

```csharp
class B
{
    public virtual int M() => 1;
}

class D : B
{
    int Run()
    {
        return {|RH3101:base|}.M();
    }
}
```

is reported, and no code fix is offered. In a sealed type, the fix removes the qualifier:

```csharp
class B
{
    public virtual int M() => 1;
}

sealed class D : B
{
    int Run()
    {
        return {|RH3101:base|}.M();
    }
}
```

```csharp
class B
{
    public virtual int M() => 1;
}

sealed class D : B
{
    int Run()
    {
        return M();
    }
}
```
