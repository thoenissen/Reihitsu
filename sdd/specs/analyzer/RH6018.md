# Analyzer — RH6018 Negative signs must be spaced correctly

| | |
|---|---|
| ID prefix | RH6018 |
| Status | Active |
| Category | Spacing |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH6018NegativeSignsMustBeSpacedCorrectlyAnalyzer`, `RH6018NegativeSignsMustBeSpacedCorrectlyCodeFixProvider` |
| Uses | FMT-CLEAN-001, FMT-SPACE-007, SHARED-WS-001, SHARED-WS-002 |

RH6018 reports whitespace directly after a unary minus, and offers a code fix that deletes it as SHARED-WS-001 and SHARED-WS-002 specify.

In the examples, `→` marks a tab and `·` a space at the end of a line.

## Non-goals

- The binary minus — RH6024.
- The unary plus — RH6019; the address-of and pointer-indirection operators — RH6020.
- The whitespace in front of a unary minus — the operator rules, such as RH6023 and RH6024, for the operator before it.

## Requirements

### RH6018-001 — Whitespace after a unary minus is reported

The analyzer MUST report the run of spaces and tabs directly after the operator of a unary minus expression when the run is followed by a token or by the end of the line. A unary minus directly followed by its operand or by a line break MUST NOT be reported.

Why: A sign belongs to the operand it negates; a space after it makes it read like a binary minus. The formatter removes the same whitespace — before a token on the same line (FMT-SPACE-007), at the end of the line (FMT-CLEAN-001) — so formatted code raises no RH6018 in these places.

Example:

```csharp
class C
{
    void M(int a)
    {
        var x = -{|RH6018: |}1;
        var y = -{|RH6018:→|}a;
        var u = -{|RH6018: |}(-a);
        var t = a - -{|RH6018: |}1;
        var s = $"{-{|RH6018: |}a}";
        var r = -{|RH6018:···|}
            a;
        var q = -
            a;
    }
}
```

### RH6018-002 — The space that keeps two minus signs apart is not reported

The analyzer MUST NOT report the whitespace after a unary minus whose operand starts with `-` or `--`, however much whitespace there is.

Why: Deleting it would make the lexer read `- -a` as the pre-decrement `--a` and `- --a` as `---a`, which changes the program. The formatter keeps that whitespace for the same reason (FMT-SPACE-007).

Example:

```csharp
class C
{
    void M(int a)
    {
        var x = - -a;
        var y = -  -a;
        var z = - --a;
    }
}
```

is not reported.

### RH6018-003 — One diagnostic per sign

The analyzer MUST report one diagnostic per unary minus, located on the whitespace run after it.

Why: The run is the text that is wrong and the text the fix deletes.

Example: see RH6018-001.

### RH6018-004 — The fix deletes the whitespace unless a comment is in the gap

The code fix MUST delete the reported whitespace as SHARED-WS-001 specifies, and MUST NOT be offered when a comment or directive sits between the sign and its operand, as SHARED-WS-002 specifies.

Why: A comment in the gap is the author's placement; the fix does not decide whether the deletion affects it.

Example:

```csharp
class C
{
    void M(int a)
    {
        var x = -{|RH6018: |}1;
        var y = -{|RH6018:→|}a;
        var u = -{|RH6018: |}(-a);
        var r = -{|RH6018:···|}
            a;
    }
}
```

```csharp
class C
{
    void M(int a)
    {
        var x = -1;
        var y = -a;
        var u = -(-a);
        var r = -
            a;
    }
}
```

A comment on the next line of the gap withholds the fix:

```csharp
class C
{
    void M(int a)
    {
        var x = -{|RH6018:·|}
            // the operand
            a;
    }
}
```

is reported, and no code fix is offered.
