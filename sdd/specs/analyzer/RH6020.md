# Analyzer — RH6020 Dereference and access-of symbols must be spaced correctly

| | |
|---|---|
| ID prefix | RH6020 |
| Status | Active |
| Category | Spacing |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH6020DereferenceAndAccessOfSymbolsMustBeSpacedCorrectlyAnalyzer`, `RH6020DereferenceAndAccessOfSymbolsMustBeSpacedCorrectlyCodeFixProvider` |
| Uses | FMT-CLEAN-001, FMT-SPACE-007, SHARED-WS-001, SHARED-WS-002 |

RH6020 reports whitespace directly after an address-of `&` or a pointer-indirection `*`, and offers a code fix that deletes it as SHARED-WS-001 and SHARED-WS-002 specify.

In the examples, `→` marks a tab and `·` a space at the end of a line.

## Non-goals

- The `*` of a pointer type, such as `int * p`, and the binary `&` and `*` — RH6024 for the binary operators; no analyzer rule checks the pointer type.
- The `->` of a pointer member access — RH6016.
- The unary minus and plus — RH6018 and RH6019.

## Requirements

### RH6020-001 — Whitespace after `&` or `*` of a pointer expression is reported

The analyzer MUST report the run of spaces and tabs directly after the operator of an address-of or a pointer-indirection expression when the run is followed by a token or by the end of the line. An operator directly followed by its operand or by a line break MUST NOT be reported.

Why: The operator belongs to the operand it takes the address of or dereferences; a space after it makes it read like a binary operator. The formatter removes the same whitespace — before a token on the same line (FMT-SPACE-007), at the end of the line (FMT-CLEAN-001) — so formatted code raises no RH6020 in these places.

Example:

```csharp
unsafe class C
{
    void M(int a, int* p, int** pp)
    {
        int* x = &{|RH6020: |}a;
        int y = *{|RH6020: |}p;
        int z = *{|RH6020:→|}p;
        int w = *{|RH6020: |}*pp;
        int* r = &{|RH6020: |}*p;
        int s = *{|RH6020: |}(p + 1);
        int t = *{|RH6020:···|}
            p;
        int u = *
            p;
    }
}
```

### RH6020-002 — The space that keeps two `&` apart is not reported

The analyzer MUST NOT report the whitespace after an address-of `&` whose operand starts with `&` or `&&`, however much whitespace there is.

Why: Deleting it would make the lexer read `& &a` as the logical-and operator `&&a`, and the code would no longer parse. The formatter keeps that whitespace for the same reason (FMT-SPACE-007).

Example:

```csharp
unsafe class C
{
    void M(int a)
    {
        int** q = & &a;
    }
}
```

is not reported. The code does not compile, because the address of an address cannot be taken; the rule still leaves it alone.

### RH6020-003 — One diagnostic per operator

The analyzer MUST report one diagnostic per address-of or pointer-indirection operator, located on the whitespace run after it.

Why: The run is the text that is wrong and the text the fix deletes.

Example: see RH6020-001.

### RH6020-004 — The fix deletes the whitespace unless a comment is in the gap

The code fix MUST delete the reported whitespace as SHARED-WS-001 specifies, and MUST NOT be offered when a comment or directive sits between the operator and its operand, as SHARED-WS-002 specifies.

Why: A comment in the gap is the author's placement; the fix does not decide whether the deletion affects it.

Example:

```csharp
unsafe class C
{
    void M(int a, int* p, int** pp)
    {
        int* x = &{|RH6020: |}a;
        int z = *{|RH6020:→|}p;
        int w = *{|RH6020: |}*pp;
    }
}
```

```csharp
unsafe class C
{
    void M(int a, int* p, int** pp)
    {
        int* x = &a;
        int z = *p;
        int w = **pp;
    }
}
```

A comment on the next line of the gap withholds the fix:

```csharp
unsafe class C
{
    void M(int* p)
    {
        int y = *{|RH6020:·|}
            // the pointer
            p;
    }
}
```

is reported, and no code fix is offered.
