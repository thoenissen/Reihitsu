# Analyzer — RH5110 Generic type constraints should be on their own line with proper indentation

| | |
|---|---|
| ID prefix | RH5110 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5110GenericTypeConstraintsShouldBeOnTheirOwnLineAnalyzer`, `RH5110GenericTypeConstraintsShouldBeOnTheirOwnLineCodeFixProvider` |
| Uses | FMT-BLANK-011, FMT-BREAK-001, FMT-BREAK-023, FMT-BREAK-037, FMT-INDENT-017, FMT-INDENT-032, FMT-UNSUP-009, SHARED-COMMENT-011, SHARED-FIX-003, SHARED-FIX-006, SHARED-FIX-010 |

RH5110 reports a generic constraint clause that does not start its own line one level deeper than its declaration, and offers a code fix that lays the constraint clauses out the way the formatter does.

## Non-goals

- Reporting line breaks inside a constraint clause, such as a wrap after `where T :`. The fix lays them out with the rest of the declaration (RH5110-003).
- The column of a constructor initializer — the formatter (FMT-INDENT-017).

## Requirements

### RH5110-001 — A constraint clause off its own line or column is reported

The analyzer MUST report the constraint clauses of a class, a struct, an interface, a record class, a union, a method, a delegate, or a local function when a `where` keyword follows the token in front of it on the same line, or starts a line with only whitespace in front of it in another column than four spaces right of the first token of the declaration. A declaration whose `where` keywords each start their own line in that column MUST NOT be reported. A line that starts with a comment is judged as SHARED-COMMENT-011 specifies.

Why: Constraints are part of the signature but not of its name or parameters; on their own lines, one level deeper than the declaration, they stay readable when there are several, and the body's braces stay at the declaration's column (FMT-BREAK-023, FMT-INDENT-017).

Example:

```csharp
class C<T> {|RH5110:where|} T : class
{
    void M<TKey, TValue>()
    {|RH5110:where|} TKey : notnull
    where TValue : class
    {
    }

    void N<TKey, TValue>()
        where TKey : notnull {|RH5110:where|} TValue : class
    {
    }

    void O<TKey>()
        where TKey : notnull
    {
    }
}

delegate void D<T>() {|RH5110:where|} T : class;
```

Example — a union, with and without a body:

```csharp
union U<T>(T, string) {|RH5110:where|} T : class;

union V<T>(T, string)
    where T : class
{
    public int X => 1;
}
```

### RH5110-002 — One diagnostic per declaration, on the first misplaced clause

The analyzer MUST report at most one diagnostic per declaration, located on the `where` keyword of its first constraint clause that is misplaced. Later misplaced clauses of the same declaration MUST NOT be reported on their own.

Why: The fix lays out every clause of the declaration at once, so one diagnostic per declaration matches one fix; the first misplaced clause is where the reader's eye stops.

Example:

```csharp
class C
{
    void M<TKey, TValue>() {|RH5110:where|} TKey : notnull where TValue : class
    {
    }
}
```

### RH5110-003 — The fix puts each constraint clause on its own line

The code fix MUST format the declaration that owns the reported clause as the formatter formats it in place, which starts every `where` clause on a line of its own, indented one level deeper than the declaration (FMT-BREAK-023, FMT-INDENT-017), and lays out the constraints of each clause (FMT-BREAK-037, FMT-INDENT-032). Where a comment, a directive, or disabled text in a clause blocks a join that FMT-BREAK-037 would make, the fix MUST still be offered, and its result is the layout the formatter gives that clause: the blocked line break stays, and the lines it leaves are placed as FMT-INDENT-032 states. Where the formatter refuses the declaration as unsupported, the fix is withheld and the diagnostic stays (SHARED-FIX-010) — for example for a comment, a directive, or disabled text between a constraint and a comma on a later line (FMT-UNSUP-009).

Why: The formatter owns the layout of a declaration's header; delegating to it applies that layout instead of a second one. The formatter never joins across a comment, a directive, or disabled text (FMT-BREAK-001), so its layout moves none of them, and SHARED-FIX-003 gives no reason to withhold the fix.

Example:

```csharp
class C
{
    void M<TKey, TValue>() {|RH5110:where|} TKey : notnull where TValue : class
    {
    }

    void N<TKey>()
            {|RH5110:where|} TKey : notnull
    {
    }
}
```

```csharp
class C
{
    void M<TKey, TValue>()
        where TKey : notnull
        where TValue : class
    {
    }

    void N<TKey>()
        where TKey : notnull
    {
    }
}
```

Example — a comment that leads the declaration stays as written (SHARED-FIX-006):

```csharp
class C
{
    int _a;
    // c
    void M<T>() {|RH5110:where|} T : class
    {
    }
}
```

```csharp
class C
{
    int _a;
    // c
    void M<T>()
        where T : class
    {
    }
}
```

Formatting the document would also insert a blank line above `// c` (FMT-BLANK-011).

Example — a comment behind the colon keeps its line break, and the fix lays out the lines around it:

```csharp
class C
{
    void M<T>() {|RH5110:where|} T : // c
        class, new()
    {
    }
}
```

```csharp
class C
{
    void M<T>()
        where T : // c
                  class,
                  new()
    {
    }
}
```

Example — a comment in front of a comma on a later line is a shape the formatter refuses (FMT-UNSUP-009); the clause is reported, and no code fix is offered:

```csharp
class C
{
    void N<T>() {|RH5110:where|} T : class // c
        , new()
    {
    }
}
```
