# Analyzer — RH7309 Regions should follow a fixed category order

| | |
|---|---|
| ID prefix | RH7309 |
| Status | Active |
| Category | Organization |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH7309RegionsShouldFollowCategoryOrderAnalyzer`, `RH7309RegionsShouldFollowCategoryOrderCodeFixProvider`, `RegionCategoryUtilities` |
| Uses | SHARED-DOC-004, SHARED-FIX-003, SHARED-ORDER-007, SHARED-REGDESC-001, SHARED-TYPEREGION-006 |

RH7309 reports a top-level region of a type that belongs to an earlier category than a region before it — custom regions first, then base-type override regions, then interface implementation regions — and offers a code fix that reorders the type's regions by category.

## Non-goals

- The order of the regions within one category, and which members belong in a base-type or interface region — the RH74xx rules.
- The members outside every region. They stay where they are.

## Requirements

### RH7309-001 — A region's category comes from its description

The analyzer MUST give each top-level region (SHARED-TYPEREGION-006) of a type the interface category when its description (SHARED-REGDESC-001) equals, compared ordinally, the name of an interface the type implements — directly or through a base type or another interface — without its type arguments. Otherwise it MUST give the region the base-type category when the description equals the name of a type in the type's base-type chain, `Object` included. Every other region, one without a description included, MUST get the custom category.

Why: A region named after an interface conventionally groups that interface's implementation, and one named after a base type groups the members that override it; any other name describes the type's own surface. The name is compared exactly because it is a type name, and an interface wins over a base type because the members implementing it are what the region exists for.

Example — `IComparable` is an interface region, `Object` a base-type region, and `Methods` a custom region:

```csharp
using System;

public class C : IComparable<C>
{
    #region IComparable

    public int CompareTo(C other) => 0;

    #endregion // IComparable

    {|RH7309:#region Object|}

    public override string ToString() => "";

    #endregion // Object

    {|RH7309:#region Methods|}

    public void M()
    {
    }

    #endregion // Methods
}
```

and a description that differs in case, or none, is custom:

```csharp
using System;

public class C : IDisposable
{
    #region IDisposable

    public void Dispose()
    {
    }

    #endregion // IDisposable

    {|RH7309:#region idisposable|}

    private int _a;

    #endregion // idisposable

    {|RH7309:#region|}

    private int _b;

    #endregion
}
```

### RH7309-002 — A region after a region of a later category is reported

For every class, struct, record, and record struct declaration with at least two top-level regions, the analyzer MUST report each top-level region whose category comes before the category of an earlier top-level region of the same declaration, in the order custom, base-type, interface. It MUST NOT check the regions of an interface declaration.

Why: A predictable layout lets the reader find the type's own surface first, then what it overrides, then what it fulfills. Comparing with every earlier region reports each region that breaks the order, not only the first one. An interface has no base class, and the members of the interfaces it extends are not implemented in it the way a class implements them, so the categories that order a class's regions do not apply.

Example:

```csharp
using System;

public struct S : IDisposable
{
    #region IDisposable

    public void Dispose()
    {
    }

    #endregion // IDisposable

    {|RH7309:#region Methods|}

    public void M()
    {
    }

    #endregion // Methods
}
```

while the same regions in an interface are not reported:

```csharp
using System;

public interface I : IDisposable
{
    #region IDisposable

    void Close();

    #endregion // IDisposable

    #region Methods

    void M();

    #endregion // Methods
}
```

### RH7309-003 — The diagnostic is on the `#region`

The analyzer MUST report one diagnostic per reported region, located on its `#region` directive from the `#` to the end of its line.

Why: The `#region` line carries the name that decides the category, and it is where the region block starts that has to move.

Example: see RH7309-001.

### RH7309-004 — The fix orders the type's regions by category

For a type declaration whose body holds no comment outside its top-level region blocks, and for which neither RH7309-005 nor RH7309-006 withholds the fix, the code fix MUST reorder all top-level region blocks of the declaration by category, keeping the written order of the blocks within a category. A block reaches from the start of its `#region` line to the end of its `#endregion` line. The code between two blocks, and before the first and after the last, MUST stay in place. One application MUST correct every diagnostic of the type.

Why: Ordering whole blocks keeps every member in the region its author chose. Keeping the written order within a category leaves that order to the rules that own it, and keeping the code between blocks in place keeps members outside regions where they were.

Example:

```csharp
using System;

public class C : IDisposable
{
    #region IDisposable

    public void Dispose()
    {
    }

    #endregion // IDisposable

    private int _between;

    {|RH7309:#region Fields|}

    private int _a;

    #endregion // Fields
}
```

```csharp
using System;

public class C : IDisposable
{
    #region Fields

    private int _a;

    #endregion // Fields

    private int _between;

    #region IDisposable

    public void Dispose()
    {
    }

    #endregion // IDisposable
}
```

### RH7309-005 — The fix is withheld when a directive would be moved across

The code fix MUST NOT be offered when a region block, or the code between two consecutive region blocks, contains an `#if` or `#endif` whose partner lies outside that span, an `#elif` or `#else` outside any `#if` of that span, or a directive that is neither a conditional nor a region directive, such as `#pragma` or `#nullable`. The diagnostic is still reported. A conditional pair that lies wholly inside one span does not withhold the fix.

Why: Moving a block across such a directive changes which code the directive governs, or tears a conditional pair apart so the file no longer compiles. A complete pair moves with its block or stays between blocks, so the code it governs is the same afterwards.

Example:

```csharp
using System;

public class C : IDisposable
{
    #region IDisposable

    public void Dispose()
    {
    }

    #endregion // IDisposable

#pragma warning disable CS0169
    {|RH7309:#region Fields|}

    private int _a;

    #endregion // Fields
#pragma warning restore CS0169
}
```

is reported, and no code fix is offered. A balanced pair inside a block does not withhold it:

```csharp
using System;

public class C : IDisposable
{
    #region IDisposable

    public void Dispose()
    {
#if DEBUG
        Console.WriteLine();
#endif
    }

    #endregion // IDisposable

    {|RH7309:#region Methods|}

    public void M()
    {
    }

    #endregion // Methods
}
```

```csharp
using System;

public class C : IDisposable
{
    #region Methods

    public void M()
    {
    }

    #endregion // Methods

    #region IDisposable

    public void Dispose()
    {
#if DEBUG
        Console.WriteLine();
#endif
    }

    #endregion // IDisposable
}
```

### RH7309-006 — The fix is withheld when the reorder would change the program or separate a comment

The code fix MUST NOT be offered when reordering the blocks as RH7309-004 states would, in the type's body:

- put two members of one context — both static or both instance — that each have a runtime initializer, as SHARED-ORDER-007 counts them, into the other order, also when one of the two lies in the code between blocks, which keeps its place;
- put two instance fields of a type whose field order sets its layout (SHARED-FIX-003) into the other order;
- move a block away from a comment that stands directly above its `#region` line, with no blank line between them; or
- change which declaration a documentation comment documents (SHARED-DOC-004), when the documentation mode of the syntax tree is `Parse` or `Diagnose`.

The diagnostic is still reported. A comment directly above the `#region` line of a block that keeps its position is not covered by this requirement.

Why: These are the reorders that SHARED-FIX-003 forbids for this fix. Initializers of one context run in declaration order, so swapping the blocks that hold them changes the values the program computes, and the order of the instance fields of a struct is its memory layout. A comment directly above a `#region` line heads the block, and the fix moves the block without it, so the comment would head another block. A documentation comment in front of a `#region`, or behind the last code of a block, documents the first declaration after it, and moving the blocks hands it to another declaration. Where the comment should go then is the author's decision.

Example — an initializer that reads a field of a block it would cross:

```csharp
using System;

public class C : IComparable
{
    #region IComparable

    private static readonly int Y = X + 1;

    public int CompareTo(object obj) => Y;

    #endregion // IComparable

    {|RH7309:#region Fields|}

    private static readonly int X = 5;

    #endregion // Fields
}
```

is reported, and no code fix is offered: moving `Fields` in front would run `X = 5` before `Y = X + 1`, so `Y` would be `6` instead of `1`.

Example — the instance fields of a struct:

```csharp
using System;

public struct S : IDisposable
{
    #region IDisposable

    private int _handle;

    public void Dispose()
    {
    }

    #endregion // IDisposable

    {|RH7309:#region Fields|}

    private int _a;

    #endregion // Fields
}
```

is reported, and no code fix is offered: moving `Fields` in front would put `_a` in front of `_handle` and change the struct's layout.

Example — a comment directly above a block the fix would move:

```csharp
using System;

public class C : IDisposable
{
    // The disposal logic
    #region IDisposable

    public void Dispose()
    {
    }

    #endregion // IDisposable

    {|RH7309:#region Fields|}

    private int _a;

    #endregion // Fields
}
```

is reported, and no code fix is offered: the comment would stay in place and head the `Fields` block.

Example — documentation that the reorder would hand to another declaration, in the documentation mode `Parse` or `Diagnose`. In each of the three bodies, the `///` comment documents `M`:

```csharp
using System;

public class C : IDisposable
{
    #region IDisposable

    public void Dispose()
    {
    } /// <summary>M</summary>

    #endregion // IDisposable

    {|RH7309:#region Methods|}

    public void M()
    {
    }

    #endregion // Methods
}
```

```csharp
using System;

public class C : IDisposable
{
    #region IDisposable

    public void Dispose()
    {
    }

    #endregion // IDisposable

    /// <summary>M</summary>
    {|RH7309:#region Methods|}

    public void M()
    {
    }

    #endregion // Methods
}
```

```csharp
using System;

public class C : IDisposable
{
    #region IDisposable

    public void Dispose()
    {
    }

    /// <summary>M</summary>
    #endregion // IDisposable

    {|RH7309:#region Methods|}

    public void M()
    {
    }

    #endregion // Methods
}
```

Each is reported, and no code fix is offered. In the documentation mode `None`, the `///` comment behind the closing brace of `Dispose` in the first body is an ordinary comment behind that brace (SHARED-DOC-004), it moves with the `IDisposable` block, and the fix is offered:

```csharp
using System;

public class C : IDisposable
{
    #region Methods

    public void M()
    {
    }

    #endregion // Methods

    #region IDisposable

    public void Dispose()
    {
    } /// <summary>M</summary>

    #endregion // IDisposable
}
```
