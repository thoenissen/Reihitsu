# Analyzer — RH7309 Regions should follow a fixed category order

| | |
|---|---|
| ID prefix | RH7309 |
| Status | Active |
| Category | Organization |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH7309RegionsShouldFollowCategoryOrderAnalyzer`, `RH7309RegionsShouldFollowCategoryOrderCodeFixProvider`, `RegionCategoryUtilities` |
| Uses | FMT-PIPE-007, SHARED-DOC-004, SHARED-FIX-003, SHARED-FIX-008, SHARED-ORDER-007, SHARED-ORDER-008, SHARED-ORDER-011, SHARED-REGDESC-001, SHARED-TYPEREGION-006 |

RH7309 reports a top-level region of a type that belongs to an earlier category than a region before it — custom regions first, then base-type override regions, then interface implementation regions — and offers a code fix that reorders the type's regions by category.

## Non-goals

- The order of the regions within one category, and which members belong in a base-type or interface region — the RH74xx rules.
- The members outside every region. They stay where they are.

## Requirements

### RH7309-001 — A region's category comes from its description

The analyzer MUST give each top-level region (SHARED-TYPEREGION-006) of a type the interface category when its description (SHARED-REGDESC-001) equals, compared ordinally, the name of an interface the type implements — directly or through a base type or another interface — without its type arguments. Otherwise it MUST give the region the base-type category when the description equals the name of a type in the type's base-type chain, `Object` included. Every other region, one without a description included, MUST get the custom category.

Why: A region named after an interface conventionally groups that interface's implementation, and one named after a base type groups the members that override it; any other name describes the type's own surface. The name is compared exactly because it is a type name, and an interface wins over a base type because the members implementing it are what the region exists for.

Example — `IComparable` is an interface region, `Object` a base-type region, and `Methods` a custom region:

```csharp
using System;

public class C : IComparable<C>
{
    #region IComparable

    public int CompareTo(C other) => 0;

    #endregion // IComparable

    {|RH7309:#region Object|}

    public override string ToString() => "";

    #endregion // Object

    {|RH7309:#region Methods|}

    public void M()
    {
    }

    #endregion // Methods
}
```

and a description that differs in case, or none, is custom:

```csharp
using System;

public class C : IDisposable
{
    #region IDisposable

    public void Dispose()
    {
    }

    #endregion // IDisposable

    {|RH7309:#region idisposable|}

    private int _a;

    #endregion // idisposable

    {|RH7309:#region|}

    private int _b;

    #endregion
}
```

### RH7309-002 — A region after a region of a later category is reported

For every class, struct, record, record struct, and union declaration with at least two top-level regions, the analyzer MUST report each top-level region whose category comes before the category of an earlier top-level region of the same declaration, in the order custom, base-type, interface. It MUST NOT check the regions of an interface declaration.

The analyzer MUST judge the regions as the active build configuration leaves them. A top-level region whose `#region` lies in a branch — `#if`, `#elif`, or `#else` — of a conditional directive that the configuration excludes MUST NOT be reported and MUST NOT count as an earlier region. A region in the branch the configuration compiles is checked like any other top-level region: against the regions outside every branch and against the earlier regions of its own branch. Two regions in different branches of one conditional directive are therefore never compared (SHARED-TYPEREGION-006).

Why: A predictable layout lets the reader find the type's own surface first, then what it overrides, then what it fulfills. Comparing with every earlier region reports each region that breaks the order, not only the first one. An interface has no base class, and the members of the interfaces it extends are not implemented in it the way a class implements them, so the categories that order a class's regions do not apply. A build compiles one branch of a conditional directive, so the outline it shows holds the regions of that branch and of no other; a region of an excluded branch is no part of the outline the analyzer judges, while a region of the compiled branch stands in one outline with the regions around it.

Example:

```csharp
using System;

public struct S : IDisposable
{
    #region IDisposable

    public void Dispose()
    {
    }

    #endregion // IDisposable

    {|RH7309:#region Methods|}

    public void M()
    {
    }

    #endregion // Methods
}
```

while the same regions in an interface are not reported:

```csharp
using System;

public interface I : IDisposable
{
    #region IDisposable

    void Close();

    #endregion // IDisposable

    #region Methods

    void M();

    #endregion // Methods
}
```

Example — regions in the `#if` and the `#else` branch of one conditional directive:

```csharp
using System;

public class C : IDisposable
{
    public void Dispose()
    {
    }

#if DEBUG
    #region IDisposable

    private int _a;

    #endregion
#else
    #region Fields

    private int _b;

    #endregion
#endif
}
```

is not reported, whether `DEBUG` is defined or not: each configuration compiles one of the two regions.

Example — a region in a branch after a region outside every branch:

```csharp
using System;

public class C : IDisposable
{
    #region IDisposable

    public void Dispose()
    {
    }

    #endregion

#if DEBUG
    {|RH7309:#region Diagnostics|}

    private int _calls;

    #endregion
#endif
}
```

is reported where `DEBUG` is defined, and no code fix is offered (RH7309-005: the `#if` between the two blocks has its `#endif` outside that span). Where `DEBUG` is not defined, the `Diagnostics` region lies in an excluded branch, and nothing is reported.

Example — a union is checked like a struct:

```csharp
using System;

public union U(int, string) : IComparable
{
    #region IComparable

    public int CompareTo(object o)
    {
        return 0;
    }

    #endregion // IComparable

    {|RH7309:#region Methods|}

    public void M()
    {
    }

    #endregion // Methods
}
```

### RH7309-003 — The diagnostic is on the `#region`

The analyzer MUST report one diagnostic per reported region, located on its `#region` directive from the `#` to the end of its line.

Why: The `#region` line carries the name that decides the category, and it is where the region block starts that has to move.

Example: see RH7309-001.

### RH7309-004 — The fix orders the type's regions by category

For a type declaration whose body holds no comment outside its top-level region blocks other than comments above a block's `#region` line, with nothing but blank lines between the comment and that line, and for which neither RH7309-005 nor RH7309-006 withholds the fix, the code fix MUST reorder all top-level region blocks of the declaration by category, keeping the written order of the blocks within a category. A block reaches from the start of its `#region` line to the end of its `#endregion` line. The code between two blocks, and before the first and after the last, MUST stay in place, so a comment above the `#region` line of a block that keeps its place among the blocks stays above that block. One application MUST correct every diagnostic of the type. The blocks are all top-level regions of the declaration, also one whose `#region` lies in a branch the active configuration excludes (RH7309-002): such a region is not reported and not compared, but it is a block, and the conditional directive around it lies outside it, so RH7309-005 withholds the fix (example there).

Why: Ordering whole blocks keeps every member in the region its author chose. Keeping the written order within a category leaves that order to the rules that own it, and keeping the code between blocks in place keeps members outside regions where they were.

Example:

```csharp
using System;

public class C : IDisposable
{
    #region IDisposable

    public void Dispose()
    {
    }

    #endregion // IDisposable

    private int _between;

    {|RH7309:#region Fields|}

    private int _a;

    #endregion // Fields
}
```

```csharp
using System;

public class C : IDisposable
{
    #region Fields

    private int _a;

    #endregion // Fields

    private int _between;

    #region IDisposable

    public void Dispose()
    {
    }

    #endregion // IDisposable
}
```

### RH7309-005 — The fix is withheld when a directive would be moved across

The code fix MUST NOT be offered when a region block, or the code between two consecutive region blocks, contains an `#if` or `#endif` whose partner lies outside that span, an `#elif` or `#else` outside any `#if` of that span, or a directive that is neither a conditional nor a region directive, such as `#pragma` or `#nullable`, other than a `#pragma warning` or `#nullable` pair that SHARED-ORDER-011 keeps. The code fix MUST NOT be offered either when SHARED-ORDER-008 refuses the reorder, with every region block and every piece of code between two consecutive blocks that a block is moved across as its moved and crossed spans (SHARED-ORDER-008 states which those are): every `#if`, `#elif`, `#else`, or `#endif` there withholds the fix, also one of a pair that lies wholly inside one block, and also one inside a block that keeps its place among the blocks while other blocks are moved across it. The diagnostic is still reported. A conditional pair that lies wholly inside a block, or wholly inside code between blocks, that no block is moved across does not withhold the fix — such as one in the last block when the blocks in front of it are reordered among themselves, or one between two pairs of blocks that are each reordered on their own side — unless the reorder puts instance fields into the other order and the pair stands in front of the last block or piece of code between blocks of the spans that holds an instance field (SHARED-ORDER-008, *In the reordered body, in front of the moved fields*). Neither does a `#pragma warning` or `#nullable` pair that SHARED-ORDER-011 keeps inside one member of any block or of the code between two blocks, whether or not the reorder changes the place of that block.

Why: Moving a block across such a directive changes which code the directive governs, or tears a conditional pair apart so the file no longer compiles. A complete pair moves with its block or stays between blocks, so the code it governs is the same afterwards. A conditional group in a block that moves is refused all the same, because the reorder's guards would otherwise have to read the group's excluded code as members (SHARED-ORDER-008). A block that keeps its place while blocks are moved across it is refused as well: its members change their order against the members of those blocks, so whether its group adds or changes a member that matters to that order needs the excluded code read just the same. Code that no block is moved across keeps its order against every other member.

Example:

```csharp
using System;

public class C : IDisposable
{
    #region IDisposable

    public void Dispose()
    {
    }

    #endregion // IDisposable

#pragma warning disable CS0169
    {|RH7309:#region Fields|}

    private int _a;

    #endregion // Fields
#pragma warning restore CS0169
}
```

is reported, and no code fix is offered. A conditional pair inside a block whose place the fix changes withholds it as well (SHARED-ORDER-008):

```csharp

{

    public void Dispose()
    {
#if DEBUG
        Console.WriteLine();
#endif
    }

    #endregion // IDisposable

    {|RH7309:#region Methods|}

    public void M()
    {
    }

    #endregion // Methods
}
```

is reported, and no code fix is offered. The same pair inside a block that keeps its place, and that no block is moved across, does not withhold it:

```csharp
using System;

public class C : IDisposable, IComparable
{
    #region IDisposable

    public void Dispose()
    {
    }

    #endregion // IDisposable

    {|RH7309:#region Methods|}

    public void M()
    {
    }

    #endregion // Methods

    #region IComparable

    public int CompareTo(object obj)
    {
#if DEBUG
        Console.WriteLine();
#endif
        return 0;
    }

    #endregion // IComparable
}
```

```csharp

{
    #region Methods

    }

    #endregion // Methods

    #region IDisposable

    public void Dispose()
    {
    }

    #endregion // IDisposable

    #region IComparable

    public int CompareTo(object obj)

#if DEBUG
```

A conditional pair inside a block that keeps its place withholds the fix when blocks are moved across that block. Here the blocks are reordered from `IDisposable`, `Object`, `Methods` to `Methods`, `Object`, `IDisposable`, so `Object` keeps its place, and the other two are moved across it:

### RH7309-006 — The fix is withheld when the reorder would change the program or separate a comment

The code fix MUST NOT be offered when reordering the blocks as RH7309-004 states would, in the type's body:

- put two members of one context — both static or both instance — that each have a runtime initializer, as SHARED-ORDER-007 counts them, into the other order, also when one of the two lies in the code between blocks, which keeps its place;
- put two instance fields of a type whose field order sets its layout (SHARED-FIX-003) into the other order;
- move a block away from a comment above its `#region` line, with nothing but blank lines between the comment and that line — a block moves when its place among the blocks changes; or
- change which declaration a documentation comment documents (SHARED-DOC-004), when the documentation mode of the syntax tree is `Parse` or `Diagnose`.

The diagnostic is still reported. A comment above the `#region` line of a block that keeps its place does not withhold the fix (RH7309-004).

Why: These are the reorders that SHARED-FIX-003 forbids for this fix. Initializers of one context run in declaration order, so swapping the blocks that hold them changes the values the program computes, and the order of the instance fields of a struct is its memory layout. A comment above a `#region` line heads the block, also with a blank line below it, and the fix moves the block without it, so the comment would head another block; a block that keeps its place keeps its comment. A documentation comment in front of a `#region`, or behind the last code of a block, documents the first declaration after it, and moving the blocks hands it to another declaration. Where the comment should go then is the author's decision.

Example — an initializer that reads a field of a block it would cross:

```csharp
using System;

public class C : IComparable
{
    #region IComparable

    private static readonly int Y = X + 1;

    public int CompareTo(object obj) => Y;

    #endregion // IComparable

    {|RH7309:#region Fields|}

    private static readonly int X = 5;

    #endregion // Fields
}
```

is reported, and no code fix is offered: moving `Fields` in front would run `X = 5` before `Y = X + 1`, so `Y` would be `6` instead of `1`.

Example — the instance fields of a struct:

```csharp
using System;

public struct S : IDisposable
{
    #region IDisposable

    private int _handle;

    public void Dispose()
    {
    }

    #endregion // IDisposable

    {|RH7309:#region Fields|}

    private int _a;

    #endregion // Fields
}
```

is reported, and no code fix is offered: moving `Fields` in front would put `_a` in front of `_handle` and change the struct's layout.

An auto-property has a backing field, which counts like a declared field (SHARED-FIX-003):

### RH7309-007 — The fix is withheld when a moved block holds another line ending

The code fix MUST NOT be offered when a region block whose place among the blocks changes — from the start of its `#region` line to the end of its `#endregion` line, the line break that ends that line included — holds a line break other than the line ending SHARED-FIX-008 detects for the document, also one inside a literal or inside the text of a comment. The fix moves its blocks as written, without the formatter, as the second paragraph of SHARED-FIX-008 states for such moves. The diagnostic is still reported. A block that keeps its place among the blocks, and the code between the blocks, are not moved, and a line break in them does not withhold the fix. In a document whose line breaks are all a lone `\r`, the detected line ending is `\n`, so the fix is withheld wherever a block moves. A document whose line breaks are all LF, or all CRLF, keeps the fix.

Why: The fix keeps each moved block's text as written, so rewriting a foreign line break inside it would be the one change of layout the move makes; a document with mixed or lone `\r` line breaks is rare, the formatter normalizes it (FMT-PIPE-007), and the check is a cheap look at the line breaks of the moved blocks, as for the other fixes that move code without the formatter.

Example — the input of RH7309-004 in a document whose line breaks are CRLF, except the line break behind `private int _a;`, which is LF: the `Fields` block moves and holds the LF, so the diagnostic is reported and no code fix is offered. With that LF behind `private int _between;` instead, which stays between the blocks, the fix is offered and gives the output of RH7309-004, every line break CRLF but that one. In a document whose line breaks are all a lone `\r`, the same input is reported and no code fix is offered.
