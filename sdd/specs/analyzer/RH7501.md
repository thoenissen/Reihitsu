# Analyzer — RH7501 Break statements should not be inside explicit switch case blocks

| | |
|---|---|
| ID prefix | RH7501 |
| Status | Active |
| Category | Organization |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH7501BreakStatementsShouldNotBeInsideExplicitSwitchCaseBlocksAnalyzer`, `RH7501BreakStatementsShouldNotBeInsideExplicitSwitchCaseBlocksCodeFixProvider` |
| Uses | FMT-SWITCH-002, SHARED-FIX-003 |

RH7501 reports the `break` that ends a switch section when it is the last statement of a block that ends the section. Its code fix moves the `break` behind the block's closing brace.

## Non-goals

- Wrapping the statements of a switch section in a block — the formatter (FMT-SWITCH-001), which keeps an existing block as written (FMT-SWITCH-009).
- Blank lines in front of the terminal `break` — SHARED-BLANK-004.
- Switch expressions, which have no `break`.

## Requirements

### RH7501-001 — A `break` that ends a section's block is reported

The analyzer MUST report a `break` statement when all of the following hold:

- it is the last statement of a block;
- that block is a statement owned directly by a switch section, not a block nested in another statement or block of the section;
- that block is the last statement of the section, whatever statements precede it.

Why: The braces of a section's block scope its locals; the `break` ends the section. Written inside the braces, the `break` reads as one more statement of the scoped work, and the reader has to find the closing brace to see that the section ends there. Behind the brace, the section has the shape the formatter gives every section it braces (FMT-SWITCH-002): the scoped work, then the end of the section.

Example:

```csharp
class C
{
    void M(int x)
    {
        switch (x)
        {
            case 1:
                {
                    A();
                    {|RH7501:break|};
                }

            case 2:
                A();
                {
                    A();
                    {|RH7501:break|};
                }
        }
    }

    void A()
    {
    }
}
```

while a `break` that is not the block's last statement, a block that is not the section's last statement, a block nested in the section's block, and a `break` of a loop inside the block:

```csharp
class C
{
    void M(int x)
    {
        switch (x)
        {
            case 1:
                {
                    break;
                    A();
                }

            case 2:
                {
                    A();
                    break;
                }
                A();

            case 3:
                {
                    {
                        A();
                        break;
                    }
                }

            case 4:
                {
                    while (true)
                    {
                        break;
                    }
                }
                break;
        }
    }

    void A()
    {
    }
}
```

are not reported.

### RH7501-002 — Other statements that end a section's block are not reported

The analyzer MUST NOT report a `return`, `throw`, `continue`, `goto`, or `yield break` statement, `goto case` and `goto default` included, that ends a section's block, and MUST NOT report a `break` that already follows the block.

Why: Any jump statement other than `break` is the last piece of the section's logic and belongs with the code it ends, as in the sections the formatter braces (FMT-SWITCH-002). A `break` behind the block already has the shape the rule asks for.

Example:

```csharp
class C
{
    int M(int x)
    {
        switch (x)
        {
            case 1:
                {
                    A();

                    return 1;
                }

            case 2:
                {
                    A();

                    goto case 1;
                }

            case 3:
                {
                    A();
                }
                break;
        }

        return 0;
    }

    void A()
    {
    }
}
```

and in an iterator:

```csharp
using System.Collections.Generic;

class C
{
    IEnumerable<int> M(int x)
    {
        switch (x)
        {
            case 1:
                {
                    yield return 1;
                    yield break;
                }
        }
    }
}
```

are not reported.

### RH7501-003 — The diagnostic is on the `break` keyword

The analyzer MUST report one diagnostic per reported `break` statement, located on its `break` keyword.

Why: The keyword is the token the fix moves, and one diagnostic per section lets each section be corrected on its own.

Example: see RH7501-001.

### RH7501-004 — The fix moves the `break` behind the block

When all of the following hold, the code fix MUST remove the `break` from the block and add it to the section behind the block, as the section's last statement, on a line of its own and indented with the whitespace in front of the block's closing brace:

- no blank line lies between the `break` and the token in front of it — the last token of the statement in front of the `break`, or the block's opening brace when the `break` is the block's only statement;
- the `break` is the first statement on its line, and the block's closing brace is the first token on its line;
- no preprocessor directive and no code that `#if` excludes lies between the token in front of the `break` and the block's closing brace.

The comments on the lines in front of the `break` and a comment behind it on its line MUST move with it. The fix MUST leave the rest of the switch as it is laid out, also when that layout is not the one the formatter produces. A block that the fix leaves empty MUST stay.

When the second or the third condition does not hold, the code fix MUST NOT be offered; the diagnostic is still reported. This requirement does not decide the fix for a `break` with a blank line in front of it.

Why: The `break` keeps ending the same section and only changes sides of the brace, so the program does not change. Lining it up with the brace gives the section the shape of FMT-SWITCH-002. A comment about the `break` belongs with it. Laying out the rest of the switch is not the rule's concern. An empty block stays, because the user wrote it, and removing it is not what the diagnostic names. A `break` that shares its line with other code cannot move without rearranging that line, and a directive or excluded code between the `break` and the closing brace would be separated from the `break`, its partner, or the code it governs, or would change what runs in another build; the fix would break the code or change the program (SHARED-FIX-003), so the user moves such a `break` by hand.

Example:

```csharp
class C
{
    void M(int x)
    {
        switch (x)
        {
            case 1:
                {
                    A();
                    // leave the section
                    {|RH7501:break|}; // done
                }

            case 2:
            {
                A();
                {|RH7501:break|};
            }
        }
    }

    void A()
    {
    }
}
```

```csharp
class C
{
    void M(int x)
    {
        switch (x)
        {
            case 1:
                {
                    A();
                }
                // leave the section
                break; // done

            case 2:
            {
                A();
            }
            break;
        }
    }

    void A()
    {
    }
}
```

The `break` as the block's only statement leaves the block empty, and the block stays:

```csharp
class C
{
    void M(int x)
    {
        switch (x)
        {
            case 1:
                {
                    {|RH7501:break|};
                }
        }
    }
}
```

```csharp
class C
{
    void M(int x)
    {
        switch (x)
        {
            case 1:
                {
                }
                break;
        }
    }
}
```

A `break` that shares its line with other code, and a block whose closing brace shares its line with the `break`:

```csharp
class C
{
    void M(int x)
    {
        switch (x)
        {
            case 1: { A(); {|RH7501:break|}; }

            case 2:
                {
                    A(); /* first */ {|RH7501:break|};
                }

            case 3:
                {
                    A();
                    {|RH7501:break|}; }
        }
    }

    void A()
    {
    }
}
```

are reported, and no code fix is offered. Neither is one when a directive lies between the `break` and the closing brace, or between the statement in front of the `break` and the `break`:

```csharp
class C
{
    void M(int x)
    {
        switch (x)
        {
            case 1:
                {
                    var y = 1;
#if DEBUG
                    A(y);
#endif
                    {|RH7501:break|};
                }

            case 2:
                {
                    A(0);
                    #region Exit
                    {|RH7501:break|};
                    #endregion
                }
        }
    }

    void A(int y)
    {
    }
}
```

The SHARED-FIX-003 examples show two more: a `#pragma` pair around the `break`, and code of another build configuration behind it.
