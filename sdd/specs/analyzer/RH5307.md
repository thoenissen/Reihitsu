# Analyzer — RH5307 Indexer bracketed arguments should be single lined

| | |
|---|---|
| ID prefix | RH5307 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5307IndexerBracketedArgumentsShouldBeSingleLinedAnalyzer`, `RH5307IndexerBracketedArgumentsShouldBeSingleLinedCodeFixProvider` |
| Uses | FMT-BREAK-001, FMT-BREAK-014 |

RH5307 reports the argument list of an element access (`m[1, 2]`) whose brackets are on different lines, and offers a code fix that joins it onto one line the way the formatter does.

## Non-goals

- Bracketed lists that are not the arguments of an element access, such as attribute lists, array rank specifiers, collection expressions, and list patterns.
- Parenthesized argument lists — RH5101 and RH5102.

## Requirements

### RH5307-001 — A wrapped element access is reported

The analyzer MUST report the bracketed argument list of an element access (`m[…]`) and of an implicit element access inside an object initializer (`[…] = value`) when its opening and its closing bracket are on different lines, provided that no comment and no preprocessor directive sits between the two brackets and that every argument is on one line. An argument list on one line MUST NOT be reported, and a comment behind the closing bracket MUST NOT keep the argument list from being reported.

Why: An index is short by nature and reads as part of the access expression; wrapping it breaks up the expression without making it clearer (FMT-BREAK-014).

Example:

```csharp
using System.Collections.Generic;

class C
{
    void M(int[,] m)
    {
        var a = {|RH5307:m[1,
                  2]|};
        var b = {|RH5307:m[1,
                  2]|}; // note
        var c = m[1, 2];
        var d = new Dictionary<int, int>
                {
                    {|RH5307:[1
                    ]|} = 2
                };
    }
}
```

### RH5307-002 — A wrapped element access the formatter cannot join is not reported

The analyzer MUST NOT report a bracketed argument list when a comment or a preprocessor directive sits between its two brackets, or when one of its arguments spans several lines.

Why: Joining the list would move the comment or the directive into the middle of a line, and the formatter refuses that join (FMT-BREAK-001); an argument that spans several lines cannot be on one line with the brackets, and the formatter leaves such a list as it is (FMT-BREAK-014).

Example:

```csharp
class C
{
    void M(int[,] m)
    {
        var a = m[1, // note
                  2];
        var b = m[N(1,
                    2), 3];
    }

    int N(int a, int b) => a;
}
```

is not reported.

### RH5307-003 — Where the diagnostic is

The analyzer MUST report one diagnostic per argument list, located on the whole element access expression, or, for an implicit element access inside an initializer, on the bracketed argument list.

Why: The access expression is the unit the reader sees; an implicit element access has nothing in front of its brackets.

Example: see RH5307-001.

### RH5307-004 — The fix joins the argument list

For the argument list of an implicit element access, and for that of an element access that is not inside another bracketed argument list and whose receiver does not start with an element access, the code fix MUST join the reported argument list onto one line as the formatter joins it: the brackets and the arguments on the line of the opening bracket, separated by a comma and a space (FMT-BREAK-014). A comment behind the closing bracket stays behind it.

Why: The formatter owns the layout of bracketed argument lists; delegating to it applies that layout instead of a second one.

Example:

```csharp
class C
{
    void M(int[,] m)
    {
        var a = {|RH5307:m[
            1, 2]|};
        var b = {|RH5307:m[1,
                  2]|}; // note
    }
}
```

```csharp
class C
{
    void M(int[,] m)
    {
        var a = m[1, 2];
        var b = m[1, 2]; // note
    }
}
```
