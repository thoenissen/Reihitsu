# Analyzer — RH5104 Comments must be on their own line

| | |
|---|---|
| ID prefix | RH5104 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5104CommentsMustBeOnTheirOwnLineAnalyzer`, `RH5104CommentsMustBeOnTheirOwnLineCodeFixProvider` |
| Uses | SHARED-COMMENT-002, SHARED-FIX-003, SHARED-FIX-006 |

RH5104 reports a comment that shares a line with code, and offers a code fix that moves the comment onto a line of its own above that line.

## Non-goals

- Where a comment on its own line is placed inside a declaration or a statement — the comment-placement rules (SHARED-COMMENT) and RH5048.
- Whether a comment on its own line is preceded by a blank line — RH5020.
- Code of other rules that the moved comment ends up next to, such as a comment above an `else` or above a closing brace.

## Requirements

### RH5104-001 — A comment that shares a line with code is reported

The analyzer MUST report a `//` comment that does not start with `///`, and a `/* */` comment that does not start with `/**`, when a token precedes it or follows it on one of the lines it spans and the comment is not in the trivia of a token of an interpolated string that spans several lines.

Why: A comment on the line of code competes with the code for the same space, and it is unclear whether it describes the code before it or after it. On its own line above the code, it reads as a description of what follows.

Example:

```csharp
class C
{
    int _a; {|RH5104:// first|}

    void N(int x)
    {
        var y = x {|RH5104:/* why */|} + 1;
        {|RH5104:/* lead */|} M();
        M(); {|RH5104:/* a
        b */|} M();
        var s = $"{x {|RH5104:/* hole */|}}";
    }

    void M()
    {
    }
}
```

### RH5104-002 — Comments on lines without code, of directives, and in multi-line interpolations are not reported

The analyzer MUST NOT report a comment that shares none of the lines it spans with a token — only whitespace or other comments stand around it on each of those lines —, a comment that is part of a preprocessor directive line (SHARED-COMMENT-002), such as the comment behind `#endregion`, and a comment inside an interpolation of an interpolated string that spans several lines.

Why: A comment on its own line already is where this rule wants it, and so is a comment that shares its line only with other comments: no code competes with it, and moving one of them above the other would only reorder what the author wrote. A comment behind a directive belongs to the directive, which cannot share a line with anything else. Inside a multi-line interpolated string, the line holds the string's text, and moving the comment out of the interpolation would move it into the string's lines.

Example:

```csharp
class C
{
    #region A
    int _a;
    #endregion // A

    void N(int x)
    {
        // own line
        M();
        /* own
           lines */
        M();
        /* a */ /* b */
        M();
        /* c */ // d
        M();
#if DEBUG // debug
        M();
#endif
        var t = $"""
            {x // value
            }
            """;
    }

    void M()
    {
    }
}
```

is not reported.

### RH5104-003 — The diagnostic is on the comment

The analyzer MUST report one diagnostic per comment, located on the comment.

Why: Each comment is moved on its own, and its location identifies it whatever else shares the line.

Example: see RH5104-001.

### RH5104-004 — The fix moves the comment above its line

When the line on which the comment starts does not start inside a literal or a comment, the code fix MUST remove the comment from its line and insert it, unchanged, on a new line above that line, indented like that line. When code follows the comment on its last line, the spaces and tabs behind the comment MUST be removed with it and the whitespace in front of it kept; otherwise the spaces and tabs in front of it MUST be removed with it and the whitespace behind it kept. When the comment spans lines and holds the only line break between the code before and after it, the code after it MUST stay on a line of its own.

Why: Above the code it shares a line with is where a comment describing that code belongs, and the indentation of that line is the indentation of the code it describes. Removing only the whitespace on one side of the comment keeps the code on the line apart as it was; spacing the remaining tokens is the spacing rules' concern. Keeping the line break the comment carried keeps the two statements around it apart.

Example:

```csharp
class C
{
    void N(int x)
    {
        var y = x {|RH5104:/* why */|} + 1;
    }

    void P(int a)
    {
        P(a {|RH5104:/* value */|});
    }

    void O()
    {
        M(); {|RH5104:/* a
        b */|} M();
    }

    void M()
    {
    }
}
```

```csharp
class C
{
    void N(int x)
    {
        /* why */
        var y = x + 1;
    }

    void P(int a)
    {
        /* value */
        P(a );
    }

    void O()
    {
        /* a
        b */
        M();
        M();
    }

    void M()
    {
    }
}
```

### RH5104-005 — No blank line is inserted above the moved comment

The code fix MUST NOT insert a blank line above the moved comment, whatever the line above it holds, and MUST keep the blank lines that already stand above the comment's line (SHARED-FIX-006).

Why: The fix moves a comment; whether a blank line separates it from the code before it is not what the diagnostic names, but the concern of RH5020. The blank lines the author wrote above the line stay a layout the author chose.

Example:

```csharp
class C
{
    void N(int x)
    {
        M(); {|RH5104:// first|}
        M(); {|RH5104:// second|}
        // note
        M(); {|RH5104:// third|}

        M(); {|RH5104:// fourth|}
        switch (x)
        {
            case 1:
                M(); {|RH5104:// fifth|}
                break;
        }
    }

    void M()
    {
    }
}
```

```csharp
class C
{
    void N(int x)
    {
        // first
        M();
        // second
        M();
        // note
        // third
        M();

        // fourth
        M();
        switch (x)
        {
            case 1:
                // fifth
                M();
                break;
        }
    }

    void M()
    {
    }
}
```

### RH5104-006 — The fix is withheld when the line starts inside a literal or a comment

When the line on which the comment starts begins inside the text of a literal or inside a comment that spans several lines — a verbatim string, a raw string, an interpolated raw string, or a `/** */` documentation comment —, the code fix MUST NOT be offered (SHARED-FIX-003). When that line begins outside them, the fix is offered as RH5104-004 states, also when a literal or a comment that spans several lines starts on it.

Why: RH5104-004 inserts the comment on a new line above the line it starts on. When that line begins inside a literal or a comment, the new line lands inside it: the comment becomes part of the string's value or of the other comment's text. No other place above the code keeps the comment next to the code it describes, so the comment is left to be moved by hand.

Example:

```csharp
class C
{
    /** <summary>
    M</summary> */ void M() { } {|RH5104:// c|}

    void N(int x)
    {
        var a = @"a
b" + {|RH5104:/* c */|} x;
        var b = """
            a
            """ + {|RH5104:/* c */|} x;
        var c = $"""
            {x}
            """ + {|RH5104:/* c */|} x;
    }
}
```

is reported, and no code fix is offered. A comment on the line where such a literal starts is moved:

```csharp
class C
{
    void N(int x)
    {
        var a = {|RH5104:/* c */|} @"a
b" + x;
    }
}
```

```csharp
class C
{
    void N(int x)
    {
        /* c */
        var a = @"a
b" + x;
    }
}
```
