# Analyzer — RH5106 Closing parenthesis must be on line of last argument

| | |
|---|---|
| ID prefix | RH5106 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5106ClosingParenthesisMustBeOnLineOfLastArgumentAnalyzer`, `RH5106ClosingParenthesisMustBeOnLineOfLastArgumentCodeFixProvider` |
| Uses | FMT-BREAK-001, FMT-BREAK-011, SHARED-WS-003 |

RH5106 reports the closing parenthesis of a parameter list that starts a line below the end of the last parameter, and offers a code fix that moves the parenthesis behind the last parameter.

## Non-goals

- The opening parenthesis, the first parameter, and the commas of a parameter list — RH5105, RH5108, and RH5107.
- The bracketed parameter list of an indexer.
- The closing parenthesis of an argument list.

## Requirements

### RH5106-001 — A closing parenthesis below the last parameter is reported

The analyzer MUST report the closing parenthesis of the parameter list of a method, a constructor, a finalizer, a local function, an operator, a conversion operator, a delegate, a record, an extension block, an anonymous method, a parenthesized lambda, and the primary constructor of a class or a struct, when the parenthesis starts on a later line than the last parameter ends on, or, in a list without parameters, than the opening parenthesis.

Why: A closing parenthesis on a line of its own adds a line that carries nothing and separates the parameters from what follows them (FMT-BREAK-011). A parenthesized lambda's closing parenthesis has a last parameter to sit behind just like any other list.

### RH5106-002 — A comment or directive in front of the parenthesis suppresses the diagnostic

The analyzer MUST NOT report the closing parenthesis when a comment, a preprocessor directive, or disabled text sits between it and the token in front of it.

Why: The parenthesis cannot join the last parameter's line without moving the comment or the directive, which the formatter refuses as well (FMT-BREAK-001). A diagnostic that no layout can clear would stay for good.

Example:

```csharp
class C
{
    void M(int a // last
        )
    {
    }
}
```

is not reported.

### RH5106-003 — A file with a syntax error is not analyzed

The analyzer MUST NOT report anything in a file that contains a syntax error, wherever the error is.

Why: A syntax error can make the parser end a parameter list at the wrong token, so a diagnostic there could point at code the author never wrote that way; the formatter leaves such a file untouched as well.

Example:

```csharp
class C
{
    void M(int a
        )
    {
    }

    int _x = ;
}
```

is not reported.

### RH5106-004 — The diagnostic is on the closing parenthesis

The analyzer MUST report one diagnostic per parameter list, located on its closing parenthesis.

Why: The parenthesis is the token that has to move.

Example: see RH5106-001.

### RH5106-005 — The fix joins the parenthesis to the last parameter

The code fix MUST move the closing parenthesis directly behind the token in front of it, as SHARED-WS-003 specifies.

Why: Deleting the line break and the indentation in front of the parenthesis is the whole correction.

Example:

```csharp
class C
{
    void M(int a,
           int b
           {|RH5106:)|}
    {
    }

    void N(
        {|RH5106:)|}
    {
    }
}
```

```csharp
class C
{
    void M(int a,
           int b)
    {
    }

    void N()
    {
    }
}
```
