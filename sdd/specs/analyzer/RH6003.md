# Analyzer — RH6003 Semicolons must be spaced correctly

| | |
|---|---|
| ID prefix | RH6003 |
| Status | Active |
| Category | Spacing |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH6003SemicolonsMustBeSpacedCorrectlyAnalyzer`, `RH6003SemicolonsMustBeSpacedCorrectlyCodeFixProvider` |
| Uses | FMT-SPACE-004, FMT-SPACE-013, FMT-SPACE-014, SHARED-WS-001, SHARED-WS-002 |

RH6003 reports the whitespace in front of a semicolon on the same line, and offers a code fix that deletes it as SHARED-WS-001 and SHARED-WS-002 specify.

In the examples, `→` marks a tab.

## Non-goals

- The space after a semicolon of a `for` header — the formatter (FMT-SPACE-011).
- Whether a semicolon starts its own line — the line-break rules, such as RH5113.
- Semicolons inside comments, string literals, directives, and disabled text, which are not tokens.

## Requirements

### RH6003-001 — Whitespace before a semicolon on the same line is reported

The analyzer MUST report the run of spaces and tabs directly in front of a semicolon token when that run follows code or a comment on the same line and the token before the semicolon ends on that line. This includes the semicolons of a `for` header, also when a clause is empty.

Why: A semicolon ends the statement or clause before it and belongs to it; a space in front of it is visual noise. The formatter removes the same whitespace (FMT-SPACE-004), also between a comment and the semicolon (FMT-SPACE-013, and FMT-SPACE-014 for a `/** */` comment the semicolon carries), so formatted code raises no RH6003.

Example:

```csharp
class C
{
    int _a{|RH6003: |};
    int _b{|RH6003:→|};

    void M(int a)
    {
        for (int i = 0{|RH6003: |}; i < a{|RH6003: |}; i++)
        {
        }

        for (;{|RH6003: |};)
        {
        }

        M(a) /* note */{|RH6003: |};

        return{|RH6003: |};
    }
}
```

### RH6003-002 — A semicolon that starts its line is not reported

The analyzer MUST NOT report the indentation in front of a semicolon that is the first thing on its line, including when a comment, a directive, or disabled text precedes that line.

Why: Indentation is not a gap between the semicolon and the code it ends; whether the semicolon belongs on the line before is a layout question other rules decide.

Example:

```csharp
class C
{
    void M(int a)
    {
        M(a)
            ;
        M(a) // note
            ;
#if NEVER
        int disabled = 0 ;
#endif
        ;
    }
}
```

is not reported.

### RH6003-003 — One diagnostic per semicolon

The analyzer MUST report one diagnostic per semicolon, located on the whitespace run in front of it.

Why: The run is the text that is wrong and the text the fix deletes.

Example: see RH6003-001.

### RH6003-004 — The fix deletes the whitespace unless a comment is in the gap

The code fix MUST delete the reported whitespace as SHARED-WS-001 specifies, and MUST NOT be offered when a comment or directive sits between the semicolon and the token before it, as SHARED-WS-002 specifies.

Why: Deleting the whitespace between a comment and the semicolon would glue the comment to it; the author decides whether the comment stays there.

Example:

```csharp
class C
{
    int _a{|RH6003: |};

    void M(int a)
    {
        for (int i = 0{|RH6003: |}; i < a{|RH6003:→|}; i++)
        {
        }

        M(a){|RH6003: |}; // note
    }
}
```

```csharp
class C
{
    int _a;

    void M(int a)
    {
        for (int i = 0; i < a; i++)
        {
        }

        M(a); // note
    }
}
```

The comment before the semicolon withholds the fix:

```csharp
class C
{
    void M(int a)
    {
        M(a) /* note */{|RH6003: |};
    }
}
```

is reported, and no code fix is offered.
