# Analyzer — RH3004 Use lambda syntax

| | |
|---|---|
| ID prefix | RH3004 |
| Status | Active |
| Category | Clarity |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH3004UseLambdaSyntaxAnalyzer`, `RH3004UseLambdaSyntaxCodeFixProvider` |
| Uses | FMT-BREAK-002, FMT-INDENT-028, SHARED-FIX-003, SHARED-FIX-007 |

RH3004 reports an anonymous method written with `delegate` and a parameter list and offers a code fix that rewrites it as a lambda expression.

## Non-goals

- An anonymous method without a parameter list, `delegate { }`, which no lambda expresses: a lambda always states its parameters.
- An empty parameter list `delegate () { }` as such — RH3106 reports the parentheses; RH3004 reports the anonymous method.

## Requirements

### RH3004-001 — An anonymous method with a parameter list is reported

The analyzer MUST report an anonymous method that has a parameter list, empty or not. An anonymous method without a parameter list MUST NOT be reported.

Why: A lambda is the normal C# form for an inline function and says the same with less syntax. Without a parameter list, the anonymous method converts to a delegate of any parameter list, which no lambda can express.

Example:

```csharp
using System;

class C
{
    void M()
    {
        Func<int, int> a = {|RH3004:delegate|} (int x) { return x + 1; };
        Func<int> b = {|RH3004:delegate|} () { return 1; };
        Action c = delegate { };
    }
}
```

### RH3004-002 — The diagnostic is on `delegate`

The analyzer MUST report one diagnostic per anonymous method, on its `delegate` keyword.

Why: The keyword is what marks the old syntax; the parameters and the body stay.

Example: see RH3004-001.

### RH3004-003 — The fix writes a lambda

For an anonymous method whose fix RH3004-004, RH3004-005, and RH3004-007 do not withhold, the code fix MUST replace it with a lambda that has the same parameter list, `async` when the anonymous method was `async`, and as its body:

- the expression of the only statement, when the block holds exactly one `return` statement with an expression and no comment or directive;
- the block's statements, unchanged, otherwise, laid out as RH3004-006 states.

Why: The parameter list and the statements carry the meaning and are kept as written. A block that only returns a value reads best as an expression body; any other block, or one with comments, keeps its statements.

Example:

```csharp
using System;
using System.Threading.Tasks;

class C
{
    void M()
    {
        Func<int, int> a = {|RH3004:delegate|} (int x) { return x + 1; };
        Action<int> b = {|RH3004:delegate|} (int x) { Console.WriteLine(x); };
        Func<Task> c = async {|RH3004:delegate|} () { await Task.Delay(1); };
        Func<int, int> d = {|RH3004:delegate|} (int x) { return x; /* c */ };
    }
}
```

```csharp
using System;
using System.Threading.Tasks;

class C
{
    void M()
    {
        Func<int, int> a = (int x) => x + 1;
        Action<int> b = (int x) =>
                        {
                            Console.WriteLine(x);
                        };
        Func<Task> c = async () =>
                       {
                           await Task.Delay(1);
                       };
        Func<int, int> d = (int x) =>
                           {
                               return x; /* c */
                           };
    }
}
```

### RH3004-004 — A comment or a directive outside the parameter list and the body withholds the fix

The code fix MUST NOT be offered when a comment or a preprocessor directive stands between the start of the anonymous method and its parameter list, or between the parameter list and the body. The diagnostic is still reported.

Why: The lambda is built from the parameter list and the body; a comment or directive between them belongs to neither and would be lost.

Example:

```csharp
using System;

class C
{
    void M()
    {
        Func<int, int> a = {|RH3004:delegate|} (int x) /* c */ { return x; };
    }
}
```

is reported, and no code fix is offered.

### RH3004-005 — An operand of a cast or a binary operator withholds the fix

The code fix MUST NOT be offered for an anonymous method that is directly the operand of a cast or an operand of a binary operator. The diagnostic is still reported. An anonymous method inside parentheses that are the operand, and one that is the value of an assignment, including a compound assignment such as `+=`, is rewritten as RH3004-003 states.

Why: A lambda is not a valid operand of a cast or a binary operator without parentheses: in front of an operator, the lambda's body takes in the rest of the expression, so `delegate () { return 1; } + h` would become `() => 1 + h`, and a block body in front of an operator draws warning CS8848, as `() => { } + g` does; behind a cast or an operator, the lambda does not parse as the operand (SHARED-FIX-003). The fix does not write the parentheses that would keep the meaning.

Example:

```csharp
using System;

class C
{
    void M(Func<int> h, Action g)
    {
        var a = (Func<int, int>){|RH3004:delegate|} (int x) { return x + 1; };
        var b = {|RH3004:delegate|} () { return 1; } + h;
        var c = g + {|RH3004:delegate|} () { };
    }
}
```

is reported, and no code fix is offered. Inside parentheses and as the value of a compound assignment, the fix rewrites the anonymous method:

```csharp
using System;

class C
{
    void M(Func<int> g)
    {
        var a = (Func<int, int>)({|RH3004:delegate|} (int x) { return x + 1; });
        g += {|RH3004:delegate|} () { return 1; };
    }
}
```

```csharp
using System;

class C
{
    void M(Func<int> g)
    {
        var a = (Func<int, int>)((int x) => x + 1);
        g += () => 1;
    }
}
```

### RH3004-006 — The lambda is laid out as the formatter lays it out

The code fix MUST lay out the lambda it writes as the formatter lays it out (SHARED-FIX-007): the braces of a block body each start their own line (FMT-BREAK-002), and both start in the column of the lambda's anchor — `async`, or the opening parenthesis of the parameter list (FMT-INDENT-028). This holds whether the anonymous method's block stood on one line, as in RH3004-003, or on lines of its own, also with its opening brace on the line after the parameter list. An expression body stays on the line of `=>`.

The lambda's parameter list, `=>`, and braces are the code the fix lays out. The block's statements, with the comments and blank lines between them, are code the fix moves (SHARED-FIX-007, moved code): they MUST keep their own layout — the spacing between their tokens, their line breaks, their braces, and the blank lines inside the block — also where formatting the result would change it. Only the indentation of their lines MUST follow the braces: every line moves by the same number of columns, except a directive line in column 0, a comment line in column 0, a line that continues a verbatim string literal, the lines after an opening brace that shares its line with the first statement, and the lines of a block whose shift would put a line left of column 0, as stated below, so that the block's first statement line stands one indentation level inside the braces, and the other lines keep their indentation relative to it. The first statement line is the first line of the block, in source order, on which a statement starts, whether that statement is active code or disabled text of an inactive `#if`, `#elif`, or `#else` branch; a line of disabled text counts when it holds anything other than whitespace and comments. The fix's output therefore MUST NOT depend on which preprocessor symbols are defined. The number of columns is measured on the first statement line, from the first character of the moved code on it, not on the block's first line: a directive or a comment line in front of the first statement, such as an `#if` in column 0, does not decide it. In a block in which no line holds a statement, active or disabled, it is measured on the block's first line that does not stay in column 0. A preprocessor directive line that starts in column 0 MUST stay in column 0, unless it is a `#region` or `#endregion` line: a conditional directive such as `#if`, `#elif`, `#else`, or `#endif`, and likewise `#pragma`, `#nullable`, `#define`, `#undef`, `#line`, `#error`, and `#warning`, belongs to no nesting depth. A directive line that starts in another column, and a `#region` or `#endregion` line in column 0, moves by the same number of columns as the statements. A line whose comment starts in column 0, such as a line of code commented out by an editor's comment toggle, MUST likewise stay in column 0; a comment line that starts in another column moves with the statements. Statements that stood on the block's one line move together onto one line of their own between the braces. A line that continues a verbatim string literal is part of the literal and keeps its columns, so the literal's value stays as written (SHARED-FIX-003).

When the block's first statement starts on the line of its opening brace and moved code stands on lines after that line, those lines keep their indentation relative to the first statement only when none of them starts left of the first statement in the source. Otherwise, they move together by the number of columns that puts the leftmost of them one indentation level inside the braces, in the column of the first statement, and keep their indentation relative to each other, so that no moved line stands left of the statements. Blank lines, directive and comment lines that stay in column 0, and lines that keep their columns do not count for the leftmost line.

When the first statement starts on a line of its own and moving every line by the number of columns measured on the first statement line would put a moved line left of column 0, every moved line of the block instead moves by the number of columns that puts the leftmost of them one indentation level inside the braces, in the column of the statements, and the lines keep their indentation relative to each other, so that no moved line stands left of the statements. Every moved line counts for the leftmost line, also a comment or directive line in front of the first statement, except the lines named above; a directive or comment line that stays in column 0 neither moves nor counts. Where no moved line would stand left of column 0, the measured number of columns applies, also where it moves a line left of the braces. No moved line is ever cut off at column 0.

Why: A fix whose result the formatter changes again hands the user a second diff for the same correction (SHARED-FIX-007), and a block body on one line is reported by RH5417, which offers no fix for a lambda. The statements inside the block are the author's code that only changes its position, so reformatting them would hide the rewrite in layout changes nobody asked for; the formatter and the layout rules still correct them on their own. A statement written behind the opening brace moves to the left onto its own line, while the lines after it were indented for the block, not for that statement: keeping their offset to it would put them left of the braces, or cut off at column 0. Measured on their own leftmost line, they keep the layout the author gave them relative to each other. The same holds for any block whose shift would push a line left of column 0: cutting the line off there would lose its indentation relative to the others, so the whole block moves as far right as its leftmost line needs. A comment in column 0 belongs to no nesting depth, as a directive there does; it is most often code commented out by an editor, which writes the comment marker in column 0, so it stays where it was written and does not push the statements to the right.

Example:

```csharp
using System;

class C
{
    void M()
    {
        Action<int> b = {|RH3004:delegate|} (int x)
        {
            Console.WriteLine(x);
        };
        Func<int, int> e = {|RH3004:delegate|} (int x)
        {
            return x + 1;
        };
    }
}
```

```csharp
using System;

class C
{
    void M()
    {
        Action<int> b = (int x) =>
                        {
                            Console.WriteLine(x);
                        };
        Func<int, int> e = (int x) => x + 1;
    }
}
```

A directive line that does not start in column 0, and a `#region` or `#endregion` line in column 0, moves with the statements. The output is the same with and without `DEBUG`: with it, `Console.WriteLine(x);` is the first statement as active code; without it, the same line is the first statement as disabled text, and the shift is 16 columns either way:

### RH3004-007 — A multi-line raw string literal in the block withholds the fix

The code fix MUST NOT be offered when the block of the anonymous method holds a multi-line raw string literal, also an interpolated or a UTF-8 one. The diagnostic is still reported. A raw string literal on one line and a verbatim string literal over several lines do not withhold the fix. This is a deliberate gap in the fix's coverage: such an anonymous method is rewritten by hand.

Why: The fix moves the lines of the block to new columns (RH3004-006). The value of a multi-line raw string literal depends on the column of each of its lines relative to its closing quotes, also of a line that holds only whitespace, so moving those lines risks changing the literal's value, which SHARED-FIX-003 forbids. A fix that could change a literal is withheld rather than offered. A verbatim string literal keeps its continuation lines in their columns (RH3004-006), so its value cannot change.

Example:

```csharp
using System;

class C
{
    void M()
    {
        Action<int> b = {|RH3004:delegate|} (int x)
        {
            Console.WriteLine("""
                a
                """);
        };
    }
}
```

is reported, and no code fix is offered. A raw string literal on one line does not withhold the fix:

```csharp
using System;

class C
{
    void M()
    {
        Action<int> b = {|RH3004:delegate|} (int x) { Console.WriteLine("""a"""); };
    }
}
```

```csharp
using System;

class C
{
    void M()
    {
        Action<int> b = (int x) =>
                        {
                            Console.WriteLine("""a""");
                        };
    }
}
```
