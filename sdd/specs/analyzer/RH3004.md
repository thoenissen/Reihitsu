# Analyzer — RH3004 Use lambda syntax

| | |
|---|---|
| ID prefix | RH3004 |
| Status | Active |
| Category | Clarity |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH3004UseLambdaSyntaxAnalyzer`, `RH3004UseLambdaSyntaxCodeFixProvider` |
| Uses | FMT-BREAK-002, FMT-INDENT-028, FMT-RAW-001, FMT-RAW-002, SHARED-FIX-003, SHARED-FIX-007 |

RH3004 reports an anonymous method written with `delegate` and a parameter list and offers a code fix that rewrites it as a lambda expression.

## Non-goals

- An anonymous method without a parameter list, `delegate { }`, which no lambda expresses: a lambda always states its parameters.
- An empty parameter list `delegate () { }` as such — RH3106 reports the parentheses; RH3004 reports the anonymous method.

## Requirements

### RH3004-001 — An anonymous method with a parameter list is reported

The analyzer MUST report an anonymous method that has a parameter list, empty or not. An anonymous method without a parameter list MUST NOT be reported.

Why: A lambda is the normal C# form for an inline function and says the same with less syntax. Without a parameter list, the anonymous method converts to a delegate of any parameter list, which no lambda can express.

Example:

```csharp
using System;

class C
{
    void M()
    {
        Func<int, int> a = {|RH3004:delegate|} (int x) { return x + 1; };
        Func<int> b = {|RH3004:delegate|} () { return 1; };
        Action c = delegate { };
    }
}
```

### RH3004-002 — The diagnostic is on `delegate`

The analyzer MUST report one diagnostic per anonymous method, on its `delegate` keyword.

Why: The keyword is what marks the old syntax; the parameters and the body stay.

Example: see RH3004-001.

### RH3004-003 — The fix writes a lambda

For an anonymous method whose fix RH3004-004, RH3004-005, RH3004-007, and RH3004-008 do not withhold, the code fix MUST replace it with a lambda that has the same parameter list, `async` when the anonymous method was `async`, and as its body:

- the expression of the only statement, when the block holds exactly one `return` statement with an expression and no comment or directive;
- the block's statements, unchanged, otherwise, laid out as RH3004-006 states.

Why: The parameter list and the statements carry the meaning and are kept as written. A block that only returns a value reads best as an expression body; any other block, or one with comments, keeps its statements.

Example:

```csharp
using System;
using System.Threading.Tasks;

class C
{
    void M()
    {
        Func<int, int> a = {|RH3004:delegate|} (int x) { return x + 1; };
        Action<int> b = {|RH3004:delegate|} (int x) { Console.WriteLine(x); };
        Func<Task> c = async {|RH3004:delegate|} () { await Task.Delay(1); };
        Func<int, int> d = {|RH3004:delegate|} (int x) { return x; /* c */ };
    }
}
```

```csharp
using System;
using System.Threading.Tasks;

class C
{
    void M()
    {
        Func<int, int> a = (int x) => x + 1;
        Action<int> b = (int x) =>
                        {
                            Console.WriteLine(x);
                        };
        Func<Task> c = async () =>
                       {
                           await Task.Delay(1);
                       };
        Func<int, int> d = (int x) =>
                           {
                               return x; /* c */
                           };
    }
}
```

### RH3004-004 — A comment or a directive outside the parameter list and the body withholds the fix

The code fix MUST NOT be offered when a comment or a preprocessor directive stands between the start of the anonymous method and its parameter list, or between the parameter list and the body. The diagnostic is still reported.

Why: The lambda is built from the parameter list and the body; a comment or directive between them belongs to neither and would be lost.

Example:

```csharp
using System;

class C
{
    void M()
    {
        Func<int, int> a = {|RH3004:delegate|} (int x) /* c */ { return x; };
    }
}
```

is reported, and no code fix is offered.

### RH3004-005 — An operand of a cast or a binary operator withholds the fix

The code fix MUST NOT be offered for an anonymous method that is directly the operand of a cast or an operand of a binary operator. The diagnostic is still reported. An anonymous method inside parentheses that are the operand, and one that is the value of an assignment, including a compound assignment such as `+=`, is rewritten as RH3004-003 states.

Why: A lambda is not a valid operand of a cast or a binary operator without parentheses: in front of an operator, the lambda's body takes in the rest of the expression, so `delegate () { return 1; } + h` would become `() => 1 + h`, and a block body in front of an operator draws warning CS8848, as `() => { } + g` does; behind a cast or an operator, the lambda does not parse as the operand (SHARED-FIX-003). The fix does not write the parentheses that would keep the meaning.

Example:

```csharp
using System;

class C
{
    void M(Func<int> h, Action g)
    {
        var a = (Func<int, int>){|RH3004:delegate|} (int x) { return x + 1; };
        var b = {|RH3004:delegate|} () { return 1; } + h;
        var c = g + {|RH3004:delegate|} () { };
    }
}
```

is reported, and no code fix is offered. Inside parentheses and as the value of a compound assignment, the fix rewrites the anonymous method:

```csharp
using System;

class C
{
    void M(Func<int> g)
    {
        var a = (Func<int, int>)({|RH3004:delegate|} (int x) { return x + 1; });
        g += {|RH3004:delegate|} () { return 1; };
    }
}
```

```csharp
using System;

class C
{
    void M(Func<int> g)
    {
        var a = (Func<int, int>)((int x) => x + 1);
        g += () => 1;
    }
}
```

### RH3004-006 — The lambda is laid out as the formatter lays it out

The code fix MUST lay out the lambda it writes as the formatter lays it out (SHARED-FIX-007): the braces of a block body each start their own line (FMT-BREAK-002), and both start in the column of the lambda's anchor — `async`, or the opening parenthesis of the parameter list (FMT-INDENT-028). This holds whether the anonymous method's block stood on one line, as in RH3004-003, or on lines of its own, also with its opening brace on the line after the parameter list. An expression body stays on the line of `=>`.

The lambda's parameter list, `=>`, and braces are the code the fix lays out. The block's statements, with the comments, directives, disabled text, and blank lines between them, are code the fix moves (SHARED-FIX-007, moved code): they MUST keep their own layout — the spacing between their tokens, their line breaks, their braces, and the blank lines inside the block — also where formatting the result would change it. Only the indentation of their lines MUST follow the braces, by one rule that gives every line of the block that is not blank exactly one of two outcomes, decided on the line's source text alone, whichever preprocessor symbols are defined:

- A line **stays**, keeping its columns, when it is one of these:
  - a line that starts inside a string begun on an earlier line: it is part of the string, so the string's value stays as written (SHARED-FIX-003), whatever follows the string on the line. The string is decided as a whole, never by its tokens: it is a string literal or an interpolated string expression, and its span runs from its first character (`@`, `$`, or the opening quote) through its closing quote and a `u8` suffix, holes included. Only a verbatim string, an interpolated string, or a raw string literal (RH3004-007) can span lines. A line starts inside the span when its first character, in column 0, lies inside it, after the line the string starts on: also a line that starts with the `{` of a hole, a line inside a hole that spans lines, and a line that starts with the string's closing quote. Strings nested in a hole belong to the outermost string. In disabled text, the strings are those that lexing the disabled text between its two directives gives; RH3004-008 withholds the fix where that text leaves a string open;
  - a preprocessor directive line that starts in column 0, unless it is a `#region` or `#endregion` line: a conditional directive such as `#if`, `#elif`, `#else`, or `#endif`, and likewise `#pragma`, `#nullable`, `#define`, `#undef`, `#line`, `#error`, and `#warning`, belongs to no nesting depth;
  - a line that holds no code, only comments and whitespace, and whose first comment starts in column 0, such as a line of code commented out by an editor's comment toggle, also in disabled text;
  - a line that holds no code and continues a comment whose first line stays.
- Every other line **moves**. That is every line that holds code — a token of active code, or anything other than whitespace and comments in disabled text of an inactive `#if`, `#elif`, or `#else` branch — also where a comment in front of the code starts in column 0; a line that holds no code and whose first comment starts in another column, or that continues a comment whose first line moves; a directive line that starts in another column; and a `#region` or `#endregion` line in any column.

Every moving line moves by the same number of columns, the shift, except where one of the two paragraphs below moves the moving lines by another number. A line that stays never moves, and no part of this requirement measures on it or counts it. The shift puts the block's first statement line one indentation level inside the braces, and the other moving lines keep their indentation relative to it. The first statement line is the first line of the block, in source order, on which a statement starts, whether that statement is active code or disabled text; a line of disabled text holds a statement when it holds anything other than whitespace and comments. That line holds code, so it always moves. The fix's output therefore MUST NOT depend on which preprocessor symbols are defined. The shift is measured on the first statement line from its first character, also where that character starts a comment in front of the statement, not on the block's first line: a directive or a comment line in front of the first statement, such as an `#if` in column 0, does not decide it. In a block in which no line holds a statement, active or disabled, the shift is measured on the block's first moving line, and a block without a moving line has nothing to move. Statements that stood on the block's one line move together onto one line of their own between the braces.

When the block's first statement starts on the line of its opening brace and moving lines stand after that line, those lines keep their indentation relative to the first statement only when none of them starts left of the first statement in the source. Otherwise, they move together by the number of columns that puts the leftmost of them one indentation level inside the braces, in the column of the first statement, and keep their indentation relative to each other, so that no moving line stands left of the statements. Only moving lines count for the leftmost line.

When the first statement starts on a line of its own and moving every moving line by the shift would put one of them left of column 0, every moving line instead moves by the number of columns that puts the leftmost moving line one indentation level inside the braces, in the column of the statements, and the moving lines keep their indentation relative to each other. Every moving line counts for the leftmost line, also a comment or directive line in front of the first statement; only moving lines count. Where no moving line would stand left of column 0, the shift applies, also where it puts a line in the column of the braces or left of them, such as a comment or a label the author wrote left of the statements. No moving line is ever cut off at column 0.

Why: A fix whose result the formatter changes again hands the user a second diff for the same correction (SHARED-FIX-007), and a block body on one line is reported by RH5417, which offers no fix for a lambda. The statements inside the block are the author's code that only changes its position, so reformatting them would hide the rewrite in layout changes nobody asked for; the formatter and the layout rules still correct them on their own. Giving every line exactly one outcome keeps the rule closed: a line that holds code is part of a statement and moves with it, whatever stands in front of it on the line, and the line that sets the shift is a moving line, so it always moves by the shift it sets. A directive or a comment alone in column 0 belongs to no nesting depth; such a comment is most often code commented out by an editor, which writes the comment marker in column 0, so it stays where it was written, together with the rest of its comment, and does not push the statements to the right. A statement written behind the opening brace moves to the left onto its own line, while the lines after it were indented for the block, not for that statement: keeping their offset to it would put them left of the braces, or cut off at column 0. Measured on their own leftmost line, they keep the layout the author gave them relative to each other. In a block whose first statement starts its own line, the author placed every line, so the shift keeps all of them as written relative to each other, also a line written left of the statements; only a line that would cross column 0 forces another shift, because cutting it off there would lose its indentation relative to the others, so the whole block moves as far right as its leftmost line needs.

### RH3004-007 — A multi-line raw string literal in a block body withholds the fix

The code fix MUST NOT be offered when it would keep the anonymous method's block as the lambda's block body (RH3004-003, second item) and that block holds a multi-line raw string literal, also an interpolated or a UTF-8 one. The diagnostic is still reported. Where the fix writes an expression body instead — the block holds exactly one `return` statement with an expression and no comment or directive (RH3004-003, first item) — a multi-line raw string literal in that expression does not withhold the fix: the formatter lays out the expression body, and moves the literal's content lines and closing quotes together so the closing quotes start under the opening quotes (FMT-RAW-001, FMT-RAW-002), and the literal keeps its value. A raw string literal on one line and a verbatim string literal over several lines do not withhold the fix on either path. The withheld block body is a deliberate gap in the fix's coverage: such an anonymous method is rewritten by hand.

Why: For a block body, the fix itself moves the lines of the block to new columns (RH3004-006). The value of a multi-line raw string literal depends on the column of each of its lines relative to its closing quotes, also of a line that holds only whitespace, so moving those lines risks changing the literal's value, which SHARED-FIX-003 forbids. A fix that could change a literal is withheld rather than offered. An expression body moves no line by the fix's own rule: the formatter lays it out, raw string literals included, so a guard there would refuse an input the fix rewrites safely. A verbatim or interpolated string keeps every line that starts inside it in its columns (RH3004-006), so its value cannot change.

Example:

```csharp
using System;

class C
{
    void M()
    {
        Action<int> b = {|RH3004:delegate|} (int x)
        {
            Console.WriteLine("""
                a
                """);
        };
    }
}
```

is reported, and no code fix is offered. On the other side, a block that is a single `return` of a multi-line raw string literal becomes an expression body, and the fix is offered. The literal's lines move under the opening quotes, and its value, `a`, a line break, and `  b`, stays:

```csharp
using System;

class C
{
    void M()
    {
        Func<string> f = {|RH3004:delegate|} ()
        {
            return """
                a
                  b
                """;
        };
    }
}
```

```csharp
using System;

class C
{
    void M()
    {
        Func<string> f = () => """
                               a
                                 b
                               """;
    }
}
```

A raw string literal on one line does not withhold the fix:

```csharp
using System;

class C
{
    void M()
    {
        Action<int> b = {|RH3004:delegate|} (int x) { Console.WriteLine("""a"""); };
    }
}
```

```csharp
using System;

class C
{
    void M()
    {
        Action<int> b = (int x) =>
                        {
                            Console.WriteLine("""a""");
                        };
    }
}
```

### RH3004-008 — A string that disabled text leaves open withholds the fix

The code fix MUST NOT be offered when it would keep the anonymous method's block as the lambda's block body (RH3004-003, second item) and, in disabled text of an inactive `#if`, `#elif`, or `#else` branch inside the block, a string literal or an interpolated string starts that does not end before the directive that ends that disabled text. The diagnostic is still reported. A string in disabled text that ends before that directive does not withhold the fix; its lines are decided as RH3004-006 states. The withheld fix is a deliberate gap in the fix's coverage: such an anonymous method is rewritten by hand.

Why: RH3004-006 decides on the whole string whether a line keeps its columns, and its outcome must not depend on which preprocessor symbols are defined. A string that its disabled text leaves open continues, under other symbols, across the directive into the next lines, which are then part of its value; lexed on their own, those lines hold code and would move. No reading of the source text alone decides such a line the same way for every set of symbols, so moving it risks changing the string's value, which SHARED-FIX-003 forbids.

Example:

```csharp
using System;

class C
{
    void M()
    {
        Action<string> b = {|RH3004:delegate|} (string name)
        {
            Console.WriteLine(name);
#if A
            Console.WriteLine(@"Hello
#elif B
            world");
#endif
        };
    }
}
```

is reported, and no code fix is offered: with `A` defined, `#elif B` and `            world");` are part of the verbatim string; with neither symbol defined, both branches are disabled text, and `@"Hello` is not closed before `#elif B`. On the other side, the string in the `DEBUG` example of RH3004-006 ends before `#endif`, and the fix is offered.
