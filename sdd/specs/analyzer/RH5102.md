# Analyzer — RH5102 Arguments should either all be on one line or each on its own line

| | |
|---|---|
| ID prefix | RH5102 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5102ArgumentsShouldBeOnSingleOrSeparateLinesAnalyzer`, `RH5102ArgumentsShouldBeOnSingleOrSeparateLinesCodeFixProvider` |
| Uses | FMT-BREAK-012, FMT-BREAK-013, SHARED-DIAG-008, SHARED-DIAG-010 |

RH5102 reports a multi-line argument list in which two arguments start on the same line, and offers a code fix that lays the argument list out the way the formatter does.

## Non-goals

- Whether the first argument starts on the line of the opening parenthesis — RH5101; the column of a wrapped argument — RH5203.
- Parameter lists — RH5109.
- Bracketed argument lists (`m[…]`).
- The position of a comma or of the closing parenthesis in an argument list.

## Requirements

### RH5102-001 — Arguments sharing a line in a multi-line list are reported

The analyzer MUST report a parenthesized argument list with at least two arguments when the list is multi-line and two of its arguments start on the same line. The arguments alone decide whether the list is multi-line: the list is multi-line when two of its arguments start on different lines, or when an argument spans several lines. A multi-line list in which every argument starts its own line MUST NOT be reported, however many lines an argument spans. A list whose arguments all start on one line, none of them spanning lines, MUST NOT be reported, also when that line is not the line of the opening parenthesis, when the closing parenthesis stands on a later line, also behind a comment that holds it there, or when a comment or a directive keeps the first argument off the line of the opening parenthesis.

Why: A partly wrapped list hides arguments at the end of a line; a list is either compact or one argument per line (FMT-BREAK-012). Arguments that all start on one line are compact, wherever the parentheses stand; whether a line break around them belongs there is not this rule's question — RH5101 reports a first argument below the opening parenthesis. An argument that spans lines, such as a lambda with a block body, keeps the list multi-line, so the arguments next to it get their own lines too (FMT-BREAK-013). For a list wrapped only behind its opening parenthesis, this reading is the one FMT-BREAK-012 takes by the list's elements, and the formatter joins the list; a line break in front of the closing parenthesis of an argument list the formatter keeps, so reporting it left a fix that changes nothing (SHARED-DIAG-010). For a list whose first argument a comment or a directive keeps off the line of the opening parenthesis, it is not: the formatter lays that list out one argument per line, and the formatter may do more than the rule ([P11](../../README.md#the-formatter-may-do-more-than-the-analyzers-p11)).

Example:

```csharp
using System;

class C
{
    void N()
    {
        M{|RH5102:(1, 2,
          3)|};
        M{|RH5102:(1, () =>
        {
        })|};
        M{|RH5102:(
            1, 2,
            3)|};
        M{|RH5102:(
            1, () =>
            {
            })|};
        M(1, 2, 3);
        M(1,
          2,
          3);
        M(1,
          () =>
          {
          });
    }

    void M(params object[] values)
    {
    }
}
```

A list whose arguments all start on one line, none of them spanning lines, is not reported, whether a line break stands behind its opening parenthesis, in front of its closing parenthesis, also behind a comment, or behind a comment or a directive that keeps the first argument off the line of the opening parenthesis:

```csharp
class C
{
    void N()
    {
        M(
            1, 2);
        M(1, 2
          );
        M( // c
            1, 2);
        M(
#pragma warning disable CS0168
            1, 2);
        M(1, 2 // c
          );
    }

    void M(params int[] values)
    {
    }
}
```

is not reported.

Example — the argument list of a `with(…)` element is a parenthesized argument list:

```csharp
using System;
using System.Collections.Generic;

class C
{
    static IEqualityComparer<string> Create(bool ignoreCase) => ignoreCase ? StringComparer.OrdinalIgnoreCase : StringComparer.Ordinal;

    void M()
    {
        HashSet<string> a = [with{|RH5102:(4, Create(
                                                 true))|}];
    }
}
```

### RH5102-002 — The diagnostic is on the argument list

The analyzer MUST report one diagnostic per argument list, located on the whole argument list from its opening to its closing parenthesis, however many arguments share a line.

Why: The layout of the whole list is wrong, not one argument; one diagnostic per list matches the one fix that lays out the list.

Example:

```csharp
class C
{
    void N()
    {
        M{|RH5102:(1, 2,
          3, 4)|};
    }

    void M(params int[] values)
    {
    }
}
```

### RH5102-003 — The fix lays out the argument list

The code fix MUST format the argument list as the formatter formats it in place (FMT-BREAK-012, FMT-BREAK-013), which puts every argument on its own line, the first one on the line of the opening parenthesis and the others aligned under it.

Why: The formatter owns the layout of a wrapped argument list; delegating to it applies that layout instead of a second one.

Example:

```csharp
class C
{
    void N()
    {
        M{|RH5102:(1, 2,
          3)|};
    }

    void M(params int[] values)
    {
    }
}
```

```csharp
class C
{
    void N()
    {
        M(1,
          2,
          3);
    }

    void M(params int[] values)
    {
    }
}
```

### RH5102-004 — A comment or directive in the argument list withholds the fix

The span the rule judges is where each argument starts: the gaps between the opening parenthesis, the arguments, the commas, and the closing parenthesis. An `#if`, `#elif`, `#else`, or `#endif` directive, or code such a directive excludes, in one of those gaps MUST NOT keep the argument list from being reported (SHARED-DIAG-008), and neither MUST one inside an argument, such as in the body of a lambda passed as an argument, which lies outside that span. The code fix MUST NOT be offered when a comment or a preprocessor directive of any kind, a conditional directive included (SHARED-DIAG-008), sits in one of those gaps, when a comment or a preprocessor directive of any kind sits inside an argument, a documentation comment included, or when a comment or a preprocessor directive of any kind sits on a line of its own in front of the opening parenthesis, between the line break in front of it and the parenthesis. A comment behind the closing parenthesis, and a comment on the line of the token in front of the opening parenthesis, MUST NOT withhold the fix. The diagnostic is still reported.

Why: Laying out the list would move the comment or the directive, and the formatter keeps the leading trivia of a parenthesis that starts a line only when it can rewrite it. A comment behind the closing parenthesis or behind the token in front of the opening parenthesis stays where it is when the list is laid out, so it does not get in the way.

Example:

```csharp
class C
{
    int N()
    {
        M{|RH5102:(1, // first
          2, 3)|};

        return M
            /* note */ {|RH5102:(1, 2,
            3)|};
    }

    int M(params int[] values) => 0;
}
```

is reported, and no code fix is offered. In

```csharp
class C
{
    void N()
    {
        M{|RH5102:(1, 2,
          3)|}; // note
        _ = M /* note */ {|RH5102:(1, 2,
            3)|};
    }

    int M(params int[] values) => 0;
}
```

the comments follow the closing parenthesis or the token in front of the opening parenthesis, and the fix is offered.

Example — a conditional directive or a `#pragma` in a gap between the arguments, and a conditional directive inside an argument, withhold only the fix:

```csharp
class C
{
    void N()
    {
        M{|RH5102:(1, 2,
#if DEBUG
#endif
          3)|};

        M{|RH5102:(1, 2,
#pragma warning disable CS0168
          3)|};

        Run{|RH5102:(1, 2,
            () =>
            {
#if DEBUG
                System.Console.WriteLine();
#endif
            })|};
    }

    int M(params int[] values) => 0;

    void Run(int a, int b, System.Action action)
    {
    }
}
```

All three calls are reported, and no code fix is offered.
