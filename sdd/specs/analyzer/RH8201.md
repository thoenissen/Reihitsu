# Analyzer — RH8201 The inheritdoc tag should be used if possible

| | |
|---|---|
| ID prefix | RH8201 |
| Status | Active |
| Category | Documentation |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH8201InheritdocShouldBeUsedAnalyzer`, `RH8201InheritdocShouldBeUsedCodeFixProvider` |
| Uses | SHARED-DIAG-004, SHARED-DOC-004, SHARED-DOC-008, SHARED-FIX-006, SHARED-FIX-008 |

RH8201 reports the documentation comment of a member that overrides or implements another member and does not use `<inheritdoc>`, and offers a code fix that replaces the comment with `/// <inheritdoc/>`.

## Non-goals

- Whether a member has documentation at all — RH8020 to RH8029 and RH8034.
- An `<inheritdoc>` element on a declaration that inherits nothing — RH8203.
- Types and constructors, which inherit documentation from a base type or a base constructor.

## Requirements

### RH8201-001 — A documented member that inherits its documentation is reported

The analyzer MUST report a method, property, indexer, event, field-like event, operator, or conversion operator declaration that has a documentation comment, as SHARED-DOC-004 defines it, without an `<inheritdoc>` element in it — neither at its top level nor nested inside another element — when the member inherits its documentation. A member inherits its documentation when it:

- is declared `override`;
- explicitly implements an interface member, in a type or in an interface; or
- implicitly implements an interface member: for the type that declares the member, the compiler maps a member of one of that type's interfaces to it. The interface may be listed by the type or be a base interface of one it lists, be generic, or be declared in a referenced assembly, and the interface member may be an instance member or a `static abstract` member such as an operator.

A field-like event that declares several events MUST be reported only when each of them overrides or implements an event. The member's accessibility does not matter, and nothing is reported when SHARED-DOC-008 applies. RH8201-003 restricts the report of an implicit implementation.

A method, property, indexer, or event declared with the `partial` modifier in a defining and an implementing part MUST be judged part by part: each part whose own documentation comment holds no `<inheritdoc>` element MUST be reported, whatever the other part carries — a documentation comment of its own, `<inheritdoc/>`, or nothing. Whether the member inherits its documentation MUST be decided for the member as a whole, by its symbol (SHARED-DIAG-004): both parts inherit it when the member is declared `override` or implements an interface member, whichever part the compiler maps the interface member to. A part without a documentation comment is not reported.

This requirement covers a member whose leading trivia has one documentation comment, placed as SHARED-DOC-004 covers and well-formed XML, with the tag name `inheritdoc` written in lower case, without a namespace prefix, and in no XML namespace; for a partial member, it covers each part whose leading trivia has such a comment.

Why: The overridden or implemented member already describes the contract. A copy of that description on the member has to be kept in step by hand, and the copies that are missed start describing behavior the member no longer has. A nested `<inheritdoc>` inherits the description and states what differs next to it, so it satisfies the rule. Each part of a partial member carries a documentation comment of its own, written independently of the other part, so each part can hold its own copy of the description; whether there is a description to inherit is a fact of the one member both parts declare.

Example:

```csharp
using System;

/// <summary>
/// Base
/// </summary>
public abstract class B
{
    /// <summary>
    /// Runs
    /// </summary>
    public abstract void Run();

    /// <summary>
    /// Value
    /// </summary>
    public abstract int Value { get; }
}

/// <summary>
/// Notifier
/// </summary>
public interface INotifier
{
    /// <summary>
    /// Raised first
    /// </summary>
    event EventHandler First;

    /// <summary>
    /// Raised second
    /// </summary>
    event EventHandler Second;

    /// <summary>
    /// Raised third
    /// </summary>
    event EventHandler Third;
}

/// <summary>
/// Derived
/// </summary>
public class C : B, IDisposable, INotifier
{
    ///{|RH8201: <summary>Raised</summary>
|}    public event EventHandler First, Second;

    /// <summary>
    /// Raised as well
    /// </summary>
    public event EventHandler Third, Fourth;

    ///{|RH8201: <summary>Runs here</summary>
|}    public override void Run()
    {
    }

    /// <inheritdoc/>
    /// <remarks>
    /// <inheritdoc/>
    /// </remarks>
    public override int Value => 0;

    ///{|RH8201: <summary>Disposes</summary>
|}    public void Dispose()
    {
    }

    public override string ToString() => "";
}
```

Example — a partial member, judged part by part; both parts of `M` and the implementing part of `P` are reported, and the defining part of `P`, which uses `<inheritdoc/>`, is not:

```csharp
/// <summary>

/// </summary>
public interface I
{
    /// <summary>
    /// Runs
    /// </summary>
    void M();

    /// <summary>
    /// Value
    /// </summary>

}

/// Service
/// </summary>

{
    ///{|RH8201: <summary>Runs here</summary>
|}    public partial void M();

    ///{|RH8201: <summary>Runs there</summary>
|}    public partial void M()
    {
    }

    /// <inheritdoc/>
    public partial int P { get; }

    ///{|RH8201: <summary>Value here</summary>

}
```

### RH8201-002 — A member that only resembles an inherited one is not reported

The analyzer MUST NOT report a member that neither is declared `override` nor implements an interface member for the type that declares it, even when it has the name and signature of such a member: an overload of an implemented member, a member that hides an inherited implementation with `new` in a type that does not list the interface again, a member of a base type that only a derived type's interface would map to, a member that has the signature of an interface member that the type implements explicitly elsewhere, an interface member that hides a base interface member with `new`, and an interface's own member.

Why: Only a member that overrides or implements another member has a description to inherit; `<inheritdoc/>` on any other member would leave it without documentation.

Example:

```csharp
using System;

/// <summary>
/// Contract
/// </summary>
public interface I
{
    /// <summary>
    /// Runs
    /// </summary>
    void Run();
}

/// <summary>
/// Derived contract
/// </summary>
public interface J : I
{
    /// <summary>
    /// Runs differently
    /// </summary>
    new void Run();
}

/// <summary>
/// Base
/// </summary>
public class B
{
    /// <summary>
    /// Runs
    /// </summary>
    public void Run()
    {
    }
}

/// <summary>
/// Derived
/// </summary>
public class D : B, I
{
}

/// <summary>
/// Service
/// </summary>
public class C : I
{
    /// <inheritdoc/>
    void I.Run()
    {
    }

    /// <summary>
    /// Runs as well
    /// </summary>
    public void Run()
    {
    }

    /// <summary>
    /// Runs with a value
    /// </summary>
    /// <param name="value">Value</param>
    public void Run(int value)
    {
    }
}
```

is not reported.

### RH8201-003 — An implicit implementation is not reported when its interfaces may depend on `#if`

The analyzer MUST NOT report a member that inherits its documentation only by implicitly implementing an interface member when an `#if` directive appears anywhere in a file that declares the member's type, in any of its partial declarations, or in a file that declares one of the interfaces the type implements. A member that is declared `override` or explicitly implements an interface member MUST be reported whatever directives the files contain. Other directives, such as `#region` and `#pragma`, MUST NOT prevent the report, and neither MUST an `#if` in a file that declares neither the type nor one of its interfaces.

Why: Whether a member implicitly implements an interface member depends on the type's interface lists and on the members of the interfaces, and an `#if` can change either in a build configuration the analyzer does not see. In that configuration, `<inheritdoc/>` would leave the member without documentation. An override and an explicit implementation implement their member in every configuration in which they compile.

Example:

```csharp
using System;

/// <summary>
/// Base
/// </summary>
public abstract class B
{
    /// <summary>
    /// Runs
    /// </summary>
    public abstract void Run();
}

/// <summary>
/// Service
/// </summary>
public class C : B, IDisposable
#if FEATURE
    , ICloneable
#endif
{
    ///{|RH8201: <summary>Runs here</summary>
|}    public override void Run()
    {
    }

    /// <summary>
    /// Disposes
    /// </summary>
    public void Dispose()
    {
    }

#if FEATURE
    /// <inheritdoc/>
    public object Clone() => this;
#endif
}
```

Example:

```csharp
using System;

/// <summary>
/// Service
/// </summary>
public class C : IDisposable
{
    #region Methods

    ///{|RH8201: <summary>Disposes</summary>
|}    public void Dispose()
    {
    }

    #endregion
}
```

### RH8201-004 — The diagnostic covers the documentation comment

The analyzer MUST report one diagnostic per member, and for a partial member one per reported part (RH8201-001), located on its documentation comment from the first character after the opening `///` or `/**`: through the line break that ends the last line of a `///` comment, and through the closing `*/` of a `/** */` comment.

Why: The whole comment is what the fix replaces, so the squiggle shows the text that will disappear.

Example: see RH8201-001, and RH8201-005 for a `/** */` comment.

### RH8201-005 — The fix replaces the comment with `<inheritdoc/>`

The code fix MUST replace the reported documentation comment with the single line `/// <inheritdoc/>` at the position of the comment, starting in the column in which the comment's first `///` or `/**` starts, and MUST keep the ordinary comments and preprocessor directives before or after it in the member's leading trivia, and the attribute lists that follow it, where they stand: on their lines, in their columns, with the blank lines between them. The member's lines MUST stay as they are; only a member whose first token followed `*/` gets a line of its own, as the last sentence states. When the reported comment is a `/** */` comment, the fix MUST also remove the line break that ends the line of its `*/`, together with the white space before that line break, so no empty line is left; an ordinary comment that followed `*/` on that line MUST be kept on its own line after `/// <inheritdoc/>`, indented like the member. When the member's first token followed `*/` on that line, the fix MUST put the member on the line after `/// <inheritdoc/>`, in the column in which the `/**` started, because a `///` comment ends at the end of its line.

This requirement covers a document whose line breaks are `\n` or `\r\n` (SHARED-FIX-008 states the line ending of the line the fix writes), and a member at any indentation, whose reported comment, ordinary comments, and attribute lists start their own lines, and whose leading trivia holds, apart from the reported comment, ordinary comments, blank lines, and the preprocessor directives `#if`, `#elif`, `#else`, `#endif`, `#region`, `#endregion`, `#pragma`, and `#nullable`, with the code an `#if` group excludes, each directive starting its own line in any column; after the `*/` of a reported `/** */` comment, only an ordinary comment, the member's first token, or nothing may follow on its line.

Why: `<inheritdoc/>` takes the whole description from the inherited member, so nothing of the replaced comment is needed. The comments, directives, and attribute lists around it are not part of what the diagnostic reports, so they stay where they are, in the columns and line endings the author wrote (SHARED-FIX-006): a fix that re-indents them, or the member, changes code its diagnostic is not about.

Example:

```csharp
/// <summary>
/// Base
/// </summary>
public abstract class B
{
    /// <summary>
    /// Runs
    /// </summary>
    public abstract void Run();

    /// <summary>
    /// Stops
    /// </summary>
    public abstract void Stop();
}

/// <summary>
/// Derived
/// </summary>
public class C : B
{
    // Ordinary comment
    ///{|RH8201: <summary>
    /// Runs here
    /// </summary>
    /// <remarks>
    /// Differs
    /// </remarks>
|}    [System.Obsolete]
    public override void Run()
    {
    }

    /**{|RH8201: <summary>Stops here</summary> */|} // Trailing
    public override void Stop()
    {
    }
}
```
