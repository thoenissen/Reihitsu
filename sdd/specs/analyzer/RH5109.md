# Analyzer — RH5109 Parameters must be on same line or separate lines

| | |
|---|---|
| ID prefix | RH5109 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5109ParametersMustBeOnSameLineOrSeparateLinesAnalyzer`, `RH5109ParametersMustBeOnSameLineOrSeparateLinesCodeFixProvider` |
| Uses | FMT-BREAK-012, SHARED-DIAG-008 |

RH5109 reports a parameter list whose parameters span several lines and in which two parameters start on the same line, and offers a code fix that puts every parameter on its own line.

## Non-goals

- Whether the first parameter starts on the line of the opening parenthesis — RH5108.
- The bracketed parameter list of an indexer.
- Argument lists — RH5102.

## Requirements

### RH5109-001 — Parameters sharing a line in a multi-line list are reported

The analyzer MUST report a parenthesized parameter list — of a declaration, a primary constructor, an anonymous method, or a parenthesized lambda — with at least two parameters when the list is multi-line and two of its parameters start on the same line. The parameters alone decide whether the list is multi-line, as FMT-BREAK-012 decides it by the list's elements: the list is multi-line when two of its parameters start on different lines, or when a parameter spans several lines, its type included. A multi-line list in which every parameter starts its own line MUST NOT be reported. A list whose parameters all start on one line, none of them spanning lines, MUST NOT be reported, also when that line is not the line of the opening parenthesis, when the closing parenthesis stands on a later line, or when a comment or a directive keeps the first parameter off the line of the opening parenthesis.

Why: A partly wrapped list hides parameters at the end of a line, so the reader cannot see at a glance how many there are; a list is either compact or one parameter per line (FMT-BREAK-012). Parameters that all start on one line are compact, wherever the parentheses stand; whether a line break around them belongs there is not this rule's question.

Example:

```csharp
using System.Collections.Generic;

class C
{
    void M{|RH5109:(|}int a, int b,
           int c)
    {
    }

    void N{|RH5109:(|}int a, Dictionary<int,
           int> b)
    {
    }

    void O(int a, int b)
    {
    }

    void P(int a,
           int b)
    {
    }

    void Q{|RH5109:(|}
        int a, int b,
        int c)
    {
    }
}
```

A list whose parameters all start on one line is not reported, whether a line break stands behind its opening parenthesis, in front of its closing parenthesis, or behind a comment that keeps the first parameter off the line of the opening parenthesis:

```csharp
class C
{
    void M(
        int a, int b)
    {
    }

    void N(int a, int b
          )
    {
    }

    void O( // c
        int a, int b)
    {
    }
}
```

is not reported.

### RH5109-002 — The diagnostic is on the opening parenthesis

The analyzer MUST report one diagnostic per parameter list, located on its opening parenthesis, however many parameters share a line.

Why: The layout of the whole list is wrong, not one parameter; the opening parenthesis marks the list and is the anchor its parameters align to.

Example: see RH5109-001.

### RH5109-003 — The fix puts every parameter on its own line

The code fix MUST rewrite the parameter list from its opening to its closing parenthesis with the first parameter directly behind the opening parenthesis, every further parameter on a line of its own behind the comma of the previous one, aligned one column right of the opening parenthesis, and the closing parenthesis directly behind the last parameter. The text of each parameter MUST be kept as written.

Why: One parameter per line, aligned under the first one, is the layout of a wrapped parameter list (FMT-BREAK-012). Rebuilding only the list leaves the rest of the declaration as it is.

Example:

```csharp
class C
{
    void M{|RH5109:(|}int a, int b,
           int c)
    {
    }

    void N{|RH5109:(|}
        int a, int b,
        int c)
    {
    }
}
```

```csharp
class C
{
    void M(int a,
           int b,
           int c)
    {
    }

    void N(int a,
           int b,
           int c)
    {
    }
}
```

### RH5109-004 — A comment or directive in the parameter list withholds the fix

The span the rule judges is where each parameter starts: the gaps between the opening parenthesis, the parameters, the commas, and the closing parenthesis. A parameter list with an `#if`, `#elif`, `#else`, or `#endif` directive, or code such a directive excludes, in one of those gaps MUST NOT be reported (SHARED-DIAG-008). A conditional directive inside a parameter, such as in a default value, lies outside that span and MUST NOT keep the list from being reported. The code fix MUST NOT be offered when a comment or another preprocessor directive, such as `#region` or `#pragma`, sits in one of those gaps, when a comment or a preprocessor directive of any kind sits inside a parameter, a documentation comment included, or when a comment or a preprocessor directive of any kind sits on a line of its own in front of the opening parenthesis, between the line break in front of it and the parenthesis. A comment behind the closing parenthesis, and a comment on the line of the token in front of the opening parenthesis, MUST NOT withhold the fix. The diagnostic is still reported.

Why: The fix rebuilds the list from the text of its parameters, so a comment between them would be lost. A comment behind the closing parenthesis or behind the token in front of the opening parenthesis is outside the rebuilt text and stays where it is.

Example:

```csharp
class C
{
    void M{|RH5109:(|}int a, // first
           int b, int c)
    {
    }
}
```

is reported, and no code fix is offered. In

```csharp
class C
{
    void M{|RH5109:(|}int a, int b,
           int c) // note
    {
    }

    void N /* note */ {|RH5109:(|}int a, int b,
                     int c)
    {
    }
}
```

the comments follow the closing parenthesis or the token in front of the opening parenthesis, and the fix is offered.

Example — a conditional directive in a gap between the parameters keeps the list from being reported, a `#pragma` there withholds only the fix, and a conditional directive inside a parameter withholds only the fix:

```csharp
class C
{
    void M(int a, int b,
#if DEBUG
#endif
           int c)
    {
    }

    void N{|RH5109:(|}int a, int b,
#pragma warning disable CS0168
           int c)
    {
    }

    void O{|RH5109:(|}int a, int b,
           int c = 1
#if DEBUG
               + 1
#endif
               + 2)
    {
    }
}
```

`M` is not reported; `N` and `O` are reported, and no code fix is offered.
