# Analyzer — RH5202 Raw string literals should be formatted correctly

| | |
|---|---|
| ID prefix | RH5202 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5202RawStringLiteralsShouldBeFormattedCorrectlyAnalyzer`, `RH5202RawStringLiteralsShouldBeFormattedCorrectlyCodeFixProvider` |
| Uses | FMT-RAW-001, FMT-RAW-002, FMT-RAW-003, FMT-RAW-004, FMT-RAW-009, SHARED-FIX-002, SHARED-FIX-003, SHARED-FIX-006, SHARED-FIX-007 |

RH5202 reports a multi-line raw string literal whose closing quotes do not start in the column of its opening quotes, and offers a code fix that shifts the literal's lines so that they do, unless the shift would change the value of a raw string literal nested in one of its interpolation holes (RH5202-006).

## Non-goals

- Single-line raw string literals, verbatim strings, and regular strings.
- The column of the opening quotes, which the code in front of the literal decides.

## Requirements

### RH5202-001 — A misaligned multi-line raw string literal is reported

The analyzer MUST report a multi-line raw string literal — plain, UTF-8 (`u8`), or interpolated with any number of `$` — when the whitespace in front of its closing quotes is not as wide as the column of its opening quotes. For an interpolated literal, the opening quotes start behind its `$` characters. A literal whose closing quotes start in the column of its opening quotes MUST NOT be reported.

Why: The closing quotes decide how much whitespace is stripped from every content line, so a literal aligned under its opening quotes shows its content where it ends up in the value, and it moves with the code around it as one block (FMT-RAW-001, FMT-RAW-003, FMT-RAW-004).

Example:

```csharp
class C
{
    void M(int name)
    {
        var a = {|RH5202:"""
            Test
            """|};
        var b = {|RH5202:$$"""
            Hello {{name}}
            """|};
        var c = {|RH5202:"""
                        Far
                        """u8|};
        var d = {|RH5202:""""
            Four
            """"|};
        var e = """
                Aligned
                """;
        var f = $"""
                 Hello {name}
                 """;
    }
}
```

### RH5202-002 — The diagnostic is on the literal

The analyzer MUST report one diagnostic per literal, located on the whole literal from its opening to its closing quotes, the `$` characters and the `u8` suffix included.

Why: The whole literal moves, not only its closing line.

Example: see RH5202-001.

### RH5202-003 — The fix shifts the lines after the first by the same amount

The code fix MUST shift every line of the literal after its first line, apart from the lines RH5202-004 and RH5202-005 leave as written, by the difference between the column of the opening quotes and the width of the whitespace in front of the closing quotes, adding spaces in front of each line or removing that much leading whitespace from it — all of it, when the line has less — so that the closing quotes start in the column of the opening quotes. The relative indentation of the content lines MUST be kept.

Why: Shifting the literal's own lines by the same amount keeps the value of the literal unchanged, because the stripped prefix grows or shrinks with the closing line (FMT-RAW-002). The lines of an interpolation hole move with them, so the code in the hole keeps its place in the literal.

Example:

```csharp
class C
{
    void M(int name)
    {
        var a = {|RH5202:"""
            Test
              indented
            """|};
        var b = {|RH5202:$$"""
            Hello {{name}}
            """|};
        var c = {|RH5202:"""
                        Far
                        """u8|};
    }
}
```

```csharp
class C
{
    void M(int name)
    {
        var a = """
                Test
                  indented
                """;
        var b = $$"""
                  Hello {{name}}
                  """;
        var c = """
                Far
                """u8;
    }
}
```

### RH5202-004 — The fix leaves the lines of text nested in a hole as written

For an interpolated literal, the code fix MUST leave a line as written, and MUST NOT shift it, when the line starts inside the text of a literal other than a raw string, or inside a comment, that began on an earlier line within one of the literal's interpolation holes: a space written in front of such a line would become part of that literal's value or of that comment's text. This covers the continuation lines of a verbatim string (`@"…"`, also `@"…"u8`), of an interpolated verbatim string (`$@"…"` or `@$"…"`), and the following lines of a `/* */` or `/** */` comment, whether the comment stands behind a token or in front of one, in both directions of the shift, and at every depth: directly in the hole, as an argument in the hole, in a hole of a regular or verbatim interpolated string nested in the hole. The other lines of the literal shift as RH5202-003 states, so the closing quotes start in the column of the opening quotes and the diagnostic is gone; the result is the formatter's layout of the literal (FMT-RAW-009).

The condition has three parts, each with a case on the other side:

- **Starts inside the text.** A line that starts after such a literal or comment has ended, such as the line of the hole's closing brace below the last line of a comment, does not start inside its text, and shifts.
- **Began on an earlier line.** A line on which such a literal or comment begins does not start inside it, and shifts, as the line `Hello {@"a` in the first example.
- **A literal other than a raw string.** The lines of a multi-line raw string literal nested in a hole are not left as written: they shift with the outer literal, apart from an empty line, which RH5202-005 leaves empty. To the right, each of them shifts by the same amount; to the left, a line with less leading whitespace than the shift loses all of it, and RH5202-006 withholds the fix wherever that would change the nested literal's value. The nested literal is reported on its own, and its own fix aligns it.

Why: The start of such a line is part of the nested literal's value or of the comment's text, so shifting it would change what the program does or the text the user wrote, which no code fix may do (SHARED-FIX-003). The formatter leaves the same lines as written (FMT-RAW-009), so the fix's result is the layout formatting gives it (SHARED-FIX-007). A raw string literal nested in a hole strips its own indentation, so shifting its lines by the same amount keeps its value; where a leftward shift cannot remove the same amount from each of its lines, RH5202-006 decides.

Example — the literal moves 13 columns to the right; the continuation line of the verbatim string stays in column 0:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:$"""
    Hello {@"a
b"}
    """|};
    }
}
```

```csharp
class C
{
    void M()
    {
        var a = $"""
                 Hello {@"a
b"}
                 """;
    }
}
```

Example — the literal moves 8 columns to the left; the continuation line stays in column 18:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:$"""
                         Hello {@"a
                  b"}
                         """|};
    }
}
```

```csharp
class C
{
    void M()
    {
        var a = $"""
                 Hello {@"a
                  b"}
                 """;
    }
}
```

Example — the second line of a comment in a hole stays in column 2, and the line of the hole's closing brace, which follows the comment, shifts:

```csharp
class C
{
    void M()
    {
        var name = "x";
        var a = {|RH5202:$"""
    Hello {name /* a
  b */
    }
    """|};
    }
}
```

```csharp
class C
{
    void M()
    {
        var name = "x";
        var a = $"""
                 Hello {name /* a
  b */
                 }
                 """;
    }
}
```

Example — an empty line inside a verbatim string stays empty:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:$"""
    Hello {@"a

b"}
    """|};
    }
}
```

```csharp

    void M()
    {
        var a = $"""
                 Hello {@"a

b"}

    }
}
```

Example — the lines of a raw string literal nested in a hole shift with the outer literal; the nested literal is still reported after the outer literal's fix:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:$"""
    Hello {{|RH5202:"""
        x
```

### RH5202-005 — The fix leaves an empty line empty

The code fix MUST leave every line of the literal after its first line that is empty — no character between its line breaks — empty, also when it shifts the other lines to the right. This holds for every kind of line the fix shifts: a content line of the literal's own text, a content line of a multi-line raw string literal nested in one of its interpolation holes (at any depth), and a line of the code in an interpolation hole that lies outside every literal's text, such as an empty line between the hole's expression and its closing brace. An empty line inside the text of a verbatim string or a comment nested in a hole stays as written under RH5202-004.

The condition has one qualifier, with a case on each side:

- **Empty.** A content line that holds only whitespace is not empty: it shifts as RH5202-003 states, so a content line of six spaces in place of the empty line of the first example below becomes a line of eighteen spaces.

Why: The code a fix changes is laid out as the formatter lays it out, so that formatting the result changes nothing in it (SHARED-FIX-007), and the formatter never leaves whitespace on an empty line: it keeps an empty content line empty (FMT-RAW-002), also in a raw string nested in a hole. An empty line of hole code is a blank line; the formatter keeps it empty or removes it, and removing it is a blank-line decision a fix does not make (SHARED-FIX-006), so leaving it empty is the formatter's layout of the line as far as the fix may go. Spaces written onto any of these lines would always be removed by formatting. Leaving an empty line empty also keeps the value: an empty content line contributes an empty line to the value whatever the closing quotes strip, and an empty line of hole code is no part of a value. A whitespace-only content line is shifted because its whitespace is part of the value relative to the closing quotes, and the formatter shifts it as well (FMT-RAW-002).

In the examples, `·` stands for one space at the end of a line.

Example — the lines move 12 columns to the right, and the empty content line stays empty:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:"""
    one

    two
    """|};
    }
}
```

```csharp

        var a = """
                one

                two
```

Example — a content line of six spaces in the same place is not empty and shifts with the other lines:

```csharp

    two
    """|};
    }
}
```

```csharp

    {

                two
                """;
```

Example — in an interpolated literal, the empty content line stays empty as well:

### RH5202-006 — The fix is withheld when a leftward shift would change the value of a raw string nested in a hole

The code fix MUST NOT be offered for an interpolated literal when it would shift the literal's lines to the left by more columns than the whitespace in front of the closing quotes of a multi-line raw string literal nested in one of its interpolation holes is wide, and a content line of that nested literal starts with more whitespace characters than its closing line does. A content line is a line of the nested literal after its opening line, other than its closing line, that starts in its text rather than in one of its own holes; a content line that holds only whitespace counts with all of its characters. The condition applies to every multi-line raw string literal nested in a hole — plain, UTF-8 (`u8`), or interpolated with any number of `$` — at any depth, directly in the hole or in a hole of a literal nested there. In every other case the fix is offered as RH5202-003, RH5202-004, and RH5202-005 state; the diagnostic stays reported either way.

The condition has three parts, each with a case on the other side:

- **To the left.** A shift to the right adds the same number of spaces in front of every shifted line, so it never changes a nested literal's value and is never withheld (the nested-raw-string examples of RH5202-004 and RH5202-005).
- **More columns than the nested closing whitespace is wide.** When the nested literal's closing whitespace is at least as wide as the shift, every line of the nested literal has enough leading whitespace to lose the whole shift, and the fix is offered (second example below). Narrower closing whitespace includes none at all, closing quotes in column 0.
- **A content line wider than the closing line.** When the nested closing whitespace is narrower than the shift but no content line of the nested literal starts with more whitespace characters than the closing line, each content line loses as many characters as the closing line, or all of its whitespace when it holds only whitespace and is no wider, and the fix is offered (third example below). A content line that holds only whitespace and is wider than the closing line withholds the fix like any other wider line (fourth example below).

Why: A raw string literal strips from each content line the whitespace in front of its closing quotes. When the closing line has fewer whitespace characters than the shift, it loses only those it has, while a content line with more loses more, so the stripped part of that content line shrinks and the value changes: a content line holding text loses leading whitespace from its value, and a content line holding only whitespace loses some or all of the whitespace it contributes. A fix that changes a literal's value is not offered (SHARED-FIX-003). The outer literal's own content lines never meet the condition, because each of them starts with the whitespace in front of the outer closing quotes, which is wider than the shift. When the nested literal's opening quotes stand at least as many columns from the start of their line as the shift — always the case when the nested literal opens on a content line of the outer literal, as in every example below — the nested literal's own diagnostic keeps its fix, which shifts its lines to the right until its closing quotes start in the column of its opening quotes, so its closing whitespace becomes at least as wide as the shift, and once that fix has run, the outer literal's fix is offered on the result (SHARED-FIX-002). When they stand closer to the start of their line, as when the nested literal opens on a line that starts in the outer literal's hole code at a low column, no fix of the nested literal can widen its closing whitespace to the shift, and the outer diagnostic stays without a fix.

In the examples, `·` stands for one space at the end of a line. The outer literal's lines move 8 columns to the left.

Example — the nested closing quotes start in column 4, the line of `x` in column 34. Both literals are reported, and no code fix is offered for the outer literal: the shift would remove 4 characters from the nested closing line but 8 from the line of `x`, so the value would lose 4 of the 30 spaces in front of `x`. The same holds for a nested interpolated raw string, such as `$"""` with `x{n}` on that line, and for nested closing quotes in column 0. The nested literal's fix is offered and moves its lines 28 columns to the right; after it, the outer literal's fix is offered and keeps the 30 spaces:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:$"""
                         Hello {{|RH5202:"""
                                  x
    """|}}
                         """|};
    }
}
```

Example — the nested closing quotes start in column 8, as wide as the shift: every line loses 8 columns, `x` keeps the 26 spaces in front of it in the value, and the nested literal is still reported after the outer literal's fix:
