# Analyzer — RH5202 Raw string literals should be formatted correctly

| | |
|---|---|
| ID prefix | RH5202 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5202RawStringLiteralsShouldBeFormattedCorrectlyAnalyzer`, `RH5202RawStringLiteralsShouldBeFormattedCorrectlyCodeFixProvider` |
| Uses | FMT-RAW-001, FMT-RAW-002, FMT-RAW-003, FMT-RAW-004, FMT-RAW-009, FMT-RAW-010, SHARED-DIAG-003, SHARED-FIX-002, SHARED-FIX-003, SHARED-FIX-006, SHARED-FIX-007, SHARED-FIX-008 |

RH5202 reports a multi-line raw string literal whose closing quotes do not start in the column of its opening quotes, or start there behind whitespace that holds a tab (RH5202-009), and offers a code fix that shifts the literal's lines so that they do and writes the indentation the compiler strips from a tab-indented literal as spaces (RH5202-007), unless the shift would change the value of a raw string literal nested in one of its interpolation holes (RH5202-006) or such a nested literal is indented with tabs (RH5202-008).

## Non-goals

- Single-line raw string literals, verbatim strings, and regular strings.
- The column of the opening quotes, which the code in front of the literal decides.

## Requirements

### RH5202-001 — A misaligned multi-line raw string literal is reported

The analyzer MUST report a multi-line raw string literal — plain, UTF-8 (`u8`), or interpolated with any number of `$` — when the whitespace in front of its closing quotes is not as wide as the column of its opening quotes. For an interpolated literal, the opening quotes start behind its `$` characters. A literal whose closing quotes start in the column of its opening quotes MUST NOT be reported, unless the whitespace in front of them holds a tab (RH5202-009).

The whitespace in front of the closing quotes is the whitespace between the last line break inside the literal and the closing quotes, and the column of the opening quotes is counted from the line break before them. A line break is each line terminator C# recognizes: `\r\n`, `\n`, a lone `\r`, U+0085, U+2028, and U+2029. The analyzer and the fix (RH5202-003) find the closing line and measure its whitespace in the same way, in every one of these line-break styles, also in a document whose line breaks are all a lone `\r` (SHARED-FIX-008).

Why: The closing quotes decide how much whitespace is stripped from every content line, so a literal aligned under its opening quotes shows its content where it ends up in the value, and it moves with the code around it as one block (FMT-RAW-001, FMT-RAW-003, FMT-RAW-004).

Example:

```csharp
class C
{
    void M(int name)
    {
        var a = {|RH5202:"""
            Test
            """|};
        var b = {|RH5202:$$"""
            Hello {{name}}
            """|};
        var c = {|RH5202:"""
                        Far
                        """u8|};
        var d = {|RH5202:""""
            Four
            """"|};
        var e = """
                Aligned
                """;
        var f = $"""
                 Hello {name}
                 """;
    }
}
```

Example — in a document whose line breaks are all a lone `\r`, each marked `⏎` at the end of its line, the literal `a` is aligned and `b` is not:

```csharp
class C⏎
{⏎
    void M()⏎
    {⏎
        var a = """⏎
                Hello⏎
                """;⏎
        var b = {|RH5202:$"""⏎
            Hello {1}⏎
            """|};⏎
    }⏎
}
```

### RH5202-002 — The diagnostic is on the literal

The analyzer MUST report one diagnostic per literal, located on the whole literal from its opening to its closing quotes, the `$` characters and the `u8` suffix included.

Why: The whole literal moves, not only its closing line.

Example: see RH5202-001.

### RH5202-003 — The fix shifts the lines after the first by the same amount

The code fix MUST shift every line of the literal after its first line, apart from the lines RH5202-004 and RH5202-005 leave as written, by the difference between the column of the opening quotes and the width of the whitespace in front of the closing quotes, adding spaces in front of each line or removing that much leading whitespace from it — all of it, when the line has less — so that the closing quotes start in the column of the opening quotes. The relative indentation of the content lines MUST be kept. Where the whitespace in front of the closing quotes holds a tab, the fix also writes part of the remaining whitespace as spaces, as RH5202-007 states; for a literal that RH5202-009 reports, the difference is zero, no line shifts, and the fix writes only those spaces.

Why: Shifting the literal's own lines by the same amount keeps the value of the literal unchanged, because the stripped prefix grows or shrinks with the closing line (FMT-RAW-002). The lines of an interpolation hole move with them, so the code in the hole keeps its place in the literal.

Example:

```csharp
class C
{
    void M(int name)
    {
        var a = {|RH5202:"""
            Test
              indented
            """|};
        var b = {|RH5202:$$"""
            Hello {{name}}
            """|};
        var c = {|RH5202:"""
                        Far
                        """u8|};
    }
}
```

```csharp
class C
{
    void M(int name)
    {
        var a = """
                Test
                  indented
                """;
        var b = $$"""
                  Hello {{name}}
                  """;
        var c = """
                Far
                """u8;
    }
}
```

In a document whose line breaks are all a lone `\r`, marked `⏎` as in RH5202-001, one application aligns the literal, and the analyzer no longer reports it; the line breaks inside the literal are its text and stay a lone `\r` (SHARED-FIX-008):

```csharp
class C⏎
{⏎
    void M()⏎
    {⏎
        var b = {|RH5202:$"""⏎
            Hello {1}⏎
            """|};⏎
    }⏎
}
```

```csharp

{⏎
    void M()⏎
    {⏎
        var b = $"""⏎
                 Hello {1}⏎
                 """;⏎
    }⏎
}
```

### RH5202-004 — The fix leaves the lines of text nested in a hole as written

For an interpolated literal, the code fix MUST leave a line as written, and MUST NOT shift it, when the line starts inside the text of a literal other than a raw string, or inside a comment, that began on an earlier line within one of the literal's interpolation holes: a space written in front of such a line would become part of that literal's value or of that comment's text. This covers the continuation lines of a verbatim string (`@"…"`, also `@"…"u8`), of an interpolated verbatim string (`$@"…"` or `@$"…"`), and the following lines of a `/* */` or `/** */` comment, whether the comment stands behind a token or in front of one, in both directions of the shift, and at every depth: directly in the hole, as an argument in the hole, in a hole of a regular or verbatim interpolated string nested in the hole. The other lines of the literal shift as RH5202-003 states, so the closing quotes start in the column of the opening quotes and the diagnostic is gone; the result is the formatter's layout of the literal (FMT-RAW-009).

The condition has three parts, each with a case on the other side:

- **Starts inside the text.** A line that starts after such a literal or comment has ended, such as the line of the hole's closing brace below the last line of a comment, does not start inside its text, and shifts.
- **Began on an earlier line.** A line on which such a literal or comment begins does not start inside it, and shifts, as the line `Hello {@"a` in the first example.
- **A literal other than a raw string.** The lines of a multi-line raw string literal nested in a hole are not left as written: they shift with the outer literal, apart from an empty line, which RH5202-005 leaves empty. To the right, each of them shifts by the same amount; to the left, a line with less leading whitespace than the shift loses all of it, and RH5202-006 withholds the fix wherever that would change the nested literal's value. The nested literal is reported on its own, and its own fix aligns it.

Why: The start of such a line is part of the nested literal's value or of the comment's text, so shifting it would change what the program does or the text the user wrote, which no code fix may do (SHARED-FIX-003). The formatter leaves the same lines as written (FMT-RAW-009), so the fix's result is the layout formatting gives it (SHARED-FIX-007). A raw string literal nested in a hole strips its own indentation, so shifting its lines by the same amount keeps its value; where a leftward shift cannot remove the same amount from each of its lines, RH5202-006 decides.

Example — the literal moves 13 columns to the right; the continuation line of the verbatim string stays in column 0:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:$"""
    Hello {@"a
b"}
    """|};
    }
}
```

```csharp
class C
{
    void M()
    {
        var a = $"""
                 Hello {@"a
b"}
                 """;
    }
}
```

Example — the literal moves 8 columns to the left; the continuation line stays in column 18:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:$"""
                         Hello {@"a
                  b"}
                         """|};
    }
}
```

```csharp

```

Example — the second line of a comment in a hole stays in column 2, and the line of the hole's closing brace, which follows the comment, shifts:

```csharp

    void M()
    {
        var name = "x";
```

### RH5202-005 — The fix leaves an empty line empty

The code fix MUST leave every line of the literal after its first line that is empty — no character between its line breaks — empty, also when it shifts the other lines to the right. This holds for every kind of line the fix shifts: a content line of the literal's own text, a content line of a multi-line raw string literal nested in one of its interpolation holes (at any depth), and a line of the code in an interpolation hole that lies outside every literal's text, such as an empty line between the hole's expression and its closing brace. An empty line inside the text of a verbatim string or a comment nested in a hole stays as written under RH5202-004.

The condition has one qualifier, with a case on each side:

- **Empty.** A content line that holds only whitespace is not empty: it shifts as RH5202-003 states, so a content line of six spaces in place of the empty line of the first example below becomes a line of eighteen spaces.

Why: The code a fix changes is laid out as the formatter lays it out, so that formatting the result changes nothing in it (SHARED-FIX-007), and the formatter never leaves whitespace on an empty line: it keeps an empty content line empty (FMT-RAW-002), also in a raw string nested in a hole. An empty line of hole code is a blank line; the formatter keeps it empty or removes it, and removing it is a blank-line decision a fix does not make (SHARED-FIX-006), so leaving it empty is the formatter's layout of the line as far as the fix may go. Spaces written onto any of these lines would always be removed by formatting. Leaving an empty line empty also keeps the value: an empty content line contributes an empty line to the value whatever the closing quotes strip, and an empty line of hole code is no part of a value. A whitespace-only content line is shifted because its whitespace is part of the value relative to the closing quotes, and the formatter shifts it as well (FMT-RAW-002).

In the examples, `·` stands for one space at the end of a line.

Example — the lines move 12 columns to the right, and the empty content line stays empty:

### RH5202-006 — The fix is withheld when a leftward shift would change the value of a raw string nested in a hole

The code fix MUST NOT be offered for an interpolated literal when it would shift the literal's lines to the left by more columns than the whitespace in front of the closing quotes of a multi-line raw string literal nested in one of its interpolation holes is wide, and a content line of that nested literal starts with more whitespace characters than its closing line does. A content line is a line of the nested literal after its opening line, other than its closing line, that starts in its text rather than in one of its own holes; a content line that holds only whitespace counts with all of its characters. The condition applies to every multi-line raw string literal nested in a hole — plain, UTF-8 (`u8`), or interpolated with any number of `$` — at any depth, directly in the hole or in a hole of a literal nested there. In every other case the fix is offered as RH5202-003, RH5202-004, and RH5202-005 state; the diagnostic stays reported either way.

The condition has three parts, each with a case on the other side:

- **To the left.** A shift to the right adds the same number of spaces in front of every shifted line, so it never changes a nested literal's value and is never withheld (the nested-raw-string examples of RH5202-004 and RH5202-005).
- **More columns than the nested closing whitespace is wide.** When the nested literal's closing whitespace is at least as wide as the shift, every line of the nested literal has enough leading whitespace to lose the whole shift, and the fix is offered (second example below). Narrower closing whitespace includes none at all, closing quotes in column 0.
- **A content line wider than the closing line.** When the nested closing whitespace is narrower than the shift but no content line of the nested literal starts with more whitespace characters than the closing line, each content line loses as many characters as the closing line, or all of its whitespace when it holds only whitespace and is no wider, and the fix is offered (third example below). A content line that holds only whitespace and is wider than the closing line withholds the fix like any other wider line (fourth example below).

Why: A raw string literal strips from each content line the whitespace in front of its closing quotes. When the closing line has fewer whitespace characters than the shift, it loses only those it has, while a content line with more loses more, so the stripped part of that content line shrinks and the value changes: a content line holding text loses leading whitespace from its value, and a content line holding only whitespace loses some or all of the whitespace it contributes. A fix that changes a literal's value is not offered (SHARED-FIX-003). The outer literal's own content lines never meet the condition, because each of them starts with the whitespace in front of the outer closing quotes, which is wider than the shift. While the condition holds, the outer diagnostic stays reported without a fix; it may stay so until other fixes change the code so that the condition no longer holds, and the outer literal's fix is then offered on the result (SHARED-FIX-002).

In the examples, `·` stands for one space at the end of a line. The outer literal's lines move 8 columns to the left.

Example — the nested closing quotes start in column 4, the line of `x` in column 34. Both literals are reported, and no code fix is offered for the outer literal: the shift would remove 4 characters from the nested closing line but 8 from the line of `x`, so the value would lose 4 of the 30 spaces in front of `x`. The same holds for a nested interpolated raw string, such as `$"""` with `x{n}` on that line, and for nested closing quotes in column 0. The nested literal's fix is offered and moves its lines 28 columns to the right; after it, the outer literal's fix is offered and keeps the 30 spaces:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:$"""
                         Hello {{|RH5202:"""
                                  x
    """|}}
                         """|};
    }
}
```

Example — the nested closing quotes start in column 8, as wide as the shift: every line loses 8 columns, `x` keeps the 26 spaces in front of it in the value, and the nested literal is still reported after the outer literal's fix:


### RH5202-007 — The fix writes the stripped indentation of a tab-indented literal as spaces

When the whitespace in front of the literal's closing quotes holds a tab, the code fix MUST write as one space each, after the shift of RH5202-003, every whitespace character in front of the closing quotes, and every whitespace character at the start of a content line of the literal's own text that lies within the width the whitespace in front of the closing quotes has after the shift. Every other character stays as written, and the lines RH5202-004 and RH5202-005 leave as written stay so. The result is the formatter's layout of the literal (FMT-RAW-010).

The conditions, each with a case on the other side:

- **A tab in front of the closing quotes.** When the whitespace in front of the closing quotes holds no tab, the fix writes nothing but the shift of RH5202-003, also when a content line holds a tab behind that width.
- **Within the width.** Whitespace at the start of a content line behind that width is part of the literal's value and stays, a tab included.
- **The literal's own text.** The fix writes no space on the lines of a multi-line raw string literal nested in one of the literal's interpolation holes. When the whitespace in front of that nested literal's closing quotes holds no tab, its lines are shifted as RH5202-004 states and keep their characters, which is the formatter's layout of them. When it holds a tab, the fix is not offered (RH5202-008).

The same holds when the closing quotes already start in the column of the opening quotes behind whitespace that holds a tab: such a literal is reported (RH5202-009), the shift is zero, and the fix writes only these spaces.

Why: The code a fix changes is laid out as the formatter lays it out (SHARED-FIX-007), and the formatter writes the indentation the compiler strips from a tab-indented literal as spaces (FMT-RAW-010). That indentation is no part of the literal's value, so writing it as spaces keeps the value; each character becomes one character, so the closing quotes still start in the column of the opening quotes as RH5202-001 measures it.

In the example, `→` stands for one tab. The literal moves 14 columns to the right; the two tabs in front of the closing quotes and of `Hello` become spaces, and the third tab in front of `World` is behind the width and stays:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:"""
→→Hello
→→→World
→→"""|};
    }
}
```

```csharp
class C
{
    void M()
    {
        var a = """
                Hello
                →World
                """;
    }
}
```

### RH5202-008 — The fix is withheld when a raw string nested in a hole is indented with tabs

The code fix MUST NOT be offered for an interpolated literal when the whitespace in front of the closing quotes of a multi-line raw string literal nested in one of its interpolation holes holds a tab. The condition applies to every multi-line raw string literal nested in a hole — plain, UTF-8 (`u8`), or interpolated with any number of `$` — at any depth, directly in the hole or in a hole of a literal nested there, and to a shift in either direction, also when the literal does not shift because its closing quotes stand in the column of its opening quotes behind whitespace that holds a tab (RH5202-009). The diagnostic stays reported either way.

The condition, with a case on the other side:

- **A tab in front of the nested closing quotes.** When the whitespace in front of every nested literal's closing quotes holds no tab, the fix is offered as RH5202-003 to RH5202-007 state (the nested-raw-string examples of RH5202-004 and RH5202-005), also when a content line of a nested literal holds a tab behind that width.

Why: The formatter writes the indentation the compiler strips from a nested tab-indented literal as spaces (FMT-RAW-010), so a fix that only shifts its lines leaves a result that formatting changes again, which no code fix may do (SHARED-FIX-007). The nested literal is reported on its own (RH5202-001, RH5202-009), and its own fix writes those spaces (RH5202-007). This is a deliberate gap, not an oversight: a tab-indented raw string inside a hole of another raw string is a rare class, and writing the nested literal's indentation from the outer fix would need the fix to find, for every line it shifts, the nested literal whose text the line starts in and that literal's own width — more than the cheap check a rare class allows (*Special cases do not grow the source* in `AGENTS.md`). The outer diagnostic stays without a fix until the nested literal no longer holds a tab in front of its closing quotes, such as after the nested literal's own fix or a whole-document format; the outer literal's fix is then offered on the result (SHARED-FIX-002).

In the examples, `→` stands for one tab.

Example — the nested closing quotes stand behind nine spaces and two tabs, in column 11 counted in characters, the column of the nested opening quotes; the nested literal is reported because its closing whitespace holds a tab (RH5202-009). The outer literal is reported, and no code fix is offered for it; the nested literal's fix is offered, moves no line, and writes the nested literal's indentation as spaces (RH5202-007):

```csharp
class C

         →→"""|}}
    """|};

```

```csharp
    {
        var a = {|RH5202:$"""
    Outer {"""
           inner
           """}
    """|};
    }
}
```

After it, the outer literal's fix is offered and moves every line 13 columns to the right, as in the next example.

Example — the nested closing quotes stand behind two tabs and are reported. No code fix is offered for the outer literal; the nested literal's fix is offered and moves its lines nine columns to the right, writing their indentation as spaces (RH5202-007):


### RH5202-009 — A literal aligned behind tabs is reported

The analyzer MUST report a multi-line raw string literal — plain, UTF-8 (`u8`), or interpolated with any number of `$`, also one nested in an interpolation hole of another raw string literal at any depth — whose closing quotes start in the column of its opening quotes, as RH5202-001 measures it, when the whitespace in front of its closing quotes holds a tab. The diagnostic is located as RH5202-002 states. The code fix MUST then write the spaces RH5202-007 states; the shift of RH5202-003 is zero, so no line moves and no character outside the whitespace RH5202-007 names changes. RH5202-008 withholds the fix of an interpolated literal under the same condition as for a literal that shifts. After the fix, the whitespace in front of the closing quotes holds no tab and stands in the same column, so the literal is no longer reported.

The condition has three parts, each with a case on the other side:

- **In the column of the opening quotes.** A literal whose closing quotes do not start there is reported under RH5202-001 whatever its whitespace holds, and its fix shifts it (RH5202-003, RH5202-007).
- **A tab in front of the closing quotes.** Any tab in that whitespace counts, wherever it stands in it, also tabs written for the indentation of the code and followed by spaces that align the closing quotes in characters. When the whitespace in front of the closing quotes holds no tab — only spaces, or other whitespace characters such as a no-break space — the literal is not reported, also when a content line holds a tab, within or behind the width of the closing whitespace.
- **Nested in a hole.** A raw string literal nested in an interpolation hole is judged by its own closing quotes and opening quotes, like any other literal; it is reported on its own, independently of the outer literal (RH5202-004).

Why: The formatter writes the indentation the compiler strips from a tab-indented literal as spaces, also when the literal already stands in the column of its opening quotes (FMT-RAW-010). That indentation is how the literal spells its value, which this rule judges (SHARED-DIAG-003), so a literal the formatter rewrites in this construct is the rule's own case, and a user who runs only the analyzer gets the same layout. The tab in front of the closing quotes is the one condition by which the formatter writes spaces and the fix writes them (RH5202-007), so the fix's result is neither reported nor changed by formatting (SHARED-FIX-007). In an editor that renders a tab wider than one column, such a literal does not stand under its opening quotes, although each tab counts as one column here.

In the examples, `→` stands for one tab.

Example — the closing quotes stand behind 12 spaces and four tabs, in column 16, the column of the opening quotes; the literal is reported, and the fix writes the tabs in front of `x` and of the closing quotes as spaces:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:"""
            →→→→x
            →→→→"""|};
    }
}
```

```csharp
class C
{
    void M()
    {
        var a = """
                x
                """;
    }
}
```

Example — an interpolated literal: the closing quotes stand behind 12 spaces and five tabs, in column 17. The three spaces in front of `Hello` and the two tabs in front of `World` lie behind that width, are part of the value, and stay:

```csharp
class C
{
    void M(int name)
    {
        var a = {|RH5202:$"""
            →→→→→   Hello {name}
            →→→→→→→World
            →→→→→"""|};
    }
}
```

```csharp
class C
{
    void M(int name)
    {
        var a = $"""
                    Hello {name}
                 →→World
                 """;
    }
}
```

Example — tabs for the indentation of the code and spaces for the alignment: the closing quotes stand behind two tabs and eight spaces, in column 10, the column of the opening quotes counted in characters. The literal is reported, and the fix writes the whitespace in front of `x` and of the closing quotes as 10 spaces, one per character; the tabs on the other lines are outside the literal and stay:

```csharp
class C
{
→void M()
→{
→→var a = {|RH5202:"""
→→        x
→→        """|};
→}
}
```

```csharp
class C
{
→void M()
→{
→→var a = """
          x
          """;
→}
}
```

Example — the closing quotes stand behind 16 spaces; the tab in front of `x` is part of the value, and the literal is not reported:

```csharp
class C
{
    void M()
    {
        var a = """
                →x
                """;
    }
}
```

Example — a nested literal aligned behind tabs is reported on its own, and the outer literal's fix is withheld while it holds the tabs: see the first example of RH5202-008.
