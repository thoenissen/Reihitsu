# Analyzer — RH5202 Raw string literals should be formatted correctly

| | |
|---|---|
| ID prefix | RH5202 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5202RawStringLiteralsShouldBeFormattedCorrectlyAnalyzer`, `RH5202RawStringLiteralsShouldBeFormattedCorrectlyCodeFixProvider` |
| Uses | FMT-RAW-001, FMT-RAW-002, FMT-RAW-003, FMT-RAW-004, FMT-RAW-009, SHARED-FIX-003, SHARED-FIX-007 |

RH5202 reports a multi-line raw string literal whose closing quotes do not start in the column of its opening quotes, and offers a code fix that shifts the literal's lines so that they do.

## Non-goals

- Single-line raw string literals, verbatim strings, and regular strings.
- The column of the opening quotes, which the code in front of the literal decides.

## Requirements

### RH5202-001 — A misaligned multi-line raw string literal is reported

The analyzer MUST report a multi-line raw string literal — plain, UTF-8 (`u8`), or interpolated with any number of `$` — when the whitespace in front of its closing quotes is not as wide as the column of its opening quotes. For an interpolated literal, the opening quotes start behind its `$` characters. A literal whose closing quotes start in the column of its opening quotes MUST NOT be reported.

Why: The closing quotes decide how much whitespace is stripped from every content line, so a literal aligned under its opening quotes shows its content where it ends up in the value, and it moves with the code around it as one block (FMT-RAW-001, FMT-RAW-003, FMT-RAW-004).

Example:

```csharp
class C
{
    void M(int name)
    {
        var a = {|RH5202:"""
            Test
            """|};
        var b = {|RH5202:$$"""
            Hello {{name}}
            """|};
        var c = {|RH5202:"""
                        Far
                        """u8|};
        var d = {|RH5202:""""
            Four
            """"|};
        var e = """
                Aligned
                """;
        var f = $"""
                 Hello {name}
                 """;
    }
}
```

### RH5202-002 — The diagnostic is on the literal

The analyzer MUST report one diagnostic per literal, located on the whole literal from its opening to its closing quotes, the `$` characters and the `u8` suffix included.

Why: The whole literal moves, not only its closing line.

Example: see RH5202-001.

### RH5202-003 — The fix shifts the lines after the first by the same amount

The code fix MUST shift every line of the literal after its first line, apart from the lines RH5202-004 and RH5202-005 leave as written, by the difference between the column of the opening quotes and the width of the whitespace in front of the closing quotes, adding spaces in front of each line or removing that much leading whitespace from it, so that the closing quotes start in the column of the opening quotes. The relative indentation of the content lines MUST be kept.

Why: Shifting the literal's own lines by the same amount keeps the value of the literal unchanged, because the stripped prefix grows or shrinks with the closing line (FMT-RAW-002). The lines of an interpolation hole move with them, so the code in the hole keeps its place in the literal.

Example:

```csharp
class C
{
    void M(int name)
    {
        var a = {|RH5202:"""
            Test
              indented
            """|};
        var b = {|RH5202:$$"""
            Hello {{name}}
            """|};
        var c = {|RH5202:"""
                        Far
                        """u8|};
    }
}
```

```csharp
class C
{
    void M(int name)
    {
        var a = """
                Test
                  indented
                """;
        var b = $$"""
                  Hello {{name}}
                  """;
        var c = """
                Far
                """u8;
    }
}
```

### RH5202-004 — The fix leaves the lines of text nested in a hole as written

For an interpolated literal, the code fix MUST leave a line as written, and MUST NOT shift it, when the line starts inside the text of a literal other than a raw string, or inside a comment, that began on an earlier line within one of the literal's interpolation holes: a space written in front of such a line would become part of that literal's value or of that comment's text. This covers the continuation lines of a verbatim string (`@"…"`, also `@"…"u8`), of an interpolated verbatim string (`$@"…"` or `@$"…"`), and the following lines of a `/* */` or `/** */` comment, whether the comment stands behind a token or in front of one, in both directions of the shift, and at every depth: directly in the hole, as an argument in the hole, in a hole of a regular or verbatim interpolated string nested in the hole. The other lines of the literal shift as RH5202-003 states, so the closing quotes start in the column of the opening quotes and the diagnostic is gone; the result is the formatter's layout of the literal (FMT-RAW-009).

The condition has three parts, each with a case on the other side:

- **Starts inside the text.** A line that starts after such a literal or comment has ended, such as the line of the hole's closing brace below the last line of a comment, does not start inside its text, and shifts.
- **Began on an earlier line.** A line on which such a literal or comment begins does not start inside it, and shifts, as the line `Hello {@"a` in the first example.
- **A literal other than a raw string.** The lines of a multi-line raw string literal nested in a hole are not left as written: they shift with the outer literal by the same amount, apart from an empty content line, which RH5202-005 leaves empty. The nested literal is reported on its own, and its own fix aligns it.

Why: The start of such a line is part of the nested literal's value or of the comment's text, so shifting it would change what the program does or the text the user wrote, which no code fix may do (SHARED-FIX-003). The formatter leaves the same lines as written (FMT-RAW-009), so the fix's result is the layout formatting gives it (SHARED-FIX-007). A raw string literal nested in a hole strips its own indentation, so shifting its lines keeps its value.

Example — the literal moves 13 columns to the right; the continuation line of the verbatim string stays in column 0:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:$"""
    Hello {@"a
b"}
    """|};
    }
}
```

```csharp
class C
{
    void M()
    {
        var a = $"""
                 Hello {@"a
b"}
                 """;
    }
}
```

Example — the literal moves 8 columns to the left; the continuation line stays in column 18:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:$"""
                         Hello {@"a
                  b"}
                         """|};
    }
}
```

```csharp
class C
{
    void M()
    {
        var a = $"""
                 Hello {@"a
                  b"}
                 """;
    }
}
```

Example — the second line of a comment in a hole stays in column 2, and the line of the hole's closing brace, which follows the comment, shifts:

```csharp
class C
{
    void M()
    {
        var name = "x";
        var a = {|RH5202:$"""
    Hello {name /* a
  b */
    }
    """|};
    }
}
```

```csharp
class C
{
    void M()
    {
        var name = "x";
        var a = $"""
                 Hello {name /* a
  b */
                 }
                 """;
    }
}
```

Example — an empty line inside a verbatim string stays empty:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:$"""
    Hello {@"a

b"}
    """|};
    }
}
```

```csharp
class C
{
    void M()
    {
        var a = $"""
                 Hello {@"a

b"}
                 """;
    }
}
```

Example — the lines of a raw string literal nested in a hole shift with the outer literal; the nested literal is still reported after the outer literal's fix:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:$"""
    Hello {{|RH5202:"""
        x
        """|}}
    """|};
    }
}
```

```csharp
class C
{
    void M()
    {
        var a = $"""
                 Hello {{|RH5202:"""
                     x
                     """|}}
                 """;
    }
}
```

### RH5202-005 — The fix leaves an empty line of literal text empty

The code fix MUST leave a line that is empty — no character between its line breaks — empty, also when it shifts the other lines to the right, when the line is a content line of literal text: a line of the literal's own text, or a content line of a multi-line raw string literal nested in one of its interpolation holes, at any depth. A line that holds only whitespace is not empty: it shifts as RH5202-003 states, so in the first example below a line of six spaces in place of the empty line would become a line of eighteen spaces. An empty line inside the text of a verbatim string or a comment nested in a hole stays as written under RH5202-004.

The condition has two parts, each with a case on the other side:

- **Empty.** A content line that holds only whitespace shifts like every other content line.
- **A line of literal text.** An empty line of the code in an interpolation hole — a line that lies outside every literal's text in the hole, such as an empty line between the hole's expression and its closing brace — is not a content line: it shifts as RH5202-003 states, like every other line of the hole. Shifting to the right writes the spaces onto it; shifting to the left finds no whitespace on it to remove, so it stays empty.

Why: An empty line of literal text contributes an empty line to the value whatever the closing quotes strip, so writing spaces onto it changes nothing but leaves whitespace at the end of the line. The formatter keeps such a line empty (FMT-RAW-002), so the fix's result is the layout formatting gives it (SHARED-FIX-007); this holds for a raw string nested in a hole as well, whose content lines the fix shifts with the outer literal (RH5202-004). An empty line of hole code is not part of any value; the fix shifts the lines of a hole as one block and does not decide the layout of the code in it.

Example — the lines move 12 columns to the right, and the empty line stays empty:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:"""
    one

    two
    """|};
    }
}
```

```csharp
class C
{
    void M()
    {
        var a = """
                one

                two
                """;
    }
}
```

Example — in an interpolated literal, the empty content line stays empty as well:

```csharp
class C
{
    void M(int name)
    {
        var a = {|RH5202:$"""
    one

    two {name}
    """|};
    }
}
```

```csharp
class C
{
    void M(int name)
    {
        var a = $"""
                 one

                 two {name}
                 """;
    }
}
```

Example — the lines of a raw string literal nested in a hole move 13 columns to the right with the outer literal, and its empty content line stays empty; the nested literal is still reported after the outer literal's fix:

```csharp
class C
{
    void M()
    {
        var a = {|RH5202:$"""
    Hello {{|RH5202:"""
        x

        y
        """|}}
    """|};
    }
}
```

```csharp

{
    void M()
    {
        var a = $"""
                 Hello {{|RH5202:"""
                     x

                     y
                     """|}}
                 """;
    }
}
```

Example — an empty line of hole code shifts with the hole: moving 13 columns to the right, it becomes a line of thirteen spaces, written `·············` here (`·` stands for one space):

```csharp
class C
{
    void M(string name)
    {
        var a = {|RH5202:$"""

    }

                 }

```

                         Hello {name
