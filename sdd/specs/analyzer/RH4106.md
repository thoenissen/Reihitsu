# Analyzer — RH4106 Private field casing

| | |
|---|---|
| ID prefix | RH4106 |
| Status | Active |
| Code owners | `RH4106PrivateFieldCasingAnalyzer`, `RH4106PrivateFieldCasingCodeFixProvider`, `CasingAnalyzerBase`, `CasingCodeFixProviderBase<T>`, `NamingAccessibilityClassifier`, `CasingUtilities` |
| Uses | — |

RH4106 reports a private field whose name is not in `_camelCase` and offers a code fix that renames the field and every reference to it. Category Naming, severity Warning, enabled by default. It is the reference spec for the casing rules that share `CasingAnalyzerBase` and `CasingCodeFixProviderBase<T>`.

## Non-goals

- `const` fields of any accessibility — RH4110.
- `protected` and `private protected` fields — RH4107; `internal` and `protected internal` fields — RH4108; `public` fields — RH4109.
- Whether a field should be private at all — RH2005.
- Names of locals, parameters, and properties — the other RH41xx rules.
- Names that start with an acronym in PascalCase (`HTTPClient`). The fix currently derives `_hTTPClient`; whether it should treat the acronym as a word is an open question.

## Requirements

### RH4106-001 — Private fields are checked

The analyzer MUST check every variable declarator of a field declaration whose effective accessibility is private: declared `private`, or declared without an accessibility modifier in a class, struct, or record. Static, readonly, and static readonly fields are included. `const` fields, `private protected` fields, and fields of an interface without an accessibility modifier (which are public) MUST NOT be checked.

Why: The underscore prefix tells a reader at the point of use that a name is state of the object, not a local or a parameter. That matters only for state invisible outside the type; other accessibility levels and constants have their own conventions.

Example:

```csharp
public class C
{
    private int {|RH4106:MyField|};
    int {|RH4106:my_field2|};
    private static readonly int {|RH4106:MaxValue|} = 1;
    private const int Limit = 2;
    protected int Prot;
    private protected int PrivProt;
    private int _ok, {|RH4106:Bad|};

    public int Run() => MyField + my_field2 + MaxValue + Bad;
}

public interface I
{
    static int Shared;
}
```

```csharp
public class C
{
    private int _myField;
    int _myField2;
    private static readonly int _maxValue = 1;
    private const int Limit = 2;
    protected int Prot;
    private protected int PrivProt;
    private int _ok, _bad;

    public int Run() => _myField + _myField2 + _maxValue + _bad;
}

public interface I
{
    static int Shared;
}
```

### RH4106-002 — What `_camelCase` means

A name MUST be accepted exactly when it starts with `_` and is either just `_`, or continues with a lowercase letter followed only by letters and digits. Every other name MUST be reported, including names with a second underscore or a digit after the prefix.

Why: `_` alone is the conventional name of an unused field. Anything after the prefix follows the camelCase shape used for locals and parameters, so the prefix is the only difference between a field and a local of the same meaning.

Example:

```csharp
public class C
{
    private int _;
    private int _value2;
    private int {|RH4106:__double|};
    private int {|RH4106:_Value|};
    private int {|RH4106:_1st|};
}
```

### RH4106-003 — The diagnostic is on the field name

The analyzer MUST report one diagnostic per non-conforming declarator, located on its identifier, with the message "Private field names should be in _camelCase".

Why: Each declarator is its own field with its own name, and the fix renames one symbol at a time.

Example: see RH4106-001, where `_ok` and `Bad` share a declaration and only `Bad` is reported.

### RH4106-004 — The fix derives the new name from the words of the old one

The code fix, titled "Fix casing", MUST derive the new name by splitting the old name into words at every character that is not a letter or digit, capitalizing the first character of each word, lowercasing every word whose remaining characters are all uppercase, joining the words, lowercasing the first character, and prefixing `_`.

Why: Separators such as `_` and a leading `m_` are word boundaries in common naming styles, and an all-uppercase word (`FIRST_NAME`) is a shouted word, not an acronym inside a PascalCase name. Deriving the name mechanically keeps the result predictable across every casing rule.

Example:

```csharp
public class C
{
    private int {|RH4106:FirstName|};
    private int {|RH4106:LAST_NAME|};
    private int {|RH4106:m_value|};
    private int {|RH4106:__double|};
    private int {|RH4106:URL|};

    public int Sum => FirstName + LAST_NAME + m_value + __double + URL;
}
```

```csharp
public class C
{
    private int _firstName;
    private int _lastName;
    private int _mValue;
    private int _double;
    private int _url;

    public int Sum => _firstName + _lastName + _mValue + _double + _url;
}
```

### RH4106-005 — The fix renames every reference

The code fix MUST rename the field's symbol with the Roslyn renamer, so the declaration and every reference in the solution change together. It MUST NOT be offered when the field's symbol cannot be resolved.

Why: Renaming only the declaration would leave every use pointing at a name that no longer exists.

Example: see RH4106-001 and RH4106-004, where the uses in `Run` and `Sum` are renamed with the declarations.

### RH4106-006 — The fix is withheld when the new name is unusable

The code fix MUST NOT be offered when the derived name is empty, equal to the old name, or not a valid identifier, or when the rename would conflict with an existing name — the renamer reports a conflict, a member of the containing namespace already has the name, or the rename adds a compile error. The diagnostic is still reported.

Why: A letterless name such as `__` has no words to build a name from, and a collision cannot be resolved without knowing which of the two names the author meant. Both are left to the author.

Example:

```csharp
public class D
{
    private int {|RH4106:Value|};
    private int _value;
}
```

is reported, and no code fix is offered, because `_value` already exists. The same holds for `private int __;`, which has no letters.

### RH4106-007 — Fix All skips names that would collide with each other

The Fix All provider MUST apply every rename that is safe on its own and in combination, and MUST skip every candidate of a group whose members would all receive the same new name in one binding scope. The skipped declarations keep their diagnostics.

Why: Applied one at a time, the first of two colliding fields would win and the second would be refused, so the result would depend on the order of the fixes. Skipping the whole group leaves the decision to the author.

Example:

```csharp
public class TestClass
{
    private int {|RH4106:Value|};

    private int {|RH4106:value|};

    private int {|RH4106:Count|};

    public int Sum => Value + value + Count;
}
```

After Fix All, only `Count` is renamed, to `_count`; `Value` and `value` would both become `_value` and keep their diagnostics. Applying the single fixes one after another renames `Value` to `_value` and then refuses `value` (RH4106-006).
