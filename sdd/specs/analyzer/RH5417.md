# Analyzer — RH5417 Function and accessor body braces must not share a line

| | |
|---|---|
| ID prefix | RH5417 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5417FunctionAndAccessorBodyBracesMustNotShareLineAnalyzer`, `RH5417FunctionAndAccessorBodyBracesMustNotShareLineCodeFixProvider` |
| Uses | FMT-BREAK-002, FMT-BREAK-003, FMT-BREAK-006, FMT-BREAK-025, FMT-PIPE-011 |

RH5417 reports the block body of a function or an accessor whose opening and closing brace are on the same line, and offers a code fix that makes each brace of a member's or an accessor's body start its own line, as the formatter lays them out (FMT-BREAK-002).

## Non-goals

- Braces of statement blocks, such as the bodies of `if`, `while`, or `for` statements — RH5402 decides where the opening brace of a multi-line one goes.
- Whether a member or an accessor has a block body or an expression body — RH3202, RH3203, RH3205 to RH3208, and the formatter's structural transforms.
- The layout of auto-property accessor lists (`{ get; set; }`) — RH5408.
- The column the braces start in.

## Requirements

### RH5417-001 — A function or accessor body on one line is reported

The analyzer MUST report the block that is the body of a method, a constructor, a finalizer, an operator, a conversion operator, an accessor (`get`, `set`, `init`, `add`, or `remove`), a local function, a lambda, or an anonymous method when its opening and closing brace are on the same line, with one diagnostic located on the opening brace. An empty body and a body with statements MUST be reported alike.

Why: The repository uses Allman braces: each brace of a body starts its own line, so the extent of every body is visible at the left margin. A body collapsed onto one line hides that structure, and an empty `{ }` looks different from the same body once its first statement is added (FMT-BREAK-002).

Example:

```csharp
using System;

class C
{
    int _x;

    C() {|RH5417:{|} }

    ~C() {|RH5417:{|} }

    int M() {|RH5417:{|} return 1; }

    public static C operator +(C a, C b) {|RH5417:{|} return a; }

    public static explicit operator int(C c) {|RH5417:{|} return 0; }

    int P { get {|RH5417:{|} return _x; } set {|RH5417:{|} _x = value; } }

    int Q { get => _x; init {|RH5417:{|} _x = value; } }

    event Action E { add {|RH5417:{|} } remove {|RH5417:{|} } }

    void N()
    {
        void L() {|RH5417:{|} }

        Action a = () => {|RH5417:{|} };
        Action<int> b = x => {|RH5417:{|} };
        Action c = delegate {|RH5417:{|} };
    }
}
```

`N` itself has its braces on separate lines and is not reported.

### RH5417-002 — Other blocks and bodies are not reported

The analyzer MUST NOT report a block that is not directly the body of one of the functions or accessors RH5417-001 names — a nested block, a statement block, or the block of a `catch` clause —, a body whose braces are on different lines, also when a comment follows the opening brace, an expression body, or an accessor without a body.

Why: Only the body of a function or an accessor is covered by this rule; the braces of statement blocks are outside it (see the non-goals). A comment behind the opening brace stays on the brace's line (FMT-BREAK-003), so a body laid out that way already has its braces on separate lines.

Example:

```csharp
class C
{
    int P { get; set; }

    int N() => 1;

    void M(bool a)
    {
        { }
        if (a) { return; }
        try
        {
        }
        catch { }
    }

    void O() { // c
    }
}
```

is not reported.

### RH5417-003 — The fix makes the braces of a member or accessor body start their own lines

For the body of a method, a constructor, a finalizer, an operator, a conversion operator, or an accessor, the code fix MUST make the opening brace and the closing brace each start their own line, as FMT-BREAK-002 lays them out, and MUST lay out the statements of the body between them as FMT-BREAK-006 does. A comment that followed the opening brace MUST stay on the brace's line (FMT-BREAK-003). For an accessor, the fix MUST also make the braces of the accessor list and each accessor start their own lines, as FMT-BREAK-025 does, and MUST keep the accessor's block body (FMT-PIPE-011).

Why: The fix produces the layout the rule asks for, the way the formatter produces it, so the result is not reported again. An accessor's braces cannot start their own lines while the accessor list stays on one line. Turning the block into an expression body is a different decision, which the fix does not make.

Example:

```csharp
class C
{
    int _x;

    int M() {|RH5417:{|} return 1; }

    void N() {|RH5417:{|} /* c */ }

    int P { get {|RH5417:{|} return _x; } }
}
```

```csharp
class C
{
    int _x;

    int M()
    {
        return 1;
    }

    void N()
    { /* c */
    }

    int P
    {
        get
        {
            return _x;
        }
    }
}
```

### RH5417-004 — No fix for local functions, lambdas, and anonymous methods

The code fix MUST NOT be offered for the body of a local function, a lambda, or an anonymous method. The diagnostic is still reported.

Why: These bodies sit inside a statement or an expression of another member. The fix lays out the member that owns the reported body, so for them it would lay out the enclosing member as a whole and change code the diagnostic is not about.

Example:

```csharp
using System;

class C
{
    void M()
    {
        void L() {|RH5417:{|} }

        Action a = () => {|RH5417:{|} };
        Action c = delegate {|RH5417:{|} };
    }
}
```

is reported, and no code fix is offered.
