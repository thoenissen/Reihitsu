# Analyzer — RH3001 Not operator should not be used

| | |
|---|---|
| ID prefix | RH3001 |
| Status | Active |
| Category | Clarity |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH3001NotOperatorShouldNotBeUsedAnalyzer`, `RH3001NotOperatorShouldNotBeUsedCodeFixProvider` |
| Uses | SHARED-FIX-003 |

RH3001 reports the logical negation operator `!` applied to a `bool` operand and offers a code fix that rewrites `!x` to `x == false`.

## Non-goals

- The `!` of a pattern (`is not`), of the null-forgiving operator (`x!`), and of `!=` — none of them is the logical negation operator.
- How a comparison with a constant on the left is ordered — RH3005.

## Requirements

### RH3001-001 — `!` on a `bool` operand is reported

The analyzer MUST report a logical negation `!x` whose operand has the type `bool`, wherever it stands.

Why: `!` is a single character in front of a long operand and easy to miss when reading a condition; `== false` states the negation where the reader looks.

Example:

```csharp
class C
{
    bool M(bool a, string s)
    {
        if ({|RH3001:!|}a)
        {
        }

        return {|RH3001:!|}s.Contains("a");
    }
}
```

### RH3001-002 — An operand that is not `bool` is not reported

The analyzer MUST NOT report `!` when its operand is not of the type `bool`: a `bool?` operand, or an operand whose type declares its own `operator !`.

Why: For `bool?`, `!x` propagates `null` while `x == false` does not; for a user-defined operator, `== false` means something else or does not compile. In both cases the rewrite would change the program.

Example:

```csharp
struct S
{
    public static S operator !(S s) => s;
}

class C
{
    bool? M(bool? a)
    {
        return !a;
    }

    S N(S s)
    {
        return !s;
    }
}
```

is not reported.

### RH3001-003 — The diagnostic is on the operator

The analyzer MUST report one diagnostic per negation, on the `!` token.

Why: The operator is what the rule objects to; the operand stays.

Example: see RH3001-001.

### RH3001-004 — The fix compares the operand with `false`

For a negation whose `!` is not the next token after a `>`, `>>`, or `>>>` operator, the code fix MUST replace `!x` with `x == false`, unless RH3001-006, RH3001-007, or RH3001-008 withholds it. This holds where the negation is part of a larger expression and where it is the whole of the syntax node around it: a whole argument of any argument list, such as that of an invocation, an object creation written with or without its type (`new C(!y)`, `new(!y)`), an element access or a conditional element access (`this[!y]`, `o?[!y]`), an index in an object initializer (`new E { [!x] = true }`), a constructor initializer, a primary constructor's base type (`class D(bool x) : Base(!x)`), or a tuple, also next to other arguments (`N(!x, y)`); a whole attribute argument; and a whole collection-expression element. The code fix MUST put the comparison in parentheses where it binds differently from the negation inside its parent, and MUST NOT put it in parentheses where it binds as the negation did. An operand that is already parenthesized keeps its parentheses.

Why: `==` binds more weakly than `!`, so `b == !a` needs `b == (a == false)` to keep its meaning, while `!a && b` reads as `a == false && b` without them. A negation that is a whole argument or element is the same negation as one inside a larger expression, and the same rewrite is safe there. Parentheses that group nothing tell the reader there is a grouping to look for where there is none. The operand's own parentheses group what the negation applied to.

Example:

```csharp
class C
{
    bool M(bool a, bool b)
    {
        var x = {|RH3001:!|}a && b;
        var y = b == {|RH3001:!|}a;
        return {|RH3001:!|}(a && b);
    }
}
```

```csharp
class C
{
    bool M(bool a, bool b)
    {
        var x = a == false && b;
        var y = b == (a == false);
        return (a && b) == false;
    }
}
```

Example — a negation that is a whole argument, attribute argument, or collection-expression element:

```csharp
using System;

class AAttribute : Attribute
{
    public AAttribute(bool b)
    {
    }
}

class C
{
    public C(bool b)
    {
    }

    bool this[bool b] => b;

    void M(bool b)
    {
    }

    [A({|RH3001:!|}true)]
    void Run(bool x, bool y)
    {
        M({|RH3001:!|}x);
        var t = ({|RH3001:!|}x, y);
        var c = new C({|RH3001:!|}y);
        var i = this[{|RH3001:!|}y];
        bool[] a = [{|RH3001:!|}x, y];
    }
}
```

```csharp
using System;

class AAttribute : Attribute
{
    public AAttribute(bool b)
    {
    }
}

class C
{
    public C(bool b)
    {
    }

    bool this[bool b] => b;

    void M(bool b)
    {
    }

    [A(true == false)]
    void Run(bool x, bool y)
    {
        M(x == false);
        var t = (x == false, y);
        var c = new C(y == false);
        var i = this[y == false];
        bool[] a = [x == false, y];
    }
}
```

Example — positions where the comparison binds as the negation did, so it gets no parentheses:

```csharp
using System.Linq;

class C
{
    bool? _b;

    void Run(bool x, bool[] v)
    {
        _b ??= {|RH3001:!|}x;
        var q = from w in v
                orderby {|RH3001:!|}w descending
                select {|RH3001:!|}w;
    }
}
```

```csharp
using System.Linq;

class C
{
    bool? _b;

    void Run(bool x, bool[] v)
    {
        _b ??= x == false;
        var q = from w in v
                orderby w == false descending
                select w == false;
    }
}
```

The same holds behind `>>>=`, in a named attribute argument written with `=` or `:`, behind `goto case`, and in the element and the key of a `group` clause: `goto case !true;` becomes `goto case true == false;`.

### RH3001-005 — A comment after the operator moves in front of the operand

The code fix MUST keep a comment that stands between `!` and the operand, in front of the operand, without the whitespace between `!` and the comment.

Why: The comment was written about the negated operand; it stays next to it, and the space that separated it from the removed `!` has nothing left to separate.

Example:

```csharp
class C
{
    bool M(bool a, bool b)
    {
        var x = {|RH3001:!|} /* first */ a;
        return {|RH3001:!|} // second
            b;
    }
}
```

```csharp
class C
{
    bool M(bool a, bool b)
    {
        var x = /* first */ a == false;
        return // second
            b == false;
    }
}
```

### RH3001-006 — A directive after the operator withholds the fix

The code fix MUST NOT be offered when a preprocessor directive, disabled text, or skipped text stands between `!` and its operand. The diagnostic is still reported. A directive inside a parenthesized operand MUST NOT withhold the fix.

Why: The rewrite moves the operand's leading trivia in front of the new expression; a directive there would land in the middle of a line or move across the code it guards. Inside the operand's parentheses the directives stay where they are.

Example:

```csharp
class C
{
    bool M()
    {
        return {|RH3001:!|}
#if DEBUG
            true
#else
            false
#endif
            ;
    }
}
```

is reported, and no code fix is offered. Inside the operand's parentheses, the directives do not withhold the fix:

```csharp
class C
{
    bool M()
    {
        return {|RH3001:!|}(
#if DEBUG
            true
#else
            false
#endif
        );
    }
}
```

```csharp
class C
{
    bool M()
    {
        return (
#if DEBUG
            true
#else
            false
#endif
        ) == false;
    }
}
```

### RH3001-007 — A fix that would parse as a generic name is withheld

The code fix MUST NOT be offered when the code it writes would parse as a generic name: when a `<` in front of the negation and the `>`, `>>`, or `>>>` operator in front of it would read as a type argument list, as they do when the parentheses the fix writes follow that operator. The diagnostic is still reported. Where the code the fix writes parses with the same operators and operands as the code it replaces, this requirement does not withhold the fix.

Why: `x == false` behind a `>` needs parentheses (RH3001-004), and `>` followed by `(` after an open `<` is read as the end of a type argument list, so the comparisons would become a generic invocation that does not compile (SHARED-FIX-003).

Example:

```csharp
class C
{
    int G;
    int A;
    int B;

    void M(bool x, bool y)
    {
    }

    void Run(bool x)
    {
        M(G < A, B > {|RH3001:!|}x switch { true => 1, false => 0 });
    }
}
```

is reported, and no code fix is offered: `M(G < A, B > (x == false) switch { true => 1, false => 0 })` would call a generic method `G<A, B>`.

### RH3001-008 — A negation that is a constant pattern gets no fix

The code fix MUST NOT be offered for a negation that is the whole expression of a constant pattern, such as the pattern of an `is` expression, of a switch-expression arm, or of a property subpattern. The diagnostic is still reported (SHARED-FIX-003). A constant pattern behind a `case` label with a `when` clause (`case !true when x:`) is one as well and gets no fix. A negation in the expression of a switch-expression arm, behind its `=>`, is not a pattern and gets the fix (RH3001-004), and so does the value of a `case` label without a `when` clause (`case !true:` becomes `case true == false:`), which is an expression, not a pattern.

Why: A pattern states the value the input is compared with. `x is true == false` would read as `(x is true) == false`, and `x is (true == false)` turns the pattern into a constant expression the reader has to evaluate before seeing which value is matched. The author writes the pattern they mean, such as `x is false`, by hand.

Example:

```csharp
class C
{
    int Run(bool x)
    {
        var r = x is {|RH3001:!|}true;
        return x switch
        {
            {|RH3001:!|}true => 1,
            _ => 2,
        };
    }
}
```

is reported, and no code fix is offered. Behind the arm's `=>`, the negation gets the fix:

```csharp
class C
{
    bool Run(bool x, bool y)
    {
        return x switch
        {
            true => {|RH3001:!|}y,
            _ => y,
        };
    }
}
```

```csharp
class C
{
    bool Run(bool x, bool y)
    {
        return x switch
        {
            true => y == false,
            _ => y,
        };
    }
}
```
