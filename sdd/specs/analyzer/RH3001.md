# Analyzer — RH3001 Not operator should not be used

| | |
|---|---|
| ID prefix | RH3001 |
| Status | Active |
| Category | Clarity |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH3001NotOperatorShouldNotBeUsedAnalyzer`, `RH3001NotOperatorShouldNotBeUsedCodeFixProvider` |
| Uses | — |

RH3001 reports the logical negation operator `!` applied to a `bool` operand and offers a code fix that rewrites `!x` to `x == false`.

## Non-goals

- The `!` of a pattern (`is not`), of the null-forgiving operator (`x!`), and of `!=` — none of them is the logical negation operator.
- How a comparison with a constant on the left is ordered — RH3005.

## Requirements

### RH3001-001 — `!` on a `bool` operand is reported

The analyzer MUST report a logical negation `!x` whose operand has the type `bool`, wherever it stands.

Why: `!` is a single character in front of a long operand and easy to miss when reading a condition; `== false` states the negation where the reader looks.

Example:

```csharp
class C
{
    bool M(bool a, string s)
    {
        if ({|RH3001:!|}a)
        {
        }

        return {|RH3001:!|}s.Contains("a");
    }
}
```

### RH3001-002 — An operand that is not `bool` is not reported

The analyzer MUST NOT report `!` when its operand is not of the type `bool`: a `bool?` operand, or an operand whose type declares its own `operator !`.

Why: For `bool?`, `!x` propagates `null` while `x == false` does not; for a user-defined operator, `== false` means something else or does not compile. In both cases the rewrite would change the program.

Example:

```csharp
struct S
{
    public static S operator !(S s) => s;
}

class C
{
    bool? M(bool? a)
    {
        return !a;
    }

    S N(S s)
    {
        return !s;
    }
}
```

is not reported.

### RH3001-003 — The diagnostic is on the operator

The analyzer MUST report one diagnostic per negation, on the `!` token.

Why: The operator is what the rule objects to; the operand stays.

Example: see RH3001-001.

### RH3001-004 — The fix compares the operand with `false`

For a negation that covers less text than the syntax node directly around it, and whose `!` is not the next token after a `>`, `>>`, or `>>>` operator, the code fix MUST replace `!x` with `x == false`. When the comparison binds differently from the negation inside its parent, the code fix MUST put it in parentheses. An operand that is already parenthesized keeps its parentheses.

Why: `==` binds more weakly than `!`, so `b == !a` needs `b == (a == false)` to keep its meaning, while `!a && b` reads as `a == false && b` without them. The operand's own parentheses group what the negation applied to.

Example:

```csharp
class C
{
    bool M(bool a, bool b)
    {
        var x = {|RH3001:!|}a && b;
        var y = b == {|RH3001:!|}a;
        return {|RH3001:!|}(a && b);
    }
}
```

```csharp
class C
{
    bool M(bool a, bool b)
    {
        var x = a == false && b;
        var y = b == (a == false);
        return (a && b) == false;
    }
}
```

### RH3001-005 — A comment after the operator moves in front of the operand

The code fix MUST keep a comment that stands between `!` and the operand, in front of the operand, without the whitespace between `!` and the comment.

Why: The comment was written about the negated operand; it stays next to it, and the space that separated it from the removed `!` has nothing left to separate.

Example:

```csharp
class C
{
    bool M(bool a, bool b)
    {
        var x = {|RH3001:!|} /* first */ a;
        return {|RH3001:!|} // second
            b;
    }
}
```

```csharp
class C
{
    bool M(bool a, bool b)
    {
        var x = /* first */ a == false;
        return // second
            b == false;
    }
}
```

### RH3001-006 — A directive after the operator withholds the fix

The code fix MUST NOT be offered when a preprocessor directive, disabled text, or skipped text stands between `!` and its operand. The diagnostic is still reported. A directive inside a parenthesized operand MUST NOT withhold the fix.

Why: The rewrite moves the operand's leading trivia in front of the new expression; a directive there would land in the middle of a line or move across the code it guards. Inside the operand's parentheses the directives stay where they are.

Example:

```csharp
class C
{
    bool M()
    {
        return {|RH3001:!|}
#if DEBUG
            true
#else
            false
#endif
            ;
    }
}
```

is reported, and no code fix is offered. Inside the operand's parentheses, the directives do not withhold the fix:

```csharp
class C
{
    bool M()
    {
        return {|RH3001:!|}(
#if DEBUG
            true
#else
            false
#endif
        );
    }
}
```

```csharp
class C
{
    bool M()
    {
        return (
#if DEBUG
            true
#else
            false
#endif
        ) == false;
    }
}
```
