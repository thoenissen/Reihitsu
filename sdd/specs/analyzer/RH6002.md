# Analyzer — RH6002 Commas must be spaced correctly

| | |
|---|---|
| ID prefix | RH6002 |
| Status | Active |
| Category | Spacing |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH6002CommasMustBeSpacedCorrectlyAnalyzer`, `RH6002CommasMustBeSpacedCorrectlyCodeFixProvider` |
| Uses | FMT-SPACE-004, FMT-SPACE-008, FMT-SPACE-014 |

RH6002 reports a comma with whitespace in front of it or without exactly one space after it, and offers a code fix that corrects both sides. The space after a comma is decided by `CommaSpacingUtilities`, which the formatter's FMT-SPACE-008 uses too, so formatted code raises no RH6002.

## Non-goals

- Whether a comma ends or starts a line — RH5107 and the line-break rules. A line break on either side of a comma is never changed by this rule.
- Spacing of the brackets around a compact comma form — RH6007, RH6008, RH6011, RH6012.
- Commas inside comments, string literals, and disabled text, which are not tokens.

## Requirements

### RH6002-001 — No whitespace before a comma

The analyzer MUST report a comma that is separated from the token before it by whitespace on the same line — spaces, tabs, or form feeds. A comma that starts its line, after a line break, MUST NOT be reported for its leading side.

Why: A comma ends the list element before it and belongs to it. A comma on its own line after a line break is a layout choice that other rules decide.

Example:

```csharp
class C
{
    void M(int a, int b {|RH6002:,|} int c)
    {
        M(a
          , b, c);
    }
}
```

### RH6002-002 — Exactly one space after a comma

The analyzer MUST report a comma that is followed on the same line by anything other than exactly one space before the next token — no whitespace, several spaces, a tab, or a form feed. A comma that ends its line MUST NOT be reported for its trailing side.

Why: The space makes the boundary between two list elements visible; more than one space suggests an alignment the rule does not maintain.

Example:

```csharp
class C
{
    void M(int a{|RH6002:,|}int b)
    {
        var x = new[] { 1{|RH6002:,|}  2, 3 };
        var (p{|RH6002:,|}q) = (1{|RH6002:,|}2);
        M(a,
          b);
    }
}
```

### RH6002-003 — Compact comma forms take no space after the comma

In an interpolation alignment clause (`{value,-10}`), the analyzer MUST require no whitespace after the comma, and the before-side MUST be checked as in RH6002-001. A comma of a rank-only array specifier (`int[,]`) or of an unbound generic type (`Dictionary<,>`) MUST NOT be checked at all, so it is not reported even when spaced (`int[ , ]`). A sized array rank (`new int[2,2]`) is an ordinary list and needs the space.

Why: In these forms the comma is part of one type name or one format specification, and a space would make it look like a list. The same three forms are FMT-SPACE-008's exceptions. The two type forms are skipped entirely rather than checked for zero spaces; the formatter still writes them compact (FMT-SPACE-004, FMT-SPACE-008), and the bracket rules RH6007, RH6008, and RH6012 report the spaces next to the brackets.

Example:

```csharp
using System.Collections.Generic;

class C
{
    void M(int a, int b, int c)
    {
        int[,] grid = new int[2{|RH6002:,|}2];
        var t = typeof(Dictionary<,>);
        int[ , ] spaced = null;
        var s = $"{a,-10}|{b{|RH6002:,|} 5}|{c {|RH6002:,|}3}";
    }
}
```

### RH6002-004 — A comment next to a comma keeps its place

When a comment sits between a comma and the token after it on the same line, the analyzer MUST check only the whitespace between the comment and that token, which must be exactly one space; the comment MUST stay directly where it is. When a comment sits between the token before a comma and the comma, the whitespace in front of the comment MUST NOT be reported.

Why: The comment belongs to the place the author wrote it. Moving it or squeezing the space in front of it would change what it annotates; only the gap the rule answers for — between the comment and the next list element — is normalized. The formatter treats the same gaps the same way (FMT-SPACE-014).

Example:

```csharp
class C
{
    void M(int a, int b, int c)
    {
        M(a{|RH6002:,|}/* keep */b, c);
        M(a /* fine */, b, c);
    }
}
```

### RH6002-005 — One diagnostic per comma

The analyzer MUST report one diagnostic per non-conforming comma, located on the comma token, whether the problem is on one side or on both.

Why: The comma is the token whose surroundings are wrong; one diagnostic per comma keeps one fix per comma.

Example: see RH6002-001, where the comma after `b` has whitespace on both sides and is reported once.

### RH6002-006 — The fix changes only the whitespace next to the comma

The code fix MUST remove the whitespace before the comma and set the whitespace after it to the required amount, both only on a side not broken by a line break. It MUST NOT move or remove a comment, a line break, or a directive.

Why: The fix answers exactly the question the diagnostic asks. A directive on a line-broken side is not part of the gap and stays where it is.

Example — the cases of RH6002-001 to RH6002-004:

```csharp
class C
{
    void M(int a, int b {|RH6002:,|} int c)
    {
        var x = new[] { 1{|RH6002:,|}  2, 3 };
        var s = $"{a,-10}|{b{|RH6002:,|} 5}|{c {|RH6002:,|}3}";
        M(a{|RH6002:,|}/* keep */b, c);
    }
}
```

```csharp
class C
{
    void M(int a, int b, int c)
    {
        var x = new[] { 1, 2, 3 };
        var s = $"{a,-10}|{b,5}|{c,3}";
        M(a,/* keep */ b, c);
    }
}
```

A directive on a line-broken side stays where it is:

```csharp
class C
{
    void M(
        int x {|RH6002:,|}
#if FEATURE
        int y)
#endif
    {
    }
}
```

```csharp
class C
{
    void M(
        int x,
#if FEATURE
        int y)
#endif
    {
    }
}
```

The example holds with `FEATURE` defined; without it, the `,` has no list element after it and the code does not compile.
