# Analyzer — RH6011 Opening generic brackets must be spaced correctly

| | |
|---|---|
| ID prefix | RH6011 |
| Status | Active |
| Category | Spacing |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH6011OpeningGenericBracketsMustBeSpacedCorrectlyAnalyzer`, `RH6011OpeningGenericBracketsMustBeSpacedCorrectlyCodeFixProvider` |
| Uses | FMT-SPACE-005, FMT-SPACE-013, SHARED-WS-001, SHARED-WS-002 |

RH6011 reports whitespace in front of the opening angle bracket of a type argument list or a type parameter list on the same line, and offers a code fix that deletes it as SHARED-WS-001 and SHARED-WS-002 specify.

In the examples, `→` marks a tab.

## Non-goals

- The whitespace after the opening angle bracket, such as `List< int>`, which this rule does not check; the formatter removes it (FMT-SPACE-005).
- The closing angle bracket — RH6012.
- The angle brackets of a function pointer type, such as `delegate*<int, void>`, and the `<` and `>` operators.

## Requirements

### RH6011-001 — Whitespace before an opening generic bracket on the same line is reported

The analyzer MUST report the run of spaces and tabs directly in front of the `<` of a type argument list (`List <int>`, `M <int>()`) or of a type parameter list (`class G <T>`, `void M <T>()`) when that run follows code or a comment on the same line and the token before the `<` ends on that line. A `<` that starts its line MUST NOT be reported.

Why: A space in front of the angle bracket separates a type name from its type arguments and makes the `<` read as a comparison. The formatter removes the same whitespace (FMT-SPACE-005), also between a comment and the bracket (FMT-SPACE-013), so formatted code raises no RH6011.

Example:

```csharp
using System.Collections.Generic;

class G{|RH6011: |}<T>
{
    void M{|RH6011: |}<U>(List{|RH6011:→|}<int> a)
    {
        M{|RH6011: |}<int>(null);
        var e = new List /* note */{|RH6011: |}<int>();
        List
            <int> f = null;
    }
}
```

### RH6011-002 — Type arguments in documentation references are not reported

The analyzer MUST NOT report a type argument list inside a documentation comment, such as the `{T}` of `cref="List {T}"`.

Why: A reference in documentation names a type and is not code; its spacing does not reach the compiled program.

Example:

```csharp
using System.Collections.Generic;

class C
{
    /// <see cref="List {T}"/>
    void M()
    {
    }
}
```

is not reported.

### RH6011-003 — One diagnostic per bracket

The analyzer MUST report one diagnostic per opening angle bracket, located on the whitespace run in front of it.

Why: The run is the text that is wrong and the text the fix deletes.

Example: see RH6011-001.

### RH6011-004 — The fix deletes the whitespace unless a comment is in the gap

The code fix MUST delete the reported whitespace as SHARED-WS-001 specifies, and MUST NOT be offered when a comment or directive sits between the bracket and the token before it, as SHARED-WS-002 specifies.

Why: Deleting the whitespace between a comment and the bracket would glue the comment to it; the author decides whether the comment stays there.

Example:

```csharp
using System.Collections.Generic;

class G{|RH6011: |}<T>
{
    void M{|RH6011: |}<U>(List{|RH6011:→|}<int> a)
    {
        M{|RH6011: |}<int>(null);
    }
}
```

```csharp
using System.Collections.Generic;

class G<T>
{
    void M<U>(List<int> a)
    {
        M<int>(null);
    }
}
```

The comment before the bracket withholds the fix:

```csharp
using System.Collections.Generic;

class C
{
    void M()
    {
        var e = new List /* note */{|RH6011: |}<int>();
    }
}
```

is reported, and no code fix is offered.
