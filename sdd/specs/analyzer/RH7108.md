# Analyzer — RH7108 Event accessors must follow order

| | |
|---|---|
| ID prefix | RH7108 |
| Status | Active |
| Category | Organization |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH7108EventAccessorsMustFollowOrderAnalyzer`, `RH7108EventAccessorsMustFollowOrderCodeFixProvider` |
| Uses | SHARED-ORDER-001, SHARED-ORDER-002, SHARED-ORDER-003, SHARED-ORDER-004, SHARED-ORDER-005, SHARED-ORDER-006 |

RH7108 reports an `add` accessor that follows the `remove` accessor of the same event, and offers a code fix that moves it in front of it.

## Non-goals

- The accessors of properties and indexers — RH7107.
- Event field declarations, which have no accessor list.

## Requirements

### RH7108-001 — An `add` accessor after `remove` is reported

The analyzer MUST report the `add` accessor of an event declaration whose accessor list has the `remove` accessor before it, when the accessor list contains no `#if`, `#elif`, `#else`, or `#endif` directive.

Why: Subscribing comes before unsubscribing when a reader follows an event's lifetime. One fixed order makes every custom event look the same.

Example:

```csharp
using System;

class C
{
    private Action _handlers;

    public event Action Changed
    {
        remove
        {
            _handlers -= value;
        }

        {|RH7108:add|}
        {
            _handlers += value;
        }
    }
}
```

### RH7108-002 — Accessor lists in order are not reported

The analyzer MUST NOT report an event declaration whose `add` accessor comes before its `remove` accessor.

Why: The rule asks only for `add` first.

Example:

```csharp
using System;

class C
{
    private Action _handlers;

    public event Action Changed
    {
        add
        {
            _handlers += value;
        }

        remove
        {
            _handlers -= value;
        }
    }
}
```

is not reported.

### RH7108-003 — The diagnostic is on the `add` keyword

The analyzer MUST report one diagnostic per event declaration, located on the keyword of its `add` accessor.

Why: The `add` keyword marks the accessor that has to move.

Example: see RH7108-001.

### RH7108-004 — The fix moves `add` in front of `remove`

The code fix MUST move the `add` accessor in front of the `remove` accessor, and MUST perform the move as specified in SHARED-ORDER-001 and SHARED-ORDER-002: the comments and attribute lists written above the `add` accessor travel with it.

Why: Moving the one misplaced accessor corrects the order without touching the other.

Example:

```csharp
using System;

class C
{
    private Action _handlers;

    public event Action Changed
    {
        remove
        {
            _handlers -= value;
        }

        // Subscribes
        {|RH7108:add|}
        {
            _handlers += value;
        }
    }
}
```

```csharp
using System;

class C
{
    private Action _handlers;

    public event Action Changed
    {
        // Subscribes
        add
        {
            _handlers += value;
        }

        remove
        {
            _handlers -= value;
        }
    }
}
```

### RH7108-005 — The fix is withheld when the move is unsafe

The code fix MUST NOT be offered when the move is refused by SHARED-ORDER-003, SHARED-ORDER-004, or SHARED-ORDER-005. When no `#if`, `#elif`, `#else`, or `#endif` directive takes part in the refusal, the diagnostic is still reported. A balanced directive pair alone does not withhold it (SHARED-ORDER-006).

Why: These moves would change which code a directive governs. A reported diagnostic without a fix is a supported end state.

Example:

```csharp
using System;

class C
{
    private Action _handlers;

    public event Action Changed
    {
        remove
        {
            _handlers -= value;
        }

#pragma warning disable CS0162
        {|RH7108:add|}
        {
            _handlers += value;
        }
    }
}
```

is reported, and no code fix is offered.
