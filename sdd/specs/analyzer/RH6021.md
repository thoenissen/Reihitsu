# Analyzer — RH6021 Colons must be spaced correctly

| | |
|---|---|
| ID prefix | RH6021 |
| Status | Active |
| Category | Spacing |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH6021ColonsMustBeSpacedCorrectlyAnalyzer`, `RH6021ColonsMustBeSpacedCorrectlyCodeFixProvider` |
| Uses | FMT-SPACE-009, SHARED-GAP-001 |

RH6021 reports the colon of a base list or of a constructor initializer without a space on a side it shares a line with, and offers a code fix that puts one space there.

In the examples, `→` marks a tab.

## Non-goals

- Other colons — of a `case` label, a conditional expression, a named argument, a type-parameter constraint, an attribute target, or a property pattern — which no analyzer rule checks with this rule's spacing.
- Whether a base list or a constructor initializer starts its own line — the line-break rules and the formatter.

## Requirements

### RH6021-001 — A base-list or constructor-initializer colon without a space is reported

The analyzer MUST report the colon that opens a base list — of a class, struct, interface, record, or enum, also after a primary constructor — or a constructor initializer (`: base(…)`, `: this(…)`) when, on a side without a line break, no whitespace separates it from the token on that side, or the whitespace directly next to it is a tab. On the side before the colon, a comment that ends directly in front of it counts as no whitespace.

Why: A colon written tight against its neighbors fuses them into one run of characters, so the base type or the constructor a declaration chains to is harder to pick out. The formatter puts one space on both sides of these colons (FMT-SPACE-009), so formatted code raises no RH6021.

Example:

```csharp
interface I
{
}

class B
{
    public B()
    {
    }

    public B(int a)
    {
    }
}

class C{|RH6021::|}B
{
    public C(){|RH6021::|}base(1)
    {
    }

    public C(int a) {|RH6021::|}this()
    {
    }

    public C(long a){|RH6021::|} base()
    {
    }
}

class D→{|RH6021::|} B, I
{
}

class E /* note */{|RH6021::|} B
{
}

enum F{|RH6021::|}byte
{
}

record R(int A){|RH6021::|}I;

struct S{|RH6021::|}I
{
}
```

### RH6021-002 — One space on a side, or a line break, is not reported

The analyzer MUST NOT report a base-list or constructor-initializer colon with exactly one space on each side, or with a line break on a side and exactly one space on the other. A colon in any other position MUST NOT be reported.

Why: A side that wraps to another line is laid out by the indentation, not by a gap width. The rule covers only the two colons that separate the parts of a declaration.

Example:

```csharp
class B
{
}

class C : B
{
}

class D
    : B
{
}

class E :
    B
{
}

class F<T> : B where T:class
{
    void M(int a)
    {
        _ = a > 0 ? a:1;

        switch (a)
        {
            case 1:
                break;
        }

        M(a:1);
    }
}
```

is not reported.

### RH6021-003 — One diagnostic per colon

The analyzer MUST report one diagnostic per colon, located on the colon, whether one side or both sides are wrong.

Why: The colon is the token whose surroundings are wrong; one diagnostic per colon keeps one fix per colon.

Example: see RH6021-001, where `class C:B` lacks the space on both sides and is reported once.

### RH6021-004 — The fix puts one space on each reported side

The code fix MUST replace the whole gap between the colon and its neighbor with exactly one space on each side that RH6021-001 reports. A side with a line break MUST NOT be changed, including the comment or directive on it.

Why: The fix answers exactly the question the diagnostic asks; a wrapped side belongs to the layout, not to the rule.

Example:

```csharp
class B
{
    public B()
    {
    }
}

class C{|RH6021::|}B
{
    public C(){|RH6021::|}base()
    {
    }
}

class D→{|RH6021::|} B
{
}

class E
    {|RH6021::|}B
{
}

class F{|RH6021::|}
    B
{
}

class G // note
    {|RH6021::|}B
{
}
```

```csharp
class B
{
    public B()
    {
    }
}

class C : B
{
    public C() : base()
    {
    }
}

class D : B
{
}

class E
    : B
{
}

class F :
    B
{
}

class G // note
    : B
{
}
```

### RH6021-005 — A comment in a rewritten gap withholds the fix

The code fix MUST NOT be offered when a gap it rewrites contains a comment, as SHARED-GAP-001 specifies; a comment on a side the fix does not change MUST NOT withhold it.

Why: Inserting a space between a comment and the colon changes a placement the author chose; the author decides whether the comment stays there.

Example:

```csharp
class B
{
}

class C /* note */{|RH6021::|} B
{
}
```

is reported, and no code fix is offered. In RH6021-004, the comment of `class G` is on the line-broken side, and the fix is offered.
