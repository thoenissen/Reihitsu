# Analyzer — RH3201 Comments must contain text

| | |
|---|---|
| ID prefix | RH3201 |
| Status | Active |
| Category | Clarity |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH3201CommentsMustContainTextAnalyzer`, `RH3201CommentsMustContainTextCodeFixProvider` |
| Uses | — |

RH3201 reports a `//` or `/* */` comment that contains nothing but whitespace and offers a code fix that removes it.

## Non-goals

- Documentation comments (`///` and `/** */`) without text — the documentation rules (RH8###).
- Comments whose text says nothing useful but is not empty.

## Requirements

### RH3201-001 — An empty comment is reported

The analyzer MUST report a `//` comment whose text after `//` is empty or whitespace, and a `/* */` comment whose text between `/*` and `*/` is empty or consists of whitespace and line breaks only, when the line above the comment or the line below it does not start with a comment. A comment that has any other character in its text MUST NOT be reported; `////` therefore has the text `//` and is not reported.

Why: An empty comment carries no information. It looks like a leftover or an unfinished thought and distracts from the comments that matter.

Example:

```csharp
class C
{
    {|RH3201://|}
    int _a;
    {|RH3201:/* */|}
    int _b; {|RH3201://|}
    int _c;
    // text
    int _d;
}
```

### RH3201-002 — An empty `//` line inside a block of `//` comments is not reported

The analyzer MUST NOT report an empty `//` comment that stands alone on its line when the line above it and the line below it each start with a `//` comment that is not a `///` comment, or with `////`. It MUST report such an empty `//` comment when the line above it or below it is a `///` documentation comment that documents a declaration.

Why: Between two lines of the same `//` comment block, the empty line is a paragraph break of one piece of prose. A documentation comment is a different block.

Example:

```csharp
class C
{
    // First.
    //
    // Second.
    int _a;

    //// First.
    //
    //// Second.
    int _b;
}
```

is not reported. Next to a documentation comment, the empty line is reported:

```csharp
class C
{
    // First.
    {|RH3201://|}
    /// <summary>Second.</summary>
    int _a;
}
```

### RH3201-003 — An unterminated block comment is not reported

The analyzer MUST NOT report a `/*` comment that has no closing `*/`.

Why: An unterminated comment is usually being typed; its text runs to the end of the file and is not empty in any useful sense.

Example:

```csharp
class C
{
}
/*
```

is not reported.

### RH3201-004 — The diagnostic covers the comment

The analyzer MUST report one diagnostic per comment, from its first to its last character.

Why: The comment is what the fix removes.

Example: see RH3201-001.

### RH3201-005 — The fix removes the comment

The code fix MUST remove the reported comment:

- when the comment lies on a single line and is the only thing on it, together with the whole line, its line break included;
- when code precedes the comment on its line and whitespace or the end of the line follows it, together with the spaces and tabs between that code and the comment.

Why: A line that held only the empty comment would otherwise stay behind as a blank line; after code, the whitespace that separated the comment has nothing left to separate.

Example:

```csharp
class C
{
    {|RH3201://|}
    int _a;
    {|RH3201:/* */|}
    int _b; {|RH3201://|}

    int M(int a, int b) => a + {|RH3201:/* */|} b;
}
```

```csharp
class C
{
    int _a;
    int _b;

    int M(int a, int b) => a + b;
}
```

### RH3201-006 — A comment that keeps two tokens apart withholds the fix

The code fix MUST NOT be offered for a reported comment when only comments separate the token in front of it from the token after it, and the two tokens would read as different tokens once every comment between them is removed, as `return/**/a` would read as the identifier `returna`. This holds for a comment that spans several lines and for each of several comments that stand next to each other between the two tokens, also when Fix All removes them together. The diagnostic is still reported. Where whitespace or a line break also separates the two tokens, or where the two tokens read the same without the comments, this requirement does not withhold the fix.

Why: Removing the comments would join the two tokens into one, which breaks the code or changes what it means (SHARED-FIX-003). Removing one of two adjacent comments leaves the other as the only separator, so a fix that only looks at its own comment would merge the tokens on the next one, or with Fix All, at once.

Example:

```csharp
class C
{
    int M(int a)
    {
        return{|RH3201:/**/|}a;
    }

    int N(int a)
    {
        return{|RH3201:/*
*/|}a;
    }

    int O(int a)
    {
        return{|RH3201:/**/|}{|RH3201:/**/|}a;
    }
}
```

is reported, and no code fix is offered.

### RH3201-007 — A comment directly in front of a token keeps the whitespace before it

When code precedes the reported comment on its line, separated from it by spaces or tabs, and the next token follows the comment directly, with no whitespace between them, the code fix MUST remove the comment alone and keep the whitespace in front of it. Where no whitespace stands in front of the comment either, RH3201-006 decides whether the fix is offered.

Why: The whitespace in front of the comment is what keeps the two tokens apart once the comment is gone; removing it with the comment, as RH3201-005 does when whitespace follows the comment, would join them.

Example:

```csharp
class C
{
    int M(int a)
    {
        return {|RH3201:/**/|}a;
    }
}
```

```csharp
class C
{
    int M(int a)
    {
        return a;
    }
}
```
