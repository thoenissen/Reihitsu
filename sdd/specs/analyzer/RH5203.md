# Analyzer — RH5203 Multi-line arguments should be aligned

| | |
|---|---|
| ID prefix | RH5203 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5203MultiLineArgumentsShouldBeAlignedAnalyzer`, `RH5203MultiLineArgumentsShouldBeAlignedCodeFixProvider` |
| Uses | FMT-INDENT-012, SHARED-BLANK-002, SHARED-BLANK-008, SHARED-COMMENT-011, SHARED-COMMENT-012 |

RH5203 reports an argument of a multi-line argument list that starts its own line in another column than the one right of the opening parenthesis, and offers a code fix that moves it into that column.

## Non-goals

- Whether the arguments of a list share a line — RH5102; whether the first argument is on the line of the opening parenthesis — RH5101.
- Bracketed argument lists, attribute argument lists, and parameter lists.
- The lines inside an argument after its first line.

## Requirements

### RH5203-001 — A wrapped argument outside the alignment column is reported

The analyzer MUST report an argument of a parenthesized argument list with at least two arguments whose opening and closing parentheses are on different lines when the argument starts a line below the opening parenthesis with only whitespace in front of it on that line (SHARED-BLANK-008), and its first token is not in the column directly right of the opening parenthesis. An argument on the line of the opening parenthesis, and an argument behind a leading comma or behind another argument on the same line, MUST NOT be reported. A line that starts with a comment is judged as SHARED-COMMENT-011 specifies, and an argument behind the closing `*/` of a comment that spans several lines as SHARED-COMMENT-012 specifies.

Why: Arguments aligned one under the other directly right of the opening parenthesis show where each argument begins (FMT-INDENT-012). An argument that does not start its line is positioned by the token in front of it, not by the list.

Example:

```csharp
class C
{
    void N()
    {
        M(1,
            {|RH5203:2|},
          3);
        M(
            {|RH5203:1|},
            {|RH5203:2|});
        M(1, 2,
          3);
        M(1
          , 2);
    }

    void M(params int[] values)
    {
    }
}
```

### RH5203-002 — The diagnostic is on the argument

The analyzer MUST report one diagnostic per misaligned argument, located on the whole argument.

Why: Each argument is moved on its own.

Example: see RH5203-001.

### RH5203-003 — The fix moves the argument into the alignment column

When nothing but whitespace stands in front of the reported argument since the line break that ends the previous line, the code fix MUST replace that indentation with spaces up to the column directly right of the opening parenthesis. A `//` or `/* */` comment that starts its own line (SHARED-BLANK-002) between the argument and the comma or opening parenthesis in front of it MUST be moved into the same column: the fix replaces the whitespace in front of the comment on its line in the same way. A documentation comment there (`///`, `/** */`) MUST stay in its column. The fix MUST NOT change anything else: not the blank lines between those lines, not the text of a comment, including the later lines of a comment that spans several lines, and not a comment behind the comma or the opening parenthesis on its line. This requirement decides the argument's line and the lines of such comments; it leaves the lines of a preprocessor directive or of disabled text in front of the argument unspecified.

When anything but whitespace stands in front of the reported argument on its line, such as a comment that ends on that line in front of the argument, the code fix MUST NOT be offered. The diagnostic is still reported.

Why: Only the argument's start is misplaced; the rest of the list keeps its layout. A comment on its own line above an argument describes that argument and is aligned with it, as the formatter aligns it. A documentation comment does not belong inside an argument list, and aligning it is not worth a case of its own. A comment in front of the argument on its line is a comment inside an argument list, which RH5038 reports; replacing only the whitespace in front of the comment would not put the argument into the alignment column, so the fix leaves that rare line to the author.

Example:

```csharp
class C
{
    void N()
    {
        M(1,
            {|RH5203:2|},
          3);
    }

    void M(params int[] values)
    {
    }
}
```

```csharp
class C
{
    void N()
    {
        M(1,
          2,
          3);
    }

    void M(params int[] values)
    {
    }
}
```

Example — a comment line above the argument:

```csharp
class C
{
    void N()
    {
        M(1,
 // two
 {|RH5203:2|});
    }

    void M(params int[] values)
    {
    }
}
```

```csharp
class C
{
    void N()
    {
        M(1,
          // two
          2);
    }

    void M(params int[] values)
    {
    }
}
```

Example — a comment in front of the argument on its line:

```csharp
class C
{
    void N()
    {
        M(1,
           /* two */ {|RH5203:2|});
    }

    void M(params int[] values)
    {
    }
}
```

is reported, and no code fix is offered. With only whitespace in front of `2` on its line, as in the first example, the fix is offered.
