# Analyzer — RH3208 Expression style local functions should not be used

| | |
|---|---|
| ID prefix | RH3208 |
| Status | Active |
| Category | Clarity |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH3208ExpressionStyleLocalFunctionsShouldNotBeUsedAnalyzer`, `RH3208ExpressionStyleLocalFunctionsShouldNotBeUsedCodeFixProvider` |
| Uses | SHARED-BODY-001, SHARED-BODY-002, SHARED-BODY-003, SHARED-BODY-004, FMT-STRUCT-004, SHARED-BLANK-003, SHARED-BLANK-004, SHARED-AFTERBRACE-001, SHARED-AFTERBRACE-002, SHARED-DIAG-011, SHARED-FIX-003 |

RH3208 reports an expression-bodied local function and offers a code fix that converts it to a block body, as the formatter does under FMT-STRUCT-004. Which local functions are left alone, where the diagnostic is, how the body is converted, and when the fix is withheld are SHARED-BODY-001, SHARED-BODY-002, SHARED-BODY-003, and SHARED-BODY-004; this spec adds the blank line the fix inserts after the new block, the column the block is laid out from, and the fix it withholds inside an interpolation that cannot hold a line break (RH3208-004). The fix is deliberately withheld for an `async` local function whose return type is not written as a task type (an alias, a custom task type): the local function stays reported, and the author converts it by hand (SHARED-BODY-004).

## Non-goals

- Expression-bodied methods (RH3202), constructors (RH3203), operators (RH3205), conversion operators (RH3206), and finalizers (RH3207).
- Lambdas, which stay expression-bodied (FMT-STRUCT-008).

## Requirements

### RH3208-001 — Every expression-bodied local function is reported

The analyzer MUST report every local function that has an expression body — in a method, a lambda, another local function, or top-level statements, `async` or not — unless SHARED-BODY-001 applies. A local function with a block body or without a body MUST NOT be reported.

Why: The house style uses block bodies for local functions, as for methods; the other function kinds have rules of their own, so each kind can be configured separately.

Example:

```csharp
using System;
using System.Threading.Tasks;

class C
{
    void M()
    {
        Func<int> f = () =>
        {
            int One() {|RH3208:=> 1|};

            return One();
        };

        async Task RunAsync() {|RH3208:=> await Task.Delay(1)|};

        int Fail()
        {
            throw new InvalidOperationException();
        }

        static extern int Native();
    }
}
```

### RH3208-002 — The fix separates the new block from the next statement

When the converted local function, or the labeled statement it is the statement of, is followed by another statement of the same block or switch section and SHARED-BLANK-003 requires a blank line between them, the code fix MUST insert that blank line in the same step, where SHARED-AFTERBRACE-001 puts it; when at least one line break stands between the new closing brace and the next statement and every such line break lies inside a comment, it moves the statement below that comment as SHARED-AFTERBRACE-002 states, and is not offered in the initializer cases that requirement withholds it for. No blank line MUST be inserted when one is already there, when the next statement is the terminal `break` of SHARED-BLANK-004, or when the local function is the last statement.

Why: Formatting the local function alone does not decide the gap below it, yet the new closing brace would otherwise leave code that RH5030 reports.

Example:

```csharp
class C
{
    int M()
    {
        int Twice(int x) {|RH3208:=> x * 2|};
        return Twice(1);
    }

    void O(int a)
    {
        switch (a)
        {
            case 1:
                int Twice(int x) {|RH3208:=> x * 2|};
                break;
        }
    }

    int P()
    {
        L: int Local() {|RH3208:=> 1|};
        return Local();
    }
}
```

```csharp
class C
{
    int M()
    {
        int Twice(int x)
        {
            return x * 2;
        }

        return Twice(1);
    }

    void O(int a)
    {
        switch (a)
        {
            case 1:
                int Twice(int x)
                {
                    return x * 2;
                }
                break;
        }
    }

    int P()
    {
        L: int Local()
        {
            return 1;
        }

        return Local();
    }
}
```

### RH3208-003 — The block of a labeled local function is laid out from the start of its line

When a label stands in front of the local function on the same line, the code fix MUST lay out the block from the column at which that line starts. When the local function starts its own line, the code fix MUST lay out the block from the column of the local function, also below a label on a line of its own.

Why: The block's braces line up with the start of the line the declaration begins on, as for any statement; a label on the same line belongs to that line, while a label on its own line does not move the statement below it.

Example:

```csharp
class C
{
    void M()
    {
        goto L;
        L: int Local() {|RH3208:=> 1|};
    }

    int N()
    {
        goto L;
    L:
        int Local() {|RH3208:=> 1|};
        return Local();
    }
}
```

```csharp
class C
{
    void M()
    {
        goto L;
        L: int Local()
        {
            return 1;
        }
    }

    int N()
    {
        goto L;
    L:
        int Local()
        {
            return 1;
        }

        return Local();
    }
}
```

### RH3208-004 — A local function inside a non-verbatim interpolation withholds the fix before C# 11

The code fix MUST NOT be offered for a local function that stands, at any depth, inside an interpolation of an interpolated string that is not verbatim — one that starts with `$"`, not with `$@"` or `@$"` — when the code is compiled with C# 10 or earlier. This holds also when a verbatim interpolated string lies between the local function and that interpolation. The diagnostic is still reported. A local function inside an interpolation of a verbatim interpolated string that no interpolation of a non-verbatim one contains, a local function that only contains an interpolated string, and every local function when the code is compiled with C# 11 or later get the fix as SHARED-BODY-003 states. The withheld fix is a deliberate gap in the fix's coverage: such a local function is converted by hand.

Why: Before C# 11, an interpolation of a non-verbatim interpolated string cannot contain a line break (CS8967), and the fix writes the block body the formatter lays out over several lines (SHARED-BODY-003), so its result would not compile (SHARED-FIX-003). Writing the block on one line there would be a layout of its own, for code people seldom write. The report stays, because a block body can be written on one line at that position (SHARED-DIAG-011). An interpolation of a verbatim interpolated string accepts line breaks in every language version.

Example:

```csharp
using System;

class C
{
    static int F(Func<int> f) => f();

    string M() => $"a {F(() => { int L() {|RH3208:=> 1|}; return L(); })} b";
}
```

is reported, and no code fix is offered when the code is compiled with C# 10 or earlier. When it is compiled with C# 11 or later, and in an interpolation of a verbatim interpolated string in every language version, the fix is offered as SHARED-BODY-003 states:

```csharp
using System;

class C
{
    static int F(Func<int> f) => f();

    string M() => $@"a {F(() => { int L() {|RH3208:=> 1|}; return L(); })} b";
}
```
