# Analyzer — RH8402 Files must start with configured copyright header

| | |
|---|---|
| ID prefix | RH8402 |
| Status | Active |
| Category | Documentation |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH8402FileMustStartWithConfiguredXmlStyleCopyrightHeaderAnalyzer`, `RH8402FileMustStartWithConfiguredXmlStyleCopyrightHeaderCodeFixProvider` |
| Uses | RH0001-001, RH0001-006, SHARED-DOC-008, SHARED-FIX-006 |

RH8402 reports a file that does not start with the copyright header configured in `reihitsu.json`, and offers a code fix that writes the header at the start of the file.

## Non-goals

- Loading and validating the configuration file, and the problems found in it — RH0001.
- Comments after the header, and the documentation of the declarations in the file.

## Requirements

All examples use this configuration, and the checked file is named `C.cs`:

```json
{
  "copyright": {
    "copyrightText": "// <copyright file=\"{fileName}\" company=\"{company}\">\n// Copyright (c) {company}.\n// </copyright>",
    "company": "Example"
  }
}
```

### RH8402-001 — Nothing is checked without a valid configured header

The analyzer MUST check files only when the configuration that RH0001-001 loads has a `copyright` section whose `copyrightText` is not empty or only white space, and RH0001 finds no problem in the configuration. Without a configuration, without a `copyright` section, or with any problem in the configuration, nothing is reported.

Why: The rule enforces a header that the project chose; without one there is nothing to compare. A configuration with problems is reported by RH0001, and comparing files against a header that may be wrong would only add misleading diagnostics.

Example — without `reihitsu.json`,

```csharp
namespace N;

class C
{
}
```

is not reported.

### RH8402-002 — The expected header is the configured text with its placeholders filled in

The analyzer MUST derive the expected header from `copyrightText` by replacing every placeholder `{name}` that has a setting of that name in the `copyright` section, as RH0001-006 specifies, with the setting's value, and the placeholder `{fileName}` with the name of the checked file, without its directory. Every line break of the header MUST be written as the first line break of the file, or as `\n` when the file has none.

Why: A header that names the file and the company is written once in the configuration and stays correct for every file. Comparing in the file's own line ending keeps a CRLF file from being reported only because the configuration is written with `\n`.

Example:

```csharp
// <copyright file="C.cs" company="Example">
// Copyright (c) Example.
// </copyright>
namespace N;

class C
{
}
```

is not reported.

### RH8402-003 — A file that does not start with the header is reported

The analyzer MUST report a file whose text does not start with the expected header, compared character by character and case-sensitively. Anything in front of the header counts, a blank line or white space included, and so does an empty file.

This requirement covers a file in which the expected header is followed by a line break or by the end of the file, in every documentation mode, `None` included; RH8402-007 states how mode `None` is decided.

Why: The header states the file's ownership and licence terms in the agreed words. A header with different words, a different company, or another file name states something else, and one that does not start the file is easily missed.

Example:

```csharp
{|RH8402:|}namespace N;

class C
{
}
```

```csharp
{|RH8402:|}// <copyright file="Other.cs" company="Example">
// Copyright (c) Example.
// </copyright>
namespace N;
```

```csharp
{|RH8402:|}
// <copyright file="C.cs" company="Example">
// Copyright (c) Example.
// </copyright>
namespace N;
```

### RH8402-004 — The diagnostic is at the start of the file

The analyzer MUST report one diagnostic per file, as an empty span at the start of the file.

Why: The header belongs at the start, and a missing header has no text to mark.

Example: see RH8402-003.

### RH8402-005 — The fix writes the header at the start of the file

The code fix MUST write the expected header at the start of the file. When text follows the header and does not start with a line break, the fix MUST put a line break, in the line ending of the file's first line, or `\n` when the file has only one line, between the header and that text. Where the header goes depends on what starts the file:

- when the file starts with comments, the header is inserted in front of them;
- otherwise the header replaces the white space and line breaks in front of the first token, and is written in front of a preprocessor directive or a documentation comment that starts the file.

This requirement covers a file whose comments in front of the first token, if any, do not contain the word `copyright` in any casing; RH8402-006 states what the fix does when they do.

Why: A comment at the start of a file is the author's note and stays below the new header. White space in front of the header would keep the file from starting with it.

Example:

```csharp
{|RH8402:|}namespace N;
```

```csharp
// <copyright file="C.cs" company="Example">
// Copyright (c) Example.
// </copyright>
namespace N;
```

Example — a leading blank line is replaced:

```csharp
{|RH8402:|}
namespace N;
```

```csharp
// <copyright file="C.cs" company="Example">
// Copyright (c) Example.
// </copyright>
namespace N;
```

Example — another comment is kept below the header:

```csharp
{|RH8402:|}// Orders and invoices
namespace N;
```

```csharp
// <copyright file="C.cs" company="Example">
// Copyright (c) Example.
// </copyright>
// Orders and invoices
namespace N;
```

### RH8402-006 — The fix replaces an old header and keeps the lines behind it

When the file starts with a run of comments — `//` and `/* */` comments with nothing but white space and line breaks in front of, between, and behind them, up to the first token or to the first preprocessor directive or documentation comment — and a comment of that run contains the word `copyright` in any casing, the code fix MUST replace the run with the expected header: everything from the start of the file through the run's last comment, together with the white space behind it on its line. The line break that ends the line of the run's last comment, and every line after it — blank lines included — MUST stay as they are. When code follows the run's last comment on its line, the fix MUST put a line break between the header and that code as RH8402-005 states.

When the configured `copyrightText` ends with a line break, that line break of the header takes the place of the line break that ends the line of the run's last comment: the fix MUST write one line break between the header's last line and the line behind the run, not two, so the replaced file has exactly as many blank lines behind the header as the file had behind the run — none when the code follows on the next line. When code follows the run's last comment on its line, the header's own line break separates it and the fix adds none.

This requirement covers a run in which every comment contains the word `copyright` in any casing, with a configured `copyrightText` that does or does not end with a line break. A run that also holds a comment without that word is not covered.

Why: A comment that names a copyright is an old or a wrong header, and the configured header takes its place instead of standing above it. The blank lines between the header and the code are the author's layout, not part of the header, so replacing the header leaves them as they were (SHARED-FIX-006).

Example — an old header followed by a blank line:

```csharp
{|RH8402:|}// Copyright (c) Old Corp.

namespace N;
```

```csharp
// <copyright file="C.cs" company="Example">
// Copyright (c) Example.
// </copyright>

namespace N;
```

Example — an old header directly in front of the code:

```csharp
{|RH8402:|}// <copyright file="Other.cs" company="Example">
// Copyright (c) Example.
// </copyright>
namespace N;
```

```csharp
// <copyright file="C.cs" company="Example">
// Copyright (c) Example.
// </copyright>
namespace N;
```

Example — a configured header that ends with a line break. With `copyrightText` set to

```json
"// <copyright file=\"{fileName}\" company=\"{company}\">\n// Copyright (c) {company}.\n// </copyright>\n"
```

and the old header directly in front of the code,

```csharp
{|RH8402:|}// Copyright (c) Old Corp.
namespace N;
```

```csharp
// <copyright file="C.cs" company="Example">
// Copyright (c) Example.
// </copyright>
namespace N;
```

no blank line is written in front of `namespace N;`. With one blank line behind the old header,

```csharp
{|RH8402:|}// Copyright (c) Old Corp.

namespace N;
```

```csharp
// <copyright file="C.cs" company="Example">
// Copyright (c) Example.
// </copyright>

namespace N;
```

exactly one blank line stays.

### RH8402-007 — Every documentation mode gives the same result

In a syntax tree whose documentation mode is `None`, the analyzer MUST report exactly what it reports for the same file in mode `Parse`, and the code fix MUST produce the same text as it does for that file in mode `Parse` (SHARED-DOC-008). A `///` or `/** */` comment at the start of the file MUST be treated as the documentation comment it is in mode `Parse`, also where the compiler reads it as an ordinary comment: it ends the run of comments that RH8402-006 replaces, and the header is written in front of it.

Why: The rule's subject is the text of the file, which is the same whether documentation is parsed or not; staying silent would switch the rule off only because the project does not generate documentation (SHARED-DOC-008). Without parsing, a documentation comment at the start of the file looks like an ordinary comment, and taking it into the run of an old header would replace the documentation of the first declaration together with that header.

Example — with the documentation mode `None`:

```csharp
{|RH8402:|}namespace N;
```

```csharp
// <copyright file="C.cs" company="Example">
// Copyright (c) Example.
// </copyright>
namespace N;
```

Example — with the documentation mode `None`, a documentation comment behind an old header is kept:

```csharp
{|RH8402:|}// Copyright (c) Old Corp.
/// <summary>
/// Type
/// </summary>
class C
{
}
```

```csharp
// <copyright file="C.cs" company="Example">
// Copyright (c) Example.
// </copyright>
/// <summary>
/// Type
/// </summary>
class C
{
}
```
