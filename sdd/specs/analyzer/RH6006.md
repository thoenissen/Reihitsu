# Analyzer — RH6006 Opening parenthesis must be spaced correctly

| | |
|---|---|
| ID prefix | RH6006 |
| Status | Active |
| Category | Spacing |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH6006OpeningParenthesisMustBeSpacedCorrectlyAnalyzer`, `RH6006OpeningParenthesisMustBeSpacedCorrectlyCodeFixProvider` |
| Uses | FMT-CLEAN-001, FMT-SPACE-004, SHARED-WS-001, SHARED-WS-002 |

RH6006 reports whitespace directly after an opening parenthesis, and offers a code fix that deletes it as SHARED-WS-001 and SHARED-WS-002 specify.

In the examples, `→` marks a tab and `·` a space at the end of a line.

## Non-goals

- The whitespace before an opening parenthesis — RH6001 after statement keywords; elsewhere no analyzer rule checks it.
- The whitespace before a closing parenthesis — no analyzer rule checks it; the formatter removes it (FMT-SPACE-004).
- Parentheses inside directives and documentation comments, such as `#if ( FEATURE )` and `cref="M( int)"`, which are not code tokens.

## Requirements

### RH6006-001 — Whitespace after an opening parenthesis is reported

The analyzer MUST report the run of spaces and tabs directly after an opening parenthesis token when the run is followed by a token — the closing parenthesis included — or by the end of the line. An opening parenthesis directly followed by a token or by a line break MUST NOT be reported.

Why: The parenthesis belongs to the expression it opens; a space after it draws the eye inward and hides where the enclosed expression starts. The formatter removes the same whitespace — before a token on the same line (FMT-SPACE-004), at the end of the line (FMT-CLEAN-001) — so formatted code raises no RH6006 in these places.

Example:

```csharp
class C
{
    void M(int a)
    {
        M({|RH6006: |}a);
        M({|RH6006:→|}a);
        N({|RH6006: |});
        M({|RH6006:···|}
            a);
        M(
            a);

        if ({|RH6006: |}a > 0)
        {
        }
    }

    void N()
    {
    }
}
```

### RH6006-002 — One diagnostic per parenthesis

The analyzer MUST report one diagnostic per opening parenthesis, located on the whitespace run after it.

Why: The run is the text that is wrong and the text the fix deletes.

Example: see RH6006-001.

### RH6006-003 — The fix deletes the whitespace unless a comment is in the gap

The code fix MUST delete the reported whitespace as SHARED-WS-001 specifies, and MUST NOT be offered when a comment or directive sits between the parenthesis and the next token, as SHARED-WS-002 specifies.

Why: A comment in the gap is the author's placement; the fix does not decide whether the deletion affects it.

Example:

```csharp
class C
{
    void M(int a)
    {
        M({|RH6006: |}a);
        M({|RH6006:···|}
            a);

        if ({|RH6006:→|}a > 0)
        {
        }
    }
}
```

```csharp
class C
{
    void M(int a)
    {
        M(a);
        M(
            a);

        if (a > 0)
        {
        }
    }
}
```

A comment on the next line of the gap withholds the fix:

```csharp
class C
{
    void M(int a)
    {
        M({|RH6006:··|}
            // first argument
            a);
    }
}
```

is reported, and no code fix is offered.
