# Analyzer — RH5401 Expression style get-only properties should be single lined

| | |
|---|---|
| ID prefix | RH5401 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5401ExpressionStyleGetOnlyPropertiesShouldBeSingleLinedAnalyzer`, `RH5401ExpressionStyleGetOnlyPropertiesShouldBeSingleLinedCodeFixProvider` |
| Uses | FMT-BLANK-011, FMT-BREAK-026, FMT-BREAK-027, FMT-STRUCT-028, FMT-UNSUP-012, FMT-UNSUP-013, SHARED-DIAG-010, SHARED-FIX-006, SHARED-FIX-010 |

RH5401 reports an expression-bodied property whose `=>` or the start of whose expression is not on the line of the property's name, and offers a code fix that puts the property on one line the way the formatter does when it fits there.

## Non-goals

- Properties with an accessor list, also when an accessor has an expression body (`get => 1;`).
- Expression-bodied indexers, methods, operators, and other members.
- The layout of the expression after its first token.

## Requirements

### RH5401-001 — An arrow or expression below the name is reported

The analyzer MUST report a property with an expression body when its `=>` is not on the line of the property's name, or when the first token of its expression is not on that line. A property whose `=>` and first expression token are on the line of its name MUST NOT be reported, also when the expression continues on later lines.

Why: An expression-bodied property is a one-line declaration by intent; a wrapped arrow makes the reader look at the next line to see what the property returns (FMT-BREAK-026). An expression that starts on the name's line already says what the property computes, so its continuation may wrap.

Example:

```csharp
class C
{
    {|RH5401:int A
        => 1;|}

    {|RH5401:int B =>
        1;|}

    int D => 1
             + 2;
}
```

### RH5401-002 — The diagnostic is on the property

The analyzer MUST report one diagnostic per property, located on the whole property declaration, its attribute lists and modifiers included.

Why: The declaration is laid out as a whole, so the diagnostic covers the construct the fix lays out.

Example:

```csharp
using System;

class C
{
    {|RH5401:[Obsolete]
    int A
        => 1;|}
}
```

### RH5401-003 — The fix puts the property on one line

The code fix MUST format the property as the formatter formats it in place, which puts the `=>` and the expression on the line of the property's name (FMT-BREAK-026) and the attribute lists of the property as FMT-BREAK-027 places them. The attribute lists are part of the reported property (RH5401-002), so the fix lays them out with it rather than leaving them as written. The fix is offered only where no attribute list holds a blank line, or a comment that starts its own line, between its brackets, and that layout keeps the blank lines behind the attribute lists as written (RH5401-004), so its result has the blank lines there that the input has; the line break that moves an attribute list off the property's line (example `B` below), or that separates the lists the formatter splits one list into (example `L` below), is not a blank line.

Why: The formatter owns the layout of expression-bodied properties; delegating to it applies that layout instead of a second one.

Example:

```csharp
class C
{
    {|RH5401:int A
        => 1;|}

    {|RH5401:int B =>
        1;|}
}
```

```csharp
class C
{
    int A => 1;

    int B => 1;
}
```

Example — the documentation comment stays as written (SHARED-FIX-006, *Leading trivia*):

```csharp
class C
{
    /// <summary>A</summary>
    {|RH5401:int A
        => 1;|}
}
```

```csharp
class C
{
    /// <summary>A</summary>
    int A => 1;
}
```

Formatting the document would spread the documentation comment over three lines.

Example — a property with attribute lists:

```csharp
using System;

class C
{
    {|RH5401:[Obsolete]
    [CLSCompliant(false)]
    public int A
        => 1;|}

    {|RH5401:[Obsolete] int B
        => 1;|}

    {|RH5401:[Obsolete, CLSCompliant(false)]
    int L
        => 1;|}
}
```

```csharp
using System;

class C
{
    [Obsolete]
    [CLSCompliant(false)]
    public int A => 1;

    [Obsolete]
    int B => 1;

    [Obsolete]
    [CLSCompliant(false)]
    int L => 1;
}
```

Example — a blank line that the formatter keeps behind an attribute list, in front of a comment or of the next attribute list; a comment behind the `]` of an attribute list, which is not between its brackets; and a comment between the brackets that shares its line with code in front of it:

```csharp
using System;

class C
{
    {|RH5401:[Obsolete]

    // note
    int E
        => 1;|}

    {|RH5401:[Obsolete]

    [CLSCompliant(false)]
    int F
        => 1;|}

    {|RH5401:[Obsolete] // note
    int J
        => 1;|}

    {|RH5401:[Obsolete /* c */] int U
        => 1;|}

    {|RH5401:[Obsolete("a" /* c */)]
    int V
        => 1;|}

    {|RH5401:[Obsolete("a", // c
              false)]
    int Y
        => 1;|}
}
```

```csharp
using System;

class C
{
    [Obsolete]

    // note
    int E => 1;

    [Obsolete]

    [CLSCompliant(false)]
    int F => 1;

    [Obsolete] // note
    int J => 1;

    [Obsolete /* c */] int U => 1;

    [Obsolete("a" /* c */)]
    int V => 1;

    [Obsolete("a", // c
              false)]
    int Y => 1;
}
```

### RH5401-004 — The fix is withheld when the property stays on several lines

The code fix MUST NOT be offered when the property's own code — from its first token behind its attribute lists, a modifier or its type, through its `;`, without the trivia in front of that token or behind the `;` — laid out by the formatter, would still span several lines because its expression stays wrapped. The attribute lists do not count, nor does a comment between them and that first token: a property whose own code the formatter puts on one line gets the fix (RH5401-003), however many attribute lists it has and wherever FMT-BREAK-027 places them. Nor MUST it be offered when a comment, a directive, or disabled text stands in front of the `=>`, between the property's name and the `=>`, or behind the `=>`, in front of the expression: the formatter refuses such a property as a whole (FMT-UNSUP-013, FMT-UNSUP-012), and the fix asks it before it is offered (SHARED-FIX-010). Nor MUST it be offered when the formatted property would hold, in the gap behind one of its attribute lists, a different number of blank lines than the property as written. That gap runs from the `]` that closes an attribute list of the property as written to the next token — the `[` of the next attribute list, or the property's first token behind its attribute lists — with every comment, directive, and disabled text in between. The formatter changes that number where it inserts a blank line in front of a comment on its own line (FMT-BLANK-011, examples `D`, `G`) or collapses several blank lines into one (examples `H`, `K`, `M`); a gap whose blank lines it keeps, such as a single blank line in front of a comment or of the next attribute list, gets the fix (RH5401-003, examples `E`, `F`). Nor MUST it be offered when one of its attribute lists holds, between its brackets, a blank line or a comment that starts its own line — a comment with nothing but whitespace in front of it on its line. Between its brackets means in the trivia between two tokens of the list, from its `[` through its `]`: behind the `[`, in front of the `]`, and everywhere between, inside the argument list of one of its attributes as well, whether or not the formatter splits the list (FMT-STRUCT-028) (examples `N`, `O`, `P`, `Q`, `R`, `T`, `W`). A comment between the brackets with code in front of it on its line does not withhold the fix (RH5401-003, examples `U`, `V`, `Y`). Trivia in front of the `[` or behind the `]` is not between the brackets: a blank line or a comment there counts only in a gap behind an attribute list, as stated before, and a list without a blank line or an own-line comment between its brackets gets the fix also when the formatter splits it (RH5401-003, examples `E`, `F`, `J`, `L`). A directive or disabled text between the brackets does not withhold the fix by this condition. The diagnostic is still reported in each case: a shape the formatter refuses is not one it keeps (SHARED-DIAG-010).

Why: The fix promises a one-line property. Where the formatter keeps the property on several lines, applying it would leave the expression in a shape the author did not choose without clearing the diagnostic; the author moves the arrow and the first token by hand. Where the formatter refuses the property, it changes nothing, and the author moves the comment or the directive above the property, after which the fix applies. Blank lines among the attributes and between them and the property are not what the diagnostic is about, so the fix does not insert or remove one; where the formatter would, the fix is withheld rather than undoing the formatter's blank-line layout, and the author moves the arrow by hand or adjusts the blank lines, after which the fix applies. Inside an attribute list, the formatter changes the blank lines by dropping one that is written there, where it splits the list, and by inserting one in front of a comment that starts its own line (FMT-BLANK-011); a drop in one list can offset an insertion in another (example `W`), so no count of blank lines tells whether the fix keeps them. Blank lines and own-line comments are what these changes need, so the fix refuses lists that hold one, and keeps the fix for a comment on a line with code, in front of which the formatter inserts nothing. Such a list is rare: a blank line there is a shape people seldom write, and RH5038 reports a comment inside an attribute's argument list. So the fix refuses the class by that cheap check (`AGENTS.md`, *Code-fix coverage*); the author removes the blank line or moves the comment above the attribute lists, after which the fix applies.

Example:

```csharp
using System;

class C
{
    {|RH5401:int A =>
        1
        + 2;|}

    {|RH5401:int B // note
        => 1;|}

    {|RH5401:int D => // note
        1;|}

    {|RH5401:[Obsolete]
    int E =>
        1
        + 2;|}
}
```

is reported, and no code fix is offered.

Example — the formatter would insert or remove a blank line behind an attribute list:

```csharp
using System;

class C
{
    {|RH5401:[Obsolete]
    // note
    int D
        => 1;|}

    {|RH5401:[Obsolete]
    // note
    [CLSCompliant(false)]
    int G
        => 1;|}

    {|RH5401:[Obsolete]


    // note
    int H
        => 1;|}

    {|RH5401:[Obsolete]


    [CLSCompliant(false)]
    int K
        => 1;|}

    {|RH5401:[Obsolete]


    int M
        => 1;|}
}
```

is reported, and no code fix is offered.

Example — an attribute list holds a blank line, or a comment that starts its own line, between its brackets:

```csharp
using System;
using System.ComponentModel;

class C
{
    {|RH5401:[Obsolete,

     CLSCompliant(false)]
    int N
        => 1;|}

    {|RH5401:[Obsolete

     , CLSCompliant(false)]
    int O
        => 1;|}

    {|RH5401:[

     Obsolete, CLSCompliant(false)]
    int P
        => 1;|}

    {|RH5401:[Obsolete("a",

              false)]
    int Q
        => 1;|}

    {|RH5401:[Obsolete(

        "a"), CLSCompliant(false)]
    int R
        => 1;|}

    {|RH5401:[Obsolete("a",
              // why
              false)]
    int T
        => 1;|}

    {|RH5401:[Obsolete,

     CLSCompliant(false)]
    [DefaultValue(typeof(int),
                  // why
                  "1")]
    int W
        => 1;|}
}
```

is reported, and no code fix is offered.
