# Analyzer — RH5401 Expression style get-only properties should be single lined

| | |
|---|---|
| ID prefix | RH5401 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5401ExpressionStyleGetOnlyPropertiesShouldBeSingleLinedAnalyzer`, `RH5401ExpressionStyleGetOnlyPropertiesShouldBeSingleLinedCodeFixProvider` |
| Uses | FMT-BLANK-011, FMT-BREAK-026, FMT-BREAK-027, FMT-UNSUP-012, FMT-UNSUP-013, SHARED-DIAG-010, SHARED-FIX-006, SHARED-FIX-010 |

RH5401 reports an expression-bodied property whose `=>` or the start of whose expression is not on the line of the property's name, and offers a code fix that puts the property on one line the way the formatter does when it fits there.

## Non-goals

- Properties with an accessor list, also when an accessor has an expression body (`get => 1;`).
- Expression-bodied indexers, methods, operators, and other members.
- The layout of the expression after its first token.

## Requirements

### RH5401-001 — An arrow or expression below the name is reported

The analyzer MUST report a property with an expression body when its `=>` is not on the line of the property's name, or when the first token of its expression is not on that line. A property whose `=>` and first expression token are on the line of its name MUST NOT be reported, also when the expression continues on later lines.

Why: An expression-bodied property is a one-line declaration by intent; a wrapped arrow makes the reader look at the next line to see what the property returns (FMT-BREAK-026). An expression that starts on the name's line already says what the property computes, so its continuation may wrap.

Example:

```csharp
class C
{
    {|RH5401:int A
        => 1;|}

    {|RH5401:int B =>
        1;|}

    int D => 1
             + 2;
}
```

### RH5401-002 — The diagnostic is on the property

The analyzer MUST report one diagnostic per property, located on the whole property declaration, its attribute lists and modifiers included.

Why: The declaration is laid out as a whole, so the diagnostic covers the construct the fix lays out.

Example:

```csharp
using System;

class C
{
    {|RH5401:[Obsolete]
    int A
        => 1;|}
}
```

### RH5401-003 — The fix puts the property on one line

The code fix MUST format the property as the formatter formats it in place, which puts the `=>` and the expression on the line of the property's name (FMT-BREAK-026) and the attribute lists of the property as FMT-BREAK-027 places them. The attribute lists are part of the reported property (RH5401-002), so the fix lays them out with it rather than leaving them as written.

Why: The formatter owns the layout of expression-bodied properties; delegating to it applies that layout instead of a second one.

Example:

```csharp
class C
{
    {|RH5401:int A
        => 1;|}

    {|RH5401:int B =>
        1;|}
}
```

```csharp
class C
{
    int A => 1;

    int B => 1;
}
```

Example — the documentation comment stays as written (SHARED-FIX-006, *Leading trivia*):

```csharp
class C
{
    /// <summary>A</summary>
    {|RH5401:int A
        => 1;|}
}
```

```csharp
class C
{
    /// <summary>A</summary>
    int A => 1;
}
```

Formatting the document would spread the documentation comment over three lines.

Example — a property with attribute lists:

```csharp
using System;

class C
{
    {|RH5401:[Obsolete]
    [CLSCompliant(false)]
    public int A
        => 1;|}

    {|RH5401:[Obsolete] int B
        => 1;|}
}
```

```csharp
using System;

class C
{
    [Obsolete]
    [CLSCompliant(false)]
    public int A => 1;

    [Obsolete]
    int B => 1;
}
```

Example — a comment between the attribute lists and the property's own code:

```csharp
using System;

class C
{
    {|RH5401:[Obsolete]
    // note
    int E
        => 1;|}
}
```

```csharp
using System;

class C
{
    [Obsolete]

    // note
    int E => 1;
}
```

The blank line in front of the comment is the formatter's (FMT-BLANK-011).

### RH5401-004 — The fix is withheld when the property stays on several lines

The code fix MUST NOT be offered when the property's own code — from its first token behind its attribute lists, a modifier or its type, through its `;`, without the trivia in front of that token or behind the `;` — laid out by the formatter, would still span several lines because its expression stays wrapped. The attribute lists do not count, nor does a comment between them and that first token: a property whose own code the formatter puts on one line gets the fix (RH5401-003), however many attribute lists it has and wherever FMT-BREAK-027 places them. Nor MUST it be offered when a comment, a directive, or disabled text stands in front of the `=>`, between the property's name and the `=>`, or behind the `=>`, in front of the expression: the formatter refuses such a property as a whole (FMT-UNSUP-013, FMT-UNSUP-012), and the fix asks it before it is offered (SHARED-FIX-010). The diagnostic is still reported in each case: a shape the formatter refuses is not one it keeps (SHARED-DIAG-010).

Why: The fix promises a one-line property. Where the formatter keeps the property on several lines, applying it would leave the expression in a shape the author did not choose without clearing the diagnostic; the author moves the arrow and the first token by hand. Where the formatter refuses the property, it changes nothing, and the author moves the comment or the directive above the property, after which the fix applies.

Example:

```csharp
using System;

class C
{
    {|RH5401:int A =>
        1
        + 2;|}

    {|RH5401:int B // note
        => 1;|}

    {|RH5401:int D => // note
        1;|}

    {|RH5401:[Obsolete]
    int E =>
        1
        + 2;|}
}
```

is reported, and no code fix is offered.
