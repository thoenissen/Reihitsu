# Analyzer — RH7105 Declaration keywords must follow order

| | |
|---|---|
| ID prefix | RH7105 |
| Status | Active |
| Category | Organization |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH7105DeclarationKeywordsMustFollowOrderAnalyzer`, `RH7105DeclarationKeywordsMustFollowOrderCodeFixProvider` |
| Uses | SHARED-MODORDER-001, SHARED-MODORDER-002, SHARED-MODORDER-003, RH2005-003 |

RH7105 reports a declaration whose modifiers are not in the canonical keyword order, and offers a code fix that reorders them.

## Non-goals

- The order of the keywords of a compound accessibility, such as `internal protected` — RH7106.
- Which modifiers a declaration may carry. The rule orders the modifiers that are written.

## Requirements

### RH7105-001 — Modifiers out of the canonical order are reported

The analyzer MUST report a checked declaration (SHARED-MODORDER-001) whose modifiers are not in this order: the accessibility keywords `file`, `public`, `private`, `protected`, and `internal` first, then `static`, `abstract`, `virtual`, `sealed`, `override`, `new`, `readonly`, `volatile`, `async`, `extern`, `unsafe`, `required`, `ref`, `partial`, and every other modifier last. The accessibility keywords share the first position, so their order among themselves is never reported by this rule.

Why: A fixed order makes declarations easy to compare: the accessibility a reader looks for first is always first, and keywords such as `static` or `override` are always found at the same place. `ref` and `partial` come last because C# requires them right before the type keyword.

Example:

```csharp
class B
{
    public int X;
}

class C : B
{
    {|RH7105:static|} public int A;
    public {|RH7105:readonly|} static int D = 1;
    {|RH7105:new|} public int X;
    {|RH7105:required|} public int Y;
}

interface I
{
    {|RH7105:abstract|} static void M();
}
```

### RH7105-002 — Modifiers in the canonical order are not reported

The analyzer MUST NOT report a declaration whose modifiers follow the order of RH7105-001, including a declaration whose accessibility keywords are written in any order among themselves.

Why: Only the position of the other keywords relative to the accessibility and to each other is this rule's decision.

Example:

```csharp
public readonly ref partial struct S
{
}

public unsafe partial class U
{
    internal protected static void M()
    {
    }
}
```

is not reported.

### RH7105-003 — The diagnostic is on the first misplaced modifier

The analyzer MUST report one diagnostic per declaration, located on the first modifier, from the left, that is not the modifier the canonical order puts at its position.

Why: That keyword is where the written order first departs from the canonical one; one diagnostic per declaration matches the fix, which reorders the whole list at once.

Example:

```csharp
class C
{
    public {|RH7105:readonly|} static int A = 1;
    {|RH7105:static|} internal protected void M()
    {
    }
}
```

### RH7105-004 — The fix writes the canonical order

The code fix MUST write the declaration's modifiers in the order of RH7105-001, keeping the accessibility keywords in their written order among themselves, and MUST rewrite the modifier list as specified in SHARED-MODORDER-002. It MUST NOT be offered when SHARED-MODORDER-003 withholds it.

Why: A stable sort changes only what the rule asks for; the order of `internal protected` is RH7106's to correct, so the two fixes never undo each other. The RH2005 fix puts `private` in front of the other modifiers (RH2005-003), which this order keeps.

Example:

```csharp
class C
{
    {|RH7105:static|} internal protected void M()
    {
    }
}
```

```csharp
class C
{
    internal protected static void M()
    {
    }
}
```
