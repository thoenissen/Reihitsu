# Analyzer — RH5111 Assignments must have proper line breaks

| | |
|---|---|
| ID prefix | RH5111 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5111AssignmentsMustHaveProperLineBreaksAnalyzer`, `RH5111AssignmentsMustHaveProperLineBreaksCodeFixProvider` |
| Uses | FMT-BREAK-016, FMT-PIPE-017, FMT-PIPE-018, SHARED-FIX-007 |

RH5111 reports an assignment, an initializer, or a default value whose `=` is not on the line its target ends on, or whose value does not start on the line of the `=`, and offers a code fix that lays it out the way the formatter does.

## Non-goals

- Compound assignments such as `+=` and `??=`.
- The layout of a multi-line value after its first line, such as the lines of an initializer or a lambda.
- The arrow of an expression-bodied member — RH5040 for comments around it, the formatter (FMT-BREAK-026) for its line.

## Requirements

### RH5111-001 — An `=` below its target is reported

The analyzer MUST report a simple assignment that forms an expression statement or a member of an object initializer, a variable declarator with an initializer, a property with an initializer, and a parameter with a default value when its `=` starts on a later line than its target ends on. The target of a property initializer ends with the closing brace of the accessor list, the target of the others with the last token in front of the `=`.

Why: An `=` at the start of a line separates the target from what is assigned to it, and the reader has to search for what is assigned to what (FMT-BREAK-016).

Example:

```csharp
class C
{
    {|RH5111:int P { get; set; }
        = 5;|}

    void M({|RH5111:int a
               = 1|})
    {
        var {|RH5111:x
            = 1|};
        {|RH5111:x
            = 2|};
    }
}
```

### RH5111-002 — A value below its `=` is reported

The analyzer MUST report the constructs of RH5111-001, and an enum member with a value, when the value starts on a later line than the `=`, whatever the value is — a raw string literal, an array initializer, and a collection initializer included. Inside an object initializer, a member whose value is a nested object initializer (`Member = { … }`) MUST NOT be reported for its value's position.

Why: The value starts on the line of the `=`, so the assignment reads as one unit; a value that spans several lines starts there and keeps its own layout. A nested object initializer is the exception, because its opening brace goes on a line of its own.

Example:

```csharp
using System.Collections.Generic;

enum E
{
    {|RH5111:A =
        1|},
}

class C
{
    List<int> L { get; set; } = new();
    C Inner { get; set; }
    int P { get; set; }

    void M()
    {
        var {|RH5111:s =
            """
            a
            """|};
        int[] {|RH5111:arr =
        {
            1
        }|};
        var c = new C
        {
            {|RH5111:P =
                1|},
            {|RH5111:L =
            {
                1
            }|},
            Inner =
            {
                P = 1
            }
        };
    }
}
```

### RH5111-003 — The diagnostic is on the whole construct

The analyzer MUST report one diagnostic per construct, located on the whole assignment expression, the whole variable declarator, the whole property declaration, the whole parameter, or the whole enum member, even when both its `=` and its value are misplaced.

Why: Target, operator, and value are laid out together, so the diagnostic covers the construct the fix lays out.

Example: see RH5111-001 and RH5111-002.

### RH5111-004 — The fix lays out the construct

When the reported construct is not inside the value of an assignment, the code fix MUST format it as the formatter formats it in place, which joins the `=` to the line of the target and starts the value on the line of the `=` (FMT-BREAK-016). A value that spans several lines keeps its own layout from its first line on. A construct that starts a later line of the node it is formatted in is laid out as the recorded gap below states.

Recorded gap — an enum member, a parameter, or a variable declarator that starts a later line of its enum, its parameter list, or its declaration. The fix formats such a construct within that node and keeps the construct's leading trivia as it stands in the document (FMT-PIPE-018): the construct keeps the column of its first line, and the blank lines, comments, and directives above it stay in their lines and columns, a documentation comment written behind the code in front of it included, also where formatting the document would move them. The construct's other lines take the columns the formatter gives them with its first line in the formatter's column, so a line of a multi-line value that was aligned to an anchor on the first line can stand off that anchor, and the value does not keep its own layout there. This is a decision, not an oversight: it is the gap that SHARED-FIX-007 and FMT-PIPE-017 record, the output is the one the fix gave before the change `phase-prediction-removal`, and laying such a construct out in the formatter's columns is left to a restructuring of the formatter's context entry point. The fix is offered for these constructs as for any other. A construct that does not start its line — a first parameter behind `(`, such as `int a` in the first example below, or a first declarator behind its type, such as `x` there — is not in the gap, and neither is an assignment expression, a property, or a member of an object initializer.

Why: The formatter owns the layout of assignments; delegating to it applies that layout instead of a second one. The gap keeps the fix's output for these constructs as it was, since writing the formatter's columns there needs a change to how the formatter formats a node within its context, which has not been made yet; the diagnostic itself is cleared either way, because the `=` and the value are joined.

Example — constructs outside the gap:

```csharp
class C
{
    void M({|RH5111:int a
               = 1|})
    {
        var {|RH5111:x =
            1|};
        {|RH5111:x
            = 2|};
        var {|RH5111:s =
            """
            a
            """|};
    }
}
```

```csharp
class C
{
    void M(int a = 1)
    {
        var x = 1;
        x = 2;
        var s = """
                a
                """;
    }
}
```

Example — an enum member that starts a later line of its enum, in the gap:

```csharp
enum E
{
    A = 1,
      {|RH5111:B =
      2|}
}
```

```csharp
enum E
{
    A = 1,
      B = 2
}
```

`B` keeps column 6, where formatting the document would put it in column 4.

Example — a documentation comment written behind the member in front of the reported one stays on that line, where formatting the document would move it onto a line of its own:

```csharp
internal enum Values
{
    First, /// Doc
    {|RH5111:Second =
        2|},
    Third,
}
```

```csharp
internal enum Values
{
    First, /// Doc
    Second = 2,
    Third,
}
```

Example — a declarator on a later line of its declaration, whose value is wrapped:

```csharp
class C
{
    static int Other(int x, int y)
    {
        return x + y;
    }

    void M()
    {
        int a = 1,
              {|RH5111:b =
                  Other(1,
                        2)|};
    }
}
```

```csharp
class C
{
    static int Other(int x, int y)
    {
        return x + y;
    }

    void M()
    {
        int a = 1,
              b = Other(1,
                  2);
    }
}
```

`b` keeps column 14. The formatter lays the declaration out with `b` in column 8, which puts `1` in column 18, so `2` stands in column 18 after the fix, while `1` ends up in column 24.

### RH5111-005 — A comment or directive in the construct withholds the fix

The code fix MUST NOT be offered when a comment or a preprocessor directive sits inside the reported assignment expression, property declaration, parameter, or enum member, or anywhere in the trivia of the reported variable declarator, its leading and trailing trivia included. A comment in front of a reported parameter or enum member MUST NOT withhold the fix. The diagnostic is still reported.

Why: Joining the lines would move the comment or the directive between the target and the value, or comment out code behind a `//` comment.

Example:

```csharp
class C
{
    {|RH5111:int Q { get; set; } // c
        = 5;|}

    void M()
    {
        var {|RH5111:y // c
            = 1|};
        {|RH5111:y = /* c */
            2|};
    }
}
```

is reported, and no code fix is offered. In

```csharp
enum E
{
    A,
    // second
    {|RH5111:B =
        2|},
}

class C
{
    void M(int b,
           // second
           {|RH5111:int a =
               1|})
    {
    }
}
```

the comments are in front of the enum member and the parameter, and the fix is offered.
