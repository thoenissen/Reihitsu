# Analyzer — RH5011 break-Statement should be followed by a blank line

| | |
|---|---|
| ID prefix | RH5011 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5011BreakStatementsShouldBeFollowedByABlankLineAnalyzer`, `RH5011BreakStatementsShouldBeFollowedByABlankLineCodeFixProvider`, `StatementShouldBeFollowedByABlankLineAnalyzerBase<TStatement>` |
| Uses | SHARED-BLANK-001, SHARED-FIX-003, SHARED-FIX-004, SHARED-FIX-008 |

RH5011 reports a `break` statement that is followed by more code without a blank line between them, and offers a code fix that inserts one below the `break` statement.

## Non-goals

- The blank line before a `break` statement — RH5010.
- The blank line after a statement that ends with a closing brace — RH5030.

## Requirements

### RH5011-001 — A `break` followed by a statement or a switch section needs a blank line

The analyzer MUST report a `break` statement that is followed by another statement or by the next section of its switch statement when the trivia between the `break` statement's semicolon and the next token contains no blank line as SHARED-BLANK-001 defines it. A comment between them, a documentation comment included, does not count as a blank line. A statement on the same line as the `break` statement is reported too, and so is a `break` statement that is the embedded body of another statement.

Why: `break` leaves the loop or the switch section; code after it starts a new path, and in a switch statement the next section is a new case. The blank line marks that boundary. A `///` comment inside a method body documents no declaration; it separates the code no more than any other comment does.

Example:

```csharp
class C
{
    void M(int a)
    {
        switch (a)
        {
            case 1:
                a++;
                {|RH5011:break|};
            case 2:
                break;

            default:
                break;
        }

        while (true)
        {
            if (a > 0)
                {|RH5011:break|};
            a++;
            {|RH5011:break|};
            // note
            a++;
            {|RH5011:break|}; // note
            a++;
            {|RH5011:break|};
            /// doc
            a++;
            {|RH5011:break|}; a++;
        }
    }
}
```

### RH5011-002 — A `break` before a closing brace or a directive is not reported

The analyzer MUST NOT report a `break` statement whose next token is a closing brace, or whose first trivia after the semicolon, apart from whitespace and line breaks, is a preprocessor directive.

Why: Before a closing brace nothing follows inside the block or switch statement that a blank line could separate. A directive line already separates the `break` from the code after it, and a blank line in front of the directive would separate the directive from the code it governs.

Example:

```csharp
class C
{
    void M(int a)
    {
        switch (a)
        {
            case 1:
                break;
        }

        while (true)
        {
            break;
#pragma warning disable CS0168
            a++;
        }
    }
}
```

is not reported.

### RH5011-003 — The diagnostic is on the `break` keyword

The analyzer MUST report the diagnostic on the `break` keyword.

Why: The keyword is where the missing separator becomes visible.

Example: see RH5011-001.

### RH5011-004 — The fix inserts a blank line below the `break` line

When the next token starts on a later line than the `break` statement and the `break` statement's line ends outside a comment — after the semicolon, that line holds nothing but whitespace or comments that end on it — the code fix MUST insert one empty line directly below the line of the `break` statement, ending with the line ending SHARED-FIX-008 specifies: in a document whose line breaks are all CRLF or all LF, the line break of that line, and in a document whose line breaks are all a lone `\r`, `\n`. A trailing comment on the `break` line stays there, and a comment on the lines below stays directly above the code it precedes.

Why: The `break` line is complete as written; the blank line is the only thing missing, and inserting it directly below that line changes nothing else.

Example:

```csharp
class C
{
    void M(int a)
    {
        switch (a)
        {
            case 1:
                a++;
                {|RH5011:break|};
            default:
                break;
        }

        while (true)
        {
            {|RH5011:break|};
            // note
            a++;
            {|RH5011:break|}; // note
            a++;
        }
    }
}
```

```csharp
class C
{
    void M(int a)
    {
        switch (a)
        {
            case 1:
                a++;
                break;

            default:
                break;
        }

        while (true)
        {
            break;

            // note
            a++;
            break; // note

            a++;
        }
    }
}
```

In a document whose line breaks are all a lone `\r`, the empty line the fix inserts below `break;` in the `switch` section above ends in `\n`, and the line breaks around it stay a lone `\r`.

### RH5011-005 — A statement on the `break` line is moved below a blank line

When the next statement starts on the line of the `break` statement, the code fix MUST replace the whitespace between the semicolon and that statement with two line breaks, in the line ending SHARED-FIX-008 specifies, followed by the indentation of the `break` line.

Why: A blank line can only separate the two statements once they are on lines of their own; indenting the moved statement like the `break` keeps both in the same column.

Example:

```csharp
class C
{
    void M(int a)
    {
        while (true)
        {
            {|RH5011:break|}; a++;
        }
    }
}
```

```csharp
class C
{
    void M(int a)
    {
        while (true)
        {
            break;

            a++;
        }
    }
}
```

### RH5011-006 — A comment on the `break` line withholds the same-line fix

The code fix MUST NOT be offered when the next statement starts on the line of the `break` statement and anything but spaces and tabs stands between the semicolon and that statement, such as a comment. The diagnostic is still reported.

Why: The fix would have to decide whether the comment belongs to the `break` or to the moved statement, and the author decides where a comment goes.

Example:

```csharp
class C
{
    void M(int a)
    {
        while (true)
        {
            {|RH5011:break|}; /* note */ a++;
        }
    }
}
```

is reported, and no code fix is offered.

### RH5011-007 — A comment that spans the end of the `break` line moves the blank line below it

When the `break` statement's line ends inside a comment — a comment that starts behind the semicolon on the `break` line ends on a later line — the code fix MUST insert one empty line directly below the line on which the comments behind the semicolon end — the first line, from the `break` line on, that no comment continues beyond — provided the next token, a statement or a switch label, starts on a later line than that one. That empty line ends with the same line break as the line above it; in a document whose line breaks are all CRLF or all LF, that is the line ending SHARED-FIX-008 specifies. When the next token starts on the line on which the comment ends, behind it, the code fix MUST NOT be offered. The diagnostic is reported in both cases.

Why: RH5011-004 inserts the blank line below a `break` line that ends outside a comment. Here the line below the `break` line is part of the comment's text, and an empty line inserted there would change that text (SHARED-FIX-003); below the line on which the comment ends, the blank line separates the `break` and its comment from the code after it, as RH5011-004 does for a comment on one line. When the next code starts behind the comment, it would first have to be moved onto a line of its own, and where it goes relative to the comment is the author's decision, as RH5011-006 says for a comment on the `break` line. A diagnostic without a fix is a supported end state.

Example — the next token starts on a line of its own:

```csharp
class C
{
    void M(int a)
    {
        switch (a)
        {
            case 1:
                {|RH5011:break|}; /* a
                b */
            default:
                break;
        }

        while (true)
        {
            {|RH5011:break|}; /* a
            b */
            a++;
            {|RH5011:break|}; /* x */ /* a
            b */ // c
            // note
            a++;
        }
    }
}
```

```csharp
class C
{
    void M(int a)
    {
        switch (a)
        {
            case 1:
                break; /* a
                b */

            default:
                break;
        }

        while (true)
        {
            break; /* a
            b */

            a++;
            break; /* x */ /* a
            b */ // c

            // note
            a++;
        }
    }
}
```

Example — the next token starts behind the comment on its last line:

```csharp
class C
{
    void M(int a)
    {
        switch (a)
        {
            case 1:
                {|RH5011:break|}; /* a
                b */ default:
                break;
        }

        while (true)
        {
            {|RH5011:break|}; /* a
            b */ a++;
        }
    }
}
```

is reported, and no code fix is offered.

### RH5011-008 — A `break` before a keyword that continues its statement is not reported

The analyzer MUST NOT report a `break` statement whose next token is the `else` keyword of an `if` statement or the `while` keyword of a `do` statement. Such a keyword continues a statement that holds the `break` statement as its embedded body, or as part of it. A `while` keyword that starts a `while` statement is not such a keyword: a `break` statement in front of it is reported as RH5011-001 states.

Why: `else` and the footer of a `do` statement belong to the statement that holds the `break`; nothing new starts there. A blank line in front of them would tear the statement apart, and RH5026 and RH5027 report that blank line, so the two fixes would undo each other (SHARED-FIX-004).

Example:

```csharp
class C
{
    void M(int a)
    {
        while (true)
        {
            if (a > 0) break; else a++;

            if (a > 1)
                break;
            else
                a--;

            do break; while (a > 2);

            do
                break;
            while (a > 3);

            {|RH5011:break|};
            while (a > 4) a--;
        }
    }
}
```

The `break` statements in front of `else` and in front of the footers of the `do` statements are not reported; the last `break`, in front of a `while` statement, is.
