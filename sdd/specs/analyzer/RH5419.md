# Analyzer — RH5419 Expression style get-only indexers should be single lined

| | |
|---|---|
| ID prefix | RH5419 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5419ExpressionStyleGetOnlyIndexersShouldBeSingleLinedAnalyzer`, `RH5419ExpressionStyleGetOnlyIndexersShouldBeSingleLinedCodeFixProvider` |
| Uses | FMT-BREAK-011, FMT-BREAK-012, FMT-BREAK-026, FMT-BREAK-027, FMT-UNSUP-012, FMT-UNSUP-013, RH5401-003, RH5401-004, SHARED-DIAG-010, SHARED-FIX-003, SHARED-FIX-006, SHARED-FIX-007, SHARED-FIX-010 |

RH5419 reports an expression-bodied indexer whose parameter list spans several lines, or whose `=>` or the start of whose expression is not on the line of the `]` that closes its parameter list, and offers a code fix that puts the parameter list, the `=>`, and the start of the expression on one line.

## Non-goals

- Indexers with an accessor list, also when an accessor has an expression body (`get => 1;`) — RH3210 reports a get-only accessor list.
- Expression-bodied properties — RH5401; methods, operators, and other members.
- The layout of the expression after its first token.
- The gap between the indexer's `this` and the `[` of its parameter list. The formatter joins it (FMT-BREAK-011), and no rule reports it.
- Joining the parameter list of an indexer in the formatter. The formatter keeps a parameter list on several lines (FMT-BREAK-012); RH5419 reports such a list of an expression-bodied indexer although the formatter keeps it, as SHARED-DIAG-010 records.

## Requirements

### RH5419-001 — A wrapped indexer is reported

The analyzer MUST report an indexer with an expression body when its parameter list spans several lines — when the `[` that opens it and the `]` that closes it are on different lines — when its `=>` is not on the line of that `]`, or when the first token of its expression is not on that line. An indexer whose parameter list stands on one line and whose `=>` and first expression token are on the line of its `]` MUST NOT be reported, also when the expression continues on later lines. The parameter list is reported whatever makes it span several lines: a line break between two of its tokens, or a comment, a directive, disabled text, or a literal that spans lines inside it. The `]` is the token in front of the `=>`; the line of the indexer's `this` keyword does not count, so a line break between `this` and the `[` is not reported.

Why: An expression-bodied indexer is a one-line declaration by intent, like an expression-bodied property (RH5401); a wrapped arrow makes the reader look at the next line to see what the indexer returns (FMT-BREAK-026), and a wrapped parameter list splits the short signature of a one-line member over several lines. An expression that starts on the line of the `]` already says what the indexer computes, so its continuation may wrap. Properties and indexers have separate rules so that each can be configured on its own.

Example:

```csharp
class C
{
    {|RH5419:int this[int i]
        => i;|}

    {|RH5419:int this[long i] =>
        1;|}

    {|RH5419:int this[short a,
             short b]
        => a;|}

    {|RH5419:int this[byte a,
             byte b] => a;|}

    int this[uint a, uint b] => 1;

    int this[char a, char b] => a
                                + b;

    int this
        [ulong a, ulong b] => 1;
}
```

### RH5419-002 — The diagnostic is on the indexer

The analyzer MUST report one diagnostic per indexer, located on the whole indexer declaration, its attribute lists and modifiers included.

Why: The declaration is laid out as a whole, so the diagnostic covers the construct the fix lays out.

Example:

```csharp
using System;

class C
{
    {|RH5419:[Obsolete]
    public int this[int i]
        => i;|}
}
```

### RH5419-003 — The fix puts the indexer on one line

The code fix MUST put the indexer's parameter list on one line, removing every line break in the trivia between its `[` and its `]` together with the whitespace around it, and MUST then format the indexer as the formatter formats it in place: the formatter puts the `=>` and the start of the expression on the line of the `]` (FMT-BREAK-026), spaces the tokens of the joined parameter list as on any line, and places the attribute lists of the indexer as FMT-BREAK-027 places them. The attribute lists are laid out as RH5401-003 states for the attribute lists of a property, with the indexer in the property's place. The fix leaves the gap between `this` and the `[` to the formatter.

Why: The diagnostic asks for the indexer on one line (RH5419-001), and the formatter keeps a parameter list on several lines (FMT-BREAK-012), so the fix joins the parameter list itself; everything else the formatter already lays out, and delegating to it applies that layout instead of a second one. A parameter list on one line is one the formatter keeps on one line, so formatting the result changes nothing (SHARED-FIX-007).

Example:

```csharp
class C
{
    {|RH5419:int this[int i]
        => i;|}

    {|RH5419:int this[long i] =>
        1;|}

    {|RH5419:int this[
        uint a,
        uint b]
        => 1;|}

    {|RH5419:int this[short a,
             short b] => a;|}

    {|RH5419:int this
        [ulong a,
         ulong b] => 1;|}

    {|RH5419:int this /* c */ [sbyte a,
                      sbyte b] => a;|}
}
```

```csharp
class C
{
    int this[int i] => i;

    int this[long i] => 1;

    int this[uint a, uint b] => 1;

    int this[short a, short b] => a;

    int this[ulong a, ulong b] => 1;

    int this /* c */ [sbyte a, sbyte b] => a;
}
```

Example — the documentation comment stays as written (SHARED-FIX-006, *Leading trivia*):

```csharp
class C
{
    /// <summary>A</summary>
    {|RH5419:int this[int i]
        => i;|}
}
```

```csharp
class C
{
    /// <summary>A</summary>
    int this[int i] => i;
}
```

Example — an indexer with attribute lists:

```csharp
using System;

class C
{
    {|RH5419:[Obsolete] int this[int i]
        => i;|}

    {|RH5419:[Obsolete, CLSCompliant(false)]
    int this[long i]
        => 1;|}
}
```

```csharp
using System;

class C
{
    [Obsolete]
    int this[int i] => i;

    [Obsolete]
    [CLSCompliant(false)]
    int this[long i] => 1;
}
```

### RH5419-004 — The fix is withheld where the indexer cannot be put on one line

The code fix MUST NOT be offered when the indexer's parameter list spans several lines and a comment, a directive, or disabled text stands between its `[` and its `]`, in the trivia of a token from the `[` through the `]` other than the leading trivia of the `[` and the trailing trivia of the `]`. A comment in front of the `[` or behind the `]` is not inside the parameter list, and a block comment inside a parameter list that stands on one line does not withhold the fix, because the fix joins nothing there. Nor MUST it be offered when, laid out as RH5419-003 states, the indexer's code from the first token behind its attribute lists through its `;` would still span several lines, whatever keeps a line break there. Causes include a literal inside the parameter list that spans lines, an expression the formatter keeps wrapped, a line break in front of `this` that the formatter keeps, such as one between a modifier, the type, an explicit interface name, and `this`, and a comment, a directive, or disabled text in front of the `[` that keeps a line break between two tokens of the declaration, such as a line comment behind `this`, a comment on a line of its own in front of the `[`, or a directive between `this` and the `[`. The code in front of the first token behind the attribute lists — that token's leading trivia, such as a documentation comment, and the attribute lists, which RH5419-003 lays out on lines of their own — is not measured. A block comment between two tokens on one line in front of the `[`, such as `this /* c */ [`, and a bare line break between `this` and the `[`, which the formatter joins (FMT-BREAK-011), unlike one the formatter keeps in front of `this`, do not withhold the fix. Nor MUST it be offered when a comment, a directive, or disabled text stands in front of the `=>`, between the `]` and the `=>`, or behind the `=>`, in front of the expression: the formatter refuses such an indexer as a whole (FMT-UNSUP-013, FMT-UNSUP-012), and the fix asks it before it is offered (SHARED-FIX-010). Nor MUST it be offered where RH5401-004 withholds the fix for the attribute lists of a property, with the indexer in the property's place: where the formatted indexer would hold, in the gap behind one of its attribute lists, a different number of blank lines than the indexer as written, and where one of its attribute lists holds, between its brackets, a blank line, a directive, disabled text, or a comment that starts its own line. The diagnostic is still reported in each case: a shape the formatter refuses is not one it keeps, and RH5419 reports a parameter list on several lines although the formatter keeps it (SHARED-DIAG-010).

Why: Joining the lines of a parameter list that holds a comment or a directive would move it onto another line or glue a line comment to the code behind it, and the author decides where it goes (SHARED-FIX-003). The fix promises the indexer on one line; where the expression, a literal, a line break the formatter keeps in front of `this`, or a comment or directive in front of the `[` keeps it on several lines, applying it would leave a shape the author did not choose, and the author lays out the indexer by hand. Where the formatter refuses the indexer, it changes nothing, and the author moves the comment or the directive above the indexer, after which the fix applies. The attribute lists of an indexer are the attribute lists of a member like those of a property, and RH5401-004 gives the reasons for which the fix leaves their blank lines and the lists that hold a blank line, a directive, or a comment on its own line alone.

Example:

```csharp
using System;

class C
{
    {|RH5419:int this[int i] =>
        i
        + 1;|}

    {|RH5419:int this[char a,
             char b] => Foo(a,
                            b);|}

    {|RH5419:int this[byte a, // note
             byte b] => a;|}

    {|RH5419:int this[
#if DEBUG
        uint a
#else
        ulong a
#endif
        ] => 1;|}

    {|RH5419:int this[string s = """
                        a
                        """] => 1;|}

    {|RH5419:int this // note
        [sbyte a,
         sbyte b] => a;|}

    {|RH5419:int this
        /* note */ [ushort a,
                    ushort b] => a;|}

    {|RH5419:int this
#if DEBUG
#endif
        [float a,
         float b] => 1;|}

    {|RH5419:int this // note
        [double d]
        => 1;|}

    {|RH5419:int
        this[decimal a,
             decimal b] => 1;|}

    {|RH5419:int this[long i] // note
        => 1;|}

    {|RH5419:int this[short i] => // note
        1;|}

    {|RH5419:[Obsolete]
    // note
    int this[byte i]
        => 1;|}

    {|RH5419:[Obsolete,

     CLSCompliant(false)]
    int this[char c]
        => 1;|}

    int Foo(char a, char b) => a;
}
```

is reported, and no code fix is offered.

Example — a block comment inside a parameter list on one line, one on the line of `this` in front of the `[` of a wrapped parameter list, and a documentation comment in front of the indexer do not withhold the fix:

```csharp
class C
{
    {|RH5419:int this[byte a /* c */]
        => a;|}

    {|RH5419:int this /* c */ [sbyte a,
                      sbyte b] => a;|}

    /// <summary>A</summary>
    {|RH5419:int this[short a,
             short b] => a;|}
}
```

```csharp
class C
{
    int this[byte a /* c */] => a;

    int this /* c */ [sbyte a, sbyte b] => a;

    /// <summary>A</summary>
    int this[short a, short b] => a;
}
```
