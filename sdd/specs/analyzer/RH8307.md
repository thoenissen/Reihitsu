# Analyzer — RH8307 Content after opening XML tag must be on same line as closing tag

| | |
|---|---|
| ID prefix | RH8307 |
| Status | Active |
| Category | Documentation |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH8307TextAfterOpeningXmlTagMustBeOnSameLineAsClosingTagAnalyzer`, `RH8307TextAfterOpeningXmlTagMustBeOnSameLineAsClosingTagCodeFixProvider` |
| Uses | FMT-DOC-001, FMT-DOC-003, FMT-DOC-009, FMT-DOC-011, FMT-DOC-012, FMT-DOC-013, FMT-PIPE-032, SHARED-DIAG-010, SHARED-DOC-004, SHARED-DOC-008, SHARED-FIX-006 |

RH8307 reports an XML element at the top level of a documentation comment whose content starts on the line of its start tag while its end tag is on a later line, and offers a code fix that either puts the element on one line or puts its content on lines of its own.

## Non-goals

- How many lines a summary spans — RH8305.
- Several elements on one line, and text after an end tag — RH8304 and RH8308.
- The layout of an element nested inside another element.

## Requirements

### RH8307-001 — Content that starts beside the start tag and ends below it is reported

The analyzer MUST report an XML element at the top level of a documentation comment — one that no other element encloses — whose first content — the first character of its text that is not white space, or the first other XML node, such as a nested element or an XML comment — is on the line of its start tag, while its end tag starts on a later line. Nothing is reported when SHARED-DOC-008 applies.

This requirement covers the `///` documentation comments of a declaration, as SHARED-DOC-004 defines them, and an element closed by its own end tag. An inline formatting element such as `<b>` or `<i>` written at the top level, and a comment that is not a documentation comment of a declaration, such as one inside a method body, are not covered; RH8307-002 states that an element nested inside another element, and an element of a `/** */` comment, are not reported.

Why: Content that starts beside the start tag but ends below it is the half-wrapped shape of an element that grew from one line. It reads like a broken one-line element; either everything fits on one line, or the content belongs on lines of its own between the tags. The rule judges the elements that structure the comment — `<summary>`, `<param>`, `<returns>`, `<remarks>`, and their kin; an element nested inside one of them, such as `<para>`, `<b>`, or `<see>`, is part of that element's content.

Example:

```csharp
class C
{
    /// <summary>
    /// Runs
    /// </summary>
    /// {|RH8307:<param name="value">The value
    /// </param>|}
    void M(string value)
    {
    }

    /// {|RH8307:<summary>Stops
    /// now
    /// </summary>|}
    void N()
    {
    }

    /// <summary>
    /// Count
    /// </summary>
    /// {|RH8307:<remarks><see cref="C"/>
    /// tail</remarks>|}
    int B;
}
```

### RH8307-002 — Other layouts are not reported

The analyzer MUST NOT report an element that is on one line, an element whose content starts on a line after its start tag, or an element whose content is only white space. It MUST NOT report an element of a `///` comment that the formatter leaves as written — one that holds an element without an end tag of its own (FMT-DOC-013), or one that FMT-DOC-003 keeps behind code, as SHARED-DIAG-010 requires, also when the element itself is complete. It MUST NOT report an element nested inside another element, whatever its layout and whatever its kind, such as `<para>`, `<b>`, `<c>`, or `<see>`; the element around it is judged as RH8307-001 states. It MUST NOT report an element of a delimited documentation comment (`/** … */`), whose text the formatter does not rewrite (FMT-DOC-012), as SHARED-DIAG-010 requires.

Why: The one-line form and the form with the content on lines of its own are both complete layouts. The formatter keeps a comment it leaves as written in the shape the author gave it, and it never rewrites the text of a delimited comment, so the fix would change nothing and the diagnostic would stay for good.

Example:

```csharp
class C
{
    /// <summary>Runs</summary>
    /// <param name="value">The value</param>
    void M(string value)
    {
    }

    /// <summary>
    /// Stops
    /// </summary>
    /// <remarks>
    /// Remarks</remarks>
    void N()
    {
    }

    /// <summary>
    /// Value
    /// </summary>
    /// <remarks>
    /// </remarks>
    int A;
}
```

is not reported, and neither is

```csharp
class C
{
    /// <summary>
    /// Gets A
    /// </summary>
    /// <remarks>Text
    /// more
    int A;

    /// <summary>
    /// Gets B
    /// </summary>
    /// <remarks>Text
    /// more</returns>
    int B;

    /// <summary>Gets D
    /// now</summary>
    /// <remarks>Text
    int D;

    int E; /// <remarks>a
    /// b</remarks>
}
```

and neither is

```csharp
class C
{
    /** <summary>Total
     * sum</summary> */
    int A;

    /** <summary>
    Count
    </summary>
    <remarks>Sum
    more</remarks> */
    int B;
}
```

and neither is

```csharp
class C
{
    /// <summary>
    /// Value
    /// </summary>
    /// <remarks>
    /// <para>First
    /// second</para>
    /// Text <b>bold
    /// still bold</b>
    /// </remarks>
    int A;
}
```

Example — the qualifier "at the top level": the `<remarks>` element is reported, and the `<para>` element nested inside it is not:

```csharp
class C
{
    /// <summary>
    /// Value
    /// </summary>
    /// {|RH8307:<remarks>Text
    /// <para>First
    /// second</para>
    /// </remarks>|}
    int A;
}
```

### RH8307-003 — The diagnostic covers the element

The analyzer MUST report one diagnostic per reported element, covering the whole element from its start tag through its end tag. An element in the documentation comment of a record, class, or struct with a primary constructor is reported once, like any other.

Why: The whole element is what the fix lays out again. The comment of a type with a primary constructor documents the type and its constructor at once, but it is one element in the source, and two diagnostics on the same span would make the user correct it twice.

Example: see RH8307-001, and

```csharp
/// <summary>
/// Point
/// </summary>
/// {|RH8307:<remarks>Sum
/// more</remarks>|}
public record R(int A);
```

which is reported once.

### RH8307-004 — The fix lays the element out as the formatter does

The code fix MUST lay out the reported element as FMT-DOC-009 specifies, keeping its content as FMT-DOC-011 specifies: an element other than `<summary>` whose content is one line is put on the line of its start tag; otherwise the start tag, each line of the content, and the end tag each start a `///` line of their own. The element's new text MUST be the text the formatter gives that element when it lays out one documentation element (FMT-PIPE-032), the columns of its lines included.

The fix MUST change only the reported element (SHARED-FIX-006): the other lines and elements of the comment, the other documentation comments of the declaration and the blank lines between them, and the declaration's own code MUST stay as they are written, also where the formatter would lay them out differently, and wherever the declaration stands — in a namespace, in a type, or directly in the compilation unit.

This requirement covers an element closed by its own end tag, other than an inline formatting element such as `<b>` or `<i>`, in a `///` documentation comment that starts its own line, in a document without syntax errors. RH8307-005 states that the fix is withheld for a comment that starts behind code.

Why: The fix and the formatter produce the same layout, so an element the fix has corrected stays as it is when the file is formatted. The rest of the declaration is not what the diagnostic is about; laying it out on the way would hide the correction in changes nobody asked for.

Example:

```csharp
class C
{
    /// <summary>
    /// Runs
    /// </summary>
    /// {|RH8307:<param name="value">The value
    /// </param>|}
    void M(string value)
    {
    }

    /// {|RH8307:<summary>Stops
    /// now
    /// </summary>|}
    void N()
    {
    }
}
```

```csharp
class C
{
    /// <summary>
    /// Runs
    /// </summary>
    /// <param name="value">The value</param>
    void M(string value)
    {
    }

    /// <summary>
    /// Stops
    /// now
    /// </summary>
    void N()
    {
    }
}
```

Example — the rest of the declaration stays as written, for a type directly in the compilation unit:

```csharp
/// <summary>
/// Total
/// </summary>
/// {|RH8307:<remarks>Sum
/// more</remarks>|}
public class C { int A(int a) => a; }
```

```csharp
/// <summary>
/// Total
/// </summary>
/// <remarks>
/// Sum
/// more
/// </remarks>
public class C { int A(int a) => a; }
```

### RH8307-005 — The fix is withheld for a comment written behind code

The code fix MUST NOT be offered when the documentation comment of the reported element starts behind code on its line: its first `///` follows a token on the same line, as SHARED-DOC-004 describes. The diagnostic is still reported. A comment whose first `///` has nothing but white space in front of it on its line gets the fix as RH8307-004 states.

Why: SHARED-DOC-004 requires a fix that moves neither the declaration nor the code in front of the comment to leave the comment behind that code. Laying the element out there would put `///` lines behind code, a layout that nothing else produces and the formatter replaces by moving the comment onto a line of its own (FMT-DOC-001), so the fix could only give a shape the formatter changes again. Documentation written behind code is rare, and where it belongs is the author's decision.

Example:

```csharp
class C
{
    int A; /// {|RH8307:<remarks>R
    /// more</remarks>|}
    int B;
}
```

is reported, and no code fix is offered.

### RH8307-006 — The fix is withheld for an element of a `/** */` comment

Status: Retired — an element of a delimited documentation comment is not reported at all, because the formatter does not rewrite the text of such a comment (FMT-DOC-012) and SHARED-DIAG-010 forbids a layout rule to report a shape the formatter keeps; RH8307-002 states it, so there is no diagnostic for a fix to be withheld from.
