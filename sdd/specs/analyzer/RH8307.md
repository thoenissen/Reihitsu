# Analyzer — RH8307 Content after opening XML tag must be on same line as closing tag

| | |
|---|---|
| ID prefix | RH8307 |
| Status | Active |
| Category | Documentation |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH8307TextAfterOpeningXmlTagMustBeOnSameLineAsClosingTagAnalyzer`, `RH8307TextAfterOpeningXmlTagMustBeOnSameLineAsClosingTagCodeFixProvider` |
| Uses | FMT-DOC-009, FMT-DOC-011, SHARED-DOC-004, SHARED-DOC-008 |

RH8307 reports an XML element of a documentation comment whose content starts on the line of its start tag while its end tag is on a later line, and offers a code fix that either puts the element on one line or puts its content on lines of its own.

## Non-goals

- A summary that spans fewer than three lines — RH8305.
- Several elements on one line, and text after an end tag — RH8304 and RH8308.

## Requirements

### RH8307-001 — Content that starts beside the start tag and ends below it is reported

The analyzer MUST report an XML element of a documentation comment, at the top level or nested inside another element, whose first content — the first character of its text that is not white space, or the first other XML node, such as a nested element or an XML comment — is on the line of its start tag, while its end tag starts on a later line. Nothing is reported when SHARED-DOC-008 applies.

This requirement covers the `///` and `/** */` documentation comments of a declaration, as SHARED-DOC-004 defines them, and an element closed by its own end tag. A comment that is not a documentation comment of a declaration, such as one inside a method body, is not covered.

Why: Content that starts beside the start tag but ends below it is the half-wrapped shape of an element that grew from one line. It reads like a broken one-line element; either everything fits on one line, or the content belongs on lines of its own between the tags.

Example:

```csharp
class C
{
    /// <summary>
    /// Runs
    /// </summary>
    /// {|RH8307:<param name="value">The value
    /// </param>|}
    void M(string value)
    {
    }

    /// {|RH8307:<summary>Stops
    /// now
    /// </summary>|}
    void N()
    {
    }

    /// <summary>
    /// Value
    /// </summary>
    /// <remarks>
    /// {|RH8307:<para>First
    /// second</para>|}
    /// </remarks>
    int A;

    /// <summary>
    /// Count
    /// </summary>
    /// {|RH8307:<remarks><see cref="C"/>
    /// tail</remarks>|}
    int B;

    /** {|RH8307:<summary>Total
     * sum</summary>|} */
    int D;
}
```

### RH8307-002 — Other layouts are not reported

The analyzer MUST NOT report an element that is on one line, an element whose content starts on a line after its start tag, or an element whose content is only white space.

Why: The one-line form and the form with the content on lines of its own are both complete layouts.

Example:

```csharp
class C
{
    /// <summary>Runs</summary>
    /// <param name="value">The value</param>
    void M(string value)
    {
    }

    /// <summary>
    /// Stops
    /// </summary>
    /// <remarks>
    /// Remarks</remarks>
    void N()
    {
    }

    /// <summary>
    /// Value
    /// </summary>
    /// <remarks>
    /// </remarks>
    int A;
}
```

is not reported.

### RH8307-003 — The diagnostic covers the element

The analyzer MUST report one diagnostic per reported element, covering the whole element from its start tag through its end tag.

Why: The whole element is what the fix lays out again.

Example: see RH8307-001.

### RH8307-004 — The fix lays the element out as the formatter does

The code fix MUST lay out the reported element as FMT-DOC-009 specifies, keeping its content as FMT-DOC-011 specifies: an element other than `<summary>` whose content is one line is put on the line of its start tag; otherwise the start tag, each line of the content, and the end tag each start a `///` line of their own.

This requirement covers a `///` documentation comment in a document without syntax errors, in a declaration whose code outside the reported element is already laid out as the formatter lays it out.

Why: The fix and the formatter produce the same layout, so an element the fix has corrected stays as it is when the file is formatted.

Example:

```csharp
class C
{
    /// <summary>
    /// Runs
    /// </summary>
    /// {|RH8307:<param name="value">The value
    /// </param>|}
    void M(string value)
    {
    }

    /// {|RH8307:<summary>Stops
    /// now
    /// </summary>|}
    void N()
    {
    }
}
```

```csharp
class C
{
    /// <summary>
    /// Runs
    /// </summary>
    /// <param name="value">The value</param>
    void M(string value)
    {
    }

    /// <summary>
    /// Stops
    /// now
    /// </summary>
    void N()
    {
    }
}
```
