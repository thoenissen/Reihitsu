# Analyzer — RH6008 Closing square brackets must be spaced correctly

| | |
|---|---|
| ID prefix | RH6008 |
| Status | Active |
| Category | Spacing |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH6008ClosingSquareBracketsMustBeSpacedCorrectlyAnalyzer`, `RH6008ClosingSquareBracketsMustBeSpacedCorrectlyCodeFixProvider` |
| Uses | FMT-SPACE-004, FMT-SPACE-013, FMT-SPACE-014, SHARED-WS-001, SHARED-WS-002 |

RH6008 reports whitespace in front of a closing square bracket on the line of the token before it, unless the bracket closes an attribute list, and offers a code fix that deletes it as SHARED-WS-001 and SHARED-WS-002 specify.

In the examples, `→` marks a tab.

## Non-goals

- The closing bracket of an attribute list — RH6014.
- The whitespace after an opening square bracket — RH6007.
- Whether a closing bracket starts its own line — the line-break rules and the formatter.

## Requirements

### RH6008-001 — Whitespace before a closing square bracket on the same line is reported

The analyzer MUST report the run of spaces and tabs directly in front of a closing square bracket when the bracket is on the line on which the token before it ends, also when a comment sits between that token and the run. A closing square bracket that starts its line, after a line break, MUST NOT be reported, and neither MUST the closing bracket of an attribute list.

Why: The bracket belongs to the index, rank, or elements it closes. A bracket on its own line is a layout choice other rules decide, and its indentation is not a gap. The formatter removes the same whitespace (FMT-SPACE-004), also between a comment and the bracket (FMT-SPACE-013, and FMT-SPACE-014 for a `/** */` comment the bracket carries), so formatted code raises no RH6008.

Example:

```csharp
using System;

class C
{
    [Obsolete ]
    void M(int[] arr)
    {
        var x = arr[0{|RH6008: |}];
        int[,{|RH6008: |}] g = null;
        int[] e = [1, 2{|RH6008:→|}];
        var z = arr[0 /* note */{|RH6008: |}];
        var w = arr[0
            ];
        var v = arr[0 // note
            ];
    }
}
```

### RH6008-002 — One diagnostic per bracket

The analyzer MUST report one diagnostic per closing square bracket, located on the whitespace run in front of it.

Why: The run is the text that is wrong and the text the fix deletes.

Example: see RH6008-001.

### RH6008-003 — The fix deletes the whitespace unless a comment is in the gap

The code fix MUST delete the reported whitespace as SHARED-WS-001 specifies, and MUST NOT be offered when a comment or directive sits between the bracket and the token before it, as SHARED-WS-002 specifies.

Why: Deleting the whitespace between a comment and the bracket would glue the comment to it; the author decides whether the comment stays there.

Example:

```csharp
class C
{
    void M(int[] arr)
    {
        var x = arr[0{|RH6008: |}];
        int[,{|RH6008: |}] g = null;
        int[] e = [1, 2{|RH6008:→|}];
    }
}
```

```csharp
class C
{
    void M(int[] arr)
    {
        var x = arr[0];
        int[,] g = null;
        int[] e = [1, 2];
    }
}
```

The comment before the bracket withholds the fix:

```csharp
class C
{
    void M(int[] arr)
    {
        var z = arr[0 /* note */{|RH6008: |}];
    }
}
```

is reported, and no code fix is offered.
