# Analyzer — RH8309 XML documentation elements must follow a prescribed order

| | |
|---|---|
| ID prefix | RH8309 |
| Status | Active |
| Category | Documentation |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH8309XmlDocumentationElementsMustFollowPrescribedOrderAnalyzer`, `RH8309XmlDocumentationElementsMustFollowPrescribedOrderCodeFixProvider`, `XmlDocumentationElementOrderingUtilities` |
| Uses | FMT-DOC-001, SHARED-DOC-004, SHARED-DOC-008, SHARED-DOC-017, SHARED-FIX-006 |

RH8309 reports a top-level element of a `///` documentation comment that stands after an element it has to precede in the prescribed order, and offers a code fix that sorts the elements into that order.

## Non-goals

- The order of the `<param>` and `<typeparam>` elements among themselves — RH8102 and RH8109.
- The layout of the elements — RH8304, RH8305, RH8307, and RH8308.

## Requirements

### RH8309-001 — An element out of the prescribed order is reported

The analyzer MUST report a top-level element of a `///` documentation comment that stands after an element coming later in this order: `<inheritdoc>`, `<include>`, `<summary>`, `<typeparam>`, `<param>`, `<returns>`, `<value>`, `<exception>`, `<permission>`, `<example>`, `<remarks>`, `<seealso>`. An element closed by an end tag and an empty element count alike. When the declaration has several `///` documentation comments, an element out of order within one of them is reported, in a later comment as well as in the first. Nothing is reported when SHARED-DOC-008 applies.

This requirement covers the `///` comments of a declaration as SHARED-DOC-004 defines them, whose top-level elements are each empty or closed by their own end tag, with the tag names written in lower case, without a namespace prefix, and in no XML namespace. A `/** */` documentation comment, and a `///` comment that is not a documentation comment of a declaration, such as one inside a method body, on an accessor, or after an attribute list, are not covered. Whether an element of one documentation comment is out of order with an element of another comment of the same declaration is not covered.

Why: Documentation that always follows the same order reads the same everywhere: the reader finds the summary first, then the parameters, the return value, and the details, and two versions of a comment compare line by line.

Example:

```csharp
class C
{
    /// <returns>Sum</returns>
    /// {|RH8309:<summary>
    /// Adds
    /// </summary>|}
    /// <param name="a">First</param>
    int Add(int a)
    {
        return a;
    }

    /// <summary>
    /// Value
    /// </summary>
    /// <seealso cref="C"/>
    /// {|RH8309:<inheritdoc/>|}
    int A;
}
```

### RH8309-002 — Elements in order, other elements, and nested elements are not reported

The analyzer MUST NOT report elements that follow the order, elements of the same kind in any order among themselves, an element whose name is not in the order, wherever it stands, or an element nested inside another element.

Why: Elements of one kind have an order of their own, such as the order of the parameters, which other rules check. A custom element has no place in the prescribed order, so it does not constrain the elements around it, and a nested element belongs to the content of the element around it.

Example:

```csharp
class C
{
    /// <summary>
    /// Adds
    /// </summary>
    /// <param name="b">Second</param>
    /// <param name="a">First</param>
    /// <custom>Custom</custom>
    /// <returns>Sum</returns>
    /// <remarks><returns>Nested</returns></remarks>
    int Add(int a, int b)
    {
        return a;
    }
}
```

is not reported.

### RH8309-003 — One diagnostic per comment, on the first element out of order

The analyzer MUST report one diagnostic per documentation comment, on the first element that stands after an element coming later in the order, covering that whole element. The elements after it are not reported, even when they are out of order as well.

Why: One out-of-order element is enough to tell that the comment needs sorting, and the fix sorts the whole comment at once.

Example:

```csharp
class C
{
    /// <exception cref="System.Exception">Fails</exception>
    /// {|RH8309:<returns>Value</returns>|}
    /// <example>Example</example>
    /// <value>Value</value>
    int A => 0;
}
```

### RH8309-004 — The fix sorts the elements into the prescribed order

The code fix MUST sort the top-level elements of the reported comment whose names are in the order into that order, keeping elements of the same kind in the order they are written. An element whose name is not in the order MUST keep its position, and the sorted elements MUST fill the remaining positions. Each element keeps its content.

The fix MUST change only the order of the reported comment's elements (SHARED-FIX-006): each element MUST keep its own lines as written, and the declaration's own code MUST stay as it is written, also where the formatter would lay them out differently, and wherever the declaration stands — in a namespace, in a type, or directly in the compilation unit.

This requirement covers a comment that starts its own line, the first documentation comment of its declaration, whether or not later ones follow, and whose top-level elements each stand on their own `///` lines with nothing but white space between, before, and after them, in a document without syntax errors. When any top-level element of the comment has no end tag of its own, no code fix is offered (SHARED-DOC-017). RH8309-006 and RH8309-007 state that the fix is withheld for a comment that starts behind code and for a comment that is not the declaration's first documentation comment.

Why: Sorting all elements at once corrects the comment in one step, and keeping elements of one kind in their written order leaves their own order to the rules that check it. A custom element stays where the author put it, because the rule does not know where it belongs. The layout of the elements and the rest of the declaration are not what the diagnostic is about; laying them out on the way would hide the correction in changes nobody asked for.

Example:

```csharp
class C
{
    /// <summary>
    /// Adds
    /// </summary>
    /// <remarks>Remarks</remarks>
    /// <custom>Custom</custom>
    /// {|RH8309:<param name="a">First</param>|}
    /// <returns>Sum</returns>
    int Add(int a)
    {
        return a;
    }
}
```

```csharp
class C
{
    /// <summary>
    /// Adds
    /// </summary>
    /// <param name="a">First</param>
    /// <custom>Custom</custom>
    /// <returns>Sum</returns>
    /// <remarks>Remarks</remarks>
    int Add(int a)
    {
        return a;
    }
}
```

Example — the rest of the declaration stays as written, for a type directly in the compilation unit:

```csharp
/// <remarks>Remarks</remarks>
/// {|RH8309:<summary>
/// Runs
/// </summary>|}
public class C { void I<T>() { } }
```

```csharp
/// <summary>
/// Runs
/// </summary>
/// <remarks>Remarks</remarks>
public class C { void I<T>() { } }
```

### RH8309-005 — The fix is withheld for text, comments, and other nodes beside the elements

The code fix MUST NOT be offered when text with a character that is not white space, an XML comment, a CDATA section, or a processing instruction stands at the top level of the reported comment: between two top-level elements, before the first, or after the last. Text is read as the compiler reads it, so a character or entity reference counts as the character it stands for: `&amp;` is text with a character that is not white space, and `&#32;` is white space. Text of white space only, such as the line breaks and `///` exteriors between the elements, does not withhold the fix. The diagnostic is still reported.

Why: The fix moves the elements and leaves the text where it stands, so text, a comment, a CDATA section, or a processing instruction written next to one element would end up next to another and say something the author did not write; text before the first element usually introduces it, and text after the last one usually continues it. Which element the text belongs to is the author's decision, so the comment is sorted by hand.

Example:

```csharp
class C
{
    /// <remarks>R</remarks>
    /// Text between
    /// {|RH8309:<summary>
    /// S
    /// </summary>|}
    int A;

    /// <remarks>R</remarks>
    /// <!-- c -->
    /// {|RH8309:<summary>
    /// S
    /// </summary>|}
    int B;

    /// Intro
    /// <remarks>R</remarks>
    /// {|RH8309:<summary>
    /// S
    /// </summary>|}
    int D;

    /// <remarks>R</remarks>
    /// {|RH8309:<summary>
    /// S
    /// </summary>|}
    /// Outro
    int E;

    /// <remarks>R</remarks>
    /// <![CDATA[x]]>
    /// {|RH8309:<summary>
    /// S
    /// </summary>|}
    int F;

    /// <remarks>R</remarks>
    /// <?pi x?>
    /// {|RH8309:<summary>
    /// S
    /// </summary>|}
    int G;

    /// <remarks>R</remarks>
    /// &amp;
    /// {|RH8309:<summary>
    /// S
    /// </summary>|}
    int H;
}
```

is reported, and no code fix is offered.

### RH8309-006 — The fix is withheld for a comment written behind code

The code fix MUST NOT be offered when the reported comment starts behind code on its line: its first `///` follows a token on the same line, as SHARED-DOC-004 describes. The diagnostic is still reported. A comment whose first `///` has nothing but white space in front of it on its line gets the fix as RH8309-004 states.

Why: SHARED-DOC-004 requires a fix that moves neither the declaration nor the code in front of the comment to leave the comment behind that code. Sorting the elements there would move an element behind code and others onto the lines below it, a layout that nothing else produces and the formatter replaces by moving the comment onto a line of its own (FMT-DOC-001). Documentation written behind code is rare, and where it belongs is the author's decision.

Example:

```csharp
class C
{
    int A; /// <remarks>R</remarks>
    /// {|RH8309:<summary>
    /// S
    /// </summary>|}
    int B;
}
```

is reported, and no code fix is offered.

### RH8309-007 — The fix is withheld for a later documentation comment

The code fix MUST NOT be offered when the reported comment is not the first documentation comment, `///` or `/** */`, in the leading trivia of the declaration it documents, whatever separates it from the comments before it: a blank line, an ordinary comment, or a preprocessor directive. The diagnostic is still reported. When the reported comment is the first documentation comment of the declaration, the fix sorts it as RH8309-004 states and leaves the later comments as they are.

Why: The fix sorts the declaration's first documentation comment. Applied to a diagnostic in a later comment, it would sort the wrong one, or nothing, and leave the reported element where it was. Sorting a later comment instead would have to decide what becomes of the blank lines, comments, and directives that separate it from the comments before it, which the author placed. Two documentation comments on one declaration are rare, and joining or sorting them is the author's decision.

Example:

```csharp
class C
{
    /// <summary>
    /// Adds
    /// </summary>

    /// <remarks>Remarks</remarks>
    /// {|RH8309:<param name="a">First</param>|}
    int Add(int a)
    {
        return a;
    }
}
```

is reported, and no code fix is offered.

Example — the first comment is reported, and the fix sorts it:

```csharp
class C
{
    /// <remarks>Remarks</remarks>
    /// {|RH8309:<summary>
    /// Runs
    /// </summary>|}

    /// <param name="a">First</param>
    void Run(int a)
    {
    }
}
```

```csharp
class C
{
    /// <summary>
    /// Runs
    /// </summary>
    /// <remarks>Remarks</remarks>

    /// <param name="a">First</param>
    void Run(int a)
    {
    }
}
```
