# Analyzer — RH7101 Do not combine fields

| | |
|---|---|
| ID prefix | RH7101 |
| Status | Active |
| Category | Organization |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH7101DoNotCombineFieldsAnalyzer`, `RH7101DoNotCombineFieldsCodeFixProvider` |
| Uses | FMT-PIPE-005, FMT-PIPE-017, FMT-PIPE-029, FMT-PIPE-031, FMT-STRUCT-021, FMT-STRUCT-022, FMT-STRUCT-023, FMT-STRUCT-030, FMT-UNSUP-004, FMT-UNSUP-007, SHARED-DOC-004, SHARED-FIX-003, SHARED-FIX-006, SHARED-FIX-007, SHARED-FIX-010, SHARED-JOIN-002 |

RH7101 reports a field declaration that declares more than one field, and offers a code fix that splits it into one declaration per field.

## Non-goals

- Event field declarations and local variable declarations with several declarators.
- The order of the fields after the split — RH7102, RH7103, RH7109, RH7110.

## Requirements

### RH7101-001 — A field declaration with several declarators is reported

The analyzer MUST report a field declaration with more than one declarator in a class, struct, interface, record, or record struct, whatever its modifiers — `const`, `static`, `readonly`, and fixed-size buffers included — when no `#if`, `#elif`, `#else`, or `#endif` directive stands between its declarators, except in a file with a syntax error (SHARED-JOIN-002).

Why: Each field deserves its own line for its documentation, attributes, and diff history; a combined declaration also hides a second field behind the first one's type and modifiers. In a file with a syntax error the fix could not split the declaration, because the formatter leaves such a file untouched (FMT-PIPE-005); the diagnostic comes back with its fix once the error is gone.

Example:

```csharp
interface I
{
    static int A, {|RH7101:B|};
}

struct S
{
    public int X, {|RH7101:Y|};
}

record R
{
    public const int A = 1, {|RH7101:B|} = 2;
}

unsafe struct U
{
    public fixed int A[2], {|RH7101:B|}[3];
}
```

### RH7101-002 — Event fields and locals are not reported

The analyzer MUST NOT report an event field declaration or a local variable declaration with several declarators, nor a field declaration in an extension block.

Why: The rule is about the fields of a type. An event field declaration is not a field declaration, and locals are not part of a type's state. An extension block cannot declare a field — the compiler rejects one there (CS9282) — so the declaration is no state of any type, and the fix could not split it, because the formatter splits only the fields of a class, struct, record, or interface (FMT-STRUCT-021).

Example:

```csharp
using System;

class C
{
    public event Action E1, E2;

    void M()
    {
        int a, b;
    }
}
```

is not reported, and neither is

```csharp
static class E
{
    extension(int i)
    {
        private static int _x, _y;
    }
}
```

### RH7101-003 — One diagnostic per declaration, on the second declarator

The analyzer MUST report one diagnostic per field declaration, located on the identifier of its second declarator.

Why: The second declarator is the first field that should have a declaration of its own; one diagnostic per declaration matches the fix, which splits the whole declaration at once.

Example:

```csharp
class C
{
    private int _a, {|RH7101:_b|} = 1, _c;
}
```

### RH7101-004 — The fix splits the declaration

Unless RH7101-005, RH7101-006, or RH7101-007 withholds it, the code fix MUST split the reported field declaration into one declaration per declarator as specified in FMT-STRUCT-021, and MUST keep its comments as specified in FMT-STRUCT-022. It MUST lay out the fields it creates as `FormatNodeInDocumentWithContextAsync` lays them out with the reported declaration as target and the type that declares it as context (FMT-PIPE-029): the first field keeps the declaration's leading trivia, line, and column, and every other line of the fields is laid out as the formatter lays it out (SHARED-FIX-007). The fields share no line with another member: a member in front of the declaration on its line, or behind it, has the first field or itself start the next line, with one line break and no blank line; a comment between them stays behind the code in front of it, and a documentation comment goes with the member it documents. It MUST NOT split another field declaration, neither one of the same type nor one of a nested type (SHARED-FIX-006); each keeps its own diagnostic and fix.

Why: The fix makes exactly the change the formatter makes, so applying the fix and formatting the file give the same fields. Formatting the declaration in its type is the only way the formatter splits a field, and writing back only the fields it creates leaves the rest of the type as the author wrote it.

Example:

```csharp
using System;

class C
{
    [NonSerialized]
    private static readonly string _a = "a", {|RH7101:_b|} = "b";
}
```

```csharp
using System;

class C
{
    [NonSerialized]
    private static readonly string _a = "a";
    [NonSerialized]
    private static readonly string _b = "b";
}
```

A comment in front of the declaration stays on the first field, a comment inside an initializer value stays in that value, and a comment behind the `;` stays behind the last field:

```csharp
class C
{
    // The coordinates
    private int _x = Offset(/* horizontal */ 1), {|RH7101:_y|}; // vertical
}
```

```csharp
class C
{
    // The coordinates
    private int _x = Offset(/* horizontal */ 1);
    private int _y; // vertical
}
```

The fix of one declaration leaves another combined declaration of the type as it is; Fix All splits both:

```csharp
class C
{
    private int _a, {|RH7101:_b|};
    private int _c, {|RH7101:_d|};
}
```

```csharp
class C
{
    private int _a;
    private int _b;
    private int _c, _d;
}
```

A declaration between two members on its line, with a comment in the gap in front of it:

```csharp
class C
{
    private int _p; /* c */ private int _x, {|RH7101:_y|}; private int _q;
}
```

```csharp
class C
{
    private int _p; /* c */
    private int _x;
    private int _y;
    private int _q;
}
```

A declaration off its member column keeps the column of its first line, and the later field stands at the type's member column (FMT-PIPE-017):

```csharp
class C
{
      private int _x, {|RH7101:_y|};
}
```

```csharp
class C
{
      private int _x;
    private int _y;
}
```

### RH7101-005 — The fix is withheld for a declaration with a directive

The code fix MUST NOT be offered for a field declaration that the formatter does not split under FMT-STRUCT-023; it asks the formatter whether it splits the declaration (FMT-PIPE-031). When the declaration contains no `#if`, `#elif`, `#else`, or `#endif` directive, the diagnostic is still reported.

Why: The split cannot carry a directive or disabled text over to the generated fields, so a fix would drop the directive or move it to a different field. A reported diagnostic without a fix is a supported end state.

Example:

```csharp
class C
{
    #region Fields
    private int _a, {|RH7101:_b|};
    #endregion
}
```

is reported, and no code fix is offered.

### RH7101-006 — The fix is withheld for a documented declaration

When the documentation mode of the syntax tree is `Parse` or `Diagnose`, the code fix MUST NOT be offered for a field declaration that has a documentation comment (SHARED-DOC-004): a `///` or `/** */` comment in its leading trivia. The diagnostic is still reported. In the documentation mode `None`, a `///` or `/** */` comment in the declaration's leading trivia is an ordinary comment, and the fix splits the declaration as RH7101-004 states. A `///` or `/** */` comment anywhere else in the declaration, such as in front of a later declarator, is no documentation comment of the declaration: in every documentation mode, the formatter refuses it (FMT-UNSUP-004), and RH7101-007 withholds the fix.

Why: The documentation comment of a declaration with several declarators documents each of its fields, and a split would keep it on the first field only (FMT-STRUCT-022), so every other field would lose its documentation (SHARED-FIX-003). The formatter does not split such a declaration (FMT-STRUCT-030), and the fix asks it whether it splits the declaration (FMT-PIPE-031). Whether the comment fits each field or each field needs its own is the author's decision. When documentation comments are not parsed, the comment documents no field and nothing is lost.

Example:

```csharp
class C
{
    /// <summary>The coordinates</summary>
    public int X, {|RH7101:Y|};

    /** <summary>The sizes</summary> */
    public int Width, {|RH7101:Height|};
}
```

is reported, and no code fix is offered. In the documentation mode `None`, the fix splits both declarations:

```csharp
class C
{
    /// <summary>The coordinates</summary>
    public int X;
    public int Y;

    /** <summary>The sizes</summary> */
    public int Width;
    public int Height;
}
```

A documentation comment that starts behind the code of another member on the declaration's line is in the declaration's leading trivia and withholds the fix as well:

```csharp
class C
{
    private int _p; /** X. */ private int _x, {|RH7101:_y|};
}
```

is reported, and no code fix is offered.

An ordinary comment does not withhold the fix either:

```csharp
class C
{
    // The coordinates
    public int X, {|RH7101:Y|};
}
```

```csharp
class C
{
    // The coordinates
    public int X;
    public int Y;
}
```

### RH7101-007 — The fix is withheld for a comment inside the declaration

The code fix MUST NOT be offered for a field declaration with a comment that FMT-UNSUP-004 refuses — among its attributes or modifiers, in its type, at a declarator's name, at an `=` or in front of a value, at a `,` between declarators, or in front of its `;` — nor for one whose type holds such a comment elsewhere, also in a nested type: the fix formats the declaration in its type (RH7101-004), the formatter refuses that type, and the fix asks it before it is offered (FMT-UNSUP-007, SHARED-FIX-010). The diagnostic is still reported. A comment in the declaration's leading trivia does not withhold the fix (RH7101-004, RH7101-006), and neither does a comment inside an initializer value or behind the `;`.

Why: Every field the split creates repeats the attributes, modifiers, and type (FMT-STRUCT-021), so a comment among them would be copied next to fields it was not written next to, or kept next to one field while it described all of them (SHARED-FIX-003); a comment at a name, an `=`, or a `,` would have to be moved to one of the new fields. Where the comment belongs once the declaration is split is the author's decision. The formatter declares these comments unsupported, so the fix needs no guard of its own for them.

Example:

```csharp
using System;

class C
{
    private /* c */ int _a, {|RH7101:_b|};

    [Obsolete /* why */]
    private int _c, {|RH7101:_d|};

    private int /* c */ _first, {|RH7101:_second|};

    private int _g = /* c */ 1, {|RH7101:_h|};

    private int _x, // horizontal
                {|RH7101:_y|};
}
```

is reported, and no code fix is offered for any of the declarations.

Example — a comment that FMT-UNSUP-004 refuses elsewhere in the type withholds the fix as well:

```csharp
class C
{
    private int _a, {|RH7101:_b|};

    void M()
    {
        int /* c */ x = 1;
    }
}
```

is reported, and no code fix is offered.

Example — a comment inside an initializer value does not withhold the fix:

```csharp
class C
{
    private int _first = Offset(/* c */ 1), {|RH7101:_second|};
}
```

```csharp
class C
{
    private int _first = Offset(/* c */ 1);
    private int _second;
}
```
