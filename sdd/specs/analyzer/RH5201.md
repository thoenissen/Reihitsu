# Analyzer — RH5201 Member-access chains should be aligned

| | |
|---|---|
| ID prefix | RH5201 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5201MethodChainsShouldBeAlignedAnalyzer`, `RH5201MethodChainsShouldBeAlignedCodeFixProvider` |
| Uses | SHARED-CHAIN-002, SHARED-CHAIN-004, SHARED-CHAIN-005, SHARED-CHAIN-006, SHARED-CHAIN-007, SHARED-CHAIN-008, SHARED-CHAIN-009, SHARED-COMMENT-011, SHARED-COMMENT-012 |

RH5201 reports a link of a wrapped member-access chain that does not start its own line where it must, is not aligned to the chain's anchor, or has its operator split by a line break, and offers a code fix that lays the chain out the way the formatter does.

## Non-goals

- A first link that starts a line below the root — RH5112.
- Chains written on one line (SHARED-CHAIN-002).
- Comments between the links of a chain — RH5048 for the one in front of the first link.
- The column of an attached part (SHARED-CHAIN-001), or of the token behind the first token of a link operator, that starts a line: the formatter joins such a line break (FMT-BREAK-040, SHARED-CHAIN-006), and an input in which a comment, a directive, or disabled text keeps one on its own line is refused as unsupported (FMT-UNSUP-014, FMT-UNSUP-015).

## Requirements

### RH5201-001 — A later call that shares a line is reported

In a wrapped chain (SHARED-CHAIN-002), the analyzer MUST report every link after the first invoked link that does not start a line, as SHARED-CHAIN-005 requires. A link of the prefix in front of the first invoked link, and every link of a chain without an invoked link, MUST NOT be reported for not starting a line, except the first invoked link as RH5201-006 states and a link behind the closing `*/` of a comment as RH5201-002 states. A line that starts with a comment is judged as SHARED-COMMENT-011 specifies.

Why: Once a chain is wrapped, one step per line keeps it scannable; a property prefix is not a step and may stay together (SHARED-CHAIN-005).

Example:

```csharp
using System.Linq;

class C
{
    C Next { get; set; }
    C Self() => this;

    void M(int[] items, C c)
    {
        var a = items.Where(x => x > 0)
                     .Select(x => x){|RH5201:.|}ToList();
        var b = c.Next
                 .Next.Next;
        var d = c.Next.Next
                      .Self();
    }
}
```

### RH5201-002 — A misaligned wrapped link is reported

In a wrapped chain, the analyzer MUST report every link that starts a line whose first character that is not whitespace is not in the column of the chain's anchor, as SHARED-CHAIN-007 defines it; when a comment or a directive keeps the first link on its own line (SHARED-CHAIN-004), the anchor is the start of the root. A block comment in front of a link on the link's line MUST be aligned together with the link. A line that starts with a comment is judged as SHARED-COMMENT-011 specifies. The first link MUST NOT be reported for its column when nothing keeps it on its own line.

A link other than the chain's first link whose operator stands on the last line of a delimited comment that spans several lines and stands below the token in front of the link — a line break stands between that token and the comment, also when other comments stand in front of the comment on its first line (`/* w */ /* x` ⏎ `*/ .Self()`) — behind the comment's closing `*/` MUST be reported whatever column the comment's last line starts in, also when it is a prefix link or a link of a chain without an invoked link, and whether only whitespace or also other comments stand between the closing `*/` and the operator (`*/ .Self()`, `*/ /* y */ .Self()`): the link does not start its line (SHARED-COMMENT-012), and SHARED-CHAIN-005 requires it to start its own line. The chain's first link behind such a comment MUST NOT be reported by this paragraph, whatever column the comment's last line starts in: SHARED-CHAIN-005 does not decide the chain's first link, SHARED-CHAIN-004 keeps it in place behind the comment, and a first link that starts a line below the root is RH5112's. The comment then keeps the first link on its own line, so the anchor is the start of the root and the first call is reported as RH5201-006 states (`var a = c` ⏎ `/* x` ⏎ `*/ .Next.Self();` with the comment in the root's column: `.Self` is reported, `.Next` is not). A link behind the closing `*/` of a comment that starts behind code on the line of the token in front of it is judged as a link behind code on its line (SHARED-COMMENT-012, SHARED-CHAIN-007).

Why: Aligned operators make the chain read as a column of steps under the one they continue (SHARED-CHAIN-007). A comment that starts the link's line is part of that line, so the line, not the operator, is what aligns. A first link that starts a line is RH5112's concern, and the links after it align to it. A comment's last line is not a line of its own (SHARED-COMMENT-012), so a link behind it stays misplaced even when the `*/` happens to stand in the anchor column; a comment between the `*/` and the link, or in front of the comment on its first line, does not give the link a line of its own either. The chain's first link is the exception because no rule requires it to start a line; the comment only keeps it where it stands (SHARED-CHAIN-004).

Example:

```csharp
using System.Linq;

class C
{
    void M(int[] items)
    {
        var a = items.Where(x => x > 0)
            {|RH5201:.|}Select(x => x);
        var b = items // root
            {|RH5201:.|}Where(x => x > 0);
        var c = items.Where(x => x > 0)
                     /* all */ .ToList();
        var d = items
            .Where(x => x > 0)
            .ToList();
    }
}
```

Example — a wrapped link behind a prefix of property reads aligns to the last link in front of it, in a chain with a later call and in a chain without one (SHARED-CHAIN-007):

```csharp
class C
{
    C Next { get; set; }
    C Self() => this;

    void M(C c)
    {
        var a = c.Next.Next
                 {|RH5201:.|}Self();
        var b = c.Next.Next
                      .Self();
        var d = c.Next.Next
                 {|RH5201:.|}Next;
        var e = c.Next.Next
                      .Next;
        var f = c.Next
                 .Next.Next
                 .Self();
    }
}
```

Example — the links behind the closing `*/` in `a`, `b`, `d`, `f`, and `g` are reported although the comment's last line starts in the anchor column: a later call in `a`, a link of a chain without a call in `b`, the prefix link `.Next` in `d`, whose first call `.Self` is reported as well (RH5201-006), in `f` a later call with a second comment between the `*/` and the link, and in `g` a later call behind a comment that starts behind another comment on its first line; in `e`, the comment starts behind code, so `.Next` behind its `*/` does not start a line, is the anchor, and `.Self` aligned under it is not reported:

```csharp
class C
{
    C Next { get; set; }
    C Self() => this;

    void M(C c)
    {
        var a = c.Self()
                 .Self()

                 /* x
                 */ {|RH5201:.|}Self();
        var b = c.Next
                 .Next

                 /* x
                 */ {|RH5201:.|}Next;
        var d = c.Next

                 /* x
                 */ {|RH5201:.|}Next{|RH5201:.|}Self();
        var e = c.Next /* x
            */.Next
              .Self();
        var f = c.Self()
                 .Self()

                 /* x
                 */ /* y */ {|RH5201:.|}Self();
        var g = c.Self()
                 .Self()

                 /* w */ /* x
                 */ {|RH5201:.|}Self();
    }
}
```

The code fix lays out the chain (RH5201-005); `a`, `b`, `d`, `f`, and `g` become:

```csharp
        var a = c.Self()
                 .Self()

                 /* x
                 */
                 .Self();
        var b = c.Next
                 .Next

                 /* x
                 */
                 .Next;
        var d = c.Next

                 /* x
                 */
                 .Next
                 .Self();
        var f = c.Self()
                 .Self()

                 /* x
                 */ /* y */
                 .Self();
        var g = c.Self()
                 .Self()

                 /* w */ /* x
                 */
                 .Self();
```

### RH5201-003 — A split link operator is reported

The analyzer MUST report a link whose operator holds a line break between its own tokens (SHARED-CHAIN-006). A line break that a comment, a preprocessor directive, or disabled text keeps between the operator's tokens MUST NOT count as splitting it; such a link is checked by RH5201-001 and RH5201-002 by the line its first token is on.

Why: `?.` and `!.` read as one operator; a `?` or `!` at the end of a line reads as a conditional or a negation. A line break that a comment holds cannot be removed without moving the comment, but the operator can still start its own line in front of the comment.

Example:

```csharp
#nullable enable
using System.Linq;

class C
{
    C? Next { get; set; }

    void M(int[]? items, C d)
    {
        var a = items?.Where(x => x > 0){|RH5201:?|}
                     .ToList();
        var b = d{|RH5201:!|}
            .ToString();
        var e = d.Next{|RH5201:?|}
                 .Next;
        var f = d.Next? // why
                 .Next;
        var g = items?.Where(x => x > 0){|RH5201:?|} // why
                     .ToList();
    }
}
```

The `?` in front of `// why` in `f` is not reported: the comment keeps the line break, and a link of a chain without a call need not start a line. The `?` in front of `// why` in `g` is reported because, as a later link of a chain with a call, it does not start a line (RH5201-001).

### RH5201-004 — The diagnostic is on the link's operator

The analyzer MUST report one diagnostic per misplaced link, located on the first token of its operator: the `.`, the `?` of `?.`, or the `!` of `!.` and `!?.`. A link that is misplaced in more than one way is reported once.

Why: The operator's first token is where the line break goes and what is aligned; one diagnostic per link keeps the count of diagnostics equal to the number of links that move.

Example: see RH5201-001 to RH5201-003.

### RH5201-005 — The fix lays out the chain

The code fix MUST lay out the chain as SHARED-CHAIN-008 and SHARED-CHAIN-009 specify.

Why: The links of a chain align to one anchor, so moving one link can move the others; the formatted layout of the whole chain clears every diagnostic of the chain at once.

Example:

```csharp
using System.Linq;

class C
{
    void M(int[] items)
    {
        var a = items.Where(x => x > 0)
        {|RH5201:.|}Select(x => x){|RH5201:.|}ToList();
    }
}
```

```csharp
using System.Linq;

class C
{
    void M(int[] items)
    {
        var a = items.Where(x => x > 0)
                     .Select(x => x)
                     .ToList();
    }
}
```

### RH5201-006 — A first call the root's line does not reach is reported

In a wrapped chain, the analyzer MUST report the first invoked link when it does not start a line and SHARED-CHAIN-005 requires it to start its own line because the line the root ends on does not reach it: a line break stands in front of the operator of a link between the chain's first link and the first invoked link, or between that operator's own tokens when no comment, preprocessor directive, or disabled text keeps it there, or a comment, a directive, or disabled text keeps the chain's first link on its own line (SHARED-CHAIN-004). A line break in front of the chain's first link without such trivia, a line break between the first link's own operator tokens, and a line break that a comment, a preprocessor directive, or disabled text keeps between a prefix link's operator tokens MUST NOT make the first invoked link reported; the last is counted as RH5201-003 counts it, as if it were not there. A first invoked link that starts a line is judged by RH5201-002 and RH5201-003 alone.

Why: The formatter starts such a first call on its own line (SHARED-CHAIN-005); a rule that did not report it would leave a layout the formatter changes without a diagnostic. A line break in front of the first link that nothing holds is RH5112's to report, and once it is joined, the root's line reaches the first call again.

Example — `.Select` behind the wrapped prefix link `.Items` in `a`, `.Self` behind the comment that holds the first link below the root in `b` and behind the wrapped prefix link `.Next` in `d` are reported; in `e`, the line break in front of the first link holds no comment, so `.Self` is not reported here (RH5112 reports `.Next`); in `f`, the first call starts its own line; in `h`, the chain has no call:

```csharp
using System.Linq;

class C
{
    C Next { get; set; }
    int[] Items { get; set; }
    C Self() => this;

    void M(C c)
    {
        var a = c.Next
                 .Items{|RH5201:.|}Select(x => x);
        var b = c // keep
                .Next{|RH5201:.|}Self();
        var d = c.Next // keep
                 .Next{|RH5201:.|}Self();
        var e = c
                 .Next.Self();
        var f = c.Next
                 .Next
                 .Self();
        var h = c.Next
                 .Next.Next;
    }
}
```

Example — a line break inside the operator of the prefix link `?.Next` in `a` and a directive in front of the first link in `b` leave the root's line short of the first call; the split operator in `a` is reported as well (RH5201-003):

```csharp
#nullable enable

class C
{
    C Next { get; set; }
    C? Opt { get; set; }
    C Self() => this;

    void M(C c)
    {
        var a = c.Opt{|RH5201:?|}
                 .Next{|RH5201:.|}Self();
        var b = c
#if X
                .Next.Self();
#else
                .Next{|RH5201:.|}Self();
#endif
    }
}
```

The code fix lays out the chain (RH5201-005); for the first example, `a` becomes:

```csharp
        var a = c.Next
                 .Items
                 .Select(x => x);
```

and for the second example:

```csharp
        var a = c.Opt
                 ?.Next
                 .Self();
        var b = c
#if X
                .Next.Self();
#else
                .Next
                .Self();
#endif
```

Example — the comment keeps the line break inside the operator of the prefix link `?.Next`, which does not count (RH5201-003), so the root's line reaches `.Self`:

```csharp
#nullable enable

class C
{
    C Next { get; set; }
    C? Opt { get; set; }
    C Self() => this;

    void M(C c)
    {
        var g = c.Opt? // keep
                 .Next.Self();
    }
}
```

is not reported.
