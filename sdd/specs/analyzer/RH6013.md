# Analyzer — RH6013 Opening attribute brackets must be spaced correctly

| | |
|---|---|
| ID prefix | RH6013 |
| Status | Active |
| Category | Spacing |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH6013OpeningAttributeBracketsMustBeSpacedCorrectlyAnalyzer`, `RH6013OpeningAttributeBracketsMustBeSpacedCorrectlyCodeFixProvider` |
| Uses | FMT-CLEAN-001, FMT-SPACE-004, SHARED-WS-001, SHARED-WS-002 |

RH6013 reports whitespace directly after the opening bracket of an attribute list, and offers a code fix that deletes it as SHARED-WS-001 and SHARED-WS-002 specify.

In the examples, `→` marks a tab and `·` a space at the end of a line.

## Non-goals

- Opening square brackets that do not open an attribute list — RH6007.
- The whitespace before the closing bracket of an attribute list — RH6014.
- The whitespace after the closing bracket of an attribute list — the formatter (FMT-SPACE-003); no analyzer rule checks it.

## Requirements

### RH6013-001 — Whitespace after an opening attribute bracket is reported

The analyzer MUST report the run of spaces and tabs directly after the opening bracket of an attribute list — on a type, a member, a parameter, a lambda, or with an attribute target such as `return:` or `assembly:` — when the run is followed by a token or by the end of the line. An opening attribute bracket directly followed by a token or by a line break MUST NOT be reported.

Why: The bracket belongs to the attributes it opens; a space after it makes the attribute read less like one compact annotation. The formatter removes the same whitespace — before a token on the same line (FMT-SPACE-004), at the end of the line (FMT-CLEAN-001) — so formatted code raises no RH6013 in these places.

Example:

```csharp
using System;
using System.Runtime.InteropServices;

[{|RH6013: |}assembly: CLSCompliant(true)]

[{|RH6013: |}Obsolete]
class C
{
    [{|RH6013:→|}Obsolete]
    [{|RH6013: |}return: MarshalAs(UnmanagedType.I4)]
    int M([{|RH6013: |}In] int a)
    {
        Func<int> f = [{|RH6013: |}Obsolete] () => 1;

        return a;
    }

    [{|RH6013:··|}
        Obsolete]
    void N()
    {
    }

    [
        Obsolete]
    void O()
    {
    }
}
```

### RH6013-002 — One diagnostic per bracket

The analyzer MUST report one diagnostic per opening attribute bracket, located on the whitespace run after it.

Why: The run is the text that is wrong and the text the fix deletes.

Example: see RH6013-001.

### RH6013-003 — The fix deletes the whitespace unless a comment is in the gap

The code fix MUST delete the reported whitespace as SHARED-WS-001 specifies, and MUST NOT be offered when a comment or directive sits between the bracket and the next token, as SHARED-WS-002 specifies.

Why: A comment in the gap is the author's placement; the fix does not decide whether the deletion affects it.

Example:

```csharp
using System;

[{|RH6013: |}Obsolete]
class C
{
    [{|RH6013:→|}Obsolete]
    void M()
    {
    }

    [{|RH6013:··|}
        Obsolete]
    void N()
    {
    }
}
```

```csharp
using System;

[Obsolete]
class C
{
    [Obsolete]
    void M()
    {
    }

    [
        Obsolete]
    void N()
    {
    }
}
```

A comment on the next line of the gap withholds the fix:

```csharp
using System;

class C
{
    [{|RH6013:··|}
        // why
        Obsolete]
    void M()
    {
    }
}
```

is reported, and no code fix is offered.
