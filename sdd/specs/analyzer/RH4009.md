# Analyzer — RH4009 Namespace not allowed

| | |
|---|---|
| ID prefix | RH4009 |
| Status | Active |
| Category | Naming |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | None |
| Code owners | `RH4009NamespaceNotAllowedAnalyzer` |
| Uses | RH0001-003, SHARED-DIAG-002 |

RH4009 reports a namespace declaration whose name is not on the allow-list `naming.allowedNamespaceDeclarations` of the `reihitsu.json` configuration file.

## Non-goals

- Validating the configuration file and the shape of the `naming` section — RH0001 (RH0001-005).
- The casing of namespace names — RH4007 and RH4008.
- Whether a namespace matches the folder of its file.

## Requirements

### RH4009-001 — The rule is active only with a non-empty allow-list

The analyzer MUST NOT report anything when the project has no `reihitsu.json`, when the file is empty, holds only white space, or is not valid JSON (RH0001-003), including a file with content after its root value, or when `naming.allowedNamespaceDeclarations` is missing or has no entry that is a string. Entries that are not strings MUST be ignored; the strings of the list stay in effect.

Why: Which namespaces a project may declare is the project's own decision; without a list there is nothing to check against.

Example:

```csharp
namespace Company.Product
{
}
```

is not reported without a configuration file, with `{ "naming": { } }`, with `{ "naming": { "allowedNamespaceDeclarations": [] } }`, with `{ "naming": { "allowedNamespaceDeclarations": [ 1 ] } }`, with a file whose JSON is malformed inside its root object, such as `{ "naming": { "allowedNamespaceDeclarations": [ "A" ] `, and with a file that holds more than JSON white space after its root object, such as `{ "naming": { "allowedNamespaceDeclarations": [ "A" ] } } junk`. With `{ "naming": { "allowedNamespaceDeclarations": [ "A", 1 ] } }`, the same declaration is reported, because `"A"` stays in effect.

### RH4009-002 — A namespace that is not on the list is reported

The analyzer MUST report a block-scoped or file-scoped namespace declaration of a file, declared at file level, when the value of its name (SHARED-DIAG-002), with every Unicode escape sequence replaced by the character it stands for, is not exactly one of the entries of the list. The comparison MUST be case-sensitive, and an entry MUST NOT allow its child namespaces. The diagnostic MUST be located on the whole namespace name.

Why: The list pins the namespaces of the project, so a namespace that is not on it usually comes from a file in the wrong place or copied from elsewhere. Each namespace that is allowed is listed on its own, so a child namespace is a decision of its own.

Example — with `{ "naming": { "allowedNamespaceDeclarations": [ "MyCompany.Project" ] } }`:

```csharp
namespace MyCompany.Project
{
}

namespace {|RH4009:MyCompany.Project.Data|}
{
}

namespace {|RH4009:mycompany.project|}
{
}
```

In another file of the same project,

```csharp
namespace {|RH4009:MyCompany.Internal|};
```

is reported as well.

Example — the verbatim prefix and whitespace or comments inside the name do not change it, so with the same list:

```csharp
namespace @MyCompany.Project
{
}

namespace MyCompany . Project
{
}

namespace MyCompany./* x */Project
{
}

namespace {|RH4009:@MyCompany . Data|}
{
}
```

reports only the last declaration, on its whole name. A Unicode escape is replaced too: with `{ "naming": { "allowedNamespaceDeclarations": [ "A.B" ] } }`, `namespace \u0041.B { }` is not reported. An entry is compared as it is written, so with `{ "naming": { "allowedNamespaceDeclarations": [ "@MyCompany.Project" ] } }`, both `namespace MyCompany.Project { }` and `namespace @MyCompany.Project { }` are reported.

### RH4009-003 — A nested namespace is compared by its full name

The analyzer MUST report a block-scoped namespace declaration inside the body of another block-scoped namespace declaration when its full name is not exactly one of the entries of the list. The full name is the value of the name of every enclosing namespace declaration, outermost first, followed by the value of its own name, joined by `.`; each value is taken as RH4009-002 takes it (SHARED-DIAG-002, Unicode escape sequences replaced), and the comparison is the one of RH4009-002. The diagnostic MUST be located on the whole name of the nested declaration itself, not on the names of the enclosing declarations. Each enclosing declaration is compared on its own: the outermost by RH4009-002, every other by this requirement.

Why: A nested declaration declares its full namespace — `namespace A { namespace B { } }` declares `A.B`, as `namespace A.B { }` does — so the list, which pins the declared namespaces, is checked against that full name. The nested declaration adds only its own name, so that is where a disallowed namespace is shown.

Example — with `{ "naming": { "allowedNamespaceDeclarations": [ "A", "A.B" ] } }`:

```csharp
namespace A
{
    namespace B
    {
    }
}
```

is not reported. With `{ "naming": { "allowedNamespaceDeclarations": [ "A", "B" ] } }`:

```csharp
namespace A
{
    namespace {|RH4009:B|}
    {
    }
}
```

is reported, while a file-level `namespace B { }` is not, because it is not nested. A nested name with dots and several levels of nesting are joined the same way, so with `{ "naming": { "allowedNamespaceDeclarations": [ "A", "A.B.C", "A.B.C.D" ] } }`:

```csharp
namespace A
{
    namespace B.C
    {
        namespace D
        {
        }

        namespace {|RH4009:E|}
        {
        }
    }
}
```

reports only `E`, whose full name is `A.B.C.E`. Each enclosing declaration is checked on its own, so with `{ "naming": { "allowedNamespaceDeclarations": [ "A.B" ] } }`:

```csharp
namespace {|RH4009:A|}
{
    namespace B
    {
    }
}
```

reports `A` and not `B`.
