# Analyzer — RH8305 Summary element must span at least three lines

| | |
|---|---|
| ID prefix | RH8305 |
| Status | Active |
| Category | Documentation |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH8305SummaryElementMustSpanAtLeastThreeLinesAnalyzer`, `RH8305SummaryElementMustSpanAtLeastThreeLinesCodeFixProvider` |
| Uses | FMT-DOC-001, FMT-DOC-003, FMT-DOC-008, FMT-DOC-011, FMT-DOC-013, FMT-PIPE-032, SHARED-DIAG-006, SHARED-DIAG-010, SHARED-DOC-004, SHARED-DOC-008, SHARED-FIX-006 |

RH8305 reports a `<summary>` element of a `///` documentation comment whose end tag starts less than two lines below its start tag, and offers a code fix that puts the start tag, the content, and the end tag on lines of their own.

## Non-goals

- Whether the summary has text — RH8030 and RH8031.
- The layout of elements other than `<summary>` — RH8307.

## Requirements

### RH8305-001 — A summary on fewer than three lines is reported

The analyzer MUST report a `<summary>` element at the top level of a `///` documentation comment whose end tag starts on the line of its start tag or on the next line. Every `///` documentation comment of the declaration is checked, a later one as well as the first, and every `<summary>` element at the top level of a comment is checked, whatever its position among the others (SHARED-DIAG-006). Nothing is reported when SHARED-DOC-008 applies.

This requirement covers a `///` documentation comment of a declaration, as SHARED-DOC-004 defines it, whose `<summary>` elements at its top level are each closed by their own end tag `</summary>`, with the tag name `summary` written in lower case, without a namespace prefix, and in no XML namespace. A `///` comment that is not a documentation comment of a declaration, such as one inside a method body, is not covered.

Why: A summary on its own lines reads the same however short it is, and it grows by adding lines instead of rewrapping the tags. Keeping every summary in that shape makes the documentation of all elements look alike.

Example:

```csharp
class C
{
    /// {|RH8305:<summary>Runs</summary>|}
    void M()
    {
    }

    /// {|RH8305:<summary>Stops
    /// </summary>|}
    void N()
    {
    }

    /// {|RH8305:<summary>
    /// Value</summary>|}
    int A;

    /// <remarks>Remarks</remarks>

    /// {|RH8305:<summary>Count</summary>|}
    int B;

    /// <summary>
    /// First
    /// </summary>
    /// {|RH8305:<summary>Second</summary>|}
    int D;
}
```

### RH8305-002 — Other summaries are not reported

The analyzer MUST NOT report a summary that already spans at least three lines, an empty element `<summary/>`, a `<summary>` nested inside another element, or a summary in a `/** */` documentation comment. It MUST NOT report a summary in a `///` comment that the formatter leaves as written — one that holds an element without an end tag of its own (FMT-DOC-013), or one that FMT-DOC-003 keeps behind code, as SHARED-DIAG-010 requires.

Why: A summary on three lines has the required shape, whatever line its content starts on; that layout is RH8307's concern. An empty element has no content to put on a line of its own, a nested `<summary>` is not the element's summary, and a delimited comment has no `///` lines to lay out. The formatter keeps the comment as written, so the fix would change nothing and the diagnostic would stay for good.

Example:

```csharp
class C
{
    /// <summary>
    /// Runs
    /// </summary>
    void M()
    {
    }

    /// <summary/>
    void N()
    {
    }

    /// <summary>Stops
    /// now
    /// </summary>
    void O()
    {
    }

    /// <remarks><summary>Nested</summary></remarks>
    /// <summary>
    /// Value
    /// </summary>
    int A;

    /** <summary>Count</summary> */
    int B;
}
```

is not reported, and neither is

```csharp
class C
{
    /// <summary>S
    int A;

    /// <summary>S</returns>
    int B;

    /// <summary>Gets the value.</summary>
    /// <remarks>Text
    /// more
    int D;

    int E; /// <summary>end</summary>
}
```

### RH8305-003 — The diagnostic covers the summary

The analyzer MUST report one diagnostic per reported summary, covering the whole element from its start tag through its end tag. A summary in the documentation comment of a record, class, or struct with a primary constructor is reported once, like any other.

Why: The whole element is what the fix lays out again. The comment of a type with a primary constructor documents the type and its constructor at once, but it is one summary in the source, and two diagnostics on the same span would make the user correct it twice.

Example: see RH8305-001, and

```csharp
/// {|RH8305:<summary>Point</summary>|}
public record R(int A);
```

which is reported once.

### RH8305-004 — The fix lays the summary out on three lines

The code fix MUST lay out the reported summary as FMT-DOC-008 specifies, keeping its content as FMT-DOC-011 specifies: the start tag, each line of the content, and the end tag each start a `///` line of their own. The summary's new text MUST be the text the formatter gives that element when it lays out one documentation element (FMT-PIPE-032), the columns of its lines included.

The fix MUST change only the reported summary (SHARED-FIX-006): the other lines and elements of the comment, the other documentation comments of the declaration and the blank lines between them, and the declaration's own code MUST stay as they are written, also where the formatter would lay them out differently, and wherever the declaration stands — in a namespace, in a type, or directly in the compilation unit.

This requirement covers a summary closed by its own end tag `</summary>` with content that is not only white space, in a `///` comment that starts its own line, in a document without syntax errors. RH8305-005 states that the fix is withheld for a comment that starts behind code.

Why: The fix and the formatter produce the same summary, so a summary the fix has corrected stays as it is when the file is formatted. The rest of the declaration is not what the diagnostic is about; laying it out on the way would hide the correction in changes nobody asked for.

Example:

```csharp
class C
{
    /// {|RH8305:<summary>Runs <see cref="C"/></summary>|}
    void M()
    {
    }

    /// {|RH8305:<summary>Stops
    /// now</summary>|}
    void N()
    {
    }
}
```

```csharp
class C
{
    /// <summary>
    /// Runs <see cref="C"/>
    /// </summary>
    void M()
    {
    }

    /// <summary>
    /// Stops
    /// now
    /// </summary>
    void N()
    {
    }
}
```

Example — the rest of the declaration stays as written, for a type directly in the compilation unit:

```csharp
/// {|RH8305:<summary>Runs</summary>|}
///Text
public class C { int A(int a) => a; }
```

```csharp
/// <summary>
/// Runs
/// </summary>
///Text
public class C { int A(int a) => a; }
```

Example — the other documentation comments and the blank line between them stay:

```csharp
class C
{
    /// <remarks>Remarks</remarks>

    /// {|RH8305:<summary>Count</summary>|}
    int B;
}
```

```csharp
class C
{
    /// <remarks>Remarks</remarks>

    /// <summary>
    /// Count
    /// </summary>
    int B;
}
```

### RH8305-005 — The fix is withheld for a comment written behind code

The code fix MUST NOT be offered when the documentation comment of the reported summary starts behind code on its line: its first `///` follows a token on the same line, as SHARED-DOC-004 describes. The diagnostic is still reported. A comment whose first `///` has nothing but white space in front of it on its line gets the fix as RH8305-004 states.

Why: SHARED-DOC-004 requires a fix that moves neither the declaration nor the code in front of the comment to leave the comment behind that code. Laying the summary out there would put `///` lines behind code, a layout that nothing else produces and the formatter replaces by moving the comment onto a line of its own (FMT-DOC-001), so the fix could only give a shape the formatter changes again. Documentation written behind code is rare, and where it belongs is the author's decision.

Example:

```csharp
class C
{
    int A; /// {|RH8305:<summary>Value</summary>|}
    int B;
}
```

is reported, and no code fix is offered.
