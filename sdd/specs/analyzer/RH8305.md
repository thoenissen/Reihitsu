# Analyzer — RH8305 Summary element must span at least three lines

| | |
|---|---|
| ID prefix | RH8305 |
| Status | Active |
| Category | Documentation |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH8305SummaryElementMustSpanAtLeastThreeLinesAnalyzer`, `RH8305SummaryElementMustSpanAtLeastThreeLinesCodeFixProvider` |
| Uses | FMT-DOC-008, FMT-DOC-011, SHARED-DOC-004, SHARED-DOC-008, SHARED-DOC-017 |

RH8305 reports a `<summary>` element of a `///` documentation comment whose end tag starts less than two lines below its start tag, and offers a code fix that puts the start tag, the content, and the end tag on lines of their own.

## Non-goals

- Whether the summary has text — RH8030 and RH8031.
- The layout of elements other than `<summary>` — RH8307.

## Requirements

### RH8305-001 — A summary on fewer than three lines is reported

The analyzer MUST report a `<summary>` element at the top level of a `///` documentation comment whose end tag starts on the line of its start tag or on the next line. Every `///` documentation comment of the declaration is checked, a later one as well as the first. Nothing is reported when SHARED-DOC-008 applies.

This requirement covers a `///` documentation comment of a declaration, as SHARED-DOC-004 defines it, with at most one `<summary>` element at its top level, closed by its own end tag `</summary>`, with the tag name `summary` written in lower case, without a namespace prefix, and in no XML namespace. A `///` comment that is not a documentation comment of a declaration, such as one inside a method body, is not covered.

Why: A summary on its own lines reads the same however short it is, and it grows by adding lines instead of rewrapping the tags. Keeping every summary in that shape makes the documentation of all elements look alike.

Example:

```csharp
class C
{
    /// {|RH8305:<summary>Runs</summary>|}
    void M()
    {
    }

    /// {|RH8305:<summary>Stops
    /// </summary>|}
    void N()
    {
    }

    /// {|RH8305:<summary>
    /// Value</summary>|}
    int A;

    /// <remarks>Remarks</remarks>

    /// {|RH8305:<summary>Count</summary>|}
    int B;
}
```

### RH8305-002 — Other summaries are not reported

The analyzer MUST NOT report a summary that already spans at least three lines, an empty element `<summary/>`, a `<summary>` nested inside another element, or a summary in a `/** */` documentation comment.

Why: A summary on three lines has the required shape, whatever line its content starts on; that layout is RH8307's concern. An empty element has no content to put on a line of its own, a nested `<summary>` is not the element's summary, and a delimited comment has no `///` lines to lay out.

Example:

```csharp
class C
{
    /// <summary>
    /// Runs
    /// </summary>
    void M()
    {
    }

    /// <summary/>
    void N()
    {
    }

    /// <summary>Stops
    /// now
    /// </summary>
    void O()
    {
    }

    /// <remarks><summary>Nested</summary></remarks>
    /// <summary>
    /// Value
    /// </summary>
    int A;

    /** <summary>Count</summary> */
    int B;
}
```

is not reported.

### RH8305-003 — The diagnostic covers the summary

The analyzer MUST report one diagnostic per reported summary, covering the whole element from its start tag through its end tag.

Why: The whole element is what the fix lays out again.

Example: see RH8305-001.

### RH8305-004 — The fix lays the summary out on three lines

The code fix MUST lay out the reported summary as FMT-DOC-008 specifies, keeping its content as FMT-DOC-011 specifies: the start tag, each line of the content, and the end tag each start a `///` line of their own.

This requirement covers a summary closed by its own end tag `</summary>` with content that is not only white space, in a `///` comment that starts its own line, in a document without syntax errors, in a declaration whose code outside the reported summary is already laid out as the formatter lays it out. A reported summary that has no end tag of its own gets no code fix (SHARED-DOC-017).

Why: The fix and the formatter produce the same summary, so a summary the fix has corrected stays as it is when the file is formatted.

Example:

```csharp
class C
{
    /// {|RH8305:<summary>Runs <see cref="C"/></summary>|}
    void M()
    {
    }

    /// {|RH8305:<summary>Stops
    /// now</summary>|}
    void N()
    {
    }
}
```

```csharp
class C
{
    /// <summary>
    /// Runs <see cref="C"/>
    /// </summary>
    void M()
    {
    }

    /// <summary>
    /// Stops
    /// now
    /// </summary>
    void N()
    {
    }
}
```
