# Analyzer — RH8202 Value tag must not be used

| | |
|---|---|
| ID prefix | RH8202 |
| Status | Active |
| Category | Documentation |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH8202ValueTagMustNotBeUsedAnalyzer`, `RH8202ValueTagMustNotBeUsedCodeFixProvider` |
| Uses | SHARED-DOC-004, SHARED-DOC-008, SHARED-DOC-017, SHARED-DOC-018 |

RH8202 reports a `<value>` element in the documentation of a property or indexer, and offers a code fix that removes the element.

## Non-goals

- Whether the property or indexer has a summary, and whether the summary has text — RH8022 to RH8025 and RH8030.
- The content, order, and layout of the remaining documentation — RH8301 to RH8309.

## Requirements

### RH8202-001 — A `<value>` element on a property or indexer is reported

The analyzer MUST report a `<value>` element in the documentation comment, as SHARED-DOC-004 defines it, of a property or indexer declaration, whether the element is at the top level of the comment or nested inside another element. A `<value>` element that lies inside a `<code>` or an `<example>` element MUST NOT be reported, and MUST NOT keep a `<value>` element outside them from being reported. The declaration's accessibility does not matter, and nothing is reported when SHARED-DOC-008 applies.

This requirement covers a property or indexer declaration that does not explicitly implement an interface member, whose leading trivia has one documentation comment with at most one `<value>` element outside `<code>` and `<example>` elements, placed as SHARED-DOC-004 covers and well-formed XML apart from a reported element that has no end tag at all — neither its own `</value>` nor the end tag of an element that contains it — with the tag names `value`, `code`, and `example` written in lower case, without a namespace prefix, and in no XML namespace. The documentation of other declarations is not covered.

Why: A `<value>` element repeats what the summary of a property already says, so the same information is kept in two places that drift apart, and properties end up documented in two different ways. A `<value>` element nested in `<remarks>` repeats it just the same; inside a code sample, it is sample text, such as the documentation of another member shown as an example.

Example:

```csharp
/// <summary>
/// Service
/// </summary>
public class C
{
    /// <summary>
    /// Gets the size
    /// </summary>
    /// {|RH8202:<value>The size</value>|}
    public int Size { get; }

    /// <summary>
    /// Gets the item
    /// </summary>
    /// <remarks>{|RH8202:<value>The item</value>|}</remarks>
    private int this[int index] => 0;

    /// <summary>
    /// Gets the name
    /// </summary>
    /// <example><code><value>Sample</value></code></example>
    public string Name => "";

    /// <summary>
    /// Gets the weight
    /// </summary>
    /// <example><code><value>Sample</value></code></example>
    /// <remarks>{|RH8202:<value>Nested</value>|}</remarks>
    public int Weight { get; }
}
```

### RH8202-002 — The diagnostic is on the element

The analyzer MUST report one diagnostic per declaration, located on the reported `<value>` element: from its start tag through its end tag, or to the end of its content when the end tag is missing.

Why: The element is exactly what the fix removes, so the squiggle shows the text that will disappear.

Example: see RH8202-001.

### RH8202-003 — The fix removes the element

The code fix MUST remove the reported `<value>` element as SHARED-DOC-018 specifies: with the lines it owns when it occupies them alone, and otherwise with only the horizontal white space that separates it from the content it shares a line with. A nested element is removed from the element that contains it, which stays.

Why: The summary already says what the `<value>` element said; anything else worth keeping has to be moved into the summary by hand before the fix runs. Content that shares a line with the element belongs to the rest of the documentation and stays.

Example:

```csharp
/// <summary>
/// Service
/// </summary>
public class C
{
    /// <summary>
    /// Gets the size
    /// </summary>
    /// {|RH8202:<value>
    /// The size
    /// </value>|}
    public int Size { get; }

    /// <summary>Gets the count</summary> {|RH8202:<value>The count</value>|}
    public int Count { get; }

    /// <summary>
    /// Gets the item
    /// </summary>
    /// <remarks>{|RH8202:<value>The item</value>|}</remarks>
    public int this[int index] => 0;
}
```

```csharp
/// <summary>
/// Service
/// </summary>
public class C
{
    /// <summary>
    /// Gets the size
    /// </summary>
    public int Size { get; }

    /// <summary>Gets the count</summary>
    public int Count { get; }

    /// <summary>
    /// Gets the item
    /// </summary>
    /// <remarks></remarks>
    public int this[int index] => 0;
}
```

### RH8202-004 — The fix is withheld for an element without an end tag of its own

The code fix MUST NOT be offered when the reported `<value>` element has no end tag of its own, as SHARED-DOC-017 defines it. The diagnostic is still reported.

Why: Without an end tag, the element extends to the end of the comment, so removing it would also remove the documentation that follows it; an end tag of another name belongs to the element around it.

Example:

```csharp
/// <summary>
/// Service
/// </summary>
public class C
{
    /// <summary>
    /// Gets the size
    /// </summary>
    /// <value>The size
    public int Size { get; }
}
```

is reported from `<value>` through the line break at the end of its line, and no code fix is offered.
