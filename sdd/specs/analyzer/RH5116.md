# Analyzer — RH5116 Null-forgiving operator must stay on the line of its expression

| | |
|---|---|
| ID prefix | RH5116 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5116NullForgivingOperatorMustStayOnExpressionLineAnalyzer`, `RH5116NullForgivingOperatorMustStayOnExpressionLineCodeFixProvider` |
| Uses | FMT-BREAK-040, FMT-UNSUP-014, SHARED-CHAIN-001, SHARED-CHAIN-007, SHARED-CHAIN-008, SHARED-CHAIN-009, SHARED-DIAG-008, SHARED-DIAG-010, SHARED-FIX-010, SHARED-JOIN-002, SHARED-WS-003 |

RH5116 reports a null-forgiving operator `!` that starts a line below the code in front of it, and offers a code fix that moves it onto that code's line.

Which `!` starts such a part, and which trivia form its gap, is stated once, by the attached-part predicate that FMT-BREAK-040 and FMT-UNSUP-014 use (`AttachedPartGapUtilities`); the analyzer, its code fix, and RH5115 decide by that predicate, not by a copy of it.

## Non-goals

- An index `[` or `?[` below its expression — RH5115, also where it stands behind a null-forgiving operator, as in `s!⏎?[0]`.
- A `!` that is the first token of a link operator `!.` or `!?.` — the layout of a chain's links, RH5112 and RH5201.
- The opening parenthesis of an argument list behind a `!`, as in `f!⏎(1)` — FMT-BREAK-039's, a rule of its own.
- The logical negation operator `!` in front of its operand — a prefix operator, not a null-forgiving operator.
- A comment or a directive in the gap in front of a `!` on one line, such as `s /* c */ !` — no line break separates the operator from its expression.
- Realigning a line behind the operator that was aligned to code behind it, outside a chain with links — RH5116-004.

## Requirements

### RH5116-001 — A null-forgiving operator below its expression is reported

The analyzer MUST report a null-forgiving operator (`SuppressNullableWarningExpressionSyntax`) that is not followed by `.` or by the `?.` of a conditional member access — the null-forgiving part of FMT-BREAK-040, identified by the syntax tree alone, whatever expression stands in front of it — when its `!` starts on a later line than the token in front of it ends on, except in a file with a syntax error (SHARED-JOIN-002).

This holds wherever the operator stands: in a member-access chain with links (SHARED-CHAIN-001), in an expression without any link, in front of an index or an argument list, inside an argument, an interpolation hole, or a lambda, and everywhere else. Blank lines in the gap count as a line break. A null-forgiving operator followed by `.` or `?.` MUST NOT be reported: its `!` is the first token of a link operator.

Why: A null-forgiving operator belongs to the expression in front of it: `!` at the start of a line reads as a negation of what follows, and no column shows that it belongs to the code above (FMT-BREAK-040). A `!` in front of `.` or `?.` is part of a link, whose line the chain's layout decides ([P11](../../README.md#the-formatter-may-do-more-than-the-analyzers-p11)).

Example:

```csharp
#nullable enable

class C
{
    void M(string? s, int[]? n)
    {
        var a = s
            {|RH5116:!|} + "";
        var b = n
            {|RH5116:!|}[0];
        var c = n
            {|RH5116:!|}?[0];
        var d = s

            {|RH5116:!|};
    }
}
```

Example — the other side of each condition:

```csharp
#nullable enable

class C
{
    void M(string? s, bool f)
    {
        var a = s! + "";
        var b = s
            !.Length;
        var c = s
            !?.Length;
        var d = f &&
            !f;
    }
}
```

is not reported.

### RH5116-002 — A comment or a directive in the gap does not prevent the report

An operator that RH5116-001 reports MUST be reported also when a comment, a preprocessor directive, or disabled text stands in its gap — in the trailing trivia of the token in front of the `!` or in the leading trivia of the `!`. SHARED-DIAG-008 decides a conditional directive in the gap: the operator is judged in the build being analyzed.

Why: The formatter refuses such an input as unsupported (FMT-UNSUP-014) instead of keeping it, so the shape is not one the formatter keeps (SHARED-DIAG-010): the user is asked to move the comment or the directive, and the diagnostic is what tells the analyzer-only user so.

Example:

```csharp
#nullable enable

class C
{
    void M(string? s)
    {
        var a = s // first
            {|RH5116:!|} + "";
        var b = s /* first */ ! + "";
    }
}
```

`a` is reported and no code fix is offered (RH5116-006); `b` is not reported, because no line break separates `!` from `s`.

### RH5116-003 — The diagnostic is on the `!`

The analyzer MUST report one diagnostic per null-forgiving operator, located on its `!`. A part behind it that starts a later line as well, such as the index of `s⏎!⏎?[0]`, is RH5115's and is reported by that rule.

Why: The `!` is where the line break goes, and each rule reports its own part.

Example:

```csharp
#nullable enable

class C
{
    void M(string? s)
    {
        var a = s
            {|RH5116:!|}
            ?[0];
    }
}
```

The `?` of `?[0]` is reported by RH5115.

### RH5116-004 — Outside a chain with links, the fix joins the operator

When the reported operator is not an attached part of a chain with at least one link (SHARED-CHAIN-001), the code fix MUST join its `!` to the token in front of it as SHARED-WS-003 specifies. It MUST NOT change anything else: a later line that was aligned to code behind the operator keeps its column; the rule that reports the misalignment, such as RH5203, then offers its own fix.

Why: Without a link, no column of the chain the operator belongs to depends on where it stands; deleting the gap is the whole correction and gives what the formatter gives (FMT-BREAK-040). A line aligned to code behind the operator is laid out by another rule, as the RH5105 fix leaves the later parameters of a list it joins.

Example:

```csharp
#nullable enable

class C
{
    void M(string? s)
    {
        var a = s
            {|RH5116:!|} + "";
        var b = s
            {|RH5116:!|} + Foo(1,
                    2);
    }

    string Foo(int x, int y)
    {
        return "";
    }
}
```

```csharp
#nullable enable

class C
{
    void M(string? s)
    {
        var a = s! + "";
        var b = s! + Foo(1,
                    2);
    }

    string Foo(int x, int y)
    {
        return "";
    }
}
```

`2` keeps its column; RH5203 then reports it.

### RH5116-005 — In a chain with links, the fix lays out the chain

When the reported operator is an attached part of a chain with at least one link (SHARED-CHAIN-001), the code fix MUST lay out that chain as SHARED-CHAIN-008 and SHARED-CHAIN-009 specify.

Why: Joining the operator can move the chain's first link, and with it the anchor every wrapped link aligns to (SHARED-CHAIN-007). The formatted layout of the whole chain leaves no link misaligned by the join, as the RH5112 fix does for a first link it joins.

Example:

```csharp
#nullable enable

class C
{
    void M(string s)
    {
        var a = s
            {|RH5116:!|}[0].ToString()
            .Trim();
    }
}
```

```csharp
#nullable enable

class C
{
    void M(string s)
    {
        var a = s![0].ToString()
                     .Trim();
    }
}
```

### RH5116-006 — A comment or a directive in the gap withholds the fix

The code fix MUST NOT be offered when a comment, a preprocessor directive, or disabled text stands in the gap of the reported operator that RH5116-002 names. The diagnostic is still reported. Where the fix lays out a chain, SHARED-FIX-010 withholds it as well: the formatter refuses the shape (FMT-UNSUP-014).

Why: Deleting the gap would delete the comment or the directive, and moving it elsewhere relocates user code; the author decides where it goes.

Example: see RH5116-002.
