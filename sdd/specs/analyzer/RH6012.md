# Analyzer — RH6012 Closing generic brackets must be spaced correctly

| | |
|---|---|
| ID prefix | RH6012 |
| Status | Active |
| Category | Spacing |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH6012ClosingGenericBracketsMustBeSpacedCorrectlyAnalyzer`, `RH6012ClosingGenericBracketsMustBeSpacedCorrectlyCodeFixProvider` |
| Uses | FMT-SPACE-005, FMT-SPACE-013, FMT-SPACE-014, SHARED-WS-001, SHARED-WS-002 |

RH6012 reports whitespace in front of the closing angle bracket of a type argument list or a type parameter list on the same line, and offers a code fix that deletes it as SHARED-WS-001 and SHARED-WS-002 specify.

In the examples, `→` marks a tab.

## Non-goals

- The whitespace after the closing angle bracket — not decided by this rule.
- The opening angle bracket — RH6011.
- The angle brackets of a function pointer type, such as `delegate*<int, void>`, and the `<` and `>` operators.

## Requirements

### RH6012-001 — Whitespace before a closing generic bracket on the same line is reported

The analyzer MUST report the run of spaces and tabs directly in front of the `>` of a type argument list or of a type parameter list when that run follows code or a comment on the same line and the token before the `>` ends on that line — including a `>` after the comma of an unbound generic type (`Dictionary<, >`) and a `>` after a nested list's own `>`. A `>` that starts its line MUST NOT be reported.

Why: The bracket belongs to the type arguments it closes; a space in front of it makes generic types harder to recognize. The formatter removes the same whitespace (FMT-SPACE-005), also between a comment and the bracket (FMT-SPACE-013, and FMT-SPACE-014 for a `/** */` comment the bracket carries), so formatted code raises no RH6012.

Example:

```csharp
using System.Collections.Generic;

class G<T{|RH6012: |}>
{
    void M<U>(List<int{|RH6012: |}> a, List<List<int>{|RH6012: |}> b, Dictionary<int, int{|RH6012:→|}> c)
    {
        var t = typeof(Dictionary<,{|RH6012: |}>);
        var e = new List<int /* note */{|RH6012: |}>();
        List<int
            > f = null;
    }
}
```

### RH6012-002 — Type arguments in documentation references are not reported

The analyzer MUST NOT report a type argument list inside a documentation comment, such as the `{T }` of `cref="List{T }"`.

Why: A reference in documentation names a type and is not code; its spacing does not reach the compiled program.

Example:

```csharp
using System.Collections.Generic;

class C
{
    /// <see cref="List{T }"/>
    void M()
    {
    }
}
```

is not reported.

### RH6012-003 — One diagnostic per bracket

The analyzer MUST report one diagnostic per closing angle bracket, located on the whitespace run in front of it.

Why: The run is the text that is wrong and the text the fix deletes.

Example: see RH6012-001.

### RH6012-004 — The fix deletes the whitespace unless a comment is in the gap

The code fix MUST delete the reported whitespace as SHARED-WS-001 specifies, and MUST NOT be offered when a comment or directive sits between the bracket and the token before it, as SHARED-WS-002 specifies.

Why: Deleting the whitespace between a comment and the bracket would glue the comment to it; the author decides whether the comment stays there.

Example:

```csharp
using System.Collections.Generic;

class G<T{|RH6012: |}>
{
    void M<U>(List<List<int>{|RH6012: |}> b)
    {
        var t = typeof(Dictionary<,{|RH6012:→|}>);
    }
}
```

```csharp
using System.Collections.Generic;

class G<T>
{
    void M<U>(List<List<int>> b)
    {
        var t = typeof(Dictionary<,>);
    }
}
```

The comment before the bracket withholds the fix:

```csharp
using System.Collections.Generic;

class C
{
    void M()
    {
        var e = new List<int /* note */{|RH6012: |}>();
    }
}
```

is reported, and no code fix is offered.
