# Analyzer — RH2001 Private auto-implemented properties should not be used

| | |
|---|---|
| ID prefix | RH2001 |
| Status | Active |
| Category | Design |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH2001PrivateAutoPropertiesShouldNotBeUsedAnalyzer`, `RH2001PrivateAutoPropertiesShouldNotBeUsedCodeFixProvider`, `PropertySymbolExtensions` |
| Uses | FMT-UNSUP-004, FMT-UNSUP-011, FMT-UNSUP-014, FMT-UNSUP-015, FMT-UNSUP-016, FMT-UNSUP-017, FMT-UNSUP-019, RH7105-001, SHARED-CASING-006, SHARED-CASING-007, SHARED-CASING-009, SHARED-DIAG-008, SHARED-FIX-003, SHARED-FIX-009, SHARED-FIX-010, SHARED-MODORDER-002 |

RH2001 reports a private auto-implemented property, and offers a code fix that replaces it with a private field.

## Non-goals

- Properties with any accessibility other than `private`.
- The naming of fields — RH4106 reports a private field whose name is not `_camelCase`.

## Requirements

### RH2001-001 — A private auto-implemented property is reported

The analyzer MUST report a property that is `private`, explicitly or by default, and whose accessors are all implemented by the compiler, such as `{ get; set; }`, `{ get; }`, and `{ get; init; }`, with or without an initializer, whether it is static or an instance property, in a class, a struct, a record, or an interface.

This requirement covers a property that carries no attribute, neither on the property nor on an accessor, that is not expression-bodied, and whose accessors have no bodies.

Why: A private auto-property adds accessor syntax but no encapsulation: nothing outside the type can reach it, and nothing inside runs when it is read or written. A field says the same thing more directly.

Example:

```csharp
class C
{
    private int {|RH2001:Count|} { get; set; }

    int {|RH2001:Implicit|} { get; set; }

    private string {|RH2001:Name|} { get; }

    private int {|RH2001:Id|} { get; init; }

    private static int {|RH2001:Shared|} { get; set; } = 1;
}

struct S
{
    private int {|RH2001:Value|} { get; set; }
}

interface I
{
    private static int {|RH2001:Counter|} { get; set; }
}
```

### RH2001-002 — Other properties are not reported

The analyzer MUST NOT report a property that is not `private`, a property without a backing field — an expression-bodied property whose expression does not use the `field` keyword, or one whose accessors have bodies that do not use it — a property declared with an attribute that applies to the property, or an explicit interface implementation.

Why: A property that is visible outside the type is part of its surface. A property without a backing field computes its value, which a field cannot do. An attribute that applies to the property, as in dependency injection with `[Inject]`, needs property syntax. An explicit interface implementation is private to the compiler, but it implements the interface and cannot become a field.

Example:

```csharp
using System;

interface I
{
    int X { get; set; }
}

class C : I
{
    public int Visible { get; set; }

    protected int Derived { get; set; }

    internal int Assembly { get; set; }

    private int Computed => 1;

    private int Body
    {
        get
        {
            return 1;
        }
    }

    [Obsolete]
    private int Attributed { get; set; }

    int I.X { get; set; }
}
```

is not reported.

### RH2001-003 — The diagnostic is on the property name

The analyzer MUST report one diagnostic per reported property, located on its identifier.

Why: The name is what the fix replaces, at the declaration and at every use.

Example: see RH2001-001.

### RH2001-004 — The fix replaces the property with a private field

The code fix MUST replace the property declaration with a field declaration that keeps the property's type, modifiers, initializer, documentation comment, and trailing comment. A get-only property MUST become a `readonly` field. The field's name MUST be the `_camelCase` name that SHARED-CASING-006 derives from the property's name, and the declaration and every reference to the property MUST be renamed to it as SHARED-CASING-007 specifies. A property whose name already is that name keeps it.

A property that already carries the `readonly` modifier, as a `readonly` property of a struct does, keeps that one modifier: the field is `readonly` once.

When the fix adds `readonly`, it MUST write the field's modifiers, `readonly` included, in the order of RH7105-001, also when the property's modifiers already are in that order, and MUST rewrite the modifier list as SHARED-MODORDER-002 states: the trivia in front of the property's first modifier — its indentation, a comment in front of it on its line, the blank lines above it, the comments and the directives other than `#if`, `#elif`, `#else`, and `#endif` on the lines above it, and its documentation comment — stays once in front of the field's first modifier, and each modifier is followed by a single space. The field's modifiers stay on one line. A property that becomes a field without `readonly` added, such as one with a `set` accessor, keeps its modifiers in their written order. This paragraph covers a property with no comment or directive between its modifiers or between its last modifier and its type; RH2001-009 states the fix for a comment or directive between two modifiers or between the last modifier and the type.

This requirement covers a property whose type is a reference type, a type parameter constrained to a reference type, an enum, a struct declared `readonly`, or a `Nullable<T>` whose `T` is an enum or a struct declared `readonly` (RH2001-008 states what counts as declared `readonly`), that has no comment or directive inside its declaration other than before its first token and after its last, and that no code excluded by `#if` refers to. A rename whose old or new name occurs in code that an `#if`, `#elif`, or `#else` branch excludes is outside the coverage of SHARED-CASING-007, and its fix is withheld (SHARED-FIX-003). An `#if`, `#elif`, `#else`, or `#endif` directive in front of the type of a property that has no modifier, also on the lines above the property, is not covered by this requirement either, although the type is the property's first token; RH2001-009 states that the fix is withheld for it. Nor is an `#if`, `#elif`, `#else`, or `#endif` directive in front of the first modifier of a property that has a modifier, also on the lines above the property, or behind a property without an initializer, whatever its group holds; RH2001-010 states that the fix is withheld for it. Nor is a rename whose field name is already bound at a reference to another symbol in the property's scope, or would bind a renamed reference to the property to another symbol, or in which a reference to the property gives an anonymous-object member or a tuple element its inferred name, outside the two tuple positions that RH2001-011 names, or that reaches the property through another construction of its generic containing type or through a receiver that the renamer qualifies; RH2001-011 states that the fix is withheld for it.

Why: For these properties, a field with the same type, modifiers, and initial value holds the same state, and every use of it behaves as the use of the property did. A get-only auto-property can only be assigned in a constructor or an initializer, which is what `readonly` allows for a field. The `_camelCase` name is the style RH4106 requires of a private field, so the fix does not leave a naming diagnostic behind.

Example:

```csharp
class C
{
    /// <summary>
    /// The count.
    /// </summary>
    private int {|RH2001:Count|} { get; set; } // counter

    private static string {|RH2001:CacheKey|} { get; } = "key";

    private string {|RH2001:Name|} { get; }

    private int {|RH2001:_done|} { get; set; }

    public C(string name)
    {
        Name = name;
    }

    public string Describe() => Name + Count + CacheKey + _done + nameof(Name);
}
```

```csharp
class C
{
    /// <summary>
    /// The count.
    /// </summary>
    private int _count; // counter

    private static readonly string _cacheKey = "key";

    private readonly string _name;

    private int _done;

    public C(string name)
    {
        _name = name;
    }

    public string Describe() => _name + _count + _cacheKey + _done + nameof(_name);
}
```

Example — a `readonly` property of a struct:

```csharp
struct S
{
    private readonly int {|RH2001:Value|} { get; }

    public S(int value)
    {
        Value = value;
    }
}
```

```csharp
struct S
{
    private readonly int _value;

    public S(int value)
    {
        _value = value;
    }
}
```

Example — a get-only property whose modifiers are not in the order of RH7105-001, next to one with a `set` accessor:

```csharp
class C
{
    private int _x;

    // the shared value
    static private int {|RH2001:Value|} { get; }

    /// <summary>
    /// The name.
    /// </summary>
    static private string {|RH2001:Name|} { get; } = "v"; // name

    static private int {|RH2001:Count|} { get; set; }

    int Read() => _x + Value + Name.Length + Count;
}
```

```csharp
class C
{
    private int _x;

    // the shared value
    private static readonly int _value;

    /// <summary>
    /// The name.
    /// </summary>
    private static readonly string _name = "v"; // name

    static private int _count;

    int Read() => _x + _value + _name.Length + _count;
}
```

The blank line above `Value` stays above the field, the comment and the documentation comment stand once in front of it, and the modifiers stay on one line.

Example — a comment in front of the first modifier on its line:

```csharp
class C
{
    /* lead */ static private int {|RH2001:Value|} { get; }
}
```

```csharp
class C
{
    /* lead */ private static readonly int _value;
}
```

Example — a nullable value type whose underlying type is declared `readonly` in the referenced framework, here `int` in .NET 9:

```csharp
class C
{
    private int? {|RH2001:Cache|} { get; set; }

    int Read() => Cache.HasValue ? Cache.Value : 0;
}
```

```csharp
class C
{
    private int? _cache;

    int Read() => _cache.HasValue ? _cache.Value : 0;
}
```

Example — code that `#if` excludes names the property, and in the second block the new name, so the fix is withheld:

```csharp
class C
{
    private int {|RH2001:Value|} { get; set; }

    int Read()
    {
#if NEVER
        return Value;
#else
        return 0;
#endif
    }
}
```

```csharp
class C
{
#if NEVER
    private int _value;
#endif

    private int {|RH2001:Value|} { get; set; }
}
```

Both are reported, and no code fix is offered.

### RH2001-005 — The fix is withheld for accessors a field cannot express

The code fix MUST NOT be offered for a property with an `init` accessor or with an accessor that carries a modifier, such as `readonly get`. The diagnostic is still reported.

Why: A `readonly` field cannot be set in an object initializer, as an `init` accessor can, and a field has no accessor to carry a modifier, so the field would not preserve what the property allows.

Example:

```csharp
struct S
{
    private int {|RH2001:Id|} { get; init; }

    private int {|RH2001:Value|} { readonly get; set; }
}
```

is reported, and no code fix is offered.

### RH2001-006 — The fix is withheld when the field name is taken

The code fix MUST NOT be offered when another member of the containing type already has the name the field would get. The diagnostic is still reported.

Why: Two members of one type cannot share a name; the collision can only be resolved by the author.

Example:

```csharp
class C
{
    private readonly int _value;

    private int {|RH2001:Value|} { get; }
}
```

is reported, and no code fix is offered.

### RH2001-007 — The fix is withheld for a comment or directive inside the property

The code fix MUST NOT be offered for a property with a comment or a directive in any of these places:

- in front of its name, on a line below the line of its type;
- between the name and the opening brace of the accessor list;
- inside the accessor list;
- between the closing brace of the accessor list and the `=` of the initializer;
- in front of the `;` that ends a declaration with an initializer, on a line below the initializer's last line.

A directive includes an `#if` block and the code it excludes. The diagnostic is still reported: the analyzer judges the accessors that the analyzed build compiles (SHARED-DIAG-008).

A comment in front of the property's first token and a comment behind its last token, such as `// counter` in RH2001-004, do not withhold the fix, and neither does a line break alone in front of the name or the `;`. A directive in front of the type and a directive inside the initializer behind its `=` are not covered by this requirement. A comment that the field would carry inside its declaration — in front of the type, behind the type on the type's line, such as `private int /* note */ Value`, behind the initializer's `=`, on a line of its own in front of the initializer's value, or behind the value's last token on that token's line, such as `= 5 /* five */;` — withholds the fix as well, because the formatter refuses the field the fix builds (FMT-UNSUP-004, SHARED-FIX-010). A comment inside the initializer's value, between its first and its last token, does not withhold the fix, unless it stands between a binary operator and its right operand, such as `= 2 + /* three */ 3;`, or in front of an argument list, an element access, or a null-forgiving operator, such as `= Offset /* three */ (3);`, or between the `?` and the `[` of a conditional element access, or between the tokens of a `?.`, `!.`, or `!?.` operator, such as `= Source? /* three */ .Length;`, or between the `.` of a member access or member binding and its name, such as `= Source. /* three */ Length;`, or in a gap the line-break phase joins, such as `= new /* three */ Counter();`, or behind an assignment operator inside a switch arm or an anonymous-object member, such as `= new { A = s_count += /* three */ 3 };`: the formatter refuses the field the fix builds (FMT-UNSUP-011, FMT-UNSUP-014, FMT-UNSUP-015, FMT-UNSUP-016, FMT-UNSUP-017, FMT-UNSUP-019, SHARED-FIX-010), and the fix is withheld. A comment elsewhere in the value, such as `= Offset(/* three */ 3);` or `= 2 /* two */ + 3;`, does not withhold the fix.

Why: A field has no accessor list, so a comment or directive that stands with an accessor or with the accessor list has no place in the field; dropping or moving it is what SHARED-FIX-003 forbids. A directive in the accessor list can also exclude an accessor in one configuration, so the field could not express what the property is in every build. A comment or directive on a line of its own in front of the name or the `;` stands with the property's name or with the end of its declaration; which part of the field it should stand with is the author's decision, and one rule for every such line keeps the fix simple.

Example — comments behind the name and inside the accessor list:

```csharp
class C
{
    private int {|RH2001:Value|} /* name */ { get; /* inner */ set; } // trailing
}
```

is reported, and no code fix is offered.

Example — a comment between the accessor list and the initializer:

```csharp
class C
{
    private int {|RH2001:Value|} { get; set; } /* init */ = 5;
}
```

is reported, and no code fix is offered.

Example — a comment line in a multi-line accessor list:

```csharp
class C
{
    private int {|RH2001:Value|}
    {
        // the getter
        get;
        set;
    }
}
```

is reported, and no code fix is offered.

Example — a directive inside the accessor list:

```csharp
class C
{
    private int {|RH2001:Value|}
    {
        get;
#if DEBUG
        set;
#endif
    }
}
```

is reported, and no code fix is offered.

Example — a comment line, a directive line, and an `#if` block in front of the name:

```csharp
class C
{
    private int
        // note
        {|RH2001:First|} { get; set; }

    private int
#pragma warning disable CS0169
        {|RH2001:Second|} { get; set; }

    private int
#if NEVER
        unused
#endif
        {|RH2001:Third|} { get; set; }
}
```

All three are reported, and no code fix is offered.

Example — a comment line and a directive line in front of the `;` behind the initializer:

```csharp
class C
{
    private int {|RH2001:First|} { get; set; } = 5
        // note
        ;

    private int {|RH2001:Second|} { get; set; } = 5
#pragma warning disable CS0169
        ;
}
```

Both are reported, and no code fix is offered.

Example — the `;` on a line below the initializer, with no comment or directive in front of it:

```csharp
class C
{
    private int {|RH2001:Value|} { get; set; } = 5
        ;
}
```

```csharp
class C
{
    private int _value = 5;
}
```

Example — a comment behind an operator of the initializer's value:

```csharp
class C
{
    private int {|RH2001:Value|} { get; set; } = 2 + /* three */ 3;
}
```

is reported, and no code fix is offered.

Example — a comment elsewhere inside the initializer's value does not withhold the fix:

```csharp
class C
{
    private int {|RH2001:Value|} { get; set; } = 2 /* two */ + Offset(/* three */ 3);

    private static int Offset(int value)
    {
        return value;
    }
}
```

```csharp
class C
{
    private int _value = 2 /* two */ + Offset(/* three */3);

    private static int Offset(int value)
    {
        return value;
    }
}
```

### RH2001-008 — The fix is withheld for a property of a struct type not declared `readonly`

The code fix MUST NOT be offered for a property whose type is a struct that is not declared `readonly`, or a type parameter that is not constrained to a reference type, whether the property has a `set` accessor or is get-only, and whether or not any reference to the property changes its value. The diagnostic is still reported.

A struct counts as declared `readonly` when its declaration carries the `readonly` modifier: in source, or in the metadata of the assembly the compilation references for it. The same property can therefore keep or lose the fix depending on the framework the project targets: `int`, `bool`, `DateTime`, and `Guid` are declared `readonly` in the reference assemblies of current .NET, and are not in .NET Standard 2.0 or .NET Framework. `Nullable<T>` counts as declared `readonly` when its `T` is an enum or a struct declared `readonly`, and as not declared `readonly` otherwise. An enum is not a struct in the sense of this requirement and keeps the fix (RH2001-004).

Why: Through the property, every use works on a copy of the value; through a field, it works on the field itself. A member of a struct that is not declared `readonly` may change the value in place, whether the code calls it, such as `Current.Increment()`, or a language construct calls it, such as `foreach` with a struct enumerator or `+=` on an event, so the fix would change what the program does at run time (SHARED-FIX-003). Whether any use does so would need an analysis of every construct that calls a member implicitly; one check of the type is simple and never offers an unsafe fix. No member of `Nullable<T>` changes its value in place, so its own declaration does not decide; its `T` does. A get-only property becomes a `readonly` field, and inside a constructor a call on that field runs on the field itself, where through the property it ran on a copy. A type parameter that is not constrained to a reference type can stand for such a struct.

Example — a call that changes the value:

```csharp
struct Counter
{
    private int _count;

    public void Increment()
    {
        _count++;
    }
}

class C
{
    private Counter {|RH2001:Current|} { get; set; }

    void M()
    {
        Current.Increment();
    }
}
```

is reported, and no code fix is offered.

Example — no use changes the value, and the struct is still not declared `readonly`:

```csharp
struct Point
{
    public int X;
}

class C
{
    private Point {|RH2001:Origin|} { get; set; }

    private Point? {|RH2001:Last|} { get; set; }

    int Read() => Origin.X;
}
```

Both are reported, and no code fix is offered.

Example — in a project that targets .NET Standard 2.0, whose `int` is not declared `readonly`:

```csharp
class C
{
    private int {|RH2001:Count|} { get; set; }

    private int? {|RH2001:Cache|} { get; set; }

    void M() => Count++;
}
```

Both are reported, and no code fix is offered. In a project that targets .NET 9, the fix is offered for both, as RH2001-004 states.

Example — a get-only property, whose value a constructor changes through a call:

```csharp
struct Counter
{
    private int _count;

    public void Increment()
    {
        _count++;
    }
}

class C
{
    private Counter {|RH2001:Current|} { get; }

    C()
    {
        Current.Increment();
    }
}
```

is reported, and no code fix is offered.

Example — properties typed by type parameters; only the one constrained to a reference type gets the fix:

```csharp
class C<T, TRef>
    where TRef : class
{
    private T {|RH2001:Item|} { get; set; }

    private TRef {|RH2001:Reference|} { get; set; }

    TRef Read() => Item == null ? Reference : null;
}
```

```csharp
class C<T, TRef>
    where TRef : class
{
    private T Item { get; set; }

    private TRef _reference;

    TRef Read() => Item == null ? _reference : null;
}
```

`Item` is still reported, and no code fix is offered for it.

### RH2001-009 — The fix is withheld for a comment or directive behind a modifier, or a conditional directive in front of the type

The code fix MUST NOT be offered when a comment stands between two modifiers or between the last modifier and the type — on a modifier's line or on a line of its own — whether or not the fix writes the modifiers in a new order: the field the fix builds holds the comment, and the formatter refuses that field (FMT-UNSUP-004, SHARED-FIX-010). The diagnostic is still reported.

The code fix MUST NOT be offered either when a directive, or disabled text, stands between two modifiers or between the last modifier and the type — on a modifier's line or on a line of its own — whatever kind of directive it is, whether or not the fix writes the modifiers in a new order, and whether or not it adds `readonly`: the field the fix builds holds the directive behind a modifier, and the formatter refuses that field (FMT-UNSUP-017, SHARED-FIX-010). The diagnostic is still reported.

The code fix MUST NOT be offered either when the property has no modifier and an `#if`, `#elif`, `#else`, or `#endif` directive stands in the leading trivia of its type, also on the lines above the property. This holds whatever the branches of its group hold, also when a group holds only whole members. The diagnostic is still reported. A conditional directive in front of the first modifier of a property that has a modifier is not covered by this requirement; RH2001-010 states that it withholds the fix as well.

This requirement covers a property whose comments and directives between the modifiers, and comments between its last modifier and its type, are its only ones inside its declaration, apart from those RH2001-004 covers.

Why: A comment or a directive among the modifiers, or between the last modifier and the type, would stay in the field the fix builds, behind a modifier, where the formatter does not support it (FMT-UNSUP-004 for a comment, FMT-UNSUP-017 for a directive and disabled text), so the fix that formats the field is withheld for every one of them, also for one that no reordered keyword crosses; the fix needs no check of its own for which comments or directives a reordered keyword would cross. Where the fix changes the order of the modifiers to add `readonly` where RH7105 expects it, a directive between them would also govern other keywords after the move (SHARED-FIX-003), and where it should go then is the author's decision. A conditional directive in front of the type of a property without a modifier makes the declaration depend on the build: a modifier in a branch exists only in the builds that compile it, so which modifiers the field carries in each build, and whether a field can carry them at all — `extern` cannot — would have to be worked out for each build, which no fix does (SHARED-FIX-009). In a build that excludes the branch, that directive stands in front of the property's first token, where the formatter accepts it, so the fix withholds itself for it with one check of where the directive stands, which reads no excluded code and leaves the rare shape to the author.

Example — a comment among the modifiers or in front of the type, whether a reordered modifier would cross it or not:

```csharp
class C
{
    static /* a */ private int {|RH2001:First|} { get; }

    static // b
    private int {|RH2001:Second|} { get; }

    private /* c */ static int {|RH2001:Third|} { get; }

    private static /* d */ int {|RH2001:Fourth|} { get; }
}
```

All four are reported, and no code fix is offered.

Example — a directive between the modifiers or in front of the type, whether a reordered modifier would cross it or not:

```csharp
class C
{
    static
#pragma warning disable CS0169
    private int {|RH2001:First|} { get; }

    private
#pragma warning disable CS0169
    static int {|RH2001:Second|} { get; }

    private static
#pragma warning disable CS0169
    int {|RH2001:Third|} { get; set; }
}
```

All three are reported, and no code fix is offered: the fix would move `private` across the directive of `First`, and the fields built from `Second`, which keeps its modifiers' order, and from `Third`, which gets no `readonly`, would still hold a directive behind a modifier.

Example — a conditional directive between the modifiers:

```csharp
public class C
{
    private
#if DEBUG
        static
#endif
        int {|RH2001:First|} { get; }

    private
#if DEBUG
        static
#endif
        int {|RH2001:Second|} { get; set; }

    private
#if DEBUG
        new
#endif
        int {|RH2001:Third|} { get; }

    private
#if DEBUG
        extern
#endif
        int {|RH2001:Fourth|} { get; }
}

public struct S
{
    private
#if DEBUG
        readonly
#endif
        int {|RH2001:Fifth|} { get; }
}
```

All five are reported, and no code fix is offered: each field would hold a directive behind a modifier, in every build. In a build with `DEBUG`, `Fourth` would also become an `extern` field and `Fifth` a field with `readonly` twice.

For a property without a modifier, the type is its first token, and a conditional directive in front of it withholds the fix, also when the group above holds a whole member:

```csharp
class C
{
#if DEBUG
    extern
#endif
    int {|RH2001:First|} { get; }

#if DEBUG
    private int _trace;
#endif
    int {|RH2001:Second|} { get; }
}
```

Both are reported, and no code fix is offered: in a build with `DEBUG`, `First` would become an `extern` field.

A conditional directive on the lines above a property that has a modifier stands in front of its first modifier, not between its modifiers; RH2001-010 states that it withholds the fix as well.

### RH2001-010 — The fix is withheld for a conditional directive in front of the first modifier or behind a property without an initializer

The code fix MUST NOT be offered for a property that has a modifier when an `#if`, `#elif`, `#else`, or `#endif` directive stands in the leading trivia of the property's first modifier — also on the lines above the property, up to the token in front of it. It MUST NOT be offered either for a property without an initializer, with or without a modifier, when such a directive stands in the leading trivia of the token behind the property's last token — the first token of the next member, or the closing brace of the type body. This holds whatever the branches of the directive's group hold — a modifier, an attribute list, an initializer, whole members, only a comment, or nothing — whichever of its branches the analyzed build compiles, and whether or not another group lies inside a branch. The diagnostic is still reported.

The boundary is the token whose leading trivia holds the directive:

- **In the leading trivia of the first modifier, or of the token behind the property.** A directive there withholds the fix, whether it is the group's `#if` or only its `#endif`, as in the second example below, where the group's `#if` stands in front of the member of its active branch. This includes a group that wraps only the property itself, whose `#if` stands in front of the first modifier, as in the third example below.
- **In the leading trivia of any other token.** A directive that another token's leading trivia holds — in front of an earlier member, in front of the type declaration, or inside another member's body — does not withhold the fix by this requirement, also when its group wraps the property, as in the last example below, where `#if NET` stands in front of `class` and its `#endif` behind the type body's closing brace.

A property without a modifier is covered by RH2001-009 for a directive in front of its type, which is its first token. A property with an initializer ends in `;`, and a directive behind it, in the leading trivia of the next token, does not withhold the fix by this requirement, whatever its group holds; a directive in front of its first modifier does. A directive between two modifiers, or between the last modifier and the type, is covered by RH2001-009; one inside the property's declaration otherwise by RH2001-007. A directive that is not one of `#if`, `#elif`, `#else`, and `#endif`, such as `#region` or `#pragma`, does not withhold the fix by this requirement, and RH2001-004 states the fix for it.

The fix decides this from where the directives stand, by the token whose leading trivia holds them, and reads no excluded branch for it (SHARED-FIX-009).

Why: An excluded branch next to the property is compiled together with the declaration in the builds that include it. A branch in front of the first modifier that holds a modifier or an attribute list becomes part of the declaration in those builds, and the field the fix writes would carry it there: `extern` on a field and a second `readonly` are compile errors, and an attribute may not apply to a field (SHARED-FIX-003, *Build configurations*). A branch behind a property without an initializer can give it one, such as `= 5;`, and behind the field the fix writes, which ends in `;`, that initializer is a syntax error. Telling these branches from branches that hold only whole members means reading each excluded branch as code, together with the groups nested in it — a parse of excluded text that a fix for this rare shape does not justify (`AGENTS.md`, *Special cases do not grow the source*; SHARED-FIX-009). Where the directive stands is a cheap check of one token's leading trivia, so the fix withholds itself for every conditional group there and leaves the code to its author, also where the group holds only whole members and the field would be valid in every build. Behind the `;` of a property with an initializer, every branch begins after the declaration has ended, in every build, so a group there needs no check.

### RH2001-011 — The fix is withheld when the field name is already bound at a reference

The code fix MUST NOT be offered when the rename to the field name (RH2001-004) would change which symbol an existing reference to a symbol other than the property binds to, in either way SHARED-CASING-009 states for a reference to a symbol outside the rename cascade: **rewritten**, when the renamer rewrites the reference so that it keeps its binding, such as qualifying it with `base.` or a type, or turning a call of an extension method into a static call; or **left as written**, when the renamer leaves the reference's text unchanged and it then binds to the field. This holds for a reference in any document of the solution, also in another part of a `partial` type, and for a `cref` in a documentation comment, which is a reference like any other: a `<see cref="_value"/>` that names an inherited member and would then name the field withholds the fix. The other paragraphs of SHARED-CASING-009 are not part of this requirement. The diagnostic is still reported.

The fix is withheld as well, under SHARED-FIX-003, when a reference to the property, renamed, would bind to a symbol other than the field because the renamer leaves it unqualified next to a symbol named like the field: for example a parameter of a lambda or a query range variable in a statement of a block body, a variable declared by `out` in the same expression, or a parameter of the type's primary constructor. What decides is the renamer's result for the reference, not the kind of the symbol: the same lambda parameter in an expression body, where the renamer qualifies the reference with `this.` or the type, keeps the fix (the paragraph on a symbol named like the field below).

The fix is withheld as well when a reference to the property, written `Value`, `this.Value`, or `other.Value`, gives an anonymous-object member without `Name =` or a tuple element without `Name:` its inferred name, whether or not any code reads that member or element. The fix stays offered for such a tuple element in two positions only:

- the tuple is the target of a deconstruction, also as a tuple nested in one, such as `(Value, Name) = (value, name);`, `(Value, other) = pair;`, or `((Value, other), x) = source;`;
- the tuple's own conversion drops the name: the type that the tuple itself is converted to has no name or another name at that element's position, or is not a tuple type, such as `object` or `(int, int)?`; a nullable tuple type is not a tuple type, also when it names the element, so `(int Value, int Other)? pair = (Value, 1);` keeps the fix; for example `return (Value, 1);` from a method that returns `(int, int)`, `(int First, int Second) pair = (Value, 1);`, the argument of `Use((Value, 1))` for a parameter of type `(int, int)`, the source of a deconstruction, such as `(value, count) = (Value, 1);` or `var (value, count) = (Value, 1);`, and a branch of `return flag ? (Value, 1) : (2, 3);`, whose branches carry different names, so that the conditional's type, to which each branch is converted, has no name there.

Everywhere else the fix is withheld. That covers an anonymous-object member, which is never converted to another type, and a tuple element in every other position, among them:

- a tuple in its natural type, such as `var pair = (Value, 1);`, also where no code reads the name: the governing tuple of a `switch` statement or a `switch` expression, such as `switch (Value, input)` or `(Value, input) switch { (1, 2) => 3, _ => 0 }`; a tuple tested with `is` or compared with `==`, such as `(Value, input) is (1, 2)` or `(Value, input) == (1, 2)`; and a tuple in an interpolation, such as `$"{(Value, 1)}"`;
- a tuple whose conversion is applied to an enclosing expression rather than to the tuple itself: a tuple nested in another tuple, such as `((int, int), int) pair = ((Value, 1), 2);` or `var ((a, b), c) = ((Value, 1), 2);`; a tuple cast, such as `((int, int))(Value, 1)`; and a branch of a conditional or an arm of a `switch` expression whose branches or arms all carry the name, such as `return flag ? (Value, 1) : (Value, 2);` or `return input switch { 1 => (Value, 1), _ => (Value, 2) };` from a method that returns `(int, int)`;
- a tuple converted to a tuple type that supplies the name itself, such as `(int Value, int Other) pair = (Value, 1);`; a nullable tuple type is not one (the second position above).

Where code reads the inferred name, such as `pair.Value` after `var pair = (Value, 1);`, and for every anonymous-object member, whose name the text that `ToString()` returns holds, the rename would rename that member or element as well and ship code that no longer compiles or that returns other text; SHARED-FIX-003 demands withholding there. In the other withheld positions the rename changes nothing observable, because a tuple element's name exists at compile time only; the fix is withheld there as a refusal of a rare class (`AGENTS.md`, *Code-fix coverage*), and for the governing tuple of a `switch` statement or expression by the maintainer's decision. A member or element whose name is written explicitly, such as `new { Value = Value }` or `(Value: Value, 1)`, keeps its name, and the fix stays offered.

A symbol named like the field does not withhold the fix when every reference keeps both its binding and its text, apart from the references to the property, which the fix renames and may qualify with `this.` (SHARED-CASING-007): for example a local, a method parameter, a parameter of a lambda in an expression body, a pattern variable, or a local function named like the field, next to a reference to the property that becomes `this._value`, or the type's name for a static property; an inherited method or an extension method named like the field that a call still reaches, written as before; an inherited member named like the field that no reference names; and a member named like the field that is reached through the property's own value, such as `Value._value`, whose receiver changes only by the rename, so that the access becomes `_value._value` and reads the same member as before. A member that the containing type declares itself with the field name withholds the fix under RH2001-006.

The fix is withheld as well for two rare shapes in which the rename of the property's own references changes more than their name, although every binding would stay:

- a reference to the property through another construction of its generic containing type, such as `other.Value` with a parameter `Sample<int> other` inside `Sample<T>`, or `new Sample<TOther> { Value = Value }` inside `Sample<T>`; a reference through the containing type's own construction, such as `other.Value` with a parameter `Sample<T> other` inside `Sample<T>`, keeps the fix;
- a member named like the field reached through the property's own value whose receiver the renamer also qualifies with `this.` or the type's name, because a local, a parameter, or another symbol of an inner scope is named like the field, such as `return Value._value + _value;` next to a local `_value`, which the rename would turn into `return this._value._value + _value;`; the same receiver without such a symbol, which becomes `_value._value`, keeps the fix (the paragraph on a symbol named like the field above).

Why: A rewritten reference to another symbol is an edit of code the diagnostic does not name, and a reference left as written that now binds to the field reads or writes other state at run time (SHARED-FIX-003). Which name the author keeps is the author's decision. A field name already bound at a reference in the property's scope is uncommon, and a diagnostic without a fix is a supported end state. A reference to the property that the renamer qualifies with `this.` keeps its binding and changes only by the rename, so the fix stays. A member name the compiler infers from a reference to the property is part of the type of an anonymous object, and of a tuple, so renaming the reference renames the member; where code reads it, or `ToString()` prints it, that ships broken code or other output. A deconstruction target, and a tuple whose own conversion drops the name, keep nothing of it, so renaming the reference there changes nothing but the reference; these are the positions the deconstructing constructor and a returned tuple are commonly written in. Telling the remaining positions apart by whether a conversion on an enclosing expression drops the name, or whether any code reads it, is more than a cheap check, and those positions are rare, so the fix is withheld for all of them; the maintainer decided the same for a tuple `switch` on the property. A private property read through another construction of its own generic type, and a local named like a field next to a receiver, which RH4115 reports, are rare, and a diagnostic without a fix is a supported end state.
