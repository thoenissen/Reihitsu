# Analyzer — RH2001 Private auto-implemented properties should not be used

| | |
|---|---|
| ID prefix | RH2001 |
| Status | Active |
| Category | Design |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH2001PrivateAutoPropertiesShouldNotBeUsedAnalyzer`, `RH2001PrivateAutoPropertiesShouldNotBeUsedCodeFixProvider`, `PropertySymbolExtensions` |
| Uses | RH7105-001, SHARED-CASING-006, SHARED-CASING-007, SHARED-FIX-003, SHARED-FIX-009, SHARED-MODORDER-002 |

RH2001 reports a private auto-implemented property, and offers a code fix that replaces it with a private field.

## Non-goals

- Properties with any accessibility other than `private`.
- The naming of fields — RH4106 reports a private field whose name is not `_camelCase`.

## Requirements

### RH2001-001 — A private auto-implemented property is reported

The analyzer MUST report a property that is `private`, explicitly or by default, and whose accessors are all implemented by the compiler, such as `{ get; set; }`, `{ get; }`, and `{ get; init; }`, with or without an initializer, whether it is static or an instance property, in a class, a struct, a record, or an interface.

This requirement covers a property that carries no attribute, neither on the property nor on an accessor, that is not expression-bodied, and whose accessors have no bodies.

Why: A private auto-property adds accessor syntax but no encapsulation: nothing outside the type can reach it, and nothing inside runs when it is read or written. A field says the same thing more directly.

Example:

```csharp
class C
{
    private int {|RH2001:Count|} { get; set; }

    int {|RH2001:Implicit|} { get; set; }

    private string {|RH2001:Name|} { get; }

    private int {|RH2001:Id|} { get; init; }

    private static int {|RH2001:Shared|} { get; set; } = 1;
}

struct S
{
    private int {|RH2001:Value|} { get; set; }
}

interface I
{
    private static int {|RH2001:Counter|} { get; set; }
}
```

### RH2001-002 — Other properties are not reported

The analyzer MUST NOT report a property that is not `private`, a property without a backing field — an expression-bodied property whose expression does not use the `field` keyword, or one whose accessors have bodies that do not use it — a property declared with an attribute that applies to the property, or an explicit interface implementation.

Why: A property that is visible outside the type is part of its surface. A property without a backing field computes its value, which a field cannot do. An attribute that applies to the property, as in dependency injection with `[Inject]`, needs property syntax. An explicit interface implementation is private to the compiler, but it implements the interface and cannot become a field.

Example:

```csharp
using System;

interface I
{
    int X { get; set; }
}

class C : I
{
    public int Visible { get; set; }

    protected int Derived { get; set; }

    internal int Assembly { get; set; }

    private int Computed => 1;

    private int Body
    {
        get
        {
            return 1;
        }
    }

    [Obsolete]
    private int Attributed { get; set; }

    int I.X { get; set; }
}
```

is not reported.

### RH2001-003 — The diagnostic is on the property name

The analyzer MUST report one diagnostic per reported property, located on its identifier.

Why: The name is what the fix replaces, at the declaration and at every use.

Example: see RH2001-001.

### RH2001-004 — The fix replaces the property with a private field

The code fix MUST replace the property declaration with a field declaration that keeps the property's type, modifiers, initializer, documentation comment, and trailing comment. A get-only property MUST become a `readonly` field. The field's name MUST be the `_camelCase` name that SHARED-CASING-006 derives from the property's name, and the declaration and every reference to the property MUST be renamed to it as SHARED-CASING-007 specifies. A property whose name already is that name keeps it.

A property that already carries the `readonly` modifier, as a `readonly` property of a struct does, keeps that one modifier: the field is `readonly` once.

When the fix adds `readonly`, it MUST write the field's modifiers, `readonly` included, in the order of RH7105-001, also when the property's modifiers already are in that order, and MUST rewrite the modifier list as SHARED-MODORDER-002 states: the trivia in front of the property's first modifier — its indentation, a comment in front of it on its line, the blank lines above it, the comments and directives on the lines above it, and its documentation comment — stays once in front of the field's first modifier, and each modifier is followed by a single space. The field's modifiers stay on one line. A property that becomes a field without `readonly` added, such as one with a `set` accessor, keeps its modifiers in their written order. This paragraph covers a property with no comment or directive between its modifiers or between its last modifier and its type; RH2001-009 states the fix for a comment or directive between two modifiers and for a comment between the last modifier and the type.

This requirement covers a property whose type is a reference type, a type parameter constrained to a reference type, an enum, a struct declared `readonly`, or a `Nullable<T>` whose `T` is an enum or a struct declared `readonly` (RH2001-008 states what counts as declared `readonly`), that has no comment or directive inside its declaration other than before its first token and after its last, and that no code excluded by `#if` refers to. A rename whose old or new name occurs in code that an `#if`, `#elif`, or `#else` branch excludes is outside the coverage of SHARED-CASING-007, and its fix is withheld (SHARED-FIX-003).

Why: For these properties, a field with the same type, modifiers, and initial value holds the same state, and every use of it behaves as the use of the property did. A get-only auto-property can only be assigned in a constructor or an initializer, which is what `readonly` allows for a field. The `_camelCase` name is the style RH4106 requires of a private field, so the fix does not leave a naming diagnostic behind.

Example:

```csharp
class C
{
    /// <summary>
    /// The count.
    /// </summary>
    private int {|RH2001:Count|} { get; set; } // counter

    private static string {|RH2001:CacheKey|} { get; } = "key";

    private string {|RH2001:Name|} { get; }

    private int {|RH2001:_done|} { get; set; }

    public C(string name)
    {
        Name = name;
    }

    public string Describe() => Name + Count + CacheKey + _done + nameof(Name);
}
```

```csharp
class C
{
    /// <summary>
    /// The count.
    /// </summary>
    private int _count; // counter

    private static readonly string _cacheKey = "key";

    private readonly string _name;

    private int _done;

    public C(string name)
    {
        _name = name;
    }

    public string Describe() => _name + _count + _cacheKey + _done + nameof(_name);
}
```

Example — a `readonly` property of a struct:

```csharp
struct S
{
    private readonly int {|RH2001:Value|} { get; }

    public S(int value)
    {
        Value = value;
    }
}
```

```csharp
struct S
{
    private readonly int _value;

    public S(int value)
    {
        _value = value;
    }
}
```

Example — a get-only property whose modifiers are not in the order of RH7105-001, next to one with a `set` accessor:

```csharp
class C
{
    private int _x;

    // the shared value
    static private int {|RH2001:Value|} { get; }

    /// <summary>
    /// The name.
    /// </summary>
    static private string {|RH2001:Name|} { get; } = "v"; // name

    static private int {|RH2001:Count|} { get; set; }

    int Read() => _x + Value + Name.Length + Count;
}
```

```csharp
class C
{
    private int _x;

    // the shared value
    private static readonly int _value;

    /// <summary>
    /// The name.
    /// </summary>
    private static readonly string _name = "v"; // name

    static private int _count;

    int Read() => _x + _value + _name.Length + _count;
}
```

The blank line above `Value` stays above the field, the comment and the documentation comment stand once in front of it, and the modifiers stay on one line.

Example — a comment in front of the first modifier on its line:

```csharp
class C
{
    /* lead */ static private int {|RH2001:Value|} { get; }
}
```

```csharp
class C
{
    /* lead */ private static readonly int _value;
}
```

Example — a nullable value type whose underlying type is declared `readonly` in the referenced framework, here `int` in .NET 9:

```csharp
class C
{
    private int? {|RH2001:Cache|} { get; set; }

    int Read() => Cache.HasValue ? Cache.Value : 0;
}
```

```csharp
class C
{
    private int? _cache;

    int Read() => _cache.HasValue ? _cache.Value : 0;
}
```

Example — code that `#if` excludes names the property, and in the second block the new name, so the fix is withheld:

```csharp
class C
{
    private int {|RH2001:Value|} { get; set; }

    int Read()
    {
#if NEVER
        return Value;
#else
        return 0;
#endif
    }
}
```

```csharp
class C
{
#if NEVER
    private int _value;
#endif

    private int {|RH2001:Value|} { get; set; }
}
```

Both are reported, and no code fix is offered.

### RH2001-005 — The fix is withheld for accessors a field cannot express

The code fix MUST NOT be offered for a property with an `init` accessor or with an accessor that carries a modifier, such as `readonly get`. The diagnostic is still reported.

Why: A `readonly` field cannot be set in an object initializer, as an `init` accessor can, and a field has no accessor to carry a modifier, so the field would not preserve what the property allows.

Example:

```csharp
struct S
{
    private int {|RH2001:Id|} { get; init; }

    private int {|RH2001:Value|} { readonly get; set; }
}
```

is reported, and no code fix is offered.

### RH2001-006 — The fix is withheld when the field name is taken

The code fix MUST NOT be offered when another member of the containing type already has the name the field would get. The diagnostic is still reported.

Why: Two members of one type cannot share a name; the collision can only be resolved by the author.

Example:

```csharp
class C
{
    private readonly int _value;

    private int {|RH2001:Value|} { get; }
}
```

is reported, and no code fix is offered.

### RH2001-007 — The fix is withheld for a comment or directive inside the property

The code fix MUST NOT be offered for a property with a comment or a directive in any of these places:

- in front of its name, on a line below the line of its type;
- between the name and the opening brace of the accessor list;
- inside the accessor list;
- between the closing brace of the accessor list and the `=` of the initializer;
- in front of the `;` that ends a declaration with an initializer, on a line below the initializer's last line.

A directive includes an `#if` block and the code it excludes. The diagnostic is still reported.

A comment in front of the property's first token and a comment behind its last token, such as `// counter` in RH2001-004, do not withhold the fix, and neither does a line break alone in front of the name or the `;`. A comment or directive in front of the type, a comment behind the type on the type's line, such as `private int /* note */ Value`, and a comment or directive inside the initializer behind its `=`, including one behind its last token on that token's line, are not covered by this requirement.

Why: A field has no accessor list, so a comment or directive that stands with an accessor or with the accessor list has no place in the field; dropping or moving it is what SHARED-FIX-003 forbids. A directive in the accessor list can also exclude an accessor in one configuration, so the field could not express what the property is in every build. A comment or directive on a line of its own in front of the name or the `;` stands with the property's name or with the end of its declaration; which part of the field it should stand with is the author's decision, and one rule for every such line keeps the fix simple.

Example — comments behind the name and inside the accessor list:

```csharp
class C
{
    private int {|RH2001:Value|} /* name */ { get; /* inner */ set; } // trailing
}
```

is reported, and no code fix is offered.

Example — a comment between the accessor list and the initializer:

```csharp
class C
{
    private int {|RH2001:Value|} { get; set; } /* init */ = 5;
}
```

is reported, and no code fix is offered.

Example — a comment line in a multi-line accessor list:

```csharp
class C
{
    private int {|RH2001:Value|}
    {
        // the getter
        get;
        set;
    }
}
```

is reported, and no code fix is offered.

Example — a directive inside the accessor list:

```csharp
class C
{
    private int {|RH2001:Value|}
    {
        get;
#if DEBUG
        set;
#endif
    }
}
```

is reported, and no code fix is offered.

Example — a comment line, a directive line, and an `#if` block in front of the name:

```csharp
class C
{
    private int
        // note
        {|RH2001:First|} { get; set; }

    private int
#pragma warning disable CS0169
        {|RH2001:Second|} { get; set; }

    private int
#if NEVER
        unused
#endif
        {|RH2001:Third|} { get; set; }
}
```

All three are reported, and no code fix is offered.

Example — a comment line and a directive line in front of the `;` behind the initializer:

```csharp
class C
{
    private int {|RH2001:First|} { get; set; } = 5
        // note
        ;

    private int {|RH2001:Second|} { get; set; } = 5
#pragma warning disable CS0169
        ;
}
```

Both are reported, and no code fix is offered.

Example — the `;` on a line below the initializer, with no comment or directive in front of it:

```csharp
class C
{
    private int {|RH2001:Value|} { get; set; } = 5
        ;
}
```

```csharp
class C
{
    private int _value = 5;
}
```

### RH2001-008 — The fix is withheld for a property of a struct type not declared `readonly`

The code fix MUST NOT be offered for a property whose type is a struct that is not declared `readonly`, or a type parameter that is not constrained to a reference type, whether the property has a `set` accessor or is get-only, and whether or not any reference to the property changes its value. The diagnostic is still reported.

A struct counts as declared `readonly` when its declaration carries the `readonly` modifier: in source, or in the metadata of the assembly the compilation references for it. The same property can therefore keep or lose the fix depending on the framework the project targets: `int`, `bool`, `DateTime`, and `Guid` are declared `readonly` in the reference assemblies of current .NET, and are not in .NET Standard 2.0 or .NET Framework. `Nullable<T>` counts as declared `readonly` when its `T` is an enum or a struct declared `readonly`, and as not declared `readonly` otherwise. An enum is not a struct in the sense of this requirement and keeps the fix (RH2001-004).

Why: Through the property, every use works on a copy of the value; through a field, it works on the field itself. A member of a struct that is not declared `readonly` may change the value in place, whether the code calls it, such as `Current.Increment()`, or a language construct calls it, such as `foreach` with a struct enumerator or `+=` on an event, so the fix would change what the program does at run time (SHARED-FIX-003). Whether any use does so would need an analysis of every construct that calls a member implicitly; one check of the type is simple and never offers an unsafe fix. No member of `Nullable<T>` changes its value in place, so its own declaration does not decide; its `T` does. A get-only property becomes a `readonly` field, and inside a constructor a call on that field runs on the field itself, where through the property it ran on a copy. A type parameter that is not constrained to a reference type can stand for such a struct.

Example — a call that changes the value:

```csharp
struct Counter
{
    private int _count;

    public void Increment()
    {
        _count++;
    }
}

class C
{
    private Counter {|RH2001:Current|} { get; set; }

    void M()
    {
        Current.Increment();
    }
}
```

is reported, and no code fix is offered.

Example — no use changes the value, and the struct is still not declared `readonly`:

```csharp
struct Point
{
    public int X;
}

class C
{
    private Point {|RH2001:Origin|} { get; set; }

    private Point? {|RH2001:Last|} { get; set; }

    int Read() => Origin.X;
}
```

Both are reported, and no code fix is offered.

Example — in a project that targets .NET Standard 2.0, whose `int` is not declared `readonly`:

```csharp
class C
{
    private int {|RH2001:Count|} { get; set; }

    private int? {|RH2001:Cache|} { get; set; }

    void M() => Count++;
}
```

Both are reported, and no code fix is offered. In a project that targets .NET 9, the fix is offered for both, as RH2001-004 states.

Example — a get-only property, whose value a constructor changes through a call:

```csharp
struct Counter
{
    private int _count;

    public void Increment()
    {
        _count++;
    }
}

class C
{
    private Counter {|RH2001:Current|} { get; }

    C()
    {
        Current.Increment();
    }
}
```

is reported, and no code fix is offered.

Example — properties typed by type parameters; only the one constrained to a reference type gets the fix:

```csharp
class C<T, TRef>
    where TRef : class
{
    private T {|RH2001:Item|} { get; set; }

    private TRef {|RH2001:Reference|} { get; set; }

    TRef Read() => Item == null ? Reference : null;
}
```

```csharp
class C<T, TRef>
    where TRef : class
{
    private T Item { get; set; }

    private TRef _reference;

    TRef Read() => Item == null ? _reference : null;
}
```

`Item` is still reported, and no code fix is offered for it.

### RH2001-009 — The fix is withheld for a comment or directive that a reordered modifier would cross, or for a conditional group of other modifiers

The code fix MUST NOT be offered when it writes the modifiers in a new order (RH2001-004) and a comment or a directive stands between two modifiers that the new order puts the other way round — on a modifier's line or on a line of its own. The diagnostic is still reported.

A comment or directive between two modifiers that keep their order — every modifier written in front of it stays in front of it, and every modifier written behind it stays behind it — does not withhold the fix, and it keeps its place between them. A comment between the last modifier and the type does not withhold the fix either, and it stays in front of the type; no modifier crosses it, because every modifier is written in front of it. The same holds when the fix keeps the written order and only adds `readonly`.

The fix writes `readonly` at its place in the order of RH7105-001. When a comment stands at that place — between the last modifier that RH7105-001 puts in front of `readonly` and the first it puts behind it, or between the last modifier and the type when RH7105-001 puts none behind it — `readonly` is written behind the comment.

The code fix MUST NOT be offered either when a conditional group — an `#if` with its `#elif` and `#else` branches and its `#endif` — has a directive between two modifiers or between the last modifier and the type, and a branch of the group, active or excluded, holds anything other than the modifiers `public`, `private`, `protected`, `internal`, `new`, and `static`: the modifiers that RH7105-001 puts in front of `readonly` and that a field can carry. A branch that holds `extern`, `readonly`, `unsafe`, `required`, or any other modifier, or a comment or code that is no modifier, withholds the fix. The diagnostic is still reported. A branch that holds nothing, or only modifiers of that set, does not withhold it.

When the place of `readonly` lies directly behind such a group, and every modifier written behind the group is one that RH7105-001 puts behind `readonly`, `readonly` is written behind the group, on the line that follows its `#endif`, in front of those modifiers or, when there are none, in front of the type. The group and its lines stay in place. A directive at that place that belongs to no conditional group, such as `#pragma`, is not covered by this requirement.

This requirement covers a property whose comments and directives between the modifiers, and comments between its last modifier and its type, are its only ones inside its declaration, apart from those RH2001-004 covers.

Why: The fix changes the order of the modifiers to add `readonly` where RH7105 expects it. A comment written next to one keyword cannot keep its place next to the same keyword when another keyword moves across it, and a directive between the modifiers governs the keywords behind it, so moving a keyword across it changes which code it governs (SHARED-FIX-003). Where the comment or directive should go then is the author's decision. A comment that no keyword crosses keeps the place the author gave it. `readonly` written inside a conditional group would exist only in the builds that include that branch, and written in front of a group of modifiers that RH7105-001 puts in front of `readonly` it would stand out of RH7105's order in the builds that include them; behind the group it stands at its place in every build. A modifier in a group exists only in the builds that compile its branch, and the fix does not work out which modifiers the field carries in each build (SHARED-FIX-009): `extern` is valid on a property but not on a field, a second `readonly` next to the one the fix adds is an error, and a modifier that RH7105-001 puts behind `readonly` would need its own place in each build. One set of keywords decides every group, so the check compares the tokens of each branch with that set and withholds the fix for anything else, also where a place would exist, such as for `unsafe`.

Example — a comment that a reordered modifier would cross:

```csharp
class C
{
    static /* a */ private int {|RH2001:First|} { get; }

    static // b
    private int {|RH2001:Second|} { get; }

    new /* c */ static private int {|RH2001:Third|} { get; }
}
```

All three are reported, and no code fix is offered.

Example — a directive that a reordered modifier would cross:

```csharp
class C
{
    static
#pragma warning disable CS0169
    private int {|RH2001:Value|} { get; }
}
```

is reported, and no code fix is offered.

Example — a comment that no modifier crosses:

```csharp
class C
{
    private /* a */ static int {|RH2001:First|} { get; }

    private /* b */ new static int {|RH2001:Second|} { get; }

    static private /* c */ int {|RH2001:Third|} { get; }

    private static /* d */ int {|RH2001:Fourth|} { get; }
}
```

```csharp
class C
{
    private /* a */ static readonly int _first;

    private /* b */ static new readonly int _second;

    private static /* c */ readonly int _third;

    private static /* d */ readonly int _fourth;
}
```

`readonly` goes behind `static`; for `Third` and `Fourth`, no modifier follows it, so it is written behind the comment, in front of the type.

Example — a conditional group at the place of `readonly`:

```csharp
public class C
{
    private
#if DEBUG
        static
#endif
        int {|RH2001:Value|} { get; }

    public int Get()
    {
        return Value;
    }
}
```

```csharp
public class C
{
    private
#if DEBUG
        static
#endif
    readonly int _value;

    public int Get()
    {
        return _value;
    }
}
```

The group holds `static`, which RH7105-001 puts in front of `readonly`, and no modifier follows the group, so `readonly` is written behind the `#endif`, in front of the type. Every build then writes `readonly` at its place: `private static readonly int` where `DEBUG` is defined and `private readonly int` where it is not.

Example — a conditional group that holds a modifier a field cannot carry at that place:

```csharp
public class C
{
    private
#if DEBUG
        extern
#endif
        int {|RH2001:First|} { get; }

    private
#if DEBUG
        unsafe
#endif
        int {|RH2001:Second|} { get; }
}

public struct S
{
    private
#if DEBUG
        readonly
#endif
        int {|RH2001:Third|} { get; }
}
```

All three are reported, and no code fix is offered: in a build with `DEBUG`, `First` would become an `extern` field and `Third` a field with `readonly` twice; `unsafe` withholds the fix as well, although `private readonly unsafe int` would be valid.
