# Analyzer — RH2001 Private auto-implemented properties should not be used

| | |
|---|---|
| ID prefix | RH2001 |
| Status | Active |
| Category | Design |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH2001PrivateAutoPropertiesShouldNotBeUsedAnalyzer`, `RH2001PrivateAutoPropertiesShouldNotBeUsedCodeFixProvider`, `PropertySymbolExtensions` |
| Uses | FMT-UNSUP-004, RH7105-001, SHARED-CASING-006, SHARED-CASING-007, SHARED-FIX-003, SHARED-FIX-009, SHARED-FIX-010, SHARED-MODORDER-002 |

RH2001 reports a private auto-implemented property, and offers a code fix that replaces it with a private field.

## Non-goals

- Properties with any accessibility other than `private`.
- The naming of fields — RH4106 reports a private field whose name is not `_camelCase`.

## Requirements

### RH2001-001 — A private auto-implemented property is reported

The analyzer MUST report a property that is `private`, explicitly or by default, and whose accessors are all implemented by the compiler, such as `{ get; set; }`, `{ get; }`, and `{ get; init; }`, with or without an initializer, whether it is static or an instance property, in a class, a struct, a record, or an interface.

This requirement covers a property that carries no attribute, neither on the property nor on an accessor, that is not expression-bodied, and whose accessors have no bodies.

Why: A private auto-property adds accessor syntax but no encapsulation: nothing outside the type can reach it, and nothing inside runs when it is read or written. A field says the same thing more directly.

Example:

```csharp
class C
{
    private int {|RH2001:Count|} { get; set; }

    int {|RH2001:Implicit|} { get; set; }

    private string {|RH2001:Name|} { get; }

    private int {|RH2001:Id|} { get; init; }

    private static int {|RH2001:Shared|} { get; set; } = 1;
}

struct S
{
    private int {|RH2001:Value|} { get; set; }
}

interface I
{
    private static int {|RH2001:Counter|} { get; set; }
}
```

### RH2001-002 — Other properties are not reported

The analyzer MUST NOT report a property that is not `private`, a property without a backing field — an expression-bodied property whose expression does not use the `field` keyword, or one whose accessors have bodies that do not use it — a property declared with an attribute that applies to the property, or an explicit interface implementation.

Why: A property that is visible outside the type is part of its surface. A property without a backing field computes its value, which a field cannot do. An attribute that applies to the property, as in dependency injection with `[Inject]`, needs property syntax. An explicit interface implementation is private to the compiler, but it implements the interface and cannot become a field.

Example:

```csharp
using System;

interface I
{
    int X { get; set; }
}

class C : I
{
    public int Visible { get; set; }

    protected int Derived { get; set; }

    internal int Assembly { get; set; }

    private int Computed => 1;

    private int Body
    {
        get
        {
            return 1;
        }
    }

    [Obsolete]
    private int Attributed { get; set; }

    int I.X { get; set; }
}
```

is not reported.

### RH2001-003 — The diagnostic is on the property name

The analyzer MUST report one diagnostic per reported property, located on its identifier.

Why: The name is what the fix replaces, at the declaration and at every use.

Example: see RH2001-001.

### RH2001-004 — The fix replaces the property with a private field

The code fix MUST replace the property declaration with a field declaration that keeps the property's type, modifiers, initializer, documentation comment, and trailing comment. A get-only property MUST become a `readonly` field. The field's name MUST be the `_camelCase` name that SHARED-CASING-006 derives from the property's name, and the declaration and every reference to the property MUST be renamed to it as SHARED-CASING-007 specifies. A property whose name already is that name keeps it.

A property that already carries the `readonly` modifier, as a `readonly` property of a struct does, keeps that one modifier: the field is `readonly` once.

When the fix adds `readonly`, it MUST write the field's modifiers, `readonly` included, in the order of RH7105-001, also when the property's modifiers already are in that order, and MUST rewrite the modifier list as SHARED-MODORDER-002 states: the trivia in front of the property's first modifier — its indentation, a comment in front of it on its line, the blank lines above it, the comments and directives on the lines above it, and its documentation comment — stays once in front of the field's first modifier, and each modifier is followed by a single space. The field's modifiers stay on one line. A property that becomes a field without `readonly` added, such as one with a `set` accessor, keeps its modifiers in their written order. This paragraph covers a property with no comment or directive between its modifiers or between its last modifier and its type; RH2001-009 states the fix for a comment or directive between two modifiers and for a comment between the last modifier and the type.

This requirement covers a property whose type is a reference type, a type parameter constrained to a reference type, an enum, a struct declared `readonly`, or a `Nullable<T>` whose `T` is an enum or a struct declared `readonly` (RH2001-008 states what counts as declared `readonly`), that has no comment or directive inside its declaration other than before its first token and after its last, and that no code excluded by `#if` refers to. A rename whose old or new name occurs in code that an `#if`, `#elif`, or `#else` branch excludes is outside the coverage of SHARED-CASING-007, and its fix is withheld (SHARED-FIX-003). An `#if`, `#elif`, `#else`, or `#endif` directive in front of the type of a property that has no modifier, also on the lines above the property, is not covered by this requirement either, although the type is the property's first token; RH2001-009 states that the fix is withheld for it. Nor is a conditional group with a directive in front of the first modifier, or behind a property without an initializer, that does not wrap whole members; RH2001-010 states that the fix is withheld for it.

Why: For these properties, a field with the same type, modifiers, and initial value holds the same state, and every use of it behaves as the use of the property did. A get-only auto-property can only be assigned in a constructor or an initializer, which is what `readonly` allows for a field. The `_camelCase` name is the style RH4106 requires of a private field, so the fix does not leave a naming diagnostic behind.

Example:

```csharp
class C
{
    /// <summary>
    /// The count.
    /// </summary>
    private int {|RH2001:Count|} { get; set; } // counter

    private static string {|RH2001:CacheKey|} { get; } = "key";

    private string {|RH2001:Name|} { get; }

    private int {|RH2001:_done|} { get; set; }

    public C(string name)
    {
        Name = name;
    }

    public string Describe() => Name + Count + CacheKey + _done + nameof(Name);
}
```

```csharp
class C
{
    /// <summary>
    /// The count.
    /// </summary>
    private int _count; // counter

    private static readonly string _cacheKey = "key";

    private readonly string _name;

    private int _done;

    public C(string name)
    {
        _name = name;
    }

    public string Describe() => _name + _count + _cacheKey + _done + nameof(_name);
}
```

Example — a `readonly` property of a struct:

```csharp
struct S
{
    private readonly int {|RH2001:Value|} { get; }

    public S(int value)
    {
        Value = value;
    }
}
```

```csharp
struct S
{
    private readonly int _value;

    public S(int value)
    {
        _value = value;
    }
}
```

Example — a get-only property whose modifiers are not in the order of RH7105-001, next to one with a `set` accessor:

```csharp
class C
{
    private int _x;

    // the shared value
    static private int {|RH2001:Value|} { get; }

    /// <summary>
    /// The name.
    /// </summary>
    static private string {|RH2001:Name|} { get; } = "v"; // name

    static private int {|RH2001:Count|} { get; set; }

    int Read() => _x + Value + Name.Length + Count;
}
```

```csharp
class C
{
    private int _x;

    // the shared value
    private static readonly int _value;

    /// <summary>
    /// The name.
    /// </summary>
    private static readonly string _name = "v"; // name

    static private int _count;

    int Read() => _x + _value + _name.Length + _count;
}
```

The blank line above `Value` stays above the field, the comment and the documentation comment stand once in front of it, and the modifiers stay on one line.

Example — a comment in front of the first modifier on its line:

```csharp
class C
{
    /* lead */ static private int {|RH2001:Value|} { get; }
}
```

```csharp
class C
{
    /* lead */ private static readonly int _value;
}
```

Example — a nullable value type whose underlying type is declared `readonly` in the referenced framework, here `int` in .NET 9:

```csharp
class C
{
    private int? {|RH2001:Cache|} { get; set; }

    int Read() => Cache.HasValue ? Cache.Value : 0;
}
```

```csharp
class C
{
    private int? _cache;

    int Read() => _cache.HasValue ? _cache.Value : 0;
}
```

Example — code that `#if` excludes names the property, and in the second block the new name, so the fix is withheld:

```csharp
class C
{
    private int {|RH2001:Value|} { get; set; }

    int Read()
    {
#if NEVER
        return Value;
#else
        return 0;
#endif
    }
}
```

```csharp
class C
{
#if NEVER
    private int _value;
#endif

    private int {|RH2001:Value|} { get; set; }
}
```

Both are reported, and no code fix is offered.

### RH2001-005 — The fix is withheld for accessors a field cannot express

The code fix MUST NOT be offered for a property with an `init` accessor or with an accessor that carries a modifier, such as `readonly get`. The diagnostic is still reported.

Why: A `readonly` field cannot be set in an object initializer, as an `init` accessor can, and a field has no accessor to carry a modifier, so the field would not preserve what the property allows.

Example:

```csharp
struct S
{
    private int {|RH2001:Id|} { get; init; }

    private int {|RH2001:Value|} { readonly get; set; }
}
```

is reported, and no code fix is offered.

### RH2001-006 — The fix is withheld when the field name is taken

The code fix MUST NOT be offered when another member of the containing type already has the name the field would get. The diagnostic is still reported.

Why: Two members of one type cannot share a name; the collision can only be resolved by the author.

Example:

```csharp
class C
{
    private readonly int _value;

    private int {|RH2001:Value|} { get; }
}
```

is reported, and no code fix is offered.

### RH2001-007 — The fix is withheld for a comment or directive inside the property

The code fix MUST NOT be offered for a property with a comment or a directive in any of these places:

- in front of its name, on a line below the line of its type;
- between the name and the opening brace of the accessor list;
- inside the accessor list;
- between the closing brace of the accessor list and the `=` of the initializer;
- in front of the `;` that ends a declaration with an initializer, on a line below the initializer's last line.

A directive includes an `#if` block and the code it excludes. The diagnostic is still reported.

A comment in front of the property's first token and a comment behind its last token, such as `// counter` in RH2001-004, do not withhold the fix, and neither does a line break alone in front of the name or the `;`. A directive in front of the type and a directive inside the initializer behind its `=` are not covered by this requirement. A comment that the field would carry inside its declaration — in front of the type, behind the type on the type's line, such as `private int /* note */ Value`, behind the initializer's `=`, on a line of its own in front of the initializer's value, or behind the value's last token on that token's line, such as `= 5 /* five */;` — withholds the fix as well, because the formatter refuses the field the fix builds (FMT-UNSUP-004, SHARED-FIX-010). A comment inside the initializer's value, between its first and its last token, does not withhold the fix.

Why: A field has no accessor list, so a comment or directive that stands with an accessor or with the accessor list has no place in the field; dropping or moving it is what SHARED-FIX-003 forbids. A directive in the accessor list can also exclude an accessor in one configuration, so the field could not express what the property is in every build. A comment or directive on a line of its own in front of the name or the `;` stands with the property's name or with the end of its declaration; which part of the field it should stand with is the author's decision, and one rule for every such line keeps the fix simple.

Example — comments behind the name and inside the accessor list:

```csharp
class C
{
    private int {|RH2001:Value|} /* name */ { get; /* inner */ set; } // trailing
}
```

is reported, and no code fix is offered.

Example — a comment between the accessor list and the initializer:

```csharp
class C
{
    private int {|RH2001:Value|} { get; set; } /* init */ = 5;
}
```

is reported, and no code fix is offered.

Example — a comment line in a multi-line accessor list:

```csharp
class C
{
    private int {|RH2001:Value|}
    {
        // the getter
        get;
        set;
    }
}
```

is reported, and no code fix is offered.

Example — a directive inside the accessor list:

```csharp
class C
{
    private int {|RH2001:Value|}
    {
        get;
#if DEBUG
        set;
#endif
    }
}
```

is reported, and no code fix is offered.

Example — a comment line, a directive line, and an `#if` block in front of the name:

```csharp
class C
{
    private int
        // note
        {|RH2001:First|} { get; set; }

    private int
#pragma warning disable CS0169
        {|RH2001:Second|} { get; set; }

    private int
#if NEVER
        unused
#endif
        {|RH2001:Third|} { get; set; }
}
```

All three are reported, and no code fix is offered.

Example — a comment line and a directive line in front of the `;` behind the initializer:

```csharp
class C
{
    private int {|RH2001:First|} { get; set; } = 5
        // note
        ;

    private int {|RH2001:Second|} { get; set; } = 5
#pragma warning disable CS0169
        ;
}
```

Both are reported, and no code fix is offered.

Example — the `;` on a line below the initializer, with no comment or directive in front of it:

```csharp
class C
{
    private int {|RH2001:Value|} { get; set; } = 5
        ;
}
```

```csharp
class C
{
    private int _value = 5;
}
```

### RH2001-008 — The fix is withheld for a property of a struct type not declared `readonly`

The code fix MUST NOT be offered for a property whose type is a struct that is not declared `readonly`, or a type parameter that is not constrained to a reference type, whether the property has a `set` accessor or is get-only, and whether or not any reference to the property changes its value. The diagnostic is still reported.

A struct counts as declared `readonly` when its declaration carries the `readonly` modifier: in source, or in the metadata of the assembly the compilation references for it. The same property can therefore keep or lose the fix depending on the framework the project targets: `int`, `bool`, `DateTime`, and `Guid` are declared `readonly` in the reference assemblies of current .NET, and are not in .NET Standard 2.0 or .NET Framework. `Nullable<T>` counts as declared `readonly` when its `T` is an enum or a struct declared `readonly`, and as not declared `readonly` otherwise. An enum is not a struct in the sense of this requirement and keeps the fix (RH2001-004).

Why: Through the property, every use works on a copy of the value; through a field, it works on the field itself. A member of a struct that is not declared `readonly` may change the value in place, whether the code calls it, such as `Current.Increment()`, or a language construct calls it, such as `foreach` with a struct enumerator or `+=` on an event, so the fix would change what the program does at run time (SHARED-FIX-003). Whether any use does so would need an analysis of every construct that calls a member implicitly; one check of the type is simple and never offers an unsafe fix. No member of `Nullable<T>` changes its value in place, so its own declaration does not decide; its `T` does. A get-only property becomes a `readonly` field, and inside a constructor a call on that field runs on the field itself, where through the property it ran on a copy. A type parameter that is not constrained to a reference type can stand for such a struct.

Example — a call that changes the value:

```csharp
struct Counter
{
    private int _count;

    public void Increment()
    {
        _count++;
    }
}

class C
{
    private Counter {|RH2001:Current|} { get; set; }

    void M()
    {
        Current.Increment();
    }
}
```

is reported, and no code fix is offered.

Example — no use changes the value, and the struct is still not declared `readonly`:

```csharp
struct Point
{
    public int X;
}

class C
{
    private Point {|RH2001:Origin|} { get; set; }

    private Point? {|RH2001:Last|} { get; set; }

    int Read() => Origin.X;
}
```

Both are reported, and no code fix is offered.

Example — in a project that targets .NET Standard 2.0, whose `int` is not declared `readonly`:

```csharp
class C
{
    private int {|RH2001:Count|} { get; set; }

    private int? {|RH2001:Cache|} { get; set; }

    void M() => Count++;
}
```

Both are reported, and no code fix is offered. In a project that targets .NET 9, the fix is offered for both, as RH2001-004 states.

Example — a get-only property, whose value a constructor changes through a call:

```csharp
struct Counter
{
    private int _count;

    public void Increment()
    {
        _count++;
    }
}

class C
{
    private Counter {|RH2001:Current|} { get; }

    C()
    {
        Current.Increment();
    }
}
```

is reported, and no code fix is offered.

Example — properties typed by type parameters; only the one constrained to a reference type gets the fix:

```csharp
class C<T, TRef>
    where TRef : class
{
    private T {|RH2001:Item|} { get; set; }

    private TRef {|RH2001:Reference|} { get; set; }

    TRef Read() => Item == null ? Reference : null;
}
```

```csharp
class C<T, TRef>
    where TRef : class
{
    private T Item { get; set; }

    private TRef _reference;

    TRef Read() => Item == null ? _reference : null;
}
```

`Item` is still reported, and no code fix is offered for it.

### RH2001-009 — The fix is withheld for a comment among the modifiers, a directive that a reordered modifier would cross, or a conditional directive between the modifiers

The code fix MUST NOT be offered when a comment stands between two modifiers or between the last modifier and the type — on a modifier's line or on a line of its own — whether or not the fix writes the modifiers in a new order: the field the fix builds holds the comment, and the formatter refuses that field (FMT-UNSUP-004, SHARED-FIX-010). The diagnostic is still reported.

The code fix MUST NOT be offered either when it writes the modifiers in a new order (RH2001-004) and a directive stands between two modifiers that the new order puts the other way round — on a modifier's line or on a line of its own. A directive other than `#if`, `#elif`, `#else`, and `#endif` between two modifiers that keep their order — every modifier written in front of it stays in front of it, and every modifier written behind it stays behind it — does not withhold the fix, and it keeps its place between them. The same holds when the fix keeps the written order and only adds `readonly`.

The code fix MUST NOT be offered either when an `#if`, `#elif`, `#else`, or `#endif` directive stands in the leading trivia of a modifier other than the first, or in the leading trivia of the type: between two modifiers, between the last modifier and the type, or, when the property has no modifier, in front of its type, also on the lines above the property. This holds whatever the branches of its group hold, also when a group holds only whole members, when the modifiers keep their order, and when the fix adds no `readonly`. The diagnostic is still reported. A conditional directive in front of the first modifier of a property that has a modifier is not covered by this requirement; RH2001-010 states when it withholds the fix, and RH2001-004 states the fix for the directives on the lines above such a property otherwise.

This requirement covers a property whose comments and directives between the modifiers, and comments between its last modifier and its type, are its only ones inside its declaration, apart from those RH2001-004 covers.

Why: The fix changes the order of the modifiers to add `readonly` where RH7105 expects it. A directive between the modifiers governs the keywords behind it, so moving a keyword across it changes which code it governs (SHARED-FIX-003). Where the directive should go then is the author's decision. A comment among the modifiers would stay in the field the fix builds, where the formatter does not support it, so the fix that formats the field is withheld for every such comment, also for one no keyword crosses; the fix needs no check of its own for which comments a reordered keyword would cross. A conditional directive between the modifiers makes them depend on the build: a modifier in a branch exists only in the builds that compile it, so which modifiers the field carries in each build, whether a field can carry them at all — `extern` cannot, and a second `readonly` is an error — and where `readonly` belongs among them would have to be worked out for each build, which no fix does (SHARED-FIX-009). Withholding the fix for every such directive is one check of where the directive stands, reads no excluded code, and leaves the rare shape to the author.

Example — a comment among the modifiers or in front of the type, whether a reordered modifier would cross it or not:

```csharp
class C
{
    static /* a */ private int {|RH2001:First|} { get; }

    static // b
    private int {|RH2001:Second|} { get; }

    private /* c */ static int {|RH2001:Third|} { get; }

    private static /* d */ int {|RH2001:Fourth|} { get; }
}
```

All four are reported, and no code fix is offered.

Example — a directive that a reordered modifier would cross:

```csharp
class C
{
    static
#pragma warning disable CS0169
    private int {|RH2001:Value|} { get; }
}
```

is reported, and no code fix is offered.

Example — a conditional directive between the modifiers:

```csharp
public class C
{
    private
#if DEBUG
        static
#endif
        int {|RH2001:First|} { get; }

    private
#if DEBUG
        static
#endif
        int {|RH2001:Second|} { get; set; }

    private
#if DEBUG
        new
#endif
        int {|RH2001:Third|} { get; }

    private
#if DEBUG
        extern
#endif
        int {|RH2001:Fourth|} { get; }
}

public struct S
{
    private
#if DEBUG
        readonly
#endif
        int {|RH2001:Fifth|} { get; }
}
```

All five are reported, and no code fix is offered: in a build with `DEBUG`, `Fourth` would become an `extern` field and `Fifth` a field with `readonly` twice, and the fix withholds itself for `First`, `Second`, and `Third` as well, although a field would be valid in every build.

For a property without a modifier, the type is its first token, and a conditional directive in front of it withholds the fix, also when the group above holds a whole member:

```csharp
class C
{
#if DEBUG
    extern
#endif
    int {|RH2001:First|} { get; }

#if DEBUG
    private int _trace;
#endif
    int {|RH2001:Second|} { get; }
}
```

Both are reported, and no code fix is offered: in a build with `DEBUG`, `First` would become an `extern` field.

A conditional directive on the lines above a property that has a modifier stands in front of its first modifier, not between its modifiers; when its group holds whole members, the fix is offered, as RH2001-004 states for the directives on the lines above (RH2001-010):

```csharp
class C
{
#if DEBUG
    private int _trace;
#endif
    static private int {|RH2001:Value|} { get; }
}
```

```csharp
class C
{
#if DEBUG
    private int _trace;
#endif
    private static readonly int _value;
}
```

### RH2001-010 — The fix is withheld for a conditional group in front of the first modifier or behind the property that does not wrap whole members

The code fix MUST NOT be offered for a property that has a modifier when a directive of a conditional group — an `#if` together with its `#elif` and `#else` directives and its `#endif` — stands in the leading trivia of the property's first modifier, and the group does not wrap whole members. It MUST NOT be offered either for a property without an initializer, with or without a modifier, when a directive of a conditional group stands in the leading trivia of the token behind the property's last token — the first token of the next member, or the closing brace of the type body — and the group does not wrap whole members. The group wraps whole members when both of these hold:

- **No group inside it.** No other conditional group lies inside one of its branches.
- **Whole members in every excluded branch.** The text of each branch the analyzed build excludes, parsed on its own as the content of a type body, reads as a sequence of whole member declarations without a syntax error. A branch that holds nothing but whitespace, comments, or `#region` and `#endregion` lines is a sequence of no members.

This holds for every excluded branch of the group, also for one that stands in front of another member, as in the third example below, where the excluded `#if` branch stands in front of the member that the active `#else` branch holds and only the `#endif` stands in the leading trivia of the property's first modifier. A branch that holds a modifier, an attribute list, an initializer, or text that is not code does not read as whole members. The active branch is not parsed: a modifier in the active branch of a group in front of the first modifier is itself the first modifier, and the group's next directive stands between two modifiers, which RH2001-009 covers; the active branch of a group behind the property is compiled with the property in the analyzed build, so the diagnostic and the fix already see it. The diagnostic is still reported.

A group that lies inside a branch of another group is decided by its own branches, like any other group: lying inside another group does not withhold the fix. The other group is read only when one of its own directives stands in front of the first modifier or behind the property, and then the group inside its branch withholds the fix by the first condition. A file, or a part of a type body, wrapped in `#if` around a group of whole members in front of the property therefore keeps the fix, while a group whose `#endif` stands behind the property and whose branch holds another group withholds it.

A group in front of the first modifier or behind the property that wraps whole members does not withhold the fix, and RH2001-004 states the fix for it. A property without a modifier is covered by RH2001-009 for a group in front of it, whatever the group holds. A property with an initializer ends in `;`, and a directive behind it does not withhold the fix by this requirement, whatever its group holds; a directive of the same group in front of the first modifier is decided as stated above.

The fix decides this from where the directives stand and from one parse of each excluded branch, and by nothing else (SHARED-FIX-009): it evaluates no condition and combines no branches.

Why: An excluded branch next to the property is compiled together with the declaration in the builds that include it. A branch that holds whole members adds or removes members and changes nothing of the property, so the field the fix writes is valid in every build. A branch that holds a modifier or an attribute list in front of the first modifier becomes part of the declaration in those builds, and the field the fix writes would carry it there: `extern` on a field and a second `readonly` are compile errors, and an attribute may not apply to a field (SHARED-FIX-003, *Build configurations*). A branch behind a property without an initializer can give it one, such as `= 5;`, and behind the field the fix writes, which ends in `;`, that initializer is a syntax error. A group with another group inside a branch splits that branch into several pieces of excluded text and directives, which one parse of the branch does not read; a group inside the active branch of another group is read whole, because every excluded branch of it lies inside that active branch, and an excluded branch of the other group stands next to the property only through a directive that is itself read. Working out what each build's declaration holds means combining branches, which no fix does (SHARED-FIX-009); one parse of each excluded branch tells whole members from everything else, and a branch it cannot classify withholds the fix, which can only withhold.

Example — a modifier in an excluded branch in front of the first modifier, in a class and in a struct. Without `DEBUG` defined,

```csharp
class C
{
#if DEBUG
    extern
#endif
    private int {|RH2001:Value|} { get; }

    int Read() => Value;
}

struct S
{
#if DEBUG
    readonly
#endif
    private int {|RH2001:Value|} { get; }

    int Read() => Value;
}
```

Both are reported, and no code fix is offered: in a build with `DEBUG`, the field of `C` would be `extern`, and the field of `S` would carry `readonly` twice.

Example — the excluded branch is the `#else` branch behind a group of a whole member. Without `DEBUG` defined,

```csharp
class C
{
#if !DEBUG
    private int _trace;
#else
    extern
#endif
    private int {|RH2001:Value|} { get; }

    int Read() => Value;
}
```

is reported, and no code fix is offered.

Example — the excluded branch stands in front of the member of the active `#else` branch, and only the `#endif` stands in front of the first modifier. Without `DEBUG` defined,

```csharp
class C
{
#if DEBUG
    extern
#else
    private int _trace;
#endif
    private int {|RH2001:Value|} { get; }

    int Read() => Value;
}
```

is reported, and no code fix is offered: in a build with `DEBUG`, `extern` stands in front of the property.

Example — an attribute list in an excluded branch. Without `DEBUG` defined,

```csharp
class C
{
#if DEBUG
    [System.Obsolete]
#endif
    private int {|RH2001:Value|} { get; }

    int Read() => Value;
}
```

is reported, and no code fix is offered: the branch is no whole member, and the fix does not work out whether the attribute applies to a field.

Example — a group of a whole member in front of the first modifier keeps the fix. Without `DEBUG` defined,

```csharp
class C
{
#if DEBUG
    private int _trace;
#endif
    private int {|RH2001:Value|} { get; }

    int Read() => Value;
}
```

```csharp
class C
{
#if DEBUG
    private int _trace;
#endif
    private readonly int _value;

    int Read() => _value;
}
```

Example — an initializer in an excluded branch behind a property without one. Without `X` defined,

```csharp
class C
{
    private int {|RH2001:Value|} { get; }
#if X
    = 5;
#endif

    int Read() => Value;
}
```

is reported, and no code fix is offered: in a build with `X`, the property is `private int Value { get; } = 5;`, and the field the fix would write, `private readonly int _value;`, would be followed by `= 5;`.

Example — a group of a whole member behind a property without an initializer keeps the fix. Without `DEBUG` defined,

```csharp
class C
{
    private int {|RH2001:Value|} { get; }
#if DEBUG
    private int _trace;
#endif

    int Read() => Value;
}
```

```csharp
class C
{
    private readonly int _value;
#if DEBUG
    private int _trace;
#endif

    int Read() => _value;
}
```

Example — a group behind a property with an initializer keeps the fix, whatever it holds. Without `DEBUG` defined,

```csharp
class C
{
    private int {|RH2001:Value|} { get; } = 5;
#if DEBUG
    static
#endif
    private int _other;

    int Read() => Value;
}
```

```csharp
class C
{
    private readonly int _value = 5;
#if DEBUG
    static
#endif
    private int _other;

    int Read() => _value;
}
```

In a build with `DEBUG`, `static` belongs to `_other`, behind the field's `;`.

Example — a group of a whole member in front of the first modifier, inside the active branch of a group that wraps the file, keeps the fix, as in multi-targeting code. With `NET` defined and `DEBUG` not defined,

```csharp
#define NET
#if NET
class C
{
#if DEBUG
    private int _trace;
#endif
    private int {|RH2001:Value|} { get; }

    int Read() => Value;
}
#endif
```

```csharp
#define NET
#if NET
class C
{
#if DEBUG
    private int _trace;
#endif
    private readonly int _value;

    int Read() => _value;
}
#endif
```

The group `#if NET` has no directive in front of the first modifier or behind the property, so it is not read; the group `#if DEBUG` lies inside its active branch and holds a whole member.

Example — a group whose `#endif` stands behind the property and whose branch holds another group. Without `RELEASE` defined and without `DEBUG` defined,

```csharp
class C
{
#if !RELEASE
    private int _first;
#if DEBUG
    private int _trace;
#endif
    private int {|RH2001:Value|} { get; }
#endif

    int Read() => Value;
}
```

is reported, and no code fix is offered: the group `#if DEBUG` in front of the first modifier holds a whole member, but the `#endif` of the group `#if !RELEASE` stands in front of `int Read`, the token behind the property, and that group holds the group `#if DEBUG`. The same holds for a group in front of the first modifier that holds another group, such as `#if DEBUG` around `#if TRACE` … `#endif` around `private int _trace;`.
