# Analyzer — RH2008 Methods should not exceed the line limit

| | |
|---|---|
| ID prefix | RH2008 |
| Status | Active |
| Category | Design |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | None |
| Code owners | `RH2008MethodsShouldNotExceedTheLineLimitAnalyzer` |
| Uses | RH0001-001, RH0001-007, SHARED-DIAG-007, SHARED-DIAG-012, SHARED-LINES-001, SHARED-LINES-002, SHARED-LINES-003 |

RH2008 reports a method, or another member with a body of statements or an expression, whose body holds more lines of code than its limit allows: 60 lines in production code and 100 in test code, unless the `design` section of the `reihitsu.json` configuration file sets other limits.

The examples are production code (SHARED-LINES-003) unless they say otherwise.

## Non-goals

- Loading and validating the configuration file and the `design` section — RH0001 (RH0001-007).
- Telling test code from production code — SHARED-LINES-003.
- The size of a type — RH2111.
- Lambda expressions and anonymous methods judged on their own, also a lambda in a field or property initializer; their lines count toward the member that holds them (RH2008-003), and toward the type that holds the initializer (RH2111).
- Top-level statements, which declare no method in the source.
- A field, property, or event initializer, and a constructor initializer (`: base(…)`, `: this(…)`), which are not part of a body.

## Requirements

### RH2008-001 — The limits are `design.maximumMethodLines` and `design.maximumTestMethodLines`

The analyzer MUST take the limit of a member in production code from the setting `design.maximumMethodLines`, with the default 60, and the limit of a member in test code (SHARED-LINES-003) from the setting `design.maximumTestMethodLines`, with the default 100, of the configuration that RH0001-001 loads, valid as RH0001-007 specifies, and MUST compare each judged member with its limit as SHARED-LINES-002 specifies.

Why: Most methods stay far below 60 lines of code, so a longer one stands out; test methods arrange inputs and expected results in their bodies and run longer, so their default is higher. A project that wants other limits sets them; RH0001 validates the settings, and SHARED-LINES-002 states when a default applies and how the count is compared.

Example — without a `reihitsu.json`, a member whose body holds 60 lines of code is not reported and one whose body holds 61 is, "This member has 61 lines of code, which exceeds the limit of 60.", in production code; in test code (SHARED-LINES-003), a member with 100 lines of code is not reported and one with 101 is, "This member has 101 lines of code, which exceeds the limit of 100.". With `{ "design": { "maximumMethodLines": 40 } }` alone, a test method with 70 lines of code is not reported: the test limit stays 100. With `{ "design": { "maximumMethodLines": "40" } }`, which RH0001 reports, a production method with 70 lines of code is reported against the default of 60. SHARED-LINES-002 and SHARED-LINES-003 give the examples at a configured limit.

### RH2008-002 — A member with a body is judged by the lines of its body

The analyzer MUST judge every method, constructor, finalizer, operator, conversion operator, local function, and accessor (`get`, `set`, `init`, `add`, `remove`) that has a block body or an expression body, and every property and indexer that has an expression body instead of an accessor list. It MUST count the lines of code (SHARED-LINES-001) of the body: for a block body, the tokens between its opening and its closing brace; for an expression body, the `=>` and the tokens of the expression. The declaration's attributes, modifiers, return type, name, type parameters, parameter list, constraint clauses, constructor initializer, the braces of a block body, and the `;` behind an expression body MUST NOT be counted.

Why: The body is what a reader works through to understand what the member does; the signature is read at a glance and does not grow with the work the member does. An accessor, an operator, and a constructor are methods under another syntax, so a long one is as hard to follow as a long method; a property or indexer with an expression body is a `get` accessor written without the keyword. The braces only delimit the body; counting them would give every block body two lines that an expression body does not have.

Example — with `{ "design": { "maximumMethodLines": 2 } }`; each reported member holds three lines of code, and `Short` holds two, the line of its `=>` and the line of its expression:

```csharp
class C
{
    private int _value;

    public {|RH2008:C|}()
    {
        _value = 1;
        _value = 2;
        _value = 3;
    }

    public int {|RH2008:Sum|} => _value
                         + _value
                         + _value;

    public int Short
        => _value
           + _value;

    public int Value
    {
        {|RH2008:get|}
        {
            var result = _value;
            result += _value;
            return result;
        }
    }

    public static C operator {|RH2008:+|}(C left, C right)
    {
        left._value += right._value;
        left._value += right._value;
        return left;
    }
}
```

Example — `M` holds two lines of code; its attributes, its parameter list over three lines, and its braces are not counted:

```csharp
class C
{
    [System.Obsolete]
    void M(
        int first,
        int second)
    {
        M(first,
          second);
    }
}
```

is not reported with `{ "design": { "maximumMethodLines": 2 } }`.

### RH2008-003 — Nested functions count toward the member that holds them

The lines of code of a local function, a lambda expression, or an anonymous method inside a body MUST count toward that body. A local function MUST in addition be judged on its own by the lines of its own body.

Why: A reader of the member reads the functions declared inside it; moving code into a local function or a lambda keeps the member exactly as long as it was. A local function is still a method with a name of its own, so its own size is judged too.

Example — with `{ "design": { "maximumMethodLines": 3 } }`; `M` holds ten lines of code, the braces of the lambda and of the local function included, since they are tokens of its body; its local function `Local` holds three and is not reported, and its lambda is not judged on its own:

```csharp
class C
{
    void {|RH2008:M|}()
    {
        System.Action action = () =>
        {
            Local();
        };

        void Local()
        {
            M();
            M();
            M();
        }
    }
}
```

With `{ "design": { "maximumMethodLines": 2 } }`, `Local` is reported as well.

Example — a lambda outside every judged body, such as in a field initializer, is not judged; with `{ "design": { "maximumMethodLines": 2 } }`

```csharp
using System;

class C
{
    private static readonly Func<int, int> Compute = value =>
    {
        var result = value;
        result += 1;
        return result;
    };
}
```

is not reported by RH2008; its lines count toward the body of `C` for RH2111.

### RH2008-004 — A member without a body is not reported

The analyzer MUST NOT report a member that has neither a block body nor an expression body: an abstract or `extern` member, an interface member without a default implementation, the defining part of a partial method or partial property, and an accessor written as `get;`, `set;`, `init;`, or `add;`/`remove;` without a body. A property or indexer with an accessor list is not judged itself; each of its accessors is judged on its own. A partial member is judged by the part that holds its body, and its one diagnostic stands on that part, the only part the rule would report on its own (SHARED-DIAG-012).

Why: Without a body there are no lines to count. The accessors of a property are separate bodies, each read on its own, so they are judged one by one and not summed; the part of a partial member that has a body is the only part that holds code.

Example — with `{ "design": { "maximumMethodLines": 1 } }`:

```csharp
abstract partial class C
{
    public abstract void A();

    public int P { get; set; }

    public partial void M();

    public partial void {|RH2008:M|}()
    {
        A();
        A();
    }
}
```

Example — with `{ "design": { "maximumMethodLines": 4 } }`, each accessor of `Value` holds three lines of code, and the property, whose accessors hold six together, is not judged:

```csharp
class C
{
    private int _value;

    public int Value
    {
        get
        {
            var result = _value;
            result += 1;
            return result;
        }
        set
        {
            var input = value;
            input -= 1;
            _value = input;
        }
    }
}
```

is not reported.

### RH2008-005 — One diagnostic per member, located on its name

The analyzer MUST report one diagnostic for each judged member whose count exceeds the limit, located on the member's identifier for a method, constructor, finalizer, local function, and property; on the `this` keyword for an indexer; on the operator token for an operator, such as `+` or `==`; on the `operator` keyword for a conversion operator; and on the keyword of an accessor. A member that holds a reported local function and is itself over the limit is reported as well, on its own identifier.

Why: The name is where a reader looks for the member and where a suppression is placed; a member without an identifier is marked by the token that names it in its declaration (SHARED-DIAG-007).

Example — with `{ "design": { "maximumMethodLines": 1 } }`:

```csharp
class C
{
    private int _value;

    ~{|RH2008:C|}()
    {
        _value = 0;
        _value = 1;
    }

    public int {|RH2008:this|}[int index] => index
                                    + _value;

    public static explicit {|RH2008:operator|} int(C value)
    {
        var result = value._value;
        return result;
    }
}
```
