# Analyzer — RH5101 The first argument should be on the same line as the opening parenthesis

| | |
|---|---|
| ID prefix | RH5101 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5101FirstArgumentShouldBeOnSameLineAnalyzer`, `RH5101FirstArgumentShouldBeOnSameLineCodeFixProvider` |
| Uses | FMT-BREAK-001, FMT-BREAK-012 |

RH5101 reports an argument list whose first argument starts on a line below the opening parenthesis, and offers a code fix that lays the argument list out the way the formatter does.

## Non-goals

- Whether the remaining arguments share a line — RH5102; their column — RH5203.
- The first parameter of a parameter list — RH5108.
- Bracketed argument lists (`m[…]`) and attribute argument lists.

## Requirements

### RH5101-001 — A first argument below the opening parenthesis is reported

The analyzer MUST report a parenthesized argument list — of an invocation, an object creation, an implicit object creation, a constructor initializer, or a primary constructor's base type — whose first argument starts on a later line than the opening parenthesis. An argument list without arguments, and a first argument that starts on the line of the opening parenthesis, MUST NOT be reported.

Why: The first argument on the line of the opening parenthesis keeps the call and what it receives together, and the remaining arguments can align under it. The formatter lays out a wrapped list the same way (FMT-BREAK-012).

Example:

```csharp
class B
{
    public B(params int[] values)
    {
    }
}

class C : B
{
    public C()
        : base(
            {|RH5101:1|})
    {
        M(
            {|RH5101:1|},
            2);
        _ = new B(
            {|RH5101:1|});
        B b = new(
            {|RH5101:1|});
        M(1,
          2);
        M();
    }

    void M(params int[] values)
    {
    }
}

class D(int a) : B(
    {|RH5101:a|})
{
}
```

### RH5101-002 — A comment or directive before the first argument suppresses the diagnostic

The analyzer MUST NOT report the argument list when a comment, a preprocessor directive, or disabled text sits between the opening parenthesis and the first argument.

Why: The first argument cannot join the opening line without moving the comment or the directive, which the formatter refuses as well (FMT-BREAK-001). A diagnostic that no layout can clear would stay for good.

Example:

```csharp
class C
{
    void N()
    {
        M( // first
            1,
            2);
        M(
#if DEBUG
            1,
#endif
            2);
    }

    void M(params int[] values)
    {
    }
}
```

is not reported.

### RH5101-003 — The diagnostic is on the first argument

The analyzer MUST report one diagnostic per argument list, located on its first argument.

Why: The first argument is what has to move; its location stays stable while the arguments after it change.

Example: see RH5101-001.

### RH5101-004 — The fix lays out the argument list

The code fix MUST format the argument list as the formatter formats it in place (FMT-BREAK-012), which moves the first argument onto the line of the opening parenthesis and aligns the following arguments under it.

Why: The formatter owns the layout of a wrapped argument list; delegating to it keeps the fixed code identical to formatted code.

Example:

```csharp
class C
{
    void N()
    {
        M(
            {|RH5101:1|},
            2);
    }

    void M(params int[] values)
    {
    }
}
```

```csharp
class C
{
    void N()
    {
        M(1,
          2);
    }

    void M(params int[] values)
    {
    }
}
```

### RH5101-005 — A comment or directive in the argument list withholds the fix

The code fix MUST NOT be offered when a comment or a preprocessor directive sits in front of the opening parenthesis or anywhere inside the argument list, a documentation comment included. A comment behind the closing parenthesis MUST NOT withhold the fix. The diagnostic is still reported.

Why: The formatter would have to move a comment or directive to rejoin the list. A comment behind the closing parenthesis stays where it is when the list is laid out, so it does not get in the way.

Example:

```csharp
class C
{
    int N()
    {
        M(
            {|RH5101:1|}, // first
            2);

        return M
            /* note */ (
            {|RH5101:1|},
            2);
    }

    int M(params int[] values) => 0;
}
```

is reported, and no code fix is offered. In

```csharp
class C
{
    void N()
    {
        M(
            {|RH5101:1|},
            2); // note
    }

    void M(params int[] values)
    {
    }
}
```

the comment follows the closing parenthesis, and the fix is offered.
