# Analyzer — RH7004 Using declarations should not be used

| | |
|---|---|
| ID prefix | RH7004 |
| Status | Active |
| Category | Organization |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH7004UsingDeclarationsShouldNotBeUsedAnalyzer`, `RH7004UsingDeclarationsShouldNotBeUsedCodeFixProvider` |
| Uses | RH3004-006, SHARED-FIX-003, SHARED-FIX-007, SHARED-FIX-008 |

RH7004 reports a `using` local declaration, and offers a code fix that turns it into a `using` statement whose block holds the statements that followed the declaration.

## Non-goals

- `using` statements, `using` directives, and `using static` directives — they are not using declarations.
- How small the block of the `using` statement should be. The fix moves every following statement of the block into it; narrowing the block is the author's decision.

## Requirements

### RH7004-001 — A using declaration is reported

The analyzer MUST report every local declaration that starts with the `using` keyword, with or without `await`, whether it declares its variables with `var` or with an explicit type, wherever the declaration stands — in a method, accessor, lambda, or local function body, in a nested block, or as a top-level statement.

Why: A using declaration disposes its resource at the end of the enclosing scope, which the reader has to find by looking for the closing brace. A `using` statement makes the statements that run while the resource is alive visible as one block.

Example:

```csharp
using System;
using System.IO;
using System.Threading.Tasks;

class C
{
    async Task M(IAsyncDisposable resource)
    {
        {|RH7004:using|} var stream = new MemoryStream();
        {|RH7004:using|} MemoryStream first = new MemoryStream(), second = new MemoryStream();
        await {|RH7004:using|} var handle = resource;

        Action action = () =>
        {
            {|RH7004:using|} var inner = new MemoryStream();
        };
    }
}
```

### RH7004-002 — A using statement is not reported

The analyzer MUST NOT report a `using` statement, with or without `await`.

Why: A `using` statement already states the lifetime of its resource as a block.

Example:

```csharp
using System.IO;

class C
{
    void M()
    {
        using (var stream = new MemoryStream())
        {
            stream.Flush();
        }
    }
}
```

is not reported.

### RH7004-003 — The diagnostic is on the `using` keyword

The analyzer MUST report one diagnostic per using declaration, located on its `using` keyword; for an `await using` declaration the diagnostic does not include `await`.

Why: The `using` keyword is what turns the local declaration into a using declaration, and one diagnostic per declaration keeps Fix All one action per declaration.

Example: see RH7004-001.

### RH7004-004 — The fix wraps the following statements into a using statement

The code fix MUST replace the using declaration with a `using` statement that declares the same variables with the same type and initializers, keeps `await` when the declaration had it, and whose block holds every statement that followed the declaration in the same block, in their order. When no statement follows the declaration, the block is empty. A comment behind the declaration at the end of its line MUST stay behind the header of the `using` statement, on the header's line.

Why: The resource of a using declaration lives until the end of its block, so a `using` statement over exactly the following statements disposes it at the same point and keeps every variable those statements use in scope. A comment behind the declaration describes the resource, and the header is the code the declaration is rewritten into; behind the new block's closing brace, it would describe the end of the block instead (SHARED-FIX-003).

Example:

```csharp
using System.IO;

class C
{
    void M()
    {
        {|RH7004:using|} var stream = new MemoryStream();
        stream.Flush();
    }
}
```

```csharp
using System.IO;

class C
{
    void M()
    {
        using (var stream = new MemoryStream())
        {
            stream.Flush();
        }
    }
}
```

With `await`, several declarators, and no following statement:

```csharp
using System;
using System.IO;

class C
{
    async System.Threading.Tasks.Task M(IAsyncDisposable resource)
    {
        await {|RH7004:using|} var handle = resource;
    }

    void N()
    {
        {|RH7004:using|} MemoryStream first = new MemoryStream(), second = new MemoryStream();
    }
}
```

```csharp
using System;
using System.IO;

class C
{
    async System.Threading.Tasks.Task M(IAsyncDisposable resource)
    {
        await using (var handle = resource)
        {
        }
    }

    void N()
    {
        using (MemoryStream first = new MemoryStream(), second = new MemoryStream())
        {
        }
    }
}
```

A comment behind the declaration stays on the header's line:

```csharp
using System.IO;

class C
{
    void M()
    {
        {|RH7004:using|} var s = new MemoryStream(); // resource
        s.Flush();
    }
}
```

```csharp
using System.IO;

class C
{
    void M()
    {
        using (var s = new MemoryStream()) // resource
        {
            s.Flush();
        }
    }
}
```

### RH7004-005 — The fix is withheld outside a block

The code fix MUST NOT be offered for a using declaration that is not a statement of a block, such as a top-level statement. The diagnostic is still reported.

Why: The fix closes the new `using` statement where the enclosing block ends. Top-level statements have no enclosing block whose end the fix could use, and a file with top-level statements may also declare types after them, which a block cannot hold.

Example:

```csharp
using System.IO;

{|RH7004:using|} var stream = new MemoryStream();
stream.Flush();
```

is reported, and no code fix is offered.

### RH7004-006 — The fix is withheld when a later statement of the block is a local function or label

The code fix MUST NOT be offered when any statement of the same block after the using declaration — not only the next one — is a local function declaration or a labeled statement. The diagnostic is still reported. A local function or label nested inside one of those statements, such as in the body of an `if`, does not withhold the fix.

Why: The fix moves the following statements into the new block, where the statements before the declaration can no longer see them: a call to the local function no longer compiles (CS0103), and neither does a `goto` to the label (CS0159). A local function or label nested inside a following statement was never visible to those statements, so moving it changes nothing.

Example:

```csharp
using System.IO;

class C
{
    void M()
    {
        Helper();
        {|RH7004:using|} var stream = new MemoryStream();
        stream.Flush();

        void Helper()
        {
        }
    }
}
```

is reported, and no code fix is offered. A local function nested in a following statement moves with it:

```csharp
using System.IO;

class C
{
    void M()
    {
        {|RH7004:using|} var stream = new MemoryStream();
        if (stream.CanRead)
        {
            void Helper()
            {
            }
        }
    }
}
```

```csharp
using System.IO;

class C
{
    void M()
    {
        using (var stream = new MemoryStream())
        {
            if (stream.CanRead)
            {
                void Helper()
                {
                }
            }
        }
    }
}
```

### RH7004-007 — The fix is withheld for lines it cannot change as whole lines

The code fix MUST NOT be offered when the code that would move into the new block — every statement that follows the using declaration in the same block, with its leading trivia — holds a string literal of any kind, regular, verbatim, interpolated, or raw, that spans lines, a comment that spans lines, or disabled text. An interpolated string counts in every `$` form — `$"`, `$@"`, `@$"`, and `$"""` — from its first character through its closing quote, its holes included: it spans lines when any part of it does, also where only a hole spans lines, and also where every later line starts at a hole's `{` or at the closing quote rather than inside the string's text. It MUST NOT be offered either when a line the fix changes has one of these shapes:

- the first of the moved statements starts on the line of the using declaration;
- code stands in front of the using declaration on its line, such as another statement or the opening brace of the block;
- the last of the moved statements ends on the line of the block's closing brace;
- a comment or a directive stands in the leading trivia of the declaration's semicolon;
- the whitespace in front of the first character of the declaration's line, or of a line of the moved statements that moves (SHARED-FIX-007, *Moved code*), holds a tab.

The diagnostic is still reported. A string literal or a comment on one line, a directive, and a comment line in column 0 do not withhold the fix; their lines move as SHARED-FIX-007 (*Moved code*) states. A tab elsewhere — inside a string or a comment, between two tokens of a line, on a blank line, which is written empty, or in front of a line that keeps its column, such as a directive line — does not withhold the fix. The fix writes the line ending SHARED-FIX-008 detects for every line break it creates, and is withheld where the code it moves or rewrites — the using declaration with its trailing line break, and the moved statements — holds a line break other than that line ending, also where the declaration is the last statement of its block and nothing moves (SHARED-FIX-008).

Why: Every line of the moved statements moves one indentation level deeper (SHARED-FIX-007). The whitespace at the start of a line inside a verbatim or interpolated string is part of its value, the lines of a raw string literal are bound to its closing quotes, the later lines of a delimited comment are its text, and disabled text is code the compiler does not read: none of them moves as a plain line without changing content (SHARED-FIX-003) or without a rule of its own. Withholding the fix for strings and comments that span lines is the maintainer's decision; a fix that moves them can follow when it is proportionate. Disabled text after a using declaration is rare. The other four shapes are rare as well, and the layout rules report them on their own, such as RH5103 two statements on one line and RH5113 a semicolon on a line of its own. In the first three, the header, the braces, or the moved statements of the new block would share a line with code the fix does not move, so the fix would have to decide a line break the author did not write, or give the new braces a column that no line's indentation states. In the fourth, the comment or directive would end up in front of the new closing parenthesis, on lines the fix would have to lay out. Each is a cheap check of the lines the fix changes. A tab in front of the declaration or a moved line has no single column count: the new braces would copy it in front of themselves and the moved lines would get spaces in front of it, a layout no rule states; indentation with tabs is reported by RH5601, so the fix is withheld for that class, as RH3004-006 withholds its block-body fix. An interpolated string is several tokens, so a later line of it can start at a token boundary, at a hole or at the closing quote, and still be part of the string's value; deciding on the string as a whole, not on where its lines start, keeps every such line out of the shift. A reported diagnostic without a fix is a supported end state.

Example — a string literal that spans lines:

```csharp
using System.IO;

class C
{
    string M()
    {
        {|RH7004:using|} var s = new MemoryStream();
        var t = """
            a
            """;
        return t;
    }
}
```

is reported, and no code fix is offered. The same holds for a verbatim string over two lines.

Example — an interpolated verbatim string whose second line starts at a hole:

```csharp
using System.IO;

class C
{
    string M(int x)
    {
        {|RH7004:using|} var s = new MemoryStream();
        var t = $@"a
{x}";
        return t;
    }
}
```

is reported, and no code fix is offered: shifting the line `{x}";` would write four spaces into the value of `t`. The same holds where the second line starts at the closing quote, as in `$@"a{x}` followed by a line `";`, and for `@$"`.

Example — an interpolated string whose hole spans lines:

```csharp
using System.IO;

class C
{
    string M(int x)
    {
        {|RH7004:using|} var s = new MemoryStream();
        var t = $"{x
            + 1}";
        return t;
    }
}
```

is reported, and no code fix is offered.

Example — a tab in front of a moved line. The line `s.Flush();` starts with a tab:

```csharp
using System.IO;

class C
{
    void M()
    {
        {|RH7004:using|} var s = new MemoryStream();
	s.Flush();
    }
}
```

is reported, and no code fix is offered. The same holds where the line of the using declaration starts with a tab. A tab between two tokens, such as one between `s.Flush();` and a comment behind it, does not withhold the fix.

Example — a comment that spans lines:

```csharp
using System.IO;

class C
{
    void M()
    {
        {|RH7004:using|} var s = new MemoryStream();
        /* one
           two */
        s.Flush();
    }
}
```

is reported, and no code fix is offered.

Example — disabled text. Without `NEVER` defined,

```csharp
using System.IO;

class C
{
    void M()
    {
        {|RH7004:using|} var s = new MemoryStream();
#if NEVER
        s.Close();
#endif
        s.Flush();
    }
}
```

is reported, and no code fix is offered.

Example — a statement on the line of the declaration:

```csharp
using System.IO;

class C
{
    void M()
    {
        {|RH7004:using|} var s = new MemoryStream(); s.Flush();
        s.Flush();
    }
}
```

is reported, and no code fix is offered.

Example — code in front of the declaration on its line:

```csharp
using System.IO;

class C
{
    void M()
    {
        int a = 0; {|RH7004:using|} var s = new MemoryStream();
        s.Flush();
    }
}
```

is reported, and no code fix is offered.

Example — the last statement shares its line with the block's closing brace:

```csharp
using System.IO;

class C
{
    void M()
    {
        {|RH7004:using|} var s = new MemoryStream();
        s.Flush(); }
}
```

is reported, and no code fix is offered.

Example — a comment in front of the semicolon:

```csharp
using System.IO;

class C
{
    void M()
    {
        {|RH7004:using|} var s = new MemoryStream()
            // c
            ;
        s.Flush();
    }
}
```

is reported, and no code fix is offered.

Example — a string literal and a comment on one line keep the fix:

```csharp
using System.IO;

class C
{
    string M()
    {
        {|RH7004:using|} var s = new MemoryStream();
        var t = "a"; /* b */
        return t;
    }
}
```

```csharp
using System.IO;

class C
{
    string M()
    {
        using (var s = new MemoryStream())
        {
            var t = "a"; /* b */
            return t;
        }
    }
}
```
