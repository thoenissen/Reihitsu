# Analyzer — RH7107 Property accessors must follow order

| | |
|---|---|
| ID prefix | RH7107 |
| Status | Active |
| Category | Organization |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH7107PropertyAccessorsMustFollowOrderAnalyzer`, `RH7107PropertyAccessorsMustFollowOrderCodeFixProvider` |
| Uses | SHARED-ORDER-001, SHARED-ORDER-002, SHARED-ORDER-003, SHARED-ORDER-004, SHARED-ORDER-005, SHARED-ORDER-006 |

RH7107 reports a `get` accessor that follows a `set` or `init` accessor of the same property or indexer, and offers a code fix that moves it in front of them.

## Non-goals

- The accessors of events — RH7108.
- Expression-bodied properties and indexers, which have no accessor list.
- The shape of the accessors — whether they have a block or an expression body.

## Requirements

### RH7107-001 — A `get` accessor after `set` or `init` is reported

The analyzer MUST report the `get` accessor of a property or indexer whose accessor list has a `set` or `init` accessor before it, whether the accessors have bodies or not, in classes, structs, interfaces, and records alike, when the accessor list contains no `#if`, `#elif`, `#else`, or `#endif` directive.

Why: Readers expect to see how a value is read before how it is written. One fixed order makes every property's accessor list look the same.

Example:

```csharp
class C
{
    public int A { init; {|RH7107:get|}; }

    public int this[int index] { set { } {|RH7107:get|} { return index; } }
}

interface I
{
    int B { set; {|RH7107:get|}; }
}
```

### RH7107-002 — Accessor lists in order are not reported

The analyzer MUST NOT report an accessor list whose `get` accessor comes first or that has no `get` accessor.

Why: The rule asks only for `get` first.

Example:

```csharp
class C
{
    public int A { get; set; }

    public int B { get; init; }

    public int D { set { } }
}
```

is not reported.

### RH7107-003 — The diagnostic is on the `get` keyword

The analyzer MUST report one diagnostic per accessor list, located on the keyword of its `get` accessor.

Why: The `get` keyword marks the accessor that has to move, and one diagnostic per list matches the fix, which moves one accessor.

Example: see RH7107-001.

### RH7107-004 — The fix moves `get` in front of the first `set` or `init`

The code fix MUST move the `get` accessor in front of the first `set` or `init` accessor of the list, and MUST perform the move as specified in SHARED-ORDER-001 and SHARED-ORDER-002: the comments and attribute lists written above the `get` accessor travel with it.

Why: Moving the one misplaced accessor corrects the order without touching the others.

Example:

```csharp
class C
{
    public int A { init; {|RH7107:get|}; }
}
```

```csharp
class C
{
    public int A { get; init; }
}
```

The comment above the `get` accessor travels with it:

```csharp
class C
{
    private int _value;

    public int A
    {
        set
        {
            _value = value;
        }

        // Reads the value
        {|RH7107:get|}
        {
            return _value;
        }
    }
}
```

```csharp
class C
{
    private int _value;

    public int A
    {
        // Reads the value
        get
        {
            return _value;
        }

        set
        {
            _value = value;
        }
    }
}
```

### RH7107-005 — The fix is withheld when the move is unsafe

The code fix MUST NOT be offered when the move is refused by SHARED-ORDER-003, SHARED-ORDER-004, or SHARED-ORDER-005. When no `#if`, `#elif`, `#else`, or `#endif` directive takes part in the refusal, the diagnostic is still reported. A balanced directive pair alone does not withhold it (SHARED-ORDER-006).

Why: These moves would change which code a directive governs. A reported diagnostic without a fix is a supported end state.

Example:

```csharp
class C
{
    public int A
    {
        set
        {
        }

#pragma warning disable CS0162
        {|RH7107:get|}
        {
            return 0;
        }
    }
}
```

is reported, and no code fix is offered.
