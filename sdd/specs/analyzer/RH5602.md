# Analyzer — RH5602 Code must not contain trailing whitespace

| | |
|---|---|
| ID prefix | RH5602 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5602CodeMustNotContainTrailingWhitespaceAnalyzer`, `RH5602CodeMustNotContainTrailingWhitespaceCodeFixProvider` |
| Uses | FMT-CLEAN-001, SHARED-DIAG-003, SHARED-WS-001 |

RH5602 reports whitespace at the end of a line of code, and offers a code fix that deletes it as SHARED-WS-001 specifies.

In the examples, `·` marks a space and `→` a tab at the end of a line.

## Non-goals

- Whitespace inside a line, between two tokens — the spacing rules RH6001 to RH6024.
- Tabs that are not at the end of a line — RH5601.
- Blank lines and their number — the blank-line rules RH5001 to RH5032.
- Whether the file ends with a line break — RH5603.

## Requirements

### RH5602-001 — Whitespace before a line break is reported

The analyzer MUST report the run of whitespace between the last non-whitespace character of a line and its line break when that character is the last character of a code token — a token outside directives and documentation comments — or of a `/* */` comment, and the run is not part of the text of a literal. A line that consists of whitespace only and lies outside the text of a literal, a comment, and disabled text MUST be reported as a whole. Whitespace inside a line, followed by more code on the same line, MUST NOT be reported. The whitespace behind a literal and the whitespace in the expression of an interpolation hole are code (SHARED-DIAG-003) and MUST be reported like any other, also on a line that a literal spans.

Why: Trailing whitespace is invisible, carries no meaning, and shows up as noise in every diff that touches the line. The formatter removes it in the same places (FMT-CLEAN-001), so formatted code raises no RH5602. Only the text of a literal is its value; the code on the lines a literal spans, behind it or in one of its holes, is code like any other.

Example:

```csharp
class C
{{|RH5602:···|}
    int x;{|RH5602:→|}
{|RH5602:········|}
    char c = 'a';{|RH5602:··|}
    int y; /* note */{|RH5602:···|}
    int z;  int w;
    string s = "a";{|RH5602:··|}
    string t = @"a
b";{|RH5602:··|}
    string u = $"""
        {1{|RH5602:··|}
        + 2}
        """;
}
```

### RH5602-002 — Whitespace inside a multi-line string literal is not reported

The analyzer MUST NOT report whitespace at the end of a line when that whitespace is part of the text of a string literal spanning several lines — verbatim, interpolated, or raw —, for an interpolated string the text between and around its holes.

Why: That whitespace is part of the string's value; removing it would change what the program prints or compares.

Example:

```csharp
class C
{
    string u = @"a···
b";
    string v = """
        a··
        """;
    string w = $"""
        {1}··
        """;
}
```

is not reported.

### RH5602-003 — One diagnostic per line

The analyzer MUST report one diagnostic per line, located on the whole run of trailing whitespace of that line.

Why: The run is removed as one piece, so one diagnostic per line keeps one fix per diagnostic.

Example: see RH5602-001, where the run of three spaces after `{` is one diagnostic.

### RH5602-004 — The fix deletes the trailing whitespace

The code fix MUST delete the reported whitespace as SHARED-WS-001 specifies; a line of whitespace only becomes an empty line and stays in place.

Why: The fix answers exactly what the diagnostic reports. Removing the empty line itself is a question of blank lines, which other rules decide.

Example:

```csharp
class C
{{|RH5602:···|}
    int x;{|RH5602:→|}
{|RH5602:········|}
    int y; /* note */{|RH5602:···|}
}
```

```csharp
class C
{
    int x;

    int y; /* note */
}
```
