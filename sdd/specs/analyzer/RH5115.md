# Analyzer — RH5115 Index access must stay on the line of its expression

| | |
|---|---|
| ID prefix | RH5115 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5115IndexAccessMustStayOnExpressionLineAnalyzer`, `RH5115IndexAccessMustStayOnExpressionLineCodeFixProvider` |
| Uses | FMT-BREAK-040, FMT-UNSUP-014, SHARED-CHAIN-001, SHARED-CHAIN-007, SHARED-CHAIN-008, SHARED-CHAIN-009, SHARED-DIAG-008, SHARED-DIAG-010, SHARED-FIX-010, SHARED-JOIN-002, SHARED-WS-003 |

RH5115 reports an element access or a conditional element access that starts a line below the code in front of it, and offers a code fix that moves it onto that code's line.

Which tokens start such an access, and which trivia form its gaps, is stated once, by the attached-part predicate that FMT-BREAK-040 and FMT-UNSUP-014 use (`AttachedPartGapUtilities`); the analyzer, its code fix, and RH5116 decide by that predicate, not by a copy of it.

## Non-goals

- A null-forgiving operator `!` below its expression — RH5116, also where it stands in front of an index, as in `s⏎![0]`.
- The opening parenthesis of an argument list, whose gap FMT-BREAK-039 joins — a rule of its own, not a part of this one, whether or not the argument list belongs to a member-access chain.
- The `?` of `?.` — a link operator, whose line the chain's layout decides (RH5112, RH5201).
- Every `[` that is not the first token of an element access or of a conditional element access's element binding, such as an implicit element access in an initializer, an array rank specifier, `new[]`, a collection expression, a list pattern, or an attribute list — FMT-BREAK-040 does not join it.
- A comment or a directive in the gap in front of an access on one line, such as `arr /* c */ [0]` — no line break separates the access from its expression.
- The arguments inside the brackets — RH5307.
- Realigning a line behind the access that was aligned to code behind it, outside a chain with links — RH5115-004.

## Requirements

### RH5115-001 — An index access below its expression is reported

The analyzer MUST report each of the following index accesses — the parts of FMT-BREAK-040 that start with `[` or with the `?` of `?[`, identified by the syntax tree alone, whatever expression stands in front of them — when a line break separates it from the token in front of it, except in a file with a syntax error (SHARED-JOIN-002):

- an element access (`ElementAccessExpressionSyntax`), when the `[` of its bracketed argument list starts on a later line than the token in front of it ends on;
- a conditional element access — a `ConditionalAccessExpressionSyntax` whose `?` is followed by the `[` of an `ElementBindingExpressionSyntax`'s bracketed argument list — when its `?` starts on a later line than the token in front of it ends on, or its `[` starts on a later line than its `?`.

This holds wherever the access stands: in a member-access chain with links (SHARED-CHAIN-001), in an expression without any link, behind a null-forgiving operator, inside an argument, an interpolation hole, or a lambda, as an assignment's target, and everywhere else. Blank lines in the gap count as a line break. A `[` that is not the first token of an element access or of an element binding, and the opening parenthesis of an argument list, MUST NOT be reported.

Why: An index belongs to the expression in front of it: `[0]` on a line of its own reads as a collection expression or an attribute list, and no column shows that it belongs to the code above (FMT-BREAK-040). A line break between the `?` and the `[` of a conditional element access splits one operator, as a split link operator does. An argument list's parenthesis is a different construct ([P11](../../README.md#the-formatter-may-do-more-than-the-analyzers-p11)).

Example:

```csharp
#nullable enable
using System.Linq;

class C
{
    void M(int[] arr, int[]? n, int[] items)
    {
        var a = arr
            {|RH5115:[|}0];
        var b = n
            {|RH5115:?|}[0];
        var c = n{|RH5115:?|}
            [0];
        var e = (arr)

            {|RH5115:[|}1];
        var f = items.Where(x => x > 0)
                     .ToArray()
                     {|RH5115:[|}0];
    }
}
```

Example — the other side of each condition:

```csharp
#nullable enable
using System.Collections.Generic;

class C
{
    void M(int[] arr, string? s)
    {
        var a = arr[0];

            ?.Length;
        var c = Foo
            (1);
        var d = new Dictionary<string, int>
                {
                    ["a"] = 1
                };
    }

    {
        return x;
    }

```

is not reported.

### RH5115-002 — A comment or a directive in the gap does not prevent the report

An access that RH5115-001 reports MUST be reported also when a comment, a preprocessor directive, or disabled text stands in its gap — in the trailing trivia of the token in front of the access, in the leading trivia of its first token, or, for a conditional element access, between its `?` and its `[`. SHARED-DIAG-008 decides a conditional directive in the gap: the access is judged in the build being analyzed.

Why: The formatter refuses such an input as unsupported (FMT-UNSUP-014) instead of keeping it, so the shape is not one the formatter keeps (SHARED-DIAG-010): the user is asked to move the comment or the directive, and the diagnostic is what tells the analyzer-only user so.

Example:

```csharp
class C
{
    void M(int[] arr)
    {
        var a = arr // first
            {|RH5115:[|}0];
        var b = arr
#if X
            [0];
#else
            {|RH5115:[|}1];
#endif
        var c = arr /* first */ [0];
    }
}
```

`a` and `b` are reported in a build that does not define `X`, and no code fix is offered (RH5115-006); `c` is not reported, because no line break separates `[0]` from `arr`.

### RH5115-003 — The diagnostic is on the access's first token

The analyzer MUST report one diagnostic per access, located on the access's first token: the `[` of an element access and the `?` of a conditional element access. A conditional element access whose `?` and whose `[` both start a later line is reported once, on its `?`. Two accesses of one expression are two accesses, each reported on its own.

Why: The first token is where the line break goes; for a conditional element access, the `?` and the `[` are one operator, whichever of its gaps holds the line break.

Example:

```csharp
#nullable enable

class C
{
    void M(int[][] grid, int[]? n)
    {
        var a = grid
            {|RH5115:[|}0]
            {|RH5115:[|}1];
        var b = n
            {|RH5115:?|}
            [0];
    }
}
```

### RH5115-004 — Outside a chain with links, the fix joins the access

When the reported access is not an attached part of a chain with at least one link (SHARED-CHAIN-001), the code fix MUST join it to the token in front of it as SHARED-WS-003 specifies, and, for a conditional element access, MUST also delete the gap between its `?` and its `[`. It MUST NOT change anything else: a later line that was aligned to code behind the access keeps its column, also when the access stands inside a chain with links that it is not an attached part of, such as in an argument of one of the chain's calls; the rule that reports the misalignment, such as RH5201 or RH5203, then offers its own fix.

Why: Without a link, no column of the chain the access belongs to depends on where the access stands; deleting the gap is the whole correction and gives what the formatter gives (FMT-BREAK-040). A line aligned to code behind the access is laid out by another rule, as the RH5105 fix leaves the later parameters of a list it joins.

Example:

```csharp
#nullable enable

class C
{
    void M(int[] arr, int[]? n)
    {
        var a = arr
            {|RH5115:[|}0];
        var b = n{|RH5115:?|}
            [0];
        var c = Foo(arr
                {|RH5115:[|}0]).ToString()
                     .Trim();
    }

    int Foo(int x)
    {
        return x;
    }
}
```

```csharp
#nullable enable

class C
{
    void M(int[] arr, int[]? n)
    {
        var a = arr[0];
        var b = n?[0];
        var c = Foo(arr[0]).ToString()
                     .Trim();
    }

    int Foo(int x)
    {
        return x;
    }
}
```

`.Trim` keeps its column; RH5201 then reports it.

### RH5115-005 — In a chain with links, the fix lays out the chain

When the reported access is an attached part of a chain with at least one link (SHARED-CHAIN-001), the code fix MUST lay out that chain as SHARED-CHAIN-008 and SHARED-CHAIN-009 specify.

Why: Joining the access can move the chain's first link, and with it the anchor every wrapped link aligns to (SHARED-CHAIN-007): in `x⏎[0].B()⏎.C()`, `.B` moves to the right when `[0]` joins `x`, and `.C` has to follow it. The formatted layout of the whole chain leaves no link misaligned by the join, as the RH5112 fix does for a first link it joins.

Example:

```csharp
class C
{
    void M(dynamic x)
    {
        var a = x.B()
            {|RH5115:[|}0]
            .C();
        var e = x
            {|RH5115:[|}0].B()
            .C();
    }
}
```

```csharp
class C
{
    void M(dynamic x)
    {
        var a = x.B()[0]
                 .C();
        var e = x[0].B()
                    .C();
    }
}
```

### RH5115-006 — A comment or a directive in the gap withholds the fix

The code fix MUST NOT be offered when a comment, a preprocessor directive, or disabled text stands in a gap of the reported access that RH5115-002 names. The diagnostic is still reported. Where the fix lays out a chain, SHARED-FIX-010 withholds it as well: the formatter refuses the shape (FMT-UNSUP-014).

Why: Deleting the gap would delete the comment or the directive, and moving it elsewhere relocates user code; the author decides where it goes.

Example: see RH5115-002.
