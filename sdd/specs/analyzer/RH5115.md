# Analyzer — RH5115 Index and null-forgiving operator must stay on the line of their expression

| | |
|---|---|
| ID prefix | RH5115 |
| Status | Active |
| Category | Layout |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH5115IndexAndNullForgivingOperatorMustStayOnExpressionLineAnalyzer`, `RH5115IndexAndNullForgivingOperatorMustStayOnExpressionLineCodeFixProvider` |
| Uses | FMT-BREAK-040, FMT-UNSUP-014, SHARED-CHAIN-001, SHARED-CHAIN-007, SHARED-CHAIN-008, SHARED-CHAIN-009, SHARED-DIAG-008, SHARED-DIAG-010, SHARED-FIX-010, SHARED-JOIN-002, SHARED-WS-003 |

RH5115 reports an element access, a conditional element access, or a null-forgiving operator that starts a line below the code in front of it, and offers a code fix that moves it onto that code's line.

## Non-goals

- The opening parenthesis of an argument list, whose gap FMT-BREAK-039 joins — a rule of its own, not a part of this one, whether or not the argument list belongs to a member-access chain.
- A `!` that is the first token of a link operator `!.` or `!?.`, and the `?` of `?.` — the layout of a chain's links, RH5112 and RH5201.
- Every `[` that is not the first token of an element access or of a conditional element access's element binding, such as an implicit element access in an initializer, an array rank specifier, `new[]`, a collection expression, a list pattern, or an attribute list — FMT-BREAK-040 does not join it.
- A comment or a directive in the gap in front of a part on one line, such as `arr /* c */ [0]` — no line break separates the part from its expression.
- The arguments inside the brackets — RH5307.

## Requirements

### RH5115-001 — An index or a null-forgiving operator below its expression is reported

The analyzer MUST report each of the following parts — the parts of FMT-BREAK-040, identified by the syntax tree alone, whatever expression stands in front of them — when a line break separates it from the token in front of it, except in a file with a syntax error (SHARED-JOIN-002):

- an element access (`ElementAccessExpressionSyntax`), when the `[` of its bracketed argument list starts on a later line than the token in front of it ends on;
- a conditional element access — a `ConditionalAccessExpressionSyntax` whose `?` is followed by the `[` of an `ElementBindingExpressionSyntax`'s bracketed argument list — when its `?` starts on a later line than the token in front of it ends on, or its `[` starts on a later line than its `?`;
- a null-forgiving operator (`SuppressNullableWarningExpressionSyntax`) that is not followed by `.` or by the `?.` of a conditional member access, when its `!` starts on a later line than the token in front of it ends on.

This holds wherever the part stands: in a member-access chain with links (SHARED-CHAIN-001), in an expression without any link, inside an argument, an interpolation hole, or a lambda, as an assignment's target, and everywhere else. Blank lines in the gap count as a line break. A null-forgiving operator followed by `.` or `?.` MUST NOT be reported: its `!` is the first token of a link operator. A `[` that is not the first token of an element access or of an element binding, and the opening parenthesis of an argument list, MUST NOT be reported.

Why: An index and a null-forgiving operator belong to the expression in front of them: `[0]` on a line of its own reads as a collection expression or an attribute list, and `!` as a negation of what follows (FMT-BREAK-040). A line break between the `?` and the `[` of a conditional element access splits one operator, as a split link operator does. A `!` in front of `.` or `?.` is part of a link, whose line the chain's layout decides, and an argument list's parenthesis is a different construct ([P11](../../README.md#the-formatter-may-do-more-than-the-analyzers-p11)).

Example:

```csharp
#nullable enable
using System.Linq;

class C
{
    void M(int[] arr, int[]? n, string? s, int[] items)
    {
        var a = arr
            {|RH5115:[|}0];
        var b = n
            {|RH5115:?|}[0];
        var c = n{|RH5115:?|}
            [0];
        var d = s
            {|RH5115:!|} + "";
        var e = (arr)

            {|RH5115:[|}1];
        var f = items.Where(x => x > 0)
                     .ToArray()
                     {|RH5115:[|}0];
    }
}
```

Example — the other side of each condition:

### RH5115-002 — A comment or a directive in the gap does not prevent the report

A part that RH5115-001 reports MUST be reported also when a comment, a preprocessor directive, or disabled text stands in its gap — in the trailing trivia of the token in front of the part, in the leading trivia of its first token, or, for a conditional element access, between its `?` and its `[`. SHARED-DIAG-008 decides a conditional directive in the gap: the part is judged in the build being analyzed.

Why: The formatter refuses such an input as unsupported (FMT-UNSUP-014) instead of keeping it, so the shape is not one the formatter keeps (SHARED-DIAG-010): the user is asked to move the comment or the directive, and the diagnostic is what tells the analyzer-only user so.

Example:

```csharp
class C
{
    void M(int[] arr)
    {
        var a = arr // first
            {|RH5115:[|}0];
        var b = arr
#if X
            [0];
#else
            {|RH5115:[|}1];
#endif
        var c = arr /* first */ [0];
    }
}
```

`a` and `b` are reported in a build that does not define `X`, and no code fix is offered (RH5115-006); `c` is not reported, because no line break separates `[0]` from `arr`.

### RH5115-003 — The diagnostic is on the part's first token

The analyzer MUST report one diagnostic per part, located on the part's first token: the `[` of an element access, the `?` of a conditional element access, and the `!` of a null-forgiving operator. A conditional element access whose `?` and whose `[` both start a later line is reported once, on its `?`. Two parts of one expression are two parts, each reported on its own.

Why: The first token is where the line break goes; for a conditional element access, the `?` and the `[` are one operator, whichever of its gaps holds the line break.

Example:

```csharp
#nullable enable

class C
{
    void M(int[][] grid, int[]? n)
    {
        var a = grid
            {|RH5115:[|}0]
            {|RH5115:[|}1];
        var b = n
            {|RH5115:?|}
            [0];
    }
}
```

### RH5115-004 — Outside a chain with links, the fix joins the part

When the reported part is not an attached part of a chain with at least one link (SHARED-CHAIN-001), the code fix MUST join it to the token in front of it as SHARED-WS-003 specifies, and, for a conditional element access, MUST also delete the gap between its `?` and its `[`.

Why: Without a link, no column of the code around the part depends on where the part stands; deleting the gap is the whole correction and gives what the formatter gives (FMT-BREAK-040).

Example:

```csharp
#nullable enable

class C
{
    void M(int[] arr, int[]? n, string? s)
    {
        var a = arr
            {|RH5115:[|}0];
        var b = n{|RH5115:?|}
            [0];
        var d = s
            {|RH5115:!|} + "";
    }
}
```

```csharp
#nullable enable

class C
{
    void M(int[] arr, int[]? n, string? s)
    {
        var a = arr[0];
        var b = n?[0];
        var d = s! + "";
    }
}
```

### RH5115-005 — In a chain with links, the fix lays out the chain

When the reported part is an attached part of a chain with at least one link (SHARED-CHAIN-001), the code fix MUST lay out that chain as SHARED-CHAIN-008 and SHARED-CHAIN-009 specify.

Why: Joining the part can move the chain's first link, and with it the anchor every wrapped link aligns to (SHARED-CHAIN-007): in `x⏎[0].B()⏎.C()`, `.B` moves to the right when `[0]` joins `x`, and `.C` has to follow it. The formatted layout of the whole chain leaves no link misaligned by the join, as the RH5112 fix does for a first link it joins.

Example:

```csharp
class C
{
    void M(dynamic x)
    {
        var a = x.B()
            {|RH5115:[|}0]
            .C();
        var e = x
            {|RH5115:[|}0].B()
            .C();
    }
}
```

```csharp
class C
{
    void M(dynamic x)
    {
        var a = x.B()[0]
                 .C();
        var e = x[0].B()
                    .C();
    }
}
```

### RH5115-006 — A comment or a directive in the gap withholds the fix

The code fix MUST NOT be offered when a comment, a preprocessor directive, or disabled text stands in a gap of the reported part that RH5115-002 names. The diagnostic is still reported. Where the fix lays out a chain, SHARED-FIX-010 withholds it as well: the formatter refuses the shape (FMT-UNSUP-014).

Why: Deleting the gap would delete the comment or the directive, and moving it elsewhere relocates user code; the author decides where it goes.

Example: see RH5115-002.
