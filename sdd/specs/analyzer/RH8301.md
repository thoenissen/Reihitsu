# Analyzer — RH8301 Documentation lines must begin with single space

| | |
|---|---|
| ID prefix | RH8301 |
| Status | Active |
| Category | Documentation |
| Severity | Warning |
| Enabled by default | Yes |
| Code fix | Fix All |
| Code owners | `RH8301DocumentationLinesMustBeginWithSingleSpaceAnalyzer`, `RH8301DocumentationLinesMustBeginWithSingleSpaceCodeFixProvider` |
| Uses | FMT-DOC-003, FMT-DOC-005, FMT-DOC-006, FMT-DOC-013, SHARED-DIAG-010, SHARED-DOC-004, SHARED-DOC-008 |

RH8301 reports a line of a `///` documentation comment whose text after the `///` does not start with exactly one space, and offers a code fix that writes the separator the formatter writes.

## Non-goals

- The blank lines before and after a documentation comment — RH8302 and RH8303.
- The line layout of the XML elements inside the comment — RH8304, RH8305, RH8307, and RH8308.
- Ordinary comments that start with `//` or `////`, and `/** */` comments.

## Requirements

### RH8301-001 — A `///` line without a single-space separator is reported

The analyzer MUST report a line of a `///` documentation comment whose text after the `///` differs from the shape that FMT-DOC-005 and FMT-DOC-006 give it:

- content that follows the `///` without a separator, or after a separator that is a white-space character other than a space, such as a tab or a no-break space;
- a line that carries only white space after the `///`, other than nothing at all or a single space.

White space after the first space belongs to the content and MUST NOT be reported. Nothing is reported when SHARED-DOC-008 applies.

This requirement covers the lines of a `///` documentation comment of a declaration, as SHARED-DOC-004 defines it, that start with white space and `///`. A `///` comment that starts behind code on its line, and a `///` comment that is not a documentation comment of a declaration, such as one inside a method body, are not covered.

Why: The one space after `///` separates the marker from the text. Without it, `///Summary` runs the marker into the sentence and starts one column left of every other line of the comment. Indentation after that space is the author's own layout, such as a nested list item or an indented code sample, and stays.

Example — `→` marks a tab character:

```csharp
class C
{
    /// <summary>
    {|RH8301:///|}Runs
    {|RH8301:///|}→the service
    ///   - nested item
    ///
    /// </summary>
    void M()
    {
    }
}
```

A line that holds `///` followed by two spaces, or by a tab, is reported as well; a line that holds `///` followed by one space is not.

### RH8301-002 — Lines outside `///` documentation comments are not checked

The analyzer MUST NOT report a line that starts with four or more slashes, or a line inside a string literal, inside a `/* */` or `/** */` comment, or inside code that an `#if` branch excludes. It MUST NOT report a line of a `///` comment that the formatter leaves as written — one that holds an element without an end tag of its own (FMT-DOC-013), or one that FMT-DOC-003 keeps behind code, as SHARED-DIAG-010 requires.

Why: Four slashes start an ordinary comment, text inside a literal or a block comment is content, and excluded code is not part of the compilation. The formatter leaves the separators of a comment it keeps as written alone, so the fix would ask for a layout the formatter has decided against.

Example:

```csharp
class C
{
    ////Ordinary
    int a;

    /*
    ///Block
    */
    string s = @"
///Literal
";

    /**
    ///Delimited
    */
    int b;
#if NEVER
    ///Excluded
#endif
}
```

is not reported, and neither is

```csharp
class C
{
    ///<summary>S
    int A;

    int B; ///<remarks>a
    ///b</remarks>
}
```

### RH8301-003 — The diagnostic is on the `///`

The analyzer MUST report one diagnostic per reported line, located on the three slashes of its `///`.

Why: The separator after the slashes is what the fix changes; the squiggle marks where it belongs.

Example: see RH8301-001.

### RH8301-004 — The fix writes the separator

The code fix MUST rewrite the reported line to the shape that FMT-DOC-005 and FMT-DOC-006 specify: content gets one space after the `///`, a separator that is another white-space character is replaced by that space, and a line that carries only white space after the `///` keeps nothing after it. The indentation before the `///` stays as it is, and so does the content, from its first character on.

Why: The fix corrects only the separator, so the comment's text and the indentation the author put inside it are kept.

Example — `→` marks a tab character:

```csharp
class C
{
    /// <summary>
    {|RH8301:///|}Runs
    {|RH8301:///|}→  - nested item
    /// </summary>
    void M()
    {
    }
}
```

```csharp
class C
{
    /// <summary>
    /// Runs
    ///   - nested item
    /// </summary>
    void M()
    {
    }
}
```

A line that holds `///` followed by two spaces becomes `///`.
