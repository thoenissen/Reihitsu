# Shared — Diagnostics

| | |
|---|---|
| ID prefix | SHARED-DIAG |
| Status | Active |
| Code owners | `DiagnosticAnalyzerBase` |
| Uses | — |

This spec covers what holds for every analyzer rule, so a rule spec states only what the rule itself reports. It applies to every rule without being listed under `Uses`.

## Non-goals

- Code in an inactive `#if` branch. The compiler does not hand it to any analyzer, so no rule can report it.
- Generated code in the formatter (FMT-PIPE-006) and in the CLI, which have their own specs.
- How a rule is suppressed or configured — standard .NET analyzer behavior.

## Requirements

### SHARED-DIAG-001 — Generated code is not analyzed

An analyzer rule MUST NOT report anything in generated code: a file whose name marks it as generated (such as `*.g.cs` or `*.Designer.cs`), a file that starts with an `<auto-generated>` comment, code marked with `[GeneratedCode]`, and every other form the compiler treats as generated.

Why: Generated code is rewritten by its generator; a diagnostic there cannot be fixed durably and only buries the diagnostics of the code the user maintains.

Example:

```csharp
// <auto-generated/>
internal class C
{
    public string M(string name, int id)
    {
        return "User: " + name + ", Id: " + id;
    }
}
```

is not reported by RH1003, which reports the same class without the comment.
