# Playground — Formatting in the browser

| | |
|---|---|
| ID prefix | PLAY |
| Status | Active |
| Code owners | `Home`, `MainLayout`, `PlaygroundFormatter`, `PlaygroundFormatResult`, `PlaygroundHighlighter`, `PlaygroundVersion` |
| Uses | FMT-PIPE-004, FMT-PIPE-005, FMT-PIPE-008, FMT-PIPE-007, FMT-PIPE-033, FMT-UNSUP-001, FMT-UNSUP-002 |

This spec covers the user-visible behavior of the Reihitsu Playground, a Blazor WebAssembly page that formats pasted C# with the Reihitsu formatter: what it shows, when it formats, and what it does with input it cannot format.

## Non-goals

- The formatting itself — FMT-PIPE and the phase specs.
- Analyzer diagnostics. The Playground runs only the formatter.
- Hosting and deployment (`deploy-pages.yml`), styling, and the framework's loading and error screens.
- Choosing a language version, sharing a link to the input, and download or upload of files — the Playground has none of these.
- Semantic highlighting. The Playground builds no compilation, so its highlighting tells types, methods, and variables apart only as far as the syntax tree does (PLAY-010).
- Marks in the output pane, and marks or list entries for parser warnings. Only the input carries marks, and only errors are listed and marked (PLAY-006, PLAY-014).
- Input marked as generated (`// <auto-generated/>`). The formatter leaves it unchanged (FMT-PIPE-006) and the Playground currently shows it unchanged without a message; a message that says why is a decided behavior change, tracked in thoenissen/Reihitsu#976.

## Requirements

### PLAY-001 — Formatting runs in the browser

The Playground MUST format the input inside the browser and MUST NOT send the input anywhere. The page MUST say so above the editors: "Paste C# source below and format it with the Reihitsu formatter. Formatting runs entirely in your browser; nothing is uploaded anywhere."

Why: Users paste proprietary code to try the formatter; the promise that it stays local is what makes that acceptable, and it is true because the formatter is compiled to WebAssembly and runs client-side.

### PLAY-002 — Input on the left, read-only output on the right

The page MUST show an editable "Input" text area and a read-only "Formatted output" code view side by side, with a "Format" button below them. The input MUST keep the browser's own editing, selection, and undo of a text area. The output MUST NOT be editable, and its text MUST be selectable and copy as exactly the output text. Spell checking MUST be off in the input.

Why: Before and after next to each other is what a user compares; the output is a result, not a second editor, and the user copies it into a file.

### PLAY-003 — The page opens with a formatted example

On load, the input MUST contain the example `public class Sample{public int Add(int a,int b){return a+b;}}` and the output MUST already show it formatted.

Why: A first-time visitor sees what the formatter does without typing anything.

Example — the output on load:

```csharp
public class Sample
{
    public int Add(int a, int b)
    {
        return a + b;
    }
}
```

### PLAY-004 — The output changes only on "Format"

The Playground MUST format the current input and replace the output when the "Format" button is pressed, and MUST NOT format while the user types.

Why: Formatting on every keystroke would rewrite the output for half-typed code that does not parse yet and would flash the syntax error message constantly.

### PLAY-005 — The whole input is formatted as one file

The Playground MUST parse the input as one C# file with Roslyn's default parse options — the default language version, no preprocessor symbols — and format it with `ReihitsuFormatter.FormatSyntaxTree`, so the result equals the formatter's document-level output for that text (FMT-PIPE-008 for the language version). Line breaks in the input decide the line ending of the output (FMT-PIPE-007), and the result is idempotent (FMT-PIPE-004).

Why: The Playground is a window onto the formatter, not a second formatter; it must show what `reihitsu-format` would write for the same file.

### PLAY-006 — Input with syntax errors is shown unchanged with a message

When the input has a syntax error, the Playground MUST show the input unchanged as the output and show the message "The input contains syntax errors and was left unchanged." below the button. Below that sentence, the message MUST list every error the parser reports for the input, one line each, as `line <line>, column <column> — <ID>: <message>`, where `<line>` and `<column>` are the one-based line and column of the first character of the error's span, counted as in PLAY-008, `<ID>` is the diagnostic ID, and `<message>` is the parser's message in English. The errors MUST be listed by the position of their span's first character, and errors at the same position in the order the parser reports them; an error reported twice at one position, such as two missing `}`, is listed twice. A diagnostic that is not an error, such as a warning, MUST NOT be listed. The message MUST disappear on the next successful format.

Why: The formatter never formats code it cannot parse (FMT-PIPE-005); without the message the unchanged output would look like the formatter had nothing to do, and without the list the user has to find the error in the input by hand. Only errors stop the formatter, so only errors are listed.

Example — input:

```csharp
public class Sample{ int x }
```

The output is the same text, and the message is:

```text
The input contains syntax errors and was left unchanged.
line 1, column 28 — CS1002: ; expected
```

Example — input:

```csharp
public class Sample{public int Add(int a,int b){return a+b}
```

The message is:

```text
The input contains syntax errors and was left unchanged.
line 1, column 59 — CS1002: ; expected
line 1, column 60 — CS1513: } expected
```

### PLAY-007 — The page shows the formatter version

The footer MUST show the informational version of the `Reihitsu.Formatter` assembly the page runs, as `v<version>`, and the header MUST link to the GitHub repository.

Why: A user who reports a formatting result from the Playground needs to say which version produced it.

### PLAY-008 — Input with unsupported syntax is shown unchanged with a message

When the formatter refuses the input as unsupported (FMT-UNSUP-001), the Playground MUST show the input unchanged as the output and show the message "The input contains syntax the formatter does not support and was left unchanged: line <line>, column <column> — <reason>." below the button, where `<line>` and `<column>` are the one-based line and column of the first character of the shape the formatter reports, and `<reason>` is the reason it gives. The message MUST disappear on the next format of an input the formatter does not refuse.

Why: Without the message the unchanged output would look like the formatter had nothing to do, the reason PLAY-006 gives for syntax errors; the line and the column lead the user to the code to rewrite by hand.

Example — input:

```csharp
class C
{
    void M()
    {
        int /* c */ a = 1;
    }
}
```

The output is the same text, and the message "The input contains syntax the formatter does not support and was left unchanged: line 5, column 13 — a comment between a variable declaration's own tokens." is shown.

### PLAY-009 — Input whose text another build compiles as code is shown unchanged with a message

When the input holds a hiding carrier as FMT-PIPE-033 defines it — a string literal or a delimited comment that spans lines, starts inside a conditional group, and holds a line that another build reads as an `#elif`, `#else`, or `#endif` directive — the Playground MUST show the input unchanged as the output and show the message "The input contains code hidden in another build configuration and was left unchanged." below the button. It MUST decide this by the definition of FMT-PIPE-033, not by a definition of its own. Input with a syntax error shows the message of PLAY-006 instead, and input that also holds a shape the formatter refuses as unsupported shows this message, not PLAY-008's: FMT-PIPE-033 applies before the formatter's precheck (FMT-UNSUP-002). The message MUST disappear on the next successful format.

Why: The formatter leaves such input as written (FMT-PIPE-033); without the message the unchanged output would look like the formatter had nothing to do, the reason PLAY-006 gives for syntax errors.

Example — input:

```csharp
class C
{
    void M()
    {
#if !A
        /*
#else
        var s = @"
        */
        int  x = 1; //";
#endif
    }
}
```

The output is the same text, and the message is shown.

### PLAY-010 — Both panes are highlighted by the C# syntax tree

The Playground MUST colour the text of the input and of the output by the C# syntax tree that Roslyn parses from that text with the options of PLAY-005, in these categories:

- **keyword** — a token the parser gives a keyword kind, also a contextual keyword the parser reads as a keyword, such as `partial`, `async`, `await`, `get`, `set`, or `where` in a constraint;
- **identifier** — an identifier token, also when its text can be a contextual keyword, such as `var`, `nameof`, `dynamic`, or `value` where the parser gives it an identifier token;
- **string** — a string or character literal, and the text parts and the opening and closing delimiters of an interpolated or raw string literal, but not an interpolation hole: its braces keep the normal text colour, and its code is coloured by its own tokens;
- **number** — a numeric literal;
- **comment** — a single-line or delimited comment trivia, and a documentation comment trivia as a whole, with every token inside it: a keyword or a name inside a documentation comment, such as `int` in `<see cref="int"/>`, is a comment;
- **preprocessor directive** — a directive trivia's tokens and its message trivia, such as a `#region`'s name, but not a comment trivia behind the directive, such as `// Methods` behind `#endregion`, which is a comment;
- **disabled text** — the text of a branch the conditional directives exclude.

The category is decided by the kind of the token or trivia the parser produces, never by the characters of the text: an identifier token is an identifier whatever its text, and text the parser reads as a directive's message, such as `/* c */` behind `#region X` or `// b` behind `#error a`, is a directive although it looks like a comment.

Each category MUST have its own colour, in each colour scheme the page supports; every other token and trivia — punctuation, operators, and whitespace — MUST keep the page's normal text colour. The highlighted text MUST be exactly the text it colours: no character is added, dropped, or changed. The colouring MUST be computed in the page and MUST NOT load an editor library or any script or stylesheet from another origin.

Why: Colour makes the formatted code readable; the syntax tree is already in the page, because the formatter needs it, so the colouring needs no new dependency, and nothing leaves the browser (PLAY-001).

Example — input:

```csharp
public class Sample{public int Add(int a,int b){return a+b;}}
```

`public`, `class`, `int`, and `return` are keywords, `Sample`, `Add`, `a`, and `b` identifiers; the braces, parentheses, `,`, `;`, and `+` keep the normal text colour.

Example — input:

```csharp
#region Methods
#if DEBUG
inactive text
#endif
// comment
class C { string s = $"a{n}b"; char c = 'x'; const int n = 42; }
#endregion // Methods
```

`#region Methods`, `#if DEBUG`, `#endif`, and `#endregion` are preprocessor directives, `// Methods` behind `#endregion` a comment, `inactive text` disabled text — the Playground defines no preprocessor symbol (PLAY-005) — `// comment` a comment, `$"a`, `b"`, and `'x'` strings, the `n` inside the hole an identifier, and `42` a number.

Example — input:

```csharp
/// <summary>Uses <see cref="int"/>.</summary>
partial class C { int P { set { var x = nameof(value); dynamic d = x; } } }
```

The whole documentation comment, `int` and `see` included, is a comment; `partial`, `class`, `int`, and `set` are keywords; `C`, `P`, `var`, `x`, `nameof`, `value`, `dynamic`, and `d` are identifiers, because the parser gives `var`, `nameof`, `value`, and `dynamic` identifier tokens here.

### PLAY-011 — The input is highlighted while the user types

The input's colours MUST follow its text on every change, also while the text does not parse, and MUST stay under the characters they colour while the input is scrolled in either direction. Typing MUST NOT change the output (PLAY-004). Assistive technology MUST read the input's text once: a coloured copy of the text shown with the input MUST be hidden from assistive technology.

Why: The colours of a text the user edits help only when they match what is on the screen; misaligned or stale colours are worse than none. Colouring is cheap and shows no message, so it does not have the problem PLAY-004 avoids for formatting.

Example — typing `class C{` into an empty input colours `class` as a keyword and `C` as an identifier at once, while the output keeps its text and its colours.

### PLAY-012 — Lines do not wrap

The panes MUST NOT wrap a line: each line of the text MUST stay on one visual line, and a pane whose text is wider than the pane MUST scroll horizontally. The output pane MUST be a stop in the keyboard's tab order, so a user without a pointer can reach it and scroll it; the input text area is one already.

Why: Where the formatter breaks a line is its main output; a soft wrap in a pane looks like a line break the formatter wrote.

Example — input:

```csharp
public class Sample { public int Add(int first, int second, int third, int fourth, int fifth, int sixth, int seventh) { return first + second + third + fourth + fifth + sixth + seventh; } }
```

The input shows one line and scrolls horizontally; the output's line `    public int Add(int first, int second, int third, int fourth, int fifth, int sixth, int seventh)` stays one line too. Pressing Tab from the input reaches the output pane, and the arrow keys then scroll it.

### PLAY-013 — The message is an alert box

The messages of PLAY-006, PLAY-008, and PLAY-009 MUST be shown in a box below the button that sets them apart from the page's text, and the box MUST be announced to assistive technology as an alert. When there is no message, the page MUST NOT show the box.

Why: A line of red text below the button is easy to miss, and the user must notice that the output is the input unchanged.

Example — the PLAY-006 example's input shows the box with its two lines; the PLAY-003 example shows no box.

### PLAY-014 — Error locations are marked in the input

When "Format" shows the message of PLAY-006, the input MUST mark the span of each error that message lists with a red wavy underline; when it shows the message of PLAY-008, the input MUST mark the span of the shape the formatter reports in the same way. When it shows the message of PLAY-009, the input MUST show no mark, because the formatter reports no location for that input. A format that shows no message MUST remove every mark.

An error whose span is empty MUST be marked one character wide, by what follows its position in the text:

- an ordinary character, one that is not a line break — that character is marked;
- a line break — the place directly behind the line's last character is marked, in the column after it, and the line break itself is not;
- the end of the text — the place directly behind the text's last character is marked.

A mark MUST NOT add, drop, or change a character of the input (PLAY-010).

Every mark MUST disappear at the first change of the input's text after the format that set it, and marks MUST come back only with a later format that shows the message of PLAY-006 or PLAY-008. Editing the input MUST NOT change or remove the message box; it stays until the next format (PLAY-013).

Why: The line and the column in the message say where the problem is; the mark shows it, in the text the user has to change. A mark that stays after an edit can point at code it was not about, which is worse than no mark, and recomputing marks while typing would flash errors for half-typed code, which PLAY-004 avoids.

Example — the input of PLAY-006's second example: the `}` at column 59 is marked, and the place behind it, at the end of the text, one character wide.

Example — input:

```csharp
class C
{
    int x
}
```

The message lists `line 3, column 10 — CS1002: ; expected`, whose span is empty at the line break behind `x`; the place directly behind `x`, in column 10 of line 3, is marked one character wide, and the text does not change.

Example — input:

```csharp
class C { /* open
```

The message lists `line 1, column 11 — CS1035: End-of-file found, '*/' expected` and `line 1, column 18 — CS1513: } expected`, both with empty spans; the `/` in front of which the first one sits is marked, and the place behind the text's last character for the second.

Example — after "Format" on the input of PLAY-006's second example, the user types `int y;` at the start of the input: both marks disappear at the first typed character, the message box keeps its two lines, and the next "Format" sets the marks of the new input.

Example — the input of PLAY-008's example: `/* c */` is marked.

Example — the input of PLAY-009's example: no mark.
