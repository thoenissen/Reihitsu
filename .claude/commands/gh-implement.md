# GitHub Issue Implementation

Implement GitHub issue **#$ARGUMENTS** end-to-end.

Invoke the `gh-implement` skill and follow its workflow exactly. You run in a **Linux** cloud sandbox with no .NET SDK and no `gh` CLI:

1. Read the issue via `mcp__github__issue_read` — all GitHub access goes through the GitHub MCP server, not the `gh` CLI.
2. First check the issue for an existing claim or open PR. If it is unclaimed, create `claude/issue-$ARGUMENTS-<slug>` from the current `origin/main`, add an empty `Claim issue #$ARGUMENTS [skip ci]` commit, push it, and immediately open a **draft** PR. Title and body are a fixed generic placeholder (title `Claim: issue #$ARGUMENTS`, template body with static wording) — never the issue's own title or a paraphrase of its body — with `Closes #$ARGUMENTS` mandatory in the body; do not comment on or label the issue because the linked draft PR is the ownership marker.
3. Install the .NET 10 SDK via the official `dotnet-install.sh` script (the Linux sandbox does not ship with it), then confirm `dotnet --list-sdks` shows a `10.*` SDK.
4. **Scope triage.** Classify the run as *routine* or *behavioral* against the skill's five criteria (no analyzer/formatter/code-fix/Core behavior change, exactly one reading, small listable file set, no new rule or diagnostic/API/dependency change, not an analyzer or formatter bug report). Apply the mechanical veto first: any diff touching `Reihitsu.*` source, a test project, `*.csproj`, `Directory.Build.props`, a ruleset, or `.editorconfig` — or mixing those with documentation — is behavioral. A routine run may replace the Rubber Duck subagent with a three-to-four-line contract note, and skips both the official preflight and the full .NET validation because nothing compiled changed. Any trip-wire — production behavior touched, a second interpretation, a growing file list, a test contradicting the issue — voids the classification and puts the full gates back. Record the decision and its reason.
5. **Behavior Contract gate — before editing any file (behavioral runs).** Read `.claude/skills/gh-rubber-duck/SKILL.md` completely in the parent agent, then spawn exactly one fresh, **read-only** Rubber Duck subagent with the repository root, the issue number, the PR number if one exists, the user's clarifications quoted verbatim, the skill path, a strict read-only instruction, and a request for the exact output schema — and **without** your own proposed solution. On `READY`, show the user a short version of the user-visible examples and invariants and continue automatically (no approval pause unless they asked for one). On `NEEDS DECISION`, show only the competing interpretations (`AskUserQuestion`) and wait — no production or test edits. On `BLOCKED`, report what is missing and stop. Reuse that same subagent for later clarifications instead of spawning another.
6. Convert the accepted contract — or the routine run's contract note — into the implementation plan and a complete **regression matrix** — every known defect variant, stable valid examples, invalid examples, convergence, Fix All, idempotency, analyzer/formatter/code-fix parity, the contract's trivia and directive cases, and LF/CRLF when layout is affected. Add the red tests before production code; a single narrow test is not enough when the contract names a broader defect class.
7. Pick the matching delegate from the skill's routing table (`fix-formatter`, `fix-analyzer-rule`, `create-analyzer-rule`, `extend-formatter`, `create-rule-doc`, `add-resource-texts`, `draft-issue`) or implement inline per `CLAUDE.md` when nothing fits.
8. Format changed files via `Reihitsu.Cli`, run the focused `--filter` tests, make the first focused implementation commit with `[skip ci]` in the subject, and push it. Immediately update the existing draft PR body from the generic placeholder to the actual changes (title stays the claim-time placeholder for now) while retaining `Closes #$ARGUMENTS`.
9. Run the **local self-review** in the parent: every Behavior Contract row, counterpart parity, defect-class closure, convergence, idempotency, comments and directives, documentation, changed-path formatting, focused tests. This is not an official preflight and needs no extra agent.
10. **Synchronize the base before the gate**: `git fetch origin main`, check worktree and branch state, merge current `origin/main` when the branch is behind, resolve conflicts so both sides' behavior survives, run `Reihitsu.Cli` on the resolved paths, run the affected focused tests, and push the synchronized head with `[skip ci]`.
11. Run the read-only `gh-preflight` skill against that exact head as a fresh independent subagent — **official attempt 1**. On `PASS`, continue. On `BLOCKED — findings`, consolidate every finding into **one** worklist, fix it in **one** repair cycle (full defect class, format, focused tests, local self-review, `[skip ci]` commit), then spend the single **preflight retry** on the new head. If the retry blocks too, stop and report the remaining findings; never start a third official preflight automatically. Do not post preflight findings through GitHub MCP.
12. Run the full validation suite **once** after `PASS` (build + all four test projects; `--no-build` on the test projects is fine because the Release build covered the same tree), or record the skip on a routine run. Do not skip projects and do not rerun the suite after each small fix. Commit any fixes with `[skip ci]`; a repair that touches a compiled file invalidates the build, the earlier project results, and the preflight, so re-run build and all four projects on the repaired tree.
13. Push any validation fix commits, then push one final commit *without* `[skip ci]` (an empty `Ready for CI (#$ARGUMENTS)` commit works) so CI runs exactly once, now that everything is finished. Prove it carries the audited tree with `git diff --exit-code <audited-sha> HEAD` before pushing. Then fully rewrite both the PR **title** and **body** from the actual implementation — never leave the claim-time placeholder title or wording in place. Keep the PR draft for the human reviewer.
14. Report the scope classification with its reason, the contract gate result, the regression matrix rows added, the official preflight attempts used with each result and whether the budget was exhausted, the base sync, and the full-validation outcome.

If `$ARGUMENTS` is empty or not a positive integer, stop and ask for the issue number instead of guessing.
