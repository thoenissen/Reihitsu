# RH8203 — `<inheritdoc>` must be used with inheriting class

| Property | Value |
|----------|-------|
| **ID** | RH8203 |
| **Category** | Documentation |
| **Severity** | Warning |
| **Code Fix** | ❌ |

## Description

This rule only allows `<inheritdoc/>` on declarations that actually inherit documentation from a base member, a base type, or an implemented interface.

`<inheritdoc/>` is the right choice when the declaration overrides, implements, or derives from something that is already documented: the documentation is written once on the base member and every derived member shows it. It does not apply to a declaration that introduces its own contract — there is nothing above it to inherit from, and the tag leaves the declaration with no documentation at all.

Two forms are deliberately left alone. An `<inheritdoc/>` nested inside another element, such as `<remarks>`, is not reported, and neither is `<inheritdoc cref="..."/>`, which names the declaration to take the documentation from — that form works even when the two declarations are unrelated, so it is the way to reuse documentation without an inheritance relationship.

## Why is this a problem?

`<inheritdoc/>` on a standalone declaration promises documentation that does not exist. IntelliSense and generated documentation show nothing for the member, and a reader who sees the tag assumes the contract is described somewhere else and stops looking.

## How to fix it

Write real documentation for the declaration. Keep `<inheritdoc/>` only where the declaration overrides, implements, or derives from a documented one.

No code fix is offered: only you know what the declaration is supposed to say.

## Examples

### Violation

```cs
/// <inheritdoc/>
internal class CustomerRepository
{
}
```

### Correction

```cs
/// <summary>
/// Stores and retrieves customers
/// </summary>
internal class CustomerRepository
{
}
```
