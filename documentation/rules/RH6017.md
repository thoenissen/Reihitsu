# RH6017 — Increment/decrement symbols must be spaced correctly

| Property | Value |
|----------|-------|
| **ID** | RH6017 |
| **Category** | Spacing |
| **Severity** | Warning |
| **Code Fix** | ✓ |

## Description

A postfix increment `++` or decrement `--` must sit directly against the expression it applies to, with no space in between. Only the postfix form is covered; a prefix `++value` is a different shape and is not reported here. Indentation before an operator that begins a continuation line is left unchanged.

## Why is this a problem?

A space between the operator and its operand makes the expression look like two separate tokens and reduces readability.

## How to fix it

Remove the space between the operand and the `++` or `--` operator. The code fix applies this change
automatically, unless a comment shares the same-line token gap the whitespace run sits in — for example
`value /* keep */ ++;`. Deleting the whitespace in that case would glue the comment to the operator, so the
diagnostic is still reported but no fix is offered.

`reihitsu-format` still removes the space in that case, gluing the comment directly against the operator
(`value /* keep */++;`). The formatter's horizontal-spacing phase decides this purely from the token pair, the
same way it does for every other zero-space rule, and does not special-case an adjacent comment; no manual
action is needed. A comment on a continuation line above the operator does not reach this rule at all: unlike
a sibling rule such as [RH6015](RH6015.md), this analyzer only compares the immediately preceding token's line
to the operator's line, so no diagnostic is reported there in the first place.

## Examples

### Violation

```cs
internal class TestClass
{
    void Method()
    {
        int value = 0;
        value ++;
    }
}
```

### Correction

```cs
internal class TestClass
{
    void Method()
    {
        int value = 0;
        value++;
    }
}
```
