# RH3208 — Expression style local functions should not be used

| Property | Value |
|----------|-------|
| **ID** | RH3208 |
| **Category** | Clarity |
| **Severity** | Warning |
| **Code Fix** | ✓ |

## Description

This rule disallows expression-bodied local functions (local functions using `=>`). All local functions should use block bodies with explicit `return` statements for consistency and clarity.

## Why is this a problem?

Expression-bodied local functions create inconsistency when some functions use block bodies and others use expression bodies. Requiring block bodies keeps local functions in line with methods and gives every function a uniform shape.

## How to fix it

Replace the expression-bodied local function with a block body containing a `return` statement (or just the statement for `void`, `async Task`, and `async ValueTask` local functions).

## Exceptions

The rule is not reported when a preprocessor directive sits between the arrow and the expression:

```cs
int Double(int value) =>
#pragma warning disable CS0618
    value * 2;
#pragma warning restore CS0618
```

The conversion to a block body would have to move that directive into the generated block, which the
formatter refuses to do, so the local function keeps its expression body. The same applies to a
conditional group whose partner directive lies outside the local function, and to any `#region` or
`#endregion` directive between the arrow and the semicolon. A `#pragma` or a complete `#if` group
written *after* the expression is unaffected, and such a local function is still reported.

## Examples

### Violation

```cs
internal class Calculator
{
    public int Calculate(int value)
    {
        return Double(value);

        int Double(int x) => x * 2;
    }
}
```

### Correction

```cs
internal class Calculator
{
    public int Calculate(int value)
    {
        return Double(value);

        int Double(int x)
        {
            return x * 2;
        }
    }
}
```
