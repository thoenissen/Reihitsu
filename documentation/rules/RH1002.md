# RH1002 — Types used for equality comparison must implement equality members

| Property | Value |
|----------|-------|
| **ID** | RH1002 |
| **Category** | Performance |
| **Severity** | Warning |
| **Code Fix** | ❌ |

## Description

Structs compared for equality by LINQ and collection operations must provide efficient equality members. For selector-based overloads, this rule checks the projected key type rather than the source element type.

The rule covers:

- `Distinct`, `DistinctBy`, `Union`, `UnionBy`, `Intersect`, `IntersectBy`, `Except`, and `ExceptBy`
- `ToHashSet`, `ToLookup`, `ToDictionary`, `GroupBy`, `Join`, and `GroupJoin`
- `ToImmutableHashSet`, `ToImmutableDictionary`, `ToFrozenSet`, and `ToFrozenDictionary`
- `Contains` and `SequenceEqual`

`Contains` without a comparer is not reported when the searched value is a `KeyValuePair<TKey, TValue>` and the static type of its source is a dictionary of it: any type that converts to `IDictionary<TKey, TValue>`, or an interface or type parameter that converts to `IReadOnlyDictionary<TKey, TValue>`. That call is answered by the dictionary's own key lookup, so the key/value pair's equality members are never used. A concrete type that implements only `IReadOnlyDictionary<TKey, TValue>` is not a collection, so `Contains` scans it with the default comparer and is still reported. `Contains` with a `null` or default comparer argument and `SequenceEqual` compare the pairs themselves, so they are still reported for dictionaries.

Only the `System.Linq.Enumerable` methods are checked. `Contains` and `SequenceEqual` that bind to other types — for example instance methods such as `List<T>.Contains`, `Queryable`, or the span overloads on `MemoryExtensions` that array receivers can bind to — are not reported.

## Why is this a problem?

A struct without its own equality implementation falls back to the default `ValueType` behavior. These operations can invoke equality and hash-code calculations many times, so boxing or runtime field inspection can add significant overhead.

## How to fix it

Implement `IEquatable<T>`, or override both `Equals(object)` and `GetHashCode()` on the struct used for equality comparison. Alternatively, pass your own `IEqualityComparer<T>` to the operation, which then compares (and, where applicable, hashes) through that comparer instead.

Passing `null` or `EqualityComparer<T>.Default` is not a custom comparer. Both fall back to the struct's own equality behavior, so the rule still reports.

## Examples

### Violation

```cs
using System.Collections.Generic;
using System.Linq;

internal readonly struct CustomerId
{
    public CustomerId(int value)
    {
        Value = value;
    }

    public int Value { get; }
}

internal class Example
{
    void Run(IEnumerable<CustomerId> customerIds)
    {
        var uniqueIds = customerIds.Distinct();
    }
}
```

### Correction

```cs
using System;
using System.Collections.Generic;
using System.Linq;

internal readonly struct CustomerId : IEquatable<CustomerId>
{
    public CustomerId(int value)
    {
        Value = value;
    }

    public int Value { get; }

    public bool Equals(CustomerId other)
    {
        return Value == other.Value;
    }

    public override bool Equals(object obj)
    {
        return obj is CustomerId other && Equals(other);
    }

    public override int GetHashCode()
    {
        return Value.GetHashCode();
    }
}

internal class Example
{
    void Run(IEnumerable<CustomerId> customerIds)
    {
        var uniqueIds = customerIds.Distinct();
    }
}
```
