# RH5604 — Code must not contain mixed line endings

| Property | Value |
|----------|-------|
| **ID** | RH5604 |
| **Category** | Layout |
| **Severity** | Warning |
| **Code Fix** | ✓ |

## Description

A file must end all of its lines the same way. It must not mix CRLF (carriage return followed by line feed) and LF
(line feed alone). Whichever of the two is already in the majority in the file is the one the rule treats as
intended; every line that ends differently is reported.

## Which line endings are covered

The rule and `reihitsu-format` follow the same policy: a line ending is in scope when Roslyn represents it as its own
syntax element, and out of scope when it is a character inside a larger token or trivia's text.

**Covered** (reported and normalized):

- an ordinary end-of-line between tokens (`SyntaxKind.EndOfLineTrivia`);
- a newline inside an XML documentation comment, both the single-line (`///`) and the delimited (`/** ... */`) form —
  Roslyn models each one as its own `XmlTextLiteralNewLineToken`, distinct from the comment's text content.

**Exempt** (left untouched, and not reported even when they differ from the file's predominant ending):

- a newline inside a plain, non-documentation `/* ... */` comment;
- a newline inside disabled text (an `#if false` body, or any other inactive conditional-compilation branch);
- a newline inside a string literal (verbatim, raw, or interpolated).

These three are exempt because Roslyn encodes them as characters within a single token's or trivia's text rather
than as separate newline elements, and their content may be semantically meaningful — aligned example output in a
comment, or deliberately preserved inactive code — so rewriting it would go beyond normalizing whitespace. This
mirrors `Reihitsu.Core.SyntaxTriviaUtilities.IsInsideCommentOrDisabledText`, which documents the same exemption for
other formatter and analyzer rules that must not rewrite this content.

## Why is this a problem?

Line endings are invisible, so a file usually acquires a mixed set by accident — a snippet pasted from a different
platform, a generator that hard-codes one style, an editor configured differently from the last person's. The
consequence is not invisible: the next tool that normalizes the file rewrites every odd line, and those lines appear
in the diff as changes even though nothing about their content changed. Some tools also compare files as text and
report two identical files as different.

## How to fix it

Convert the odd lines so the whole file uses one style. A code fix is offered and converts them for you;
`reihitsu-format` normalizes an entire file at once.

To keep the file from drifting back, set the line-ending style in your editor configuration, and — for a repository —
in `.gitattributes`, so a checkout produces the same endings for everyone.

## Examples

### Violation

The first line ends with CRLF and the second with LF. Neither is visible in an editor, so the endings are spelled out
here:

```text
internal class TestClass    <- ends with CRLF
{                           <- ends with LF
}
```

### Correction

Every line ends the same way:

```text
internal class TestClass    <- ends with CRLF
{                           <- ends with CRLF
}
```
