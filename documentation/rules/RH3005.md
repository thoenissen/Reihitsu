# RH3005 — Use readable conditions

| Property | Value |
|----------|-------|
| **ID** | RH3005 |
| **Category** | Clarity |
| **Severity** | Warning |
| **Code Fix** | ✓ |

## Description

This rule disallows Yoda conditions, where a constant is written on the left side of a comparison and the variable or expression is written on the right.

## Why is this a problem?

Conditions are easier to read when the changing value appears first. Writing the constant first makes the expression feel unnatural and slows down scanning.

## How to fix it

Swap the operands so the variable or expression is on the left side.

A comment written before or after the comparison is kept where it is, so the code fix is still offered.

No code fix is offered in two cases, and both are deliberate:

- A comment or a preprocessor directive is written *inside* the comparison. Swapping the operands would move the code it belongs to out from under it, so the correction is left to you.
- Swapping the operands would not mean the same thing — for example when an operand is `dynamic`, or when the comparison resolves to an operator the type declares itself, so the mirrored comparison may bind to a different operator or not compile at all.

The diagnostic is still reported in both cases; swap the operands by hand once you have confirmed the result is equivalent.

## Examples

### Violation

```cs
if (0 < count)
{
}
```

### Correction

```cs
if (count > 0)
{
}
```
