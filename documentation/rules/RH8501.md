# RH8501 — Code analysis suppressions must have a justification

| Property | Value |
|----------|-------|
| **ID** | RH8501 |
| **Category** | Documentation |
| **Severity** | Warning |
| **Code Fix** | ❌ |

## Description

Every `SuppressMessage` attribute must carry a `Justification` value, and that value must not be an empty string.

## Why is this a problem?

A suppression turns a warning off permanently. Without a stated reason, the next reader cannot tell whether the warning was analyzed and dismissed or simply silenced to get a build green, and cannot tell whether the reason still holds after the code around it has changed. The suppression then survives long after the argument for it has gone.

## How to fix it

Add a `Justification` argument that says why the reported code is correct as written.

A justification earns its place when it answers *why the warning does not apply here*, in terms a reviewer can check later:

- **Good** — `"Parameter is validated by the caller."`, `"Reflection resolves this type at run time."`, `"Native handle is released by the surrounding using statement."`
- **Not good enough** — `"By design."`, `"False positive."`, `"See ticket."`, or a repetition of the rule's own title. None of these can be re-examined without the author.

If the honest answer is that the code should be changed, change the code instead of suppressing the warning.

The value may be a string constant rather than a literal, which is convenient when the same reason applies to several suppressions.

No code fix is offered: only you know why the warning does not apply.

## Examples

### Violation

```cs
[System.Diagnostics.CodeAnalysis.SuppressMessage("Design", "CA1062")]
internal class TestClass { }
```

### Correction

```cs
[System.Diagnostics.CodeAnalysis.SuppressMessage("Design", "CA1062", Justification = "Parameter is validated by the caller.")]
internal class TestClass { }
```
