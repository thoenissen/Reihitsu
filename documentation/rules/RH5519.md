# RH5519 — Event attributes must be on their own line

| Property | Value |
|----------|-------|
| **ID** | RH5519 |
| **Category** | Layout |
| **Severity** | Warning |
| **Code Fix** | ✓ |

## Description

Event attributes must be on their own line.

This rule also reports on event field declarations, since they resolve to the same attribute target as an event.

## Why is this a problem?

A reader scanning a type for an event looks down a column of accessibility modifiers, handler types and names. An
attribute written in front of the event displaces that line to the right, so events that carry attributes no longer
line up with events that do not, and the handler type — the part that actually says how the event is consumed — is
pushed further from the left margin.

## How to fix it

Move the event declaration onto the line after the attribute list, leaving the attribute alone on its own line. A code
fix is offered and performs that edit for you.

If a comment sits inside the attribute list, the diagnostic is still reported but no code fix is offered, because the
rewrite would have to carry your comment along with the attribute. Insert the line break by hand in that case.

## Exceptions

The rule does not report when a comment or a preprocessor directive sits between the closing `]` and the event
declaration. Nothing can be moved onto its own line there without disturbing what you wrote in that gap, so the layout
you chose is left exactly as it is.

## Examples

### Violation

```cs
internal class Example
{
    [First] internal event EventHandler? Changed;
}
```

### Correction

```cs
internal class Example
{
    [First]
    internal event EventHandler? Changed;
}
```
