# RH8201 — The inheritdoc tag should be used if possible

| Property | Value |
|----------|-------|
| **ID** | RH8201 |
| **Category** | Documentation |
| **Severity** | Warning |
| **Code Fix** | ✓ |

## Description

A member declared with `override` that carries its own XML documentation is reported. The base member already describes the contract, so the override should point at that description with `<inheritdoc/>` instead of repeating it.

The rule looks only at members marked `override` — methods, properties, indexers, and events. A member that implements an interface without the `override` modifier is not reported, even though `<inheritdoc/>` usually reads well there too.

## Why is this a problem?

Repeating XML documentation on an override duplicates text that has to be kept in step by hand. When the base documentation changes, every copy has to be found and updated, and the copies that are missed quietly start describing behavior the member no longer has.

## How to fix it

Replace the documentation comment with a single `<inheritdoc/>` tag.

If the override genuinely behaves differently from the base member and callers need to know, keep `<inheritdoc/>` for the inherited contract and describe only the difference alongside it, for example in a `<remarks>` element. The rule is satisfied as soon as the comment contains an `<inheritdoc/>` tag anywhere.

## Examples

### Violation

```cs
/// <summary>
/// Returns a string representation.
/// </summary>
public override string ToString()
{
    return "";
}
```

### Correction

```cs
/// <inheritdoc/>
public override string ToString()
{
    return "";
}
```
