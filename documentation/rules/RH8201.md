# RH8201 — The inheritdoc tag should be used if possible

| Property | Value |
|----------|-------|
| **ID** | RH8201 |
| **Category** | Documentation |
| **Severity** | Warning |
| **Code Fix** | ✓ |

## Description

A documented member that overrides a base member or implements an interface member, and whose XML documentation contains no `<inheritdoc/>` tag, is reported. The overridden or implemented member already describes the contract, so the member should point at that description with `<inheritdoc/>` instead of repeating it.

The rule looks at methods, properties, indexers, events, field-like events, operators, and conversion operators that:

- are marked `override`, or
- implement an interface member, implicitly or explicitly. This includes interfaces declared in referenced assemblies, generic interfaces, `static abstract` interface members such as operators, and explicit implementations of a base interface member inside another interface.

A member only counts as an implementation when its own type implements the interface. A member of a base class is not reported just because a derived type lists an interface that the member happens to satisfy.

The rule does not check whether the overridden or implemented member is documented itself. When it is not, `<inheritdoc/>` has nothing to inherit, so document that member first.

These members are deliberately not reported and are left to manual correction:

- A field-like event that declares several events, unless every one of them overrides or implements an event. The documentation is shared by all of them, so replacing it would strip the only description of the others.
- The implementing declaration of a partial member that is not marked `override`. RH8203 does not treat that declaration as inheriting documentation, so `<inheritdoc/>` there would be reported by RH8203.
- An implicit interface implementation when a file declaring its type, or declaring one of the interfaces its type implements, contains an `#if` directive. The member may implement nothing in another build configuration, where replacing the documentation would leave it with an `<inheritdoc/>` that has nothing to inherit. The check covers whole files, so an unrelated `#if` in the same file also withholds the report. Explicit implementations and overrides are still reported, because they do not compile without the member they inherit from.

Configuration differences outside the source of the compilation — per-target-framework source files, or referenced assemblies whose interfaces differ between targets — cannot be detected. If a member only implements an interface in some configurations, keep its own documentation and add `<inheritdoc/>` inside a `<remarks>` element, or use `<inheritdoc cref="..."/>`.

## Why is this a problem?

Repeating XML documentation on an override or an interface implementation duplicates text that has to be kept in step by hand. When the base or interface documentation changes, every copy has to be found and updated, and the copies that are missed quietly start describing behavior the member no longer has.

## How to fix it

Replace the documentation comment with a single `<inheritdoc/>` tag.

When a member implements members of several interfaces, choose the documentation it inherits with `<inheritdoc cref="..."/>`.

If the member genuinely behaves differently from the member it inherits from and callers need to know, keep `<inheritdoc/>` for the inherited contract and describe only the difference alongside it, for example in a `<remarks>` element. The rule is satisfied as soon as the comment contains an `<inheritdoc/>` tag anywhere.

## Examples

### Violation

```cs
using System;

internal class Connection : IDisposable
{
    /// <summary>
    /// Returns a string representation.
    /// </summary>
    public override string ToString()
    {
        return "";
    }

    /// <summary>
    /// Closes the connection.
    /// </summary>
    public void Dispose()
    {
    }
}
```

### Correction

```cs
using System;

internal class Connection : IDisposable
{
    /// <inheritdoc/>
    public override string ToString()
    {
        return "";
    }

    /// <inheritdoc/>
    public void Dispose()
    {
    }
}
```
