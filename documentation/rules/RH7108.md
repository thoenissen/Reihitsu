# RH7108 — Event accessors must follow order

| Property | Value |
|----------|-------|
| **ID** | RH7108 |
| **Category** | Organization |
| **Severity** | Warning |
| **Code Fix** | ✓ |

## Description

This rule requires the `add` accessor to appear before `remove`.

## Why is this a problem?

Explicit event accessors are easier to read when they follow a consistent order. That consistency makes custom events look the same across the codebase.

## How to fix it

Move `add` above `remove`.

The code fix takes the comments written above the accessor with it. Preprocessor directives cannot always travel safely, so no code fix is offered in these two cases:

- An `#if` or `#region` pair with one end inside the moved accessor and the other outside it, or with one end in the accessor it moves past and the other outside it. The move would carry one half of the pair away and leave the other behind, so the file would end up with unmatched directives (CS1027/CS1028).
- A `#pragma warning`, `#nullable` or `#line` directive in either accessor. These apply from where they stand onwards, so moving code across them changes which code they cover.

Reorder those accessors by hand.

Directives whose meaning the move cannot change do not withhold the fix: a pair written entirely inside one accessor body, or opened outside the accessor list altogether. Note that a directive written directly above the first accessor counts as belonging to that accessor.

## Examples

### Violation

```cs
public event EventHandler Changed
{
    remove
    {
        _changed -= value;
    }
    add
    {
        _changed += value;
    }
}
```

### Correction

```cs
public event EventHandler Changed
{
    add
    {
        _changed += value;
    }
    remove
    {
        _changed -= value;
    }
}
```
