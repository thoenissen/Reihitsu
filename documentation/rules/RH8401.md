# RH8401 — Single-line comments must not use documentation style slashes

| Property | Value |
|----------|-------|
| **ID** | RH8401 |
| **Category** | Documentation |
| **Severity** | Warning |
| **Code Fix** | ✓ |

## Description

This rule forbids regular single-line comments that start with `///`.

## Why is this a problem?

Three leading slashes are reserved for XML documentation comments. Using them for ordinary comments makes the code look documented when it is not, and can confuse editors and readers.

## How to fix it

Change ordinary comments to use `//` instead of `///`.

## Examples

### Violation

```cs
/// temporary workaround
DoWork();
```

### Correction

```cs
// temporary workaround
DoWork();
```

## Code fix behavior

One application converts every `///` exterior in the reported comment whose line is indented with characters that `char.IsWhiteSpace` accepts, which covers every ordinary indentation including tabs and non-breaking spaces. A comment indented that way does not end up part `//` and part `///`; the two characters outside that set are listed under [Lines left to manual correction](#lines-left-to-manual-correction).

Line starts are recognized on the full C# line-terminator set — carriage return, line feed, carriage return line feed, U+0085, U+2028 and U+2029 — which is the same set the formatter's documentation-comment phase uses.

Everything after the exterior is content and is preserved verbatim, so a second `///` further along the same line is left alone.

### Lines left to manual correction

A line whose `///` is indented with a byte-order mark (U+FEFF) or a substitute character (U+001A) is reported but not converted, so such a comment keeps that line as `///` after the fix is applied.

The C# lexer accepts both characters as exterior indentation, while the shared line scanner recognizes only what `char.IsWhiteSpace` accepts — the same set the rule's previous implementation used, so this is a long-standing boundary rather than a new one. The scanner is shared with the formatter's documentation-comment phase, whose output has to stay byte-identical, so widening it for this rule alone is not available. Correct these lines by hand.
