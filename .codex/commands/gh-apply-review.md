# GitHub PR Apply Review

Apply the review on GitHub Pull Request **#$ARGUMENTS**: implement the reviewer's findings and the user's extra hints, validate, and push.

Run this in the PR author's Codex task, normally the same task that ran `gh-implement`. This is the fix step; `gh-review` and `gh-rereview` run in the reviewer's task.

`$ARGUMENTS` is optional. When it is empty, reuse the PR created by `gh-implement` in the current task. Ask only when no PR can be identified.

Invoke the `gh-apply-review` skill and follow it exactly. It supports Linux cloud and local Windows. Use authenticated `gh` for GitHub operations and local `git` for the branch:

1. Confirm identity and fetch PR metadata, GraphQL review-thread state, inline comments, general comments, diff, files, and commits in one batch. Build **one complete, deduplicated worklist before editing anything**: unresolved reviewer threads, review summary bodies, user-authored PR hints, every line of a pasted `gh-review` Copy block, relevant task clarifications, and any unfixed finding or confirmed scope hint from a previous official preflight. Do not start editing after reading only the first thread.
2. Build the scope ledger before editing: state the PR's decidable defect mechanism or accepted requirement boundary, already-authorized shipped surfaces, and every finding's mechanism, origin, change type, surface impact, disposition, and evidence. Classify confirmed actionable items as `fix here` only when they are the same mechanism/requirement or PR-introduced, are bug fixes rather than new behavior, and change no shipped diagnostic, public API, or dependency. Classify the rest as `follow-up draft`; reserve `dismissed` for disproved, duplicate, already-fixed, or inapplicable findings, and use `needs decision` for material ambiguity. Freeze that boundary after the complete first classification; severity never expands it.
3. For every follow-up, search for duplicates, then render a stable `F<n>` English issue draft using the matching repository template. Put the complete copy-ready frontmatter and body in the final chat response and store the same text only as a redundant ignored cache under `plans/issues/pr-<PR>/`. Never call `scripts/upload-issues.ps1` and never create a GitHub issue before the user explicitly approves that draft ID and content.
4. Implement all `fix here` items as **one cohesive repair cycle** on the PR branch: generalize each finding to its defect class, inspect sibling shapes and shared helpers, follow the repository workflow in `AGENTS.md` (regression/repro test first for analyzer/formatter bug fixes; format the changed files with `scripts/format.ps1 -NoInstall` before tests; code fix only if comprehensive), and run the focused tests with `scripts/test.ps1 -NoInstall -Project <name> -Filter <expression>` as you go. Treat every `Required change` as a suggestion, not a specification: whenever a repair moves a guard, predicate, or exemption, re-derive its scope with the guard-delta and predicate-boundary tables against the guard *as repaired*, and add a test on **each** side of every boundary it moves. Changed code-fix registration or applicability additionally requires two coexisting safe diagnostics fixed in one Fix All iteration with clean re-analysis; changed cancellation-aware traversal requires no-match and post-match-tail cancellation unit tests.
5. Commit and push the fixes with `[skip ci]`, then run the **local self-review**: every worklist row, counterpart parity, defect-class closure, boundary closure, convergence, idempotency, comments and directives, documentation, changed-path formatting, focused tests, the mandatory cancellation/Fix All unit-test boundaries from step 4, and a re-read of the XML summary and inline comments of **every method whose body changed**. Record the **admission artifact** — qualifiers and owners, changed predicates with tests on both sides, the exact `rg` result per changed policy owner, each worklist row with its regression test, each new test's invariant, falsifier, and helper, plus the comment/documentation check. A missing row blocks admission to preflight. It is not an official preflight and needs no admission script.
6. **Synchronize the base before the gate**: `git fetch origin main`, check worktree and branch state, merge current `origin/main` when the branch is behind, resolve conflicts so both sides' behavior survives, format and focused-test the resolutions, and push the synchronized head with `[skip ci]`.
7. Decide from `gh-preflight`'s trigger list whether an audit is required. A round whose accepted findings only touch comments, documentation, Markdown, skill and command files, or templates — including inside `.cs` — records a skip proven by `scripts/verify-text-only.ps1 -NoInstall` instead of spending an attempt; ask the user when the round fits neither list. Otherwise select `reihitsu-deep-preflight` for attempt 1 only when the final diff changes public API, semantic or trivia rewrite behavior, a security boundary, or destructive behavior; select `reihitsu-preflight` otherwise. Start at most one deep-preflight process per PR and use `reihitsu-preflight` for every retry. Run the selected agent with no model or effort override and the neutral evidence bundle — issue and PR by number, SHAs, diff, checkout proof, build result, contract-artifact path, and checklist applicability — **official attempt 1**. Run `git ls-remote origin refs/heads/main` in the same step as every reviewer spawn. On `PASS — non-blocking cleanup`, apply the listed text fixes and prove them non-behavioral with `scripts/verify-text-only.ps1 -NoInstall -StrictDocs -Base <audited-sha> -Head worktree`. On `BLOCKED — findings`, merge every finding into one worklist, fix the in-scope rows in one repair cycle, redo self-review, then spend the retry on a fresh standard `reihitsu-preflight` with the previous compact report and evidence-artifact path plus the repair SHAs and diff. If the retry blocks too, stop and report; never start a third official preflight automatically. Do not post preflight findings to GitHub.
8. Prepare the toolchain with `scripts/prepare.ps1 -NoInstall`, then after a passing result run `scripts/build.ps1 -NoInstall` and `scripts/test.ps1 -NoInstall -NoBuild` **once** in a `reihitsu-validate` custom agent that returns pass/fail, failing assertions, and the raw-log path rather than the whole log. Pass no model or effort override. A skipped audit does not skip validation; only a round whose diff contains no compiled file at all skips it.
9. After the preflight decision and validation are settled and green, push the final trigger commit without `[skip ci]`, reply to fixed threads (`Addressed: … (<sha>)`) without resolving them, and report only the Applied / Follow-up drafts / Dismissed / Needs decision / Validation / Pushed structure defined by the skill. Pending follow-ups remain copy-ready and `awaiting approval`.
10. When the user later approves a draft, search for duplicates again, create it directly with authenticated `gh issue create` from the approved chat content, update the PR's `Follow-up work` with the issue URL and scope rationale, and reply to its review thread. Do not resolve the thread. Because this changes no tracked file, verify the tree is unchanged and carry validation forward without rerunning it.

A non-empty argument from which no valid PR number or URL can be extracted is an error. Ask rather than guess.
