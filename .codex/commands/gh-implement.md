# GitHub Issue Implementation

Implement GitHub issue **#$ARGUMENTS** end-to-end.

Invoke the `gh-implement` skill and follow its workflow exactly. It supports Linux cloud and local Windows environments. Use the authenticated `gh` CLI for GitHub platform operations:

1. Confirm authentication with `gh auth status`, then read the issue with `gh issue view $ARGUMENTS --json number,title,body,labels,state,url`.
2. Check for an existing claim or open draft PR. If unclaimed, create `codex/issue-$ARGUMENTS-<slug>` from the current `origin/main`, add an empty `Claim issue #$ARGUMENTS [skip ci]` commit, push it, and immediately open a **draft** PR. Title and body are a fixed generic placeholder (title `Claim: issue #$ARGUMENTS`, template body with static wording) — never the issue's own title or a paraphrase of its body — with `Closes #$ARGUMENTS` mandatory in the body; do not comment on or label the issue because the linked draft PR is the ownership marker.
3. Confirm the preinstalled .NET 10 SDK with `scripts/prepare.sh --no-install`; the flag turns a missing SDK into a failure instead of an installation. Do not install an SDK, modify `PATH`, or otherwise change the environment. Use `scripts/build.sh`, `scripts/test.sh`, `scripts/format.sh`, and `scripts/verify-text-only.sh` — always with `--no-install` — instead of hand-written `dotnet` invocations.
4. **Scope triage.** Classify the run as *routine* or *behavioral* against the skill's five criteria (no analyzer/formatter/code-fix/Core behavior change, exactly one reading, small listable file set, no new rule or diagnostic/API/dependency change, not an analyzer or formatter bug report). Apply the mechanical veto first: any diff touching `Reihitsu.*` source, a test project, `*.csproj`, `Directory.Build.props`, a ruleset, `.editorconfig`, `scripts/**`, or a CI workflow — or mixing those with documentation — is behavioral. Touching a `.cs` file is not by itself a reason to audit when only its comments changed: `scripts/verify-text-only.sh --no-install --base <base-sha> --head <head-sha>` proves that mechanically, and its `TEXT-ONLY PROOF: PASS …` line is the record. A rename never qualifies. A routine run may replace the Rubber Duck subagent with a three-to-four-line contract note. Any trip-wire — production behavior touched, a second interpretation, a growing file list, a test contradicting the issue — voids the classification and puts the full gates back. Record the decision and its reason.
5. **Behavior Contract gate — before editing any file (behavioral runs).** Read `.codex/skills/gh-rubber-duck/SKILL.md` completely in the parent agent. Gather the neutral **evidence bundle** once (issue JSON and clarifications, PR metadata, base and head SHAs, merge base, changed files and diff, and your proof that the checkout matches that head), then spawn exactly one fresh, **read-only** Rubber Duck subagent with that bundle, the repository root, the user's clarifications quoted verbatim, the skill path, a strict read-only instruction, and a request for the exact output schema — and **without** your own proposed solution. Every bug-report contract must name a decidable mechanism, enumerate the complete candidate set from the dispatch code, and contain an executed sweep row per candidate; every contract that moves a guard, predicate, or exemption must carry the guard-delta and predicate-boundary tables with a verdict per row and a boundary test named on both sides. Reject a malformed `READY`. On `READY`, show the user a short version of the user-visible examples and invariants and continue automatically (no approval pause unless they asked for one). On `NEEDS DECISION`, show only the competing interpretations and wait — no production or test edits. On `BLOCKED`, report what is missing and stop. Reuse that same subagent for later clarifications instead of spawning another; a start that returns no contract costs a process start, not a gate result.
6. **Freeze the scope ledger** at contract acceptance: the accepted mechanism or requirement boundary, the behavior rows, the initial production owners, the intended production and test file set, and the shipped diagnostics, public APIs, and dependencies that must stay unchanged. Classify every later discovery as `same mechanism/requirement`, `PR-introduced`, or `new mechanism or pre-existing`; the last leaves the PR as an `F<n>` follow-up draft. Take the mandatory scope checkpoint — narrow/revert, approve an expanded contract, or create and link a follow-up issue — whenever a change or repair touches a new diagnostic or behavior owner, a shared base or utility with other consumers, public API or dependencies, repository-wide canonical policy ownership, a materially enlarged compiled file set, or more than double the intended production paths.
7. Convert the accepted contract — or the routine run's contract note — into the implementation plan and a complete **regression matrix** — every defect-class sweep candidate, a test on **both** sides of every boundary named in the delta tables, one test per region losing guard coverage, known defect variants, stable valid examples, invalid examples, convergence, Fix All, idempotency, analyzer/formatter/code-fix parity, the contract's trivia and directive cases, and LF/CRLF when layout is affected. Map every reproducing in-scope sweep row to a regression test before production code; a single narrow test is not enough when the contract names a broader defect class.
8. Pick the matching delegate from the skill's routing table (`fix-formatter`, `fix-analyzer-rule`, `create-analyzer-rule`, `extend-formatter`, `create-rule-doc`, `add-resource-texts`, `draft-issue`) or implement inline per `AGENTS.md` when nothing fits.
9. Format changed files via `scripts/format.sh --no-install`, run the focused tests with `scripts/test.sh --no-install --project <name> --filter <expression>`, make the first focused implementation commit with `[skip ci]` in the subject, and push it. Immediately update the existing draft PR body from the generic placeholder to the actual changes (title stays the claim-time placeholder for now) while retaining `Closes #$ARGUMENTS`.
10. Run the **local self-review** in the parent: every Behavior Contract row, counterpart parity, defect-class closure, boundary closure, convergence, idempotency, comments and directives, documentation, changed-path formatting, focused tests — plus, for **every method whose body changed**, a re-read of its XML summary and inline comments. Then record the **admission artifact**: requirement qualifiers and their owners, each changed predicate with the test on both sides of its boundary, the exact `rg` result per changed policy owner, each contract and sweep row with its regression test, each new test's invariant, falsifier, and helper, and the comment/documentation check. A missing row blocks admission to preflight. This is not an official preflight and needs no extra agent.
11. **Synchronize the base before the gate**: `git fetch origin main`, check worktree and branch state, merge current `origin/main` when the branch is behind, resolve conflicts so both sides' behavior survives, run `scripts/format.sh --no-install` on the resolved paths, run the affected focused tests, and push the synchronized head with `[skip ci]`.
12. Decide from `gh-preflight`'s trigger list whether an audit is required; record a proven skip or run the read-only `gh-preflight` skill against that exact head as a fresh independent subagent with the same evidence bundle — **official attempt 1**. On `PASS`, continue. On `PASS — non-blocking cleanup`, apply the listed text fixes, prove them non-behavioral with `scripts/verify-text-only.sh --no-install --base <audited-sha> --head worktree`, and continue without spending an attempt. On `BLOCKED — findings`, consolidate every finding into **one** worklist, classify it against the frozen ledger, fix it in **one** repair cycle (full defect class, delta tables re-derived against the repair itself, tests on both sides of every moved boundary, format, focused tests, local self-review and admission artifact, `[skip ci]` commit), then spend the single **preflight retry** on the new head with the previous report, the previously audited SHA, the repaired SHA, and the repair diff. If the retry blocks too, stop and report the remaining findings; never start a third official preflight automatically. Do not post preflight findings to GitHub.
13. Run the full validation suite **once** with `scripts/build.sh --no-install` and `scripts/test.sh --no-install --no-build`, or record the skip when the diff contains no compiled file at all — a skipped audit does not skip validation. Do not skip projects and do not rerun the suite after each small fix. Commit any fixes with `[skip ci]`; a repair that touches a compiled file invalidates the build, the earlier project results, and the preflight, so re-run build and all four projects on the repaired tree.
14. Push any validation fix commits, then push one final commit *without* `[skip ci]` (an empty `Ready for CI (#$ARGUMENTS)` commit works) so CI runs exactly once, now that everything is finished. Prove it carries the audited tree with `git diff --exit-code <audited-sha> HEAD` before pushing. Then fully rewrite both the PR **title** and **body** from the actual implementation — never leave the claim-time placeholder title or wording in place. Keep the PR draft for the human reviewer.
15. Report the scope classification with its reason, the contract gate result, the regression matrix rows added, the preflight decision with its trigger or proof line, official attempts and reviewer process starts as separate numbers with each result and whether the budget was exhausted, scope growth against the frozen ledger, the base sync, and the full-validation outcome.

If `$ARGUMENTS` is empty or not a positive integer, stop and ask for the issue number instead of guessing.
