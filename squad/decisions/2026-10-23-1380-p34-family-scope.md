# Scope of P34 against per-construct layout decisions (#1380)

| | |
|---|---|
| Date | 2026-10-23 |
| Escalation | 3 |
| Run | issue #1380 |

## Question

P34 (one treatment per syntax family) read literally contradicts layout decisions the formatter specs make on purpose inside a family: function-pointer parameter lists are joined (FMT-BREAK-014), array initializers and collection expressions stay on one line (FMT-BREAK-021, FMT-BREAK-022) while object initializers expand, property arrows are joined (FMT-BREAK-026) while lambda and switch-arm arrows keep their wraps. Options: (a) P34 overrides these, each shape becomes a new P34 instance; (b) P34 governs the members its sources named (indexer parameter lists, compound assignments, attribute-target colons, a comment before `]`, arrow spacing) within the layout each construct's own requirement chooses.

## Answer

(b): the per-construct decisions stay; FMT-PIPE-014 says so, and nothing new is filed for them.
